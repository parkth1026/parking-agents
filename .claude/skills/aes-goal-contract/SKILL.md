# 锁定验收

验收条件是执行 Agent 唯一的终止条件，也是审计器每一轮反复消费的判定依据。混在整份
任务记录里一起确认，用户扫一眼就点头了，写偏了要等执行完才发现。所以单独一步。

契约长什么样、条数怎么得出、Verify 四档怎么写，都在
[goal-contract-shape.md](references/goal-contract-shape.md)；拿不准信息密度时看一眼
[goal-contract-example.md](references/goal-contract-example.md)。提问方法论在
[asking.md](../workflow-interview/references/asking.md)。这份 SKILL.md 只写**怎么把
验收条件问出来**。

## 开头

```bash
node <workflow-interview>/scripts/session.mjs init <date>-<任务词组>
```

幂等。产物落在 `3-contract/` 下。上游是 `1-interview/context.md` 与
`2-prototype/` 下的确认版对照物；读不到时告诉用户缺什么、验收条件可能因此缺乏具体
例子支撑，然后照常做。

## 1. 收集判定例子

验收条件不是发明出来的，是从具体例子里聚出来的。发散地想「这个需求有哪些方面要验」
没有天然终点，只有上限，写到上限附近就会停手；从例子聚类有天然终点，例子举完就完了，
条数是数出来的，不是定出来的。

**走过 `aes-prototype` 的需求，例子已经在手，直接读，不重新问一遍：**

- `2-prototype/behavior.md` 的每个变化行
- `2-prototype/api-mock.md` 的每对报文
- `2-prototype/example-run.md` 的每个场景
- `2-prototype/mock.html` 的每个关键状态与交互

没走过对照物阶段的需求在这里补齐。问法要紧：问「验收标准是什么」是在要求用户做抽象，
他多半只能答「能用就行」；问「做完之后你会怎么试它」「什么情况下你会说这没做对」是在
要求他回忆一个具体动作，这他答得出来。每个回答都是一个例子，带着具体输入和期望结果。

一个例子都举不出来，说明这个目标还没有可观察的完成形态。报 `needs_reinterview`，
不靠想象补足。

聚类是一个动作，不是一份产物：把例子按「同一条规则的不同侧面」聚起来，一个簇一条 AC，
簇里的例子成为它的 Verify 素材。结果就是下面那几条 AC，不另出一份聚类清单。

## 2. 逐条带候选，批量提问

每条验收条件是一个带候选的问题，不是一份等待点头的定稿。给定稿求确认只暴露你的结论，
用户只能凭直觉觉得哪里不对；带候选则暴露你考虑过的备选空间，他能看见你排除了什么。

候选的主轴是「这条错了会怎样，那就这么验」：先写后果，再写对应的验证途径与真实代价。
需求方天然知道后果，不天然知道「跑现有测试」和「端到端跑一遍」差在哪；要他把自己的
需求翻译成验证深度，中间隔着他没有的知识。这件事的两半本来就分处两边：影响（赔钱、
用户看得见、只是难看）只有他清楚，发生概率（这块多常改、多复杂、依赖多深）你从仓库
查得到。**你出概率和途径，他出影响。**

这条分工正好划出这里的分诊线，它和需求阶段的分诊是同一把尺子在两个地方用：

- **「这条错了会怎样」永远要问。** 它跨在仓库边界之外，没有任何仓库事实能代答，
  你的置信在这里天然不可靠。每条 AC 都要带着你写的后果一句话请他确认或改写。
- **「那就用哪条途径验」按分诊走。** 途径是仓库事实加你的判断，够格进默认区。
  基建现成、途径可逆、后果不严重的，一行定掉：`AC-003 用现有 npm test 断言，
  仓库测试就是这个风格，代价：覆盖不到真实数据形态`。

三种情况即使你很确定也必须进提问区，因为它们要么难逆、要么要用户付出成本：含数字
门槛的（门槛值、用什么尺子量、尺子锁不锁）、需要用户提供真实数据的、仓库没有基建
得先建的。这三类恰好是验收里最贵的部分，省这里的轮次等于在唯一不能省的地方省。

进了提问区的照 [asking.md](../workflow-interview/references/asking.md) 的三段格式与
百分比写，这里的好处就是这条能给多少信心、多快出结果，代价就是要先付出什么。形如：

```text
AC-002 <这条要判定什么>
这条错了会怎样：<一句话，等用户确认或改写>

A. 错了只是难看 → `[A]` 跑现有 `npm test` 断言 — 62%（推荐）
- 选什么：只断言函数返回值，不覆盖真实数据形态。
- 好处：仓库现成基建，一分钟出结果，每次改动都跑得起。
- 代价：真实数据里的形态问题这条验不出来。

B. 错了用户看得见 → `[B]` 你给一组真实数据做黄金用例 — 33%
- 选什么：你提供一份真实数据与期望输出，双双落盘成 fixture。
- 好处：能验出合成数据验不出的形态问题。
- 代价：要你提供数据并确认能否脱敏，拿不到就是阻塞。

C. 错了会赔钱 → 端到端跑一遍核心流程 — 5%
- 选什么：新建端到端基建，跑完整链路。
- 好处：置信度最高，回归也一起兜住。
- 代价：仓库目前没有这套基建，得先建，大致 X 个工作日。
```

候选池就是 `context.md` 的「验证基建候选池」，加上「用户提供一份真实数据或场景」。
后者始终在场，不是选了 `[B]` 之后才追问。不要预设 L1、L2、L3 这类通用阶梯：阶梯是
先验的，答不出「这个仓库此刻有没有」，而在没有端到端基建的仓库里，「跑一遍端到端」
的真实代价不是「较高」，是先花时间把基建建起来。

以下情况必须在候选里写明真实代价，不能含糊带过：

- 仓库没有现成基建，该途径的代价包含先把基建建起来，写出大致工作量；
- 涉及真实数据或外部系统，写明合成数据说明不了问题，不许替用户发明「代表性数据」；
- 含数字门槛，门槛值、用什么尺子量、尺子锁不锁一并进候选。优化型目标把测量脚本
  声明为不可修改，防止执行 Agent 改测量而不是改工件。

其余候选轴按需附加：判到多严（整体一致、关键字段一致、逐字节一致）、边界算不算
（空值、超长、并发）、门槛定在哪、这条要不要留。一样附百分比和理由。口径变了
Verify 跟着变，一起给。

用户选了 `[B]` 后一次问全：数据在哪、能否脱敏、期望输出以什么为准、fixture 放哪。
数据拿不到是客观阻塞，写明精确解除条件，不拿「大概的数据」凑数。

一轮发全所有验收条件的候选，让用户一次看见全貌。每轮追加进 `rounds.jsonl`，
`stage` 写 `3-contract`。

问到这个程度才算收口：还想问的问题，不同答案只会改变 Verify 的措辞，不会改变执行
Agent 到底要跑什么、跑到什么程度。没到就继续问，问了几轮都一样。

起草时暴露出新的材料歧义，报 `needs_reinterview`，不在这里现场糊过去。

### 对照物怎么进验收条件

走过对照物阶段的需求，对照物经由例子进入验收条件，**不在聚类之外另加一条整体对照**。

界面向：mock 的每个关键状态与交互作为例子参与聚类，Verify 默认 `[C]` 并写明 mock
路径（`强约束` 声明像素级时按像素级判），仓库存在截图 diff 或视觉回归基建时升级
`[A]`；只有当整体结构或信息层级确实无法被任何一条逐点验收覆盖时，才单独立一条结构
对照。逐点已经覆盖完还立一条，是同一件事判两遍。

行为变更：确认的例子行直接转化为 Verify，有测试基建时写成 `[A]` 断言，含具体数据
样例时落成 `[B]` 黄金用例，输入与期望输出取自对照表，不另行发明。

确认版对照物一律在 `强约束` 里声明为不可修改，执行 Agent 改的是产品不是对照物。

用户回答完全部问题后验收条件定稿。之后要改就回本阶段，不在契约里悄悄改。

## 3. 落盘

访谈过程本身是产物，不是通往契约的一次性开销。所以它作为「访谈记录」「设计取舍」
两个可选节写进契约本身——它是 `rounds.jsonl` 的聚合定稿，不是逐行搬运。

落盘到 `<issue-dir>/3-contract/contract.md`，照
[goal-contract-shape.md](references/goal-contract-shape.md) 写。

任务已经存在时改它的契约文件，不新建。判据只有一条：这次要动的是现有验收标准，还是
一件新的事。改现有标准、补现有实现、修刚发现的缺陷都回原契约重做，把改动过的内容
换成新版本；只有能独立交付的新事才另开一个 issue。

「设计取舍」节允许极简。没有需要取舍的实现路径时，写明「本次无需取舍」及其原因，
这句话本身就是记录，它证明这件事被问过而不是被忘了。用户说方案他定了、说别问了
直接干，记录照留：记下他定的那个，另一栏写「为什么没选别的」，一句话就够。

「访谈记录」节里被否决的候选要留着，那是它最值钱的部分。执行 Agent 只需要「验收条件」
和「强约束」就能干活，「访谈记录」是留给人看的，不必强求执行 Agent 通读。

`context.md` 里实际依赖的证据来源和确认版对照物写进「读什么」；`[B]` 档 fixture 和
其它必须落盘才能被验证的产物写进「要落盘的东西」。对照物是访谈产物、设计输入，不是
执行交付物，进「读什么」而不是「要落盘的东西」。指路不是预写事实：告诉执行 Agent
先读哪份文件，不泄露任何它该自己发现的结论。

契约描述做什么、为什么、边界和怎么算做完，不预写执行 Agent 可从仓库发现的事实、
可逆实现方案、逐文件任务或猜测性命令。一份契约只承载一件能独立交付的事。

**核心不变量：`contract.md` 单独拿走仍完整可交接。** 除了「读什么」点名的对照物，
不引用 issue 目录里的任何过程文件。

向用户展示目标、范围、验收条件和阻塞项摘要。只有用户确认这些表达了当前共同理解后
才落盘；未确认时保持候选状态并继续修改。推荐项、浏览器草稿、沉默或未回复都不是确认。

## 4. 校验与交接

```bash
node <workflow-interview>/scripts/session.mjs finalize <issue-dir>
```

一条命令做三件事：跑结构校验并把结果回填进 manifest；跑全部 `[A]` 档 Verify 命令；
按 [handoff-prompt.md](references/handoff-prompt.md) 生成交接指令并检查它没超
4000 字符。

### 冒烟怎么读

此刻实现还没做，所以**期望全红**。三种判读：

| 结果 | 意思 | 怎么办 |
| --- | --- | --- |
| `FAIL` | 命令跑起来了，退出码非 0 | 正常。功能还没做，这条 AC 是活的 |
| `PASS` | 现在就是绿的 | 看一眼：这条 AC 是不是已经成立了，还是验得太浅 |
| `UNRUNNABLE` | 命令根本没跑起来 | **AC 写错了**。命令名、包名或脚本名不存在，回去改 |

`UNRUNNABLE` 是这一步唯一要拦的东西。放它过去，执行 Agent 会撞上一条无法执行的验收
标准，然后自己发明一个替代判据——那条 AC 就被架空了，而报告上看起来跟通过了一样。

校验失败时修正契约，不降低规则。校验器只证明结构有效，冒烟只证明命令可执行，两者
都不证明产品目标已经实现。

### 收尾

```bash
node <workflow-interview>/scripts/session.mjs stage <issue-dir> 3-contract done --next "<一句话>"
```

最终报告契约路径、目标、范围、验收条件数量、校验与冒烟结果，以及精确阻塞项或那条
可复制的交接指令。**交接指令不落盘**：它是模板加两个变量，落一份只会在契约改了之后
变成陈旧的错误指令，每次由 `finalize` 现场生成。

把执行 Agent 直接指向这份契约，不点名交给哪个特定 skill 或工具，用户手上有什么执行
Agent 就交给它。有阻塞项时不启动实现。
