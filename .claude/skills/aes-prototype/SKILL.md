# 锁定对照物

把问清楚的理解翻译成一份用户能**逐处质疑**的具体物，迭代到确认。

原理和提问时先给候选靶子是同一个：人对着具体物挑毛病，比对着抽象文字空想可靠得多。
出得太早会跟着未收口的歧义反复重做；出得太晚，验收条件就只能引用一份没人看过的想象。

这一步撞出来的是第三类东西：**双方都没想到**的那些。它比用户知道却没说的更难够到，
因为提问的前提是已经知道该问什么。歧义收口之后仍然要走这一步，问不出来的部分只剩
它能兜。

## 开头

```bash
node <workflow-interview>/scripts/session.mjs init <date>-<任务词组>
```

幂等。产物落在 `2-prototype/` 下。上游是 `1-interview/context.md` 与 `rounds.jsonl`；
读不到时告诉用户缺什么、你的影响面判断可能因此失准，然后照常做——用户显式调用你
就是显式意图。

## 1. 先扫影响面

判据只有一句，写在最前面因为它决定后面全部工作：

> **改完之后，这个程序在哪些地方跑起来不一样了？每一处不一样，谁会看见、谁会受影响？**

每一处可观察的差异都要出一个可逐处质疑的对照物。逐面扫，一面都不许跳过：

| 影响面 | 问什么 | 有的话出什么 |
| --- | --- | --- |
| 用户可见界面 | 新增或改动了人眼看得见的东西吗 | `mock.html` |
| 可观察行为 | 同样的输入，输出或状态流转变了吗 | `behavior.md` |
| 可运行输出 | 在终端或日志里跑起来长得不一样了吗 | `example-run.md` |
| 对外接口报文 | 请求或响应的结构变了、新增了吗 | `api-mock.md` |
| 用户配置 | 配置文件、环境变量、命令行选项变了吗 | `behavior.md` 的配置差异节 |
| 历史兼容性 | 现有调用方、现有数据、现有脚本会受影响吗 | `behavior.md` 的不变清单 |
| 架构与依赖 | 依赖方向、模块归属、组件间边界变了吗 | `diagram.html` 的架构视图 |

后五面是这份清单存在的理由。只判「有界面还是有行为」会把接口兼容性、配置变更、
历史数据兼容、依赖归属整片漏掉，而它们恰恰是返工代价最高的那几种。

结果写成 `2-prototype/impact-surface.md`，逐面给出「有/无」、具体差异、谁受影响、
出哪份对照物。**判为「无」的那几面也要写出来**，写下「无」这个动作本身就是记录，
它证明这一面被扫过而不是被忘了。

### 七面全为否

这不是「跳过」，是信号：

> 扫不出任何可观察差异，说明这个目标还没有可观察的完成形态。举不出例子，
> 就写不出可判定的验收条件。

把结论写进 `impact-surface.md`，然后：

```bash
node <workflow-interview>/scripts/session.mjs stage <issue-dir> 2-prototype needs_reinterview \
  --reason "扫不出可观察差异，需问清「做完之后能观察到什么」"
```

回 `aes-interview`，不进下一阶段，也不硬造一份对照物。

真正的 `skipped` 只留给一种情况：差异确实存在但极小，且用户已经在需求阶段用文字确认过
它的具体形态。理由必须写进 `impact-surface.md`——`stage` 命令收到 skipped 时会当场验
七面扫描在盘，`impact-surface.md` 不齐就跳不了。

## 2. 出对照物

未确认的草稿放 `2-prototype/drafts/`，一版一个文件，顶部三行元数据：

```markdown
<!-- draft v1 | published <ISO 时间>
     用户意见：<他说了什么>
     状态：superseded by v2 / confirmed -->
```

确认后草稿可清，不强制留存。确认版落 `2-prototype/` 根下，用下面的固定文件名。

### `mock.html` — 界面

单文件自包含：内联 CSS 和 JS，写死示例数据，不连真实后端。呈现本次改动涉及的界面
结构、关键状态和关键交互。改动现有界面时对照现状标出改动点（一个 `.changed` 类框出来
就够），并在文件末尾用注释列清「新增什么、不变什么」。

宿主能直接展示 HTML 时直接展示，否则给出绝对路径请用户在浏览器打开。邀请用户对布局、
字段、文案、状态、交互、边界逐处质疑。

Mock 定的是结构、信息与关键交互方向，**不是像素规范**；用户明确要求像素级还原时把
该要求写进契约的 `强约束`，否则执行 Agent 只需结构对照。

### `behavior.md` — 行为对照表

```markdown
# 行为对照表: <slug>

**确认版·锁定。** 执行 Agent 改的是产品，不是这份对照表。
用户确认：<ISO 时间>

## 变化行

| # | 输入 / 前置 | 现在的行为 | 改后的行为 |
| --- | --- | --- | --- |

## 不变清单

<与变化行同等重要。逐条列出哪些现有行为必须保持原样，写明谁在依赖它>

## 配置差异

| 字段 | 现在 | 改后 | 迁移 |
| --- | --- | --- | --- |

<配置没变就整节省略；变了要写清旧配置文件还能不能原样用>
```

用具体数据写例子，不写抽象规则。变化行标出，**边界值单独成行**（空结果、超长、
非法值、并发）。

不变清单不是凑数：用户既要确认「变的是他要的」，也要确认「不变的是他依赖的」。
后者往往是需求阶段问不出来的那部分——他不觉得那算个要求。

流程类变化行可以再配一张 `diagram.html` 流程视图，让用户对着流向逐处质疑——
**行是源，图是行的一面**（图怎么做见下文 `diagram.html` 节）。

### `api-mock.md` — 接口报文对

定**报文结构**：字段名、类型、有没有、错误形态。每种结局给一对具体报文，含成功、
业务失败、用法错、意外错误。末尾用「已锁定的约定」列出字段级裁决（哪个字段始终存在、
哪个是闭集、哪种情况不出报文），并注明是哪一问定下来的。

### `example-run.md` — 可执行示例

定**端到端跑起来的样子**：怎么调用、管道怎么接、退出码怎么用、人看到什么。写死的
示例输出，不连真实系统。

**它和 `api-mock.md` 的边界要守住**：报文结构只在 api-mock 里定义一次，example-run
只写「怎么用、看到什么」并指回去。同一件事写两遍，改的时候必然只改一处。

必须保持不变的现有用法也要单独成一个场景，写明「这条现在能跑，改完之后必须逐字节
一样能跑」。

### `diagram.html` — 架构与流程视图

单文件自包含：内联 SVG 与 CSS，零 JS、零外链、系统字体——断网双击可开，与
mock.html 同一等级的硬规则。画**改后态**单视图，不做 before/after 双图：改动的
节点与连线用 `.changed`（accent 描边 + tint 填充）标注，删除项不占图面、进页脚
「删除清单」；图例固定两行——橙 = 本次新增/变更，灰 = 既有（不动）。

两种视图，事实源地位不同：

- **架构视图**是拓扑事实源：模块、依赖方向、本次动的是哪条边。它的每处标注变化
  都要经得起质疑，并作为例子进下一节的例子池。
- **流程视图**是 `behavior.md` 变化行的视图：同一批变化行换个画法，不另立例子；
  行是源，图是面。

每张图页脚必带 fidelity ledger：Detail/Merged/Collapsed/Dropped/Kept 逐条申报，
合并与删减绝不静默。色板、4px 网格、圆角正交连线、复杂度预算（≤9 节点、
≤12 箭头、≤2 accent，超了拆 overview + detail）、流程视图语法等绘图内核见
[diagram.md](references/diagram.md)。架构视图与流程视图默认同住一个
`diagram.html`（两张 SVG、预算各算）；只有超预算才拆出 `diagram-detail.html`，
`--artifacts` 里把两个都列上。

## 3. 迭代到确认

用户改哪就改哪，迭代到明确确认为止。

**迭代中暴露的新材料歧义要报回去问清，不在对照物里现场糊过去。** 撞出新歧义是这个
阶段的价值所在，不是它的失败：

```bash
node <workflow-interview>/scripts/session.mjs round <issue-dir> \
  '{"stage":"2-prototype","tier":"ask","question":"...","triggered_by":"2-prototype/drafts/v1-api-mock.md",...}'
```

再报 `needs_reinterview`，由编排器回 `aes-interview`。

确认版一律声明为**不可修改**：执行 Agent 改的是产品，不是对照物。与优化型目标锁
测量脚本同理——不锁住尺子，被优化的就会是尺子。

## 4. 它同时是下一阶段的例子池

验收条件不是发明出来的，是从具体例子里聚出来的。每份确认版对照物同时就是例子来源，
**不另立一份例子清单**：

- `behavior.md` 的每个变化行 = 一个例子
- `api-mock.md` 的每对报文 = 一个例子
- `example-run.md` 的每个场景 = 一个例子
- `mock.html` 的每个关键状态与交互 = 一个例子
- `diagram.html` 架构视图的每处改动标注 = 一个例子（依赖断言进契约「强约束」或
  `[A]`；流程视图不另立——它就是 behavior.md 的变化行）

`aes-goal-contract` 直接读这几份文件，不重新问一遍。

## 收尾

```bash
node <workflow-interview>/scripts/session.mjs stage <issue-dir> 2-prototype done \
  --artifacts "behavior,api-mock,example-run,diagram" --next "<下一步一句话>"
```

`--artifacts` 只列实际产出的确认版；第七面判「有」时**必须**包含 `diagram`
（diagram.html 架构视图）——这不是自觉，`done` 闸门会当场拦下缺图的清单。`done`
不是自报的：命令会当场校验
impact-surface.md 七面都被扫过、`--artifacts` 至少一份且列的文件真的在
`2-prototype/` 下，不过就拒收。挡的是结构不是质量——对照物像不像，由用户确认负责。

然后交回 `workflow-interview` 继续流转。
