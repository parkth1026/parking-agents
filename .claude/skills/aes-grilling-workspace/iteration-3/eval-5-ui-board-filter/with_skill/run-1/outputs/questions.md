**Q1 筛选状态的持久化与分享方式？**
- 证据：现有页面无任何 URL 参数或本地存储逻辑；「筛选要不要活过刷新、能不能发给同事」直接改变公共行为，属用户决定。
- A. URL 查询参数（推荐）：刷新保持，链接可直接分享给同事；代价是 URL 会变长、需处理无效参数。
- B. localStorage：刷新保持，但链接发给同事无效；代价是「分享视图」做不到。
- C. 不持久化：最简单；代价是刷新即丢。

**Q2 负责人筛选是单选还是多选？**
- 证据：现有 UI 无筛选控件，无先例可循；单/多选改变交互与 URL 形态，属用户决定。
- A. 单选（推荐）：一次看一个人，控件简单（下拉即可）；代价是想同时看两人做不到。
- B. 多选：更灵活；代价是控件、空态、URL 编码复杂度都上升。

**Q3 本次筛选范围只按负责人，还是顺带做状态/标签筛选？**
- 证据：原始请求只提负责人；范围直接决定 In/Out，属用户决定。
- A. 只按负责人（推荐）：范围最小；代价是后续要扩展需另立需求。
- B. 顺带做状态/标签：一次到位；代价是范围膨胀、交付变慢。

**Q4 筛选下拉的负责人选项从哪来？**
- 证据：任务数据里有 `assignee` 字段；仓库没有独立的成员名单。
- A. 从当前任务数据去重得出（推荐）：零新增数据源；代价是没有任务的人不会出现在选项里。
- B. 维护一份固定成员名单：人员全；代价是要新增数据源和维护成本。
