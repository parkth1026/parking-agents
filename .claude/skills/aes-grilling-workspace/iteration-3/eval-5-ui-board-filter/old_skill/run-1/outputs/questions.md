- In（一句话）：看板页面新增负责人筛选控件、过滤渲染逻辑、筛选状态持久化、无匹配时的空态处理、配套测试。

- AC 大致方向：控件与选项来源；过滤正确性；刷新/分享后筛选保持；一键回到全部；空态；`npm test` 兼容 + 新增筛选逻辑断言。

宿主无 AskUserQuestion 工具，按 Skill 约定退化为编号文本，一轮问全 4 个互不依赖的歧义：

**Q1. 筛选状态的持久与分享语义（决定公共行为：URL 是否成为对外可见接口）**
- 证据：当前页面无任何状态持久化；「筛选要不要跨刷新/跨人保持」无法从仓库查出，是产品决定。
- A. URL 查询参数：刷新后保持，把链接发给同事打开是同样筛选结果（推荐；代价：URL 带参数，成为对外可见、需长期兼容的行为）。
- B. localStorage：本机刷新保持，但链接不可分享（代价：同事打开同一链接看不到相同结果）。
- C. 不持久：实现最简（代价：一刷新就丢）。

**Q2. 负责人选择方式**
- 证据：种子数据只有 3 个负责人，单选/多选 UI 与 URL 语义复杂度差异明显。
- A. 单选一个负责人（推荐；代价：想同时看两人需切换两次）。
- B. 多选（代价：控件与 URL 语义更复杂，验收面变大）。

**Q3. 筛选维度范围**
- A. 只按负责人（推荐；代价：以后要按状态/标签筛需另起需求）。
- B. 这次顺带加状态/标签筛选（代价：范围扩大，改动与验收显著变多）。

**Q4. 筛选后一张卡片都没有时的行为**
- 证据：选项若来自现有任务数据则界面操作不会筛空，但 URL 直接携带无任务的负责人时会出现空结果。
- A. 显示空态提示文案，例如「没有匹配的任务」（推荐；代价：多一处 UI 文案需维护）。
- B. 三列留空不提示（代价：容易被误认为数据没加载）。
