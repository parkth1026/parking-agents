## 第 1 轮（阶段 2：批量问清歧义）

### 执行方展示的内容

先给出完整推荐候选作为靶子：

> **候选草案**
> - Goal（一句话）：order-consumer 处理失败的订单事件不再被静默丢弃——失败自动重试，重试耗尽后留痕可人工恢复，成功路径不变。
> - In（一句）：src/consumer.mjs 消费链路的失败处理（重试 + 最终失败留痕）及配套失败路径测试。
> - Out（一句）：不改 handler 业务校验规则，不引入新基础设施。
> - AC 方向：失败事件自动重试并可恢复；重试耗尽的事件有可解析留痕；成功路径与台账格式兼容；单条失败不阻塞其余事件。

随后一次列出全部独立歧义（共 5 个，超过 4 个上限，按技能约定用编号文本一次全列；每题附证据、互斥选项、推荐与代价）：

**Q1. 失败后的处理策略是什么？**
证据：src/consumer.mjs 注释明确「handle 抛错时该事件被直接丢弃，没有重试也没有留痕」；handler.mjs 注释提示存在偶发网络抖动类临时错误。
- (a) 自动重试 N 次（间隔递增），重试耗尽后留痕 —— 推荐。代价：消费单条事件的最坏耗时变长。
- (b) 不重试，失败直接留痕。代价：网络抖动类可自愈失败也要人工处理。
- (c) 失败即中止整个消费进程。代价：一条坏事件阻塞全部订单。

**Q2. 重试耗尽仍失败的事件，留痕位置与格式？**
证据：仓库数据均为 data/ 下 jsonl（events.jsonl、ledger.jsonl）。
- (a) 追加写 data/dead-letter.jsonl，每行含完整原始事件 + 失败原因 —— 推荐。代价：新增一个需要人工关注的文件。
- (b) 写回 ledger.jsonl 标记 ok:false。代价：改变现有台账行含义，下游可能不兼容。
- (c) 每个失败事件单独落一个文件。代价：文件散落，难以批量回放。

**Q3. 是否区分永久性错误（如 invalid amount）与临时性错误（网络抖动）？**
证据：handler.mjs 对 amount 非法直接抛错（重试注定失败），网络抖动类则可能重试成功。
- (a) 不区分，统一重试后进死信 —— 推荐。代价：永久性错误会白重试 N 次（本地操作，成本很低）。
- (b) 永久性错误跳过重试直接进死信。代价：需要定义并维护错误分类契约，分类错了会误伤。

**Q4. 范围边界：是否需要配套管理界面 / 监控面板 / 告警，或更换队列、引入消息中间件？**
证据：仓库为纯 Node 脚本消费者，无任何前端与中间件依赖。
- (a) 纯后端改动：不加界面 / 监控 / 告警，不换队列不引中间件 —— 推荐。代价：最终失败仍需人工查看死信文件发现。
- (b) 附带最小告警通知。代价：引入外部依赖与配置，超出本次修复动机。

**Q5. 兼容性底线：现有 ledger.jsonl 台账格式与成功路径行为是否必须原样保持？**
证据：consumer.mjs 成功路径写 {"id":...,"ok":true}；下游是否依赖该格式仓库内查不到，属于用户裁决。
- (a) 台账格式与成功路径行为都不变 —— 推荐。代价：失败信息只能落在新文件，不能就地扩展台账行。
- (b) 允许扩展台账行字段。代价：下游解析方可能不兼容。

同时告知（Fact，不占提问轮次）：仓库验证基建已查清——`npm test`（node test/run-tests.mjs，退出码 0 为过）；docs/testing.md 约定消费链路改动需补失败路径断言、无集成环境、用本地 jsonl 数据验证。本请求判定为纯后端（消费者链路，无任何界面成分），将跳过界面 Mock 阶段。

- Q3：PERSONA 未覆盖 → 按约定取推荐项 (a)：统一重试，不区分错误类型。
