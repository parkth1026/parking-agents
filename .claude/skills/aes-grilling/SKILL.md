# 问清楚要做什么，以及怎么算做完

一个任务只锁两个点：要做什么，以及怎么算做完。中间怎么实现，交给执行 Agent
自己发挥。这两个点定偏了，中间做得再好也是错的，所以这个技能全程用提问达成。

写记录时照 [goal-contract-shape.md](references/goal-contract-shape.md) 的样子写，
写完跑 `scripts/validate-goal-contract.mjs` 判定。产出是一份自包含的 Goal
Contract，不依赖任何外部工作流工具或其它 skill 才能被读懂、被交接。

当前宿主 Agent 负责全过程，subagent 只调查事实。用户明确要求 Web 工作台时，
改用 `aes-grilling-web`。本技能不实现任务里的目标。

## 1. 调查事实

读取目标仓库适用的规则，以及请求牵涉的代码、测试、设计、日志和必要的一手资料。
只调查会改变目标、范围、公共行为、兼容性、验收条件、硬约束或难逆成本的事实。

无论请求内容为何，固定查清一项事实：仓库现有的验证基建，包括测试命令、CI 门、
覆盖率工具、fixture 约定。查到的清单就是第 4 步验证途径的候选池。「这个项目能
怎么验」是查出来的，不是套通用分级套出来的。查不到基建时可选途径只剩用户真实
测试与新建基建，两者都要在候选里写明代价。

同样固定判定一项分类：本次请求需要哪种对照物。新增或改动用户可见界面出界面
mock；改变现有可观察行为或兼容性（输入输出、接口报文、状态流转的今昔差异）出
行为对照表；两者兼有各出各的；两者皆无（纯新增能力、无既有行为可对照，或不触及
公共行为的内部改动）跳过第 3 步。现有页面、代码行为和设计稿是 `Fact`，直接调查；
但请求本身落在哪类读不出来时，这是 `User decision`，要问。

存在两个以上互不依赖的事实问题且可以创建 subagent 时，并行派遣只读调查；为每个
subagent 限定问题、目标路径和所需证据。subagent 返回事实、证据位置和未知项后结束，
不询问用户、不替用户作决定、不修改产品。当前宿主 Agent 同时调查其余事实并汇总证据；
无法使用 subagent 时自行完成调查。

能由仓库或环境证据回答的事实，查清后写进上下文并告知用户，不占用提问。但事实一旦
暗示该怎么做（该跟哪个模式、该接受哪种代价、该把什么排除在外），整个决定仍然归用户。

用户用的词与仓库文档或代码里的词冲突、或者一词多义时，拿出具体出处，把「按哪个
意思走」列为用户决定。仓库语言是证据，不是权威。

将每个相关事项归为：

- `Fact`：由仓库或环境证据回答；
- `User decision`：会改变结果或边界，必须由用户裁决；
- `Agent-owned`：局部、可逆且不改变外部契约，交给执行 Agent。有几条都成熟、
  但成本结构不同的路径可走时，它不再是 `Agent-owned`，选哪条是 `User decision`；
- `Blocked`：缺少权限、凭据、外部前置条件或当前无法取得的必要用户决定。

推荐项只是建议，不能代替用户决定。

## 2. 批量问清歧义

一轮问完此刻所有互不依赖的歧义。不要挤牙膏：问一个等一个会让用户反复切回上下文，
也会让你误以为问题在变少。

提问之前先给出一份完整的推荐候选：目标一句话，做什么和不做什么各一句，验收的
大致方向。对着一份具体草案挑毛病，比对着空白回答问题容易得多，你也更容易看出
自己猜错了哪里。候选是靶子不是结论，用户改哪条就是哪条。

只问不同答案会改变目标、范围、公共行为、兼容性、可观察验收、权限风险或难逆成本的
问题。不问可调查事实、成熟的低风险默认做法或 `Agent-owned` 实现选择。

问到本质那一层，不要停在表面选项上。「筛选控件放顶部还是侧边」是表面，两个答案
最后落到同一个东西；「看板一多，人要的是只看自己的，还是快速定位某个人的」才是
本质，两个答案通向不同的实现（筛选器或者搜索加高亮）。判据很简单：如果两个选项
最终落到同一个实现，这个问题就没问到点上，往下再挖一层。表面问题问得再多，
也只是把用户的原话换个说法还给他。

几条实践路径都成熟、但成本结构不同时（性能与可读性、改动面与工期、通用与专用），
不能拿「都是最佳实践」把选择权含糊过去。这类选择定下来要写进 `强约束`，回头改要
重做已经做完的工作，按下面的分诊至少进确认区；你自己也说不清哪条更划算时进提问区，
并写明各自的真实代价。写成约束而不是实现步骤：「必须走 X，不引入 Y」不会过时，
步骤会过时，而且会挤掉执行 Agent 本该自行发挥的部分。

### 先分诊，再决定什么配得上一个问题

提问预算是稀缺的。用户一次能认真读的东西就那么多，把预算花在他一眼就答「按你说的
办」的地方，真正的分歧就没人细看了——满屏的问题反而降低了访谈质量。所以每个待定项
先分诊，只有一档配得上完整提问。

先看你的倾向有多强，再看选错了能不能回头：

| | 选错了可逆 | 选错了难回头 |
| --- | --- | --- |
| 置信 ≥ 80% | **默认区**：一行写清，不反对就算定 | **确认区**：一行写清，要他回一个字 |
| 置信 < 80% | **提问区**：完整三段加百分比 | **提问区**，并标明难逆 |

难逆指改公共契约、改默认行为、改数据格式、删除既有能力、迁移数据这类做完了回头要
付第二次代价的事。

**但百分比只在你有证据的地盘上可信，这条比上面那张表更要紧。** 仓库里读得到的事——
现有实现怎么写、测试怎么跑、哪个模式是这个项目的惯例——你的 80% 有根据。跨出仓库
边界的事——下游还有谁在用、为什么现在要做、错了谁挨骂、组织上允不允许——你的 80%
是猜的，你只是把「我想不出反例」当成了「没有反例」。这类项一律进提问区，置信多高
都一样。

举个具体的：一个脚本的默认输出路径要不要保持原样，取决于仓库外有没有别的东西在按
老路径捞文件。这件事代码里一个字都没写，你读得再仔细也读不出来。给它 85% 然后默认
掉，就是直接翻车。

还有一类东西连提问都问不出来：用户知道、但他自己没意识到需要说的（他漏掉是因为
没觉得那算个要求，或者想说却说不出来）。对这类东西「还有别的要求吗」永远是空问，
因为对他来说那是显然的。它靠第 3 步的具体物撞出来，不靠提问——这也是那一步存在的
理由。

### 默认区和确认区怎么写

两档合成一份清单一次发出，一行一条：定什么 — 为什么这么定 — 一句代价。代价必须
有，没有代价用户就没有判断依据，「不反对」会退化成盲签。

```text
以下 N 条我按查到的事实定了，你不反对就算定：
- <定什么> — <为什么> — 代价：<一句>

这 M 条我也有倾向，但选错了不好回头，请各回一个字：
- <定什么> — <为什么> — 代价：<一句>
```

用户翻掉其中一条，不要辩护，改掉就是。他翻的那条恰好说明你在那个方向上置信虚高，
记住它，同一份访谈里别再犯第二次。

默认区不设条数上限：查得越清，能进默认区的越多，这正是第 1 步的回报。分诊之后提问
区还剩七八条的话，多半是第 1 步没查够（一半「问题」其实是可查事实），或者这个任务
太大，该拆成几件能独立交付的事。

### 提问区的选项长什么样

只有进了提问区的项才写成下面这样。默认区和确认区一行就够，别给它们套三段——那正是
把访谈变成仪式的做法。

提问区的项不超过 4 个时用 `AskUserQuestion` 一次发全，超过 4 个改用编号文本一次
全列。该工具一次最多 4 题，那是工具的上限，不是拆轮次的理由；宿主没有该工具时
退化为编号文本，提问范围不变。

提问区的每个选项固定三段，一段都不省。用户要做的判断是「哪个代价我付得起」，三段
就是他做这个判断的最小材料：

```text
Q1. <问到本质那一层的问题>
已知事实：<一两句，带出处>

A. <一句话说清这个选项> — 62%（推荐）
- 选什么：<覆盖什么、不覆盖什么，写到用户能确认边界>
- 好处：<最多三条>
- 代价：<最多三条>

B. <一句话> — 26%
- 选什么 / 好处 / 代价 同上

C. <一句话> — 12%
- 选什么 / 好处 / 代价 同上
```

「选什么」尤其要写清这个选项**不**覆盖什么。用户翻车多半翻在他以为包含、实际没
包含的那部分，而这部分只有你知道边界画在哪。

好处和代价都写这个仓库里的具体后果。「更灵活」「符合最佳实践」等于没写：它对每个
选项都成立，用户拿它没法比较。每边最多三条，写不满不用凑，超过三条说明混进了不
影响选择的话。

### 百分比怎么给

百分比是你的判断：在你已经查到的事实和用户已经说过的话之下，这个选项就是他要的
那个的可能性。全部选项加起来 100%。它先决定这个项走哪一档，再作为选项的一部分
发给用户，所以它不是排版元素，给虚了会直接把该问的问题误分到默认区。

它比「推荐」两个字多出来的信息是分布形状。65/25/10 是在说差距明显、翻推荐要有
理由；45/40/15 是在说这题你也在两难之间、值得他多想一会儿。这个信息只有你有。

反过来，分布拉平到 34/33/33 是个警报：要么该查的事实还没查（回第 1 步），要么这题
停在表面、两个答案最后落到同一个实现（往下再挖一层）。

注意分诊之后提问区里剩下的都是你没把握的项，所以这里出现 80% 以上的选项本身就
可疑——要么它该进默认区，要么你给高了。真两难就写 45/40/15，别为了显得有主见硬拉。

用户选了 10% 的那个照样算定了，不复述你的推荐、不再劝一遍。他知道的影响面你不知道，
这正是这个问题归他裁决的原因。

`AskUserQuestion` 的选项卡片装不下三段。完整问题块先以文本发出，用户在那里读代价；
紧接着用工具收选择，选项 label 写 `A. <一句话> — 45%`，description 写最关键的那
一条代价。工具收答案，文本给判断依据，缺一个用户就只能凭猜。

用户回答会改写歧义地图：解锁下一层问题，也可能让原本要问的问题消失。重算之后继续
批量问，直到收口。批量是为了让用户一次看全，不是为了少问。追加不需要额外理由，
判据是收没收口，不是问了几轮。要压的从来不是轮次，是问题质量：显而易见的、
可调查的、答案不改变执行的，一个都不该出现，问一个都嫌多。

### 什么时候停

每轮回答后逐维度自评并显式报告状态（已定、部分、未定）：

- `意图`：为什么要做，解决谁的什么问题；
- `结果`：做完之后能观察到什么，用什么判；
- `边界`：做到哪里，明确不做什么；
- `约束`：什么现有行为、兼容性或限制必须保持；
- `现状`：已有代码库时，相关现状是否已查清。

两条同时成立才结束提问：

1. 没有维度停在「未定」，且不做什么和执行 Agent 可自行决定的范围都已写明；
2. 收口审计通过。还想问的问题，不同答案只会改变措辞，不会改变执行。

歧义低是开始审计收口的许可，不是继续钻的许可。判据没满足就不进下一阶段，问了
多少轮都一样。没有材料歧义时直接进下一阶段，不为流程制造提问。

## 3. 对齐对照物

第 1 步判定两者皆无时跳过本阶段，直接进第 4 步。其余请求在材料歧义收口后、
起草验收条件前，先把问清楚的理解翻译成一份用户能逐处质疑的具体物，迭代到确认。
原理同第 2 步的候选靶子：人对着具体物挑毛病，比对着抽象文字空想可靠得多。
出得太早会跟着未收口的歧义反复重做；出得太晚，验收条件就只能引用一份没人看过
的想象。

这一步撞出来的是另一类东西：不是用户知道却没说的，而是**双方都没想到**的。这类
东西提问永远问不出来，因为提问的前提是已经知道该问什么。所以歧义收口不是跳过本
阶段的理由——恰恰相反，问不出来的部分只剩这一步能兜。

界面向产出单文件自包含的 mock HTML：内联 CSS 和 JS，写死示例数据，呈现本次改动
涉及的界面结构、关键状态和关键交互，不连真实后端。改动现有界面时对照现状标出
改动点。宿主能直接展示 HTML 时直接展示，否则给出文件绝对路径请用户在浏览器打开。
邀请用户对布局、字段、文案、状态、交互、边界逐处质疑。Mock 定的是结构、信息与
关键交互方向，不是像素规范；用户明确要求像素级还原时把该要求写进 `强约束`，
否则执行 Agent 只需结构对照。

行为变更产出行为对照表：每行一个具体场景，写输入或前置条件、现在的行为、改后的
行为。用具体数据写例子，不写抽象规则；变化行标出，边界值单独成行。表后附不变
清单，明确列出哪些现有行为保持原样。它与变化行同等重要：用户既确认「变的是他要
的」，也确认「不变的是他依赖的」。接口或格式变更时例子行写成具体样例报文对；
流程或状态变更时可附轻量状态图。邀请用户逐行质疑：改结果、补场景、挪边界。

混合请求界面部分出 mock、行为部分出对照表，各自迭代确认。用户改哪就改哪，迭代到
明确确认为止。迭代中暴露的新材料歧义回第 2 步批量问清，不在对照物里现场糊过去。

确认版落盘为契约的同目录同 slug 文件，未确认的草稿放临时目录，不占用该路径：

```text
docs/goal-contracts/<date>-<任务词组>-mock.html   # 界面对照物
```

行为对照表不单独成文件，整张写进 Goal Contract 的「访谈记录」一节。任务目录里
除了契约本身只放这一个 html，截图、压缩包、导出的数据都不要往里塞。

## 4. 对齐验收条件

验收条件是执行 Agent 唯一的终止条件，也是审计器每一轮反复消费的判定依据。混在
整份任务记录里一起确认，用户扫一眼就点头了，写偏了要等执行完才发现。所以单独一步。

分流规则、条数怎么得出、Verify 四档怎么写，都在
[goal-contract-shape.md](references/goal-contract-shape.md)。这里说怎么把它们问出来。

### 4a 收集判定例子

验收条件不是发明出来的，是从具体例子里聚出来的。发散地想「这个需求有哪些方面
要验」没有天然终点，只有上限，写到上限附近就会停手；从例子聚类有天然终点，
例子举完就完了，条数是数出来的，不是定出来的。

走过第 3 步的需求，例子已经在手：行为对照表的每个变化行是一个例子，mock 的每个
关键状态与交互是一个例子。直接用，不重新问一遍。

跳过第 3 步的需求（纯新增能力、无既有行为可对照）在这里补齐。问法要紧：问「验收
标准是什么」是在要求用户做抽象，他多半只能答「能用就行」；问「做完之后你会怎么
试它」「什么情况下你会说这没做对」是在要求他回忆一个具体动作，这他答得出来。
每个回答都是一个例子，带着具体输入和期望结果。

一个例子都举不出来，说明这个目标还没有可观察的完成形态，回第 2 步问清楚结果，
不靠想象补足。

### 4b 逐条带候选，批量提问

每条验收条件是一个带候选的问题，不是一份等待点头的定稿。给定稿求确认只暴露你的
结论，用户只能凭直觉觉得哪里不对；带候选则暴露你考虑过的备选空间，他能看见你
排除了什么。这与第 2 步用候选靶子是同一个道理，在验收上同样成立。

候选的主轴是「这条错了会怎样，那就这么验」：先写后果，再写对应的验证途径与真实
代价。需求方天然知道后果，不天然知道「跑现有测试」和「端到端跑一遍」差在哪；
要他把自己的需求翻译成验证深度，中间隔着他没有的知识。这件事的两半本来就分处
两边：影响（赔钱、用户看得见、只是难看）只有他清楚，发生概率（这块多常改、
多复杂、依赖多深）你从仓库查得到。你出概率和途径，他出影响。

这条分工正好划出这里的分诊线，它和第 2 步的分诊是同一把尺子在两个地方用：

- **「这条错了会怎样」永远要问。** 它跨在仓库边界之外，没有任何仓库事实能代答，
  你的置信在这里天然不可靠。每条 AC 都要带着你写的后果一句话请他确认或改写。
- **「那就用哪条途径验」按分诊走。** 途径是仓库事实加你的判断，够格进默认区。
  基建现成、途径可逆、后果不严重的，一行定掉：`AC-003 用现有 npm test 断言 —
  仓库测试就是这个风格 — 代价：覆盖不到真实数据形态`。

三种情况即使你很确定也必须进提问区，因为它们要么难逆、要么要用户付出成本：含数字
门槛的（门槛值、用什么尺子量、尺子锁不锁）、需要用户提供真实数据的、仓库没有基建
得先建的。这三类恰好是验收里最贵的部分，省这里的轮次等于在唯一不能省的地方省。

进了提问区的照第 2 步「提问区的选项长什么样」和「百分比怎么给」写，这里的好处就是
这条能给多少信心、多快出结果，代价就是要先付出什么。形如：

```text
AC-002 <这条要判定什么>
这条错了会怎样：<一句话，等用户确认或改写>

A. 错了只是难看 → `[A]` 跑现有 `npm test` 断言 — 62%（推荐）
- 选什么：只断言函数返回值，不覆盖真实数据形态。
- 好处：仓库现成基建，一分钟出结果，每次改动都跑得起。
- 代价：真实数据里的形态问题这条验不出来。

B. 错了用户看得见 → `[B]` 你给一组真实数据做黄金用例 — 33%
- 选什么：你提供一份真实数据与期望输出，双双落盘成 fixture。
- 好处：能验出合成数据验不出的形态问题。
- 代价：要你提供数据并确认能否脱敏，拿不到就是阻塞。

C. 错了会赔钱 → 端到端跑一遍核心流程 — 5%
- 选什么：新建端到端基建，跑完整链路。
- 好处：置信度最高，回归也一起兜住。
- 代价：仓库目前没有这套基建，得先建，大致 X 个工作日。
```

候选池就是第 1 步查到的验证基建，加上「用户提供一份真实数据或场景」。后者始终在场，
不是选了 `[B]` 之后才追问。不要预设 L1、L2、L3 这类通用阶梯：阶梯是先验的，答不出
「这个仓库此刻有没有」，而在没有端到端基建的仓库里，「跑一遍端到端」的真实代价不是
「较高」，是先花时间把基建建起来。候选写的是这个仓库此刻能跑什么、各自要付什么。

以下情况必须在候选里写明真实代价，不能含糊带过：

- 仓库没有现成基建，该途径的代价包含先把基建建起来，写出大致工作量；
- 涉及真实数据或外部系统，写明合成数据说明不了问题，不许替用户发明「代表性数据」；
- 含数字门槛，门槛值、用什么尺子量、尺子锁不锁一并进候选。优化型目标把测量脚本
  声明为不可修改，防止执行 Agent 改测量而不是改工件。

其余候选轴按需附加：判到多严（整体一致、关键字段一致、逐字节一致）、边界算不算
（空值、超长、并发）、门槛定在哪、这条要不要留。一样附百分比和理由。口径变了
Verify 跟着变，一起给。

用户选了 `[B]` 后一次问全：数据在哪、能否脱敏、期望输出以什么为准、fixture 放哪。
数据拿不到是客观阻塞，写明精确解除条件，不拿「大概的数据」凑数。

一轮发全所有验收条件的候选，让用户一次看见全貌。四条以内用 `AskUserQuestion`
一次发全；超过四条改用编号文本一次全列，并告诉用户可以一次回复完，比如「1 选 B，
3 的门槛改成 500ms，删 5，其余按推荐」。

分诊压掉的是版面，不是决定。每条 AC 都还在，只是够格进默认区的那些从三段压成一行，
用户照样能一句话翻掉任何一条。回答暴露出新的判定分歧就接着问，追问不需要额外理由。

问到这个程度才算收口：还想问的问题，不同答案只会改变 Verify 的措辞，不会改变
执行 Agent 到底要跑什么、跑到什么程度。没到就继续问，问了几轮都一样。

起草时暴露出新的材料歧义，回第 2 步问清楚，不在这里现场糊过去。

走过第 3 步的需求，对照物经由 4a 的例子进入验收条件，不在聚类之外另加一条整体
对照。界面向：mock 的每个关键状态与交互作为例子参与聚类，Verify 默认 `[C]` 并
写明 mock 路径（`强约束` 声明像素级时按像素级判），仓库存在截图 diff 或视觉回归
基建时升级 `[A]`；只有当整体结构或信息层级确实无法被任何一条逐点验收覆盖时，
才单独立一条结构对照。逐点已经覆盖完还立一条，是同一件事判两遍。行为变更：确认
的例子行直接转化为 Verify，有测试基建时写成 `[A]` 断言，含具体数据样例时落成
`[B]` 黄金用例，输入与期望输出取自对照表，不另行发明。确认版对照物一律声明为
不可修改，执行 Agent 改的是产品不是对照物，与优化型目标锁测量脚本同理。

用户回答完全部问题后验收条件定稿。之后要改就回本阶段，不在任务记录里悄悄改。

## 5. 落盘

访谈过程本身是产物，不是通往契约的一次性开销。问过什么、否决过什么、为什么这么
定，只留在聊天记录里等于没留：下一个人看不到，你自己过两周也看不到。所以它们不
是丢掉，而是作为「访谈记录」「设计取舍」两个可选节写进同一份契约。

产出是一份自包含的 Goal Contract，照 [goal-contract-shape.md](references/goal-contract-shape.md)
写；拿不准信息密度时看一眼 [goal-contract-example.md](references/goal-contract-example.md)：

```text
docs/goal-contracts/<date>-<任务词组>.md         契约本身：目标、范围、强约束、
                                                验收条件，外加访谈记录、设计取舍
docs/goal-contracts/<date>-<任务词组>-mock.html  可选，第 3 步的确认版界面对照物
```

任务已经存在时改它的契约文件，不新建。判据只有一条：这次要动的是现有验收标准，
还是一件新的事。改现有标准、补现有实现、修刚发现的缺陷都回原契约重做，把改动过
的内容换成新版本；只有能独立交付的新事才另开一份新契约。

「设计取舍」节允许极简。没有需要取舍的实现路径时，写明「本次无需取舍」及其原因，
这句话本身就是记录，它证明这件事被问过而不是被忘了。用户说方案他定了、说别问了
直接干，记录照留：记下他定的那个，另一栏写「为什么没选别的」，一句话就够。

「访谈记录」节里被否决的候选要留着，那是它最值钱的部分：说明当时考虑过什么、为
什么没走那条路。执行 Agent 只需要「验收条件」和「强约束」就能干活，「访谈记录」
是留给人看、留给下一次改动这份契约时的人看的，不必强求执行 Agent 通读。

第 1 步实际依赖的证据来源和第 3 步的确认版对照物写进契约的可选节「读什么」；
`[B]` 档 fixture 和其它必须落盘才能被验证的产物写进可选节「要落盘的东西」。
对照物是访谈产物、设计输入，不是执行交付物，进「读什么」而不是「要落盘的东西」。
指路不是预写事实：告诉执行 Agent 先读哪份文件，不泄露任何它该自己发现的结论。

契约描述做什么、为什么、边界和怎么算做完，不预写执行 Agent 可从仓库发现的事实、
可逆实现方案、逐文件任务或猜测性命令。一份契约只承载一件能独立交付的事。

向用户展示目标、范围、验收条件和阻塞项摘要。只有用户确认这些表达了当前共同理解
后才落盘；未确认时保持候选状态并继续修改。

Web 选择只是设计输入，不能代替最终确认。推荐项、浏览器草稿、沉默或未回复都不是确认。

## 6. 校验与交接

落盘后跑：

```bash
node <skill-dir>/scripts/validate-goal-contract.mjs <契约路径>
```

退出码 0 是过，1 是有 ERROR，2 是路径不对。`WARNING` 不挡，但每条都值得看一眼。

校验失败时修正记录，不降低规则。校验器只证明结构有效，不证明产品目标已经实现。

最终报告契约路径、目标、范围、验收条件数量、校验结果，以及精确阻塞项或可复制的
启动指令。启动指令按 [handoff-prompt.md](references/handoff-prompt.md) 生成，
把执行 Agent 直接指向这份契约——不点名交给哪个特定 skill 或工具，用户手上有什么
执行 Agent 就交给它。有阻塞项时不启动实现。

## 简单不是跳过访谈的理由

多简单的需求都留下这份契约、访谈记录和设计取舍，设计取舍可以只有五句话。简单
需求带着没验证的假设开工，返工代价和复杂需求一样。

| 听到这句 | 怎么回 |
| --- | --- |
| 需求我说清楚了，别再问了 | 那就不问了，我把你说的写成记录，你看一眼对不对 |
| 你问得太啰嗦了，像走仪式 | 有把握的我直接定，列成一行一条你扫一遍；只有真两难的才占你一个问题 |
| 方案我定了，不用列备选 | 记下你定的那个，另一栏写「为什么没选别的」，一句话就够 |
| 上一轮已经分析过了 | 上一轮在聊天记录里，下一个人看不到。落成文件 |
| 就这么点事，直接排计划 | 计划的每一步都要指回设计里的某条决定，没有设计计划无处生根 |
| 验收标准你看着定就行 | 定偏了要执行完才发现。你只要答「什么情况下你会说这没做对」 |
