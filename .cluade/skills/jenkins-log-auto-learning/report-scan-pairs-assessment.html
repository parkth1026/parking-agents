2 scan-pairs.ps1 架构分析

双阶段设计

Phase 1 快速分类（行 60–94）
  • 遍历所有构建，逐一快速分类
  • SUCCESS → 直接写 track（success:w=?）
  • ABORTED / NOT_BUILT / BUILDING → 直接写 track（skip:xxx）
  • FAILURE → 仅计数，留给 Phase 2 配对
Phase 2 滑动窗口配对（行 97–152）
  • 过滤出 FAILURE + SUCCESS 的有意义序列
  • 连续 FAILURE 收集为 failGroup
  • failGroup 后紧跟 SUCCESS → 记录 pair（hasFix=true）
  • failGroup 后无 SUCCESS → 标记 failure:no-fix-found

3 发现的问题

严重

🔴 Bug 1：Track Key 路径前缀不一致

问题描述
analyzed-builds.json 中的 key 存在路径前缀不一致，同一构建可能被记录为两个不同的 key
示例（无前缀）
"wdp-ue/job/Earth/job/twe-ue5.5#890"
示例（有前缀）
"job/wdp-ue/job/Earth/job/twe-ue5.5#890"
影响
去重失效，同一个构建可能被重复处理，导致分析结果不准确
根因
config.json 中的 job.path 以 job/ 开头，但 scan-pairs.ps1 在某些代码路径中可能裁剪了前缀
修复建议
统一使用 config.json 中的 job.path 原值作为 key 前缀，确保所有代码路径一致
中等

🟠 Bug 2：历史遗留 PSObject 序列化条目

问题描述
analyzed-builds.json 中存在旧格式条目，无法被正确解析
示例
"@{errorPhase=Cook; fixResult=SUCCESS; ...}"
影响
这些条目等同于垃圾数据，破坏数据一致性，可能导致后续分析逻辑出错
根因
早期代码将 PowerShell 对象直接序列化为字符串，而非手动构造格式化字符串
修复建议
编写一次性清理脚本，将旧格式转换为标准 "failure:score=N:ErrorCode:fix=#N" 格式
低优先级

🔵 性能问题：O(n²) 的 track 查找

问题描述
-contains 在 PSObject.Properties.Name 上是线性查找，复杂度 O(n)
当前影响
track 文件约 60+ 条目时可忽略，但增长到数千条时会明显变慢
修复建议
PowerShell 中改用 Hashtable（将 $track.PSObject.Properties.Name 转为 HashSet），或迁移 JS 时自然解决

4 PS1 vs JS 迁移评估

维度 PS1（当前） JS (Node.js)
JSON 处理 痛点：PSObject 陷阱，序列化踩坑 原生，零摩擦
性能（大 track） O(n²) 的 -contains O(1) 的 Map/Set
测试能力 困难（Pester 较重） 简单（vitest/jest）
git/curl 调用 原生顺畅 child_process 略啰嗦但完全可行
迁移成本 0 中等（约 2–3 天）
当前可用性 已在运行，84 对已扫描 需完全重写
错误处理 模式不够优雅 try/catch/async 更自然
可维护性 4 个 .psm1 模块，理解成本中等 模块化更自然（import/export）

迁移建议

✅ 短期
继续使用 PS1，修复上述两个 bug
🕐 中期
如需增加更多逻辑（增量 fetch、changeset 深度解析、评分自动化），考虑迁移到 JS
❌ 不建议立即迁移
当前脚本可用，84 对已扫描，迁移会中断工作流
