# 增强版 Grill with Docs

运行 `/grilling`，并在整个过程中使用 `/domain-modeling`。

本技能是与 `/grill-with-docs` 长期并存的严格增强版。完整保留原版的一问一答、每题给出推荐答案、事实由代理调查、决策由用户确认、即时维护领域词汇、稀少 ADR 和共享理解确认。只增强访谈控制协议，不改变原版文档产物或后续构建职责。

当 `/grilling` 的“全面追问”与本技能的消歧门槛冲突时，以本技能为准：只问会改变设计的问题。不要调用或读取其他访谈技能，也不要继承它们的固定轮次、深度档位、状态机、额外产物或执行交接契约。

## 提问前取证

第一轮问题前，只读取与当前设计直接相关的：

- 适用于目标路径的仓库规则和 README；
- `CONTEXT.md`、`CONTEXT-MAP.md`、相关 ADR 和设计文档；
- 相关代码、测试与当前行为。

将信息区分为：

1. **已确认事实**：有当前、直接证据，作为问题依据，不再询问用户。
2. **待确认解释**：证据需要推断，或代码、文档、术语相互冲突；先继续调查。
3. **用户决策**：目标、范围、非目标、业务规则、公共契约和取舍，必须由用户决定。

代码与文档是证据，不是不可挑战的权威。发生冲突时，优先用可复现运行行为或测试、目标边界附近的代码与契约、当前有效文档、历史约束依次确定当前事实。不要静默选择一边，也不要把可调查事实变成用户问题。当前事实即使已经确认，“未来应以哪种行为为准”仍可能是用户决策。

只有不同外部调查结果会改变设计时，才从官方、标准或上游一手来源做最小必要核实。

## 实质设计歧义

只有不同答案会改变以下至少一项时，才算**实质设计歧义**：

- 意图或期望结果；
- 范围或非目标；
- 领域含义或公共契约；
- 必须保持的约束或兼容性；
- 可观察、可判定的成功证据；
- 用户与代理的决策边界。

成熟最佳实践、命名、代码组织、可调查事实，以及容易撤销且不改变外部行为的实现细节，都不是设计歧义，由代理自行决定。只有它们会改变公共契约、兼容性、成本边界或用户可见结果时，才升级为用户决策。

默认决策边界是：目标、范围、非目标、业务规则、用户可见行为、兼容性取舍和难以逆转的选择由用户确认；可逆且不改变外部行为的实现细节由代理决定。没有反向证据时直接采用，不要逐项要求确认。

## 设计歧义指数

在取证后和每次用户回答后，按以下维度更新清晰度：

| 维度 | 权重 |
| --- | ---: |
| 期望结果 | 20% |
| 范围与非目标 | 15% |
| 约束与兼容性 | 15% |
| 意图与根本问题 | 15% |
| 可观察成功证据 | 15% |
| 领域含义与公共契约 | 10% |
| 用户与代理决策边界 | 10% |

每个维度使用证据锚定的五档清晰度：

- `0`：没有答案，或仍只是症状描述；
- `25`：已有方向，但关键主体、边界或结果不明确；
- `50`：主路径明确，仍有会改变设计的重要分支；
- `75`：设计基本明确，仅剩一个局部但实质性的边界；
- `100`：有证据支撑，清晰、可判定，已无会改变设计的未知项。

只有证据确实介于两档时才使用中间值，并说明仍缺什么。若某项结论依赖尚未核实的代码、测试、文档或外部事实，该维度最高为 `75`；先调查，不能通过询问用户来伪造事实置信度。

计算：

```text
加权清晰度 = Σ(维度清晰度 × 维度权重)
设计歧义指数 = 100 - 加权清晰度
```

分数是可解释的启发式仪表，不是客观测量。它控制问题粗细，但不能覆盖下方的关键歧义和硬门槛。

## 选择下一问题

先按歧义区间决定问题粒度：

- `60–100%`：询问意图、问题主体、期望结果等粗粒度上游问题；
- `30–59%`：询问范围、非目标、主要约束和关键取舍；
- `15–29%`：只问具体契约、兼容性边界、反例和成功证据；
- `0–14%`：停止普通提问，进入收口审计。

在允许的粒度内，按“清晰度缺口 × 设计影响 × 上游依赖程度”选择影响最大的一个未决项。不同答案不会改变共同理解的问题直接跳过。不要为了覆盖维度而机械轮换，也不要用固定轮数决定是否继续。

在对话内维护不落盘的：

- **未决歧义清单**：标记为已解决、已排除、已延期或仍未决；
- **当前理解摘要**：只保留最新有效的目标、范围、非目标、约束、成功证据、决策边界和未决歧义。

新答案推翻旧结论时立即替换旧结论，不让冲突版本并存。

## 提问方式

每轮只问一个问题并等待回答。使用：

```text
当前设计歧义：42%｜本轮聚焦：兼容性边界｜原因：不同答案会改变公开契约

依据：已确认事实，以及仍需用户裁决的解释
问题：一个会实质改变设计的决策
建议：推荐答案，以及最关键的理由或代价
```

每轮只展示一行指数摘要。只有指数跨越区间、用户质疑评分，或准备收口时，才展示完整维度评分、证据依据和剩余缺口。

回答仍不可判定、与证据冲突、依赖未验证假设、隐藏设计取舍、存在设计改变型反例，或仍停留在症状时，选择一种方式继续施压：

- 要求具体例子、反例或可观察证据；
- 揭示隐藏假设或依赖；
- 要求明确本轮必要、延期或排除；
- 用代码、文档或既有术语指出矛盾；
- 构造一个边界场景并询问期望结果；
- 从症状继续追问根本问题。

清晰、一致、可判定且没有实质边界风险的回答直接视为已解决。不要为了完成形式化压力测试而回访。

## 保持原版文档契约

完全遵循 `/domain-modeling`：

- 术语一旦真正解析，就即时更新正确上下文的 `CONTEXT.md`；
- `CONTEXT.md` 只作为领域词汇表，不写范围、验收标准、方案或访谈记录；
- ADR 只使用 `/domain-modeling` 的准入门槛和格式；
- 不创建 Plus 专属文档或状态文件。

## 收口审计

任何一个尚未裁决、足以改变设计的关键歧义，都可以覆盖总分并阻止收口。

进入 `0–14%` 后，强制检查三个硬门槛：

1. **非目标明确**：本轮在哪里停止已经可判定；
2. **决策边界明确**：用户决定与代理默认决定没有实质冲突；
3. **关键假设已审计**：不存在未经验证且一旦错误就会改变设计的假设。

硬门槛可以由用户答案、仓库证据或默认规则自动满足，但必须有可说明的依据。强制执行一次内部压力审计，尝试构造最可能推翻当前方案的反例：

- 若反例降低某项评分或触发硬门槛，只询问影响最大的一个问题；
- 若反例已被证据、默认规则或现有答案排除，不产生形式化挑战问题。

审计通过后，输出固定的对话内共享理解摘要：

- 根本问题与意图；
- 期望的可观察结果；
- 本轮范围与非目标；
- 已确定的领域含义或公共契约；
- 必须保持的约束与兼容性；
- 可判定的成功证据；
- 用户决定与代理默认决定的边界；
- 已排除、已延期及其不阻塞本轮的理由；
- 关键证据与仍被接受的假设。

然后只问用户是否确认已经达成共享理解。

- 用户未确认：更新评分，选择影响最大的分歧继续一问一答；
- 用户确认：停止访谈，不生成额外产物，然后按下方原版流程给出后续建议；
- 用户暂停、停止或关键事实无法确认：总结已确认、未决、阻塞，明确尚未达成共享理解。

## 按原版流程选择后续

只有用户确认共享理解后才选择后续。设计歧义指数只判断访谈是否完成，不参与任务规模路由。

默认建议直接进入 `/implement`。只有满足以下至少一项时，才建议先进入 `/to-spec`：

- 工作明显需要多个会话才能完成；
- 存在多个可独立实施、验证或并行推进的功能切片；
- 关键决策、验收标准或上下文需要持久化，供新的上下文窗口继续使用；
- 当前上下文接近推理质量边界，继续实施容易丢失访谈结论；
- 用户明确要求持久 spec、拆票或跨会话交接。

后续提醒必须明确给出一个建议和最关键理由：

```text
后续建议：`/implement`
理由：这是一个可在当前上下文内完成并验证的单一工作单元，不需要持久 spec 或拆票。
```

或：

```text
后续建议：`/to-spec`
理由：工作跨多个会话或包含多个独立切片，需要先固化访谈结论；spec 完成后再用 `/to-tickets` 拆分，并逐票 `/implement`。
```

不要把 `/to-spec` 当作所有实施工作的必经门。路由证据不明确时，采用原版的轻量默认：建议 `/implement`，同时指出若工作扩展成多会话或多切片，应切换到 `/to-spec`。

本技能只提供后续提醒，不自动调用 `/implement` 或 `/to-spec`。不要引入固定轮数、深度档位、持久状态、Plus 专属访谈产物或执行交接契约。
