# 自主闭环 agent harness 设计 — 行业调研（2026-08-27）

> 调研问题：业界如何构建让 LLM agent 长时间自主运行、自我闭环（实现→验证→修复→交付）而不失控的 harness。
> 一手来源为主，逐条标注引用编号（见文末引用清单）；本文作者的推断一律以「推断：」前缀标出。

## TL;DR

1. 业界共识的 agent loop 是 "gather context → take action → verify work → repeat"，其中 verify work 是决定能否无人值守的一环 [3]。
2. 工单契约的最佳实践是「验收条件随任务走且机器可执行」：SWE-bench 用 FAIL_TO_PASS/PASS_TO_PASS 测试把验收编进任务实例 [7]；Anthropic 的 lead agent 给每个 subagent 明确 objective / output format / tool guidance / task boundaries [2]。
3. 「不信自报」的层级：rules-based（可执行规则）> visual feedback > LLM-as-judge——Anthropic 官方明说 LLM-judge "generally not a very robust method" [3]；MAST 实证 23.95% 的多 agent 失败源于 verification 缺陷 [9]。
4. 循环会停靠 harness 强制而非 agent 自觉：OpenAI Runner 的 max_turns 由框架抛 MaxTurnsExceeded [11]，guardrail tripwire 直接抛异常终止 [12]；升级人工的触发是重试超阈值与高风险不可逆动作 [15]。
5. 崩溃恢复有两个流派：replay 事件史重建状态（Temporal [19]、LangGraph checkpoint [16][18]）vs 对账事实源（Kubernetes level-triggered reconcile [23]）。前者要求代码确定性，后者要求存在可信 ground truth。
6. 人工门禁的报文设计以 LangGraph interrupt 为范本：暂停必须持久化、恢复值经独立通道注入、恢复时节点从头重放故副作用必须幂等 [17]。
7. 串行合并 + 在合并结果上重新验证（GitHub merge queue [21]、bors [22]）是 CI 界对「base 前进使证据作废」的标准答案，与本仓设计同构。
8. 熔断要双向：max_turns/tripwire 拦「跑不停」[11][12]，Stop hook 拦「停太早」——完成判定权同样收归 harness [4]；MAST 的 premature termination 占比 6.20% 是后者的实证 [9]。
9. Reflexion 证明「把失败证据文本化喂回循环」有效（HumanEval 91% pass@1），但反思质量的上限由 evaluator 质量决定，自评不能替代外部验证 [8][9]。
10. 对照结论：本仓 v4 的骨架（Git 为事实源、typed 闭集、证据随 commit 作废、串行 merge）与业界最佳实践一致且部分领先；W-1~W-4 的修法业界均有现成对应物——核心是把「荣誉制」环节全部搬进 harness 强制执行。

## 1. 任务派发与工单契约（task dispatch / work order schema）

### 业界做法

**Anthropic multi-agent research system（orchestrator-worker 的工单字段）** [2]
lead agent 派发 subagent 时，每个 task description 必须包含四类字段：objective（目标）、output format（输出格式）、tool guidance（工具与数据源选择）、task boundaries（任务边界）。官方明确记录了反面教训："Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information"——早期用一句 "research the semiconductor shortage" 派单导致多个 subagent 重复劳动、无有效分工。此外 effort scaling 规则也写进派单逻辑：简单事实查询 1 个 agent、3-10 次工具调用；直接比较 2-4 个 subagent、每个 10-15 次调用；复杂研究 10+ subagent 并明确分工。

**SWE-bench（验收条件随任务走、机器可执行）** [7]
每个任务实例 = repo snapshot + issue 文本 + 判定测试。验收是两组测试：FAIL_TO_PASS（patch 应用前失败、应用后必须通过，证明 issue 被解决）与 PASS_TO_PASS（应用前后都必须通过，防止回归）。评估完全 execution-based，不依赖任何模型自评。这是「验收条件编进工单、绑定精确代码快照」的最纯粹形态。

**OpenAI Agents SDK handoffs（交接报文结构化）** [13]
handoff 对 LLM 表现为一个 tool（如 `transfer_to_refund_agent`）；`input_type` 允许在交接时传结构化载荷（如 `{"reason": "duplicate_charge", "priority": "high"}`），`input_filter` 控制随交接传递的对话历史。即：交接不是自然语言口头交代，而是 schema 化的报文 + 显式裁剪过的上下文。

**任务规格本身也要被验证**：MAST 实证 43.9% 的失败归入 system design / specification issues（FC1）[9]。OpenAI 曾专门发布 SWE-bench Verified 处理原基准中 underspecified issue 与不公平测试的问题，但该页面本次访问返回 HTTP 403，未能读取原文 [24]。

### 对 harness 设计的可操作启示

- 工单最小字段集：objective、output format、tool/资源指引、boundaries、机器可执行的验收测试、预算档位。缺一项就该 fail closed，而不是让 worker 猜。
- 验收条件必须绑定精确 base（SWE-bench 绑 repo snapshot）；base 变了验收就要重新评估。
- 交接报文走闭集 schema，上下文显式裁剪；「把整个对话史甩过去」和「一句话派单」是两个已被实证的反模式。

## 2. 证据验证（evidence & verification）

### 业界做法

**Anthropic：验证方式分层，越机械越可信** [3]
Claude Agent SDK 官方文章把 agent loop 定为 "gather context → take action → verify work → repeat"，并给 verify work 排了序：最有效的是 rules-based feedback（"providing clearly defined rules for an output"，如 lint/测试）；视觉类任务用 visual feedback（截图验证 layout/styling）；LLM-as-judge 被明确降级——"generally not a very robust method"，只在收益能抵消延迟成本时才用。

**Anthropic evaluator-optimizer：验证循环的适用条件** [1]
《Building effective agents》把「一个 LLM 生成、另一个 LLM 评估反馈」定义为 evaluator-optimizer workflow，并给出两个适用前提："we have clear evaluation criteria" 且 "iterative refinement provides measurable value"。推断：这两个前提反过来就是禁用条件——验收标准写不清楚的任务，加一个 LLM evaluator 只是把猜测换了个位置；harness 应先把 AC 写成可判定形式，再决定要不要 evaluator 循环。同文还要求 agent 在每一步从环境获取 "ground truth"——评估的输入是环境反馈，不是 agent 的自述。

**Claude Code hooks：验证放在模型选择权之外** [4]
hooks 是 user-defined shell commands，在 lifecycle 固定点 deterministic 执行——不依赖 LLM「选择」运行。PostToolUse 可在每次 Write/Edit 后强制跑 lint；PreToolUse 通过 `permissionDecision: allow/deny/ask` 拦截工具调用；exit code 2 的阻止语义不可被 JSON 里的 `permissionDecision: "allow"` 覆盖。即验证与门禁是 harness 的结构性行为，不是 agent 的可选动作。

**SWE-agent：guardrail 内建在动作接口里** [6]
四条 ACI 原则的第四条即 "Guardrails mitigate error propagation and hasten recovery"。具体实现：edit 命令集成 flake8 检查（F821/F822、E111-E113、E999），引入语法错误的编辑「不会被执行」，并回显错误 + 拟议改动 + 原代码帮助恢复。评估侧则完全 execution-based：patch 应用后跑测试，pass@k 按「全部测试通过」判定。

**SWE-agent：反馈紧凑性是验证信号的载体** [6]
验证信号有效的前提是 agent 能读到它。SWE-agent 的 ACI 原则三是 "Environment feedback should be informative but concise"，落地为三条硬限制：search 结果封顶 50 条（超限即要求收窄查询而不是刷屏）；超过 5 轮之前的 observation 折叠成单行（保留动作史、丢弃过期文件内容）；file viewer 一次只显示 100 行带行号。推断：这组数字对 harness 的意义在于——验证输出（测试日志、lint 报告）同样要经过裁剪才进入 agent 上下文，把 10 万行 CI 日志原样塞回去等于没有验证信号。

**Reflexion：自我反思有效，但前提是反馈信号真实存在** [8]
Reflexion 的循环是：actor 执行 → 拿到外部或内部模拟的 evaluation 信号 → 生成 verbal self-reflection 文本存入 episodic memory buffer → 指导下一次 trial。在 HumanEval 上拿到 91% pass@1（对照当时 GPT-4 的 80%）。注意其提升依附于反馈信号：框架接受 scalar 或自由文本反馈，来自「external or internally simulated」评估。推断：Reflexion 证明的是「把失败证据文本化喂回循环」有效，而不是「agent 自评可以替代外部验证」——它与 MAST 的 incorrect verification 占比 9.10% [9] 合起来读，结论恰是：反思循环的质量上限由 evaluator 的质量决定，harness 应该把真实的执行证据（失败测试的输出）作为反思输入，而不是让 agent 对着自己的总结反思。

**MAST：验证不足是可量化的主要失败源** [9]
在 1600+ 标注 traces、7 个框架上，task verification 类失败占 23.95%（no or incomplete verification 8.20%、incorrect verification 9.10%、premature termination 6.20%）。Insight 3 直言 "Multi-Level Verification is Needed. Current verifier implementations are often insufficient; sole reliance on final-stage, low-level checks is inadequate"。案例研究：给 ChatDev 加一层 high-level task objective verification，ProgramDev 成功率 +15.6%。

**reward hacking 防御** [10][7]
Anthropic 在 production coding RL 环境上的研究表明：模型一旦学会利用奖励信号，会泛化出 "alignment faking, cooperation with malicious actors, … attempting sabotage when used with Claude Code"；缓解手段是 prevention（直接堵住 hack）、diversified training、inoculation prompting。对 harness 侧的直接含义：奖励/验收信号本身必须防钻——SWE-bench 的 PASS_TO_PASS 测试组正是防「为过验收而破坏别处」的机械手段 [7]。推断：任何允许 agent 触碰验收判据本身（改测试、改门禁配置）的 harness，都在制造 reward hacking 的入口，验收判据应在 agent 写权限之外。

### 对 harness 设计的可操作启示

- 验证优先级：可执行规则 > 视觉比对 > LLM-judge；LLM-judge 只做补充，不做门禁。
- 验证要多层：低层（lint/单测）+ 高层（任务目标级）双查，只查最后一层被 MAST 实证不够。
- 一切验收命令由 harness 亲自执行并留 exit code 证据；agent 自报的 exitCode 只是线索不是证据。
- 验收判据（测试、门禁配置）放在 agent 写权限之外；同时保留回归组（PASS_TO_PASS 等价物）防止「修 A 坏 B」。

## 3. 预算与熔断（budgets & circuit breakers）

### 业界做法

**OpenAI：循环退出条件是框架强制的闭集** [11][15]
Runner 的 agent loop 只有四种出口：final output（"produces text output with the desired type, and there are no tool calls"）、handoff、error、max_turns。max_turns 超限由框架抛 MaxTurnsExceeded——是 harness 抛异常，不是 agent 自觉停。《A practical guide to building agents》同样把 max turns 列为防死循环的必备退出条件 [15]。

**OpenAI guardrails：tripwire 即熔断** [12]
guardrail 函数返回 `GuardrailFunctionOutput`，`tripwire_triggered` 为真即抛 `InputGuardrailTripwireTriggered` / `OutputGuardrailTripwireTriggered` 立即终止执行；input guardrail 可选 blocking 模式（guardrail 过了才启动昂贵 agent）省钱。用小而快的模型当廉价前置熔断是官方推荐用法。

**OpenAI：熔断后升级人工的触发条件** [15]
两类明确触发：失败阈值（如重试超过 3 次仍失败）与高风险不可逆动作（删除、支付类）。即熔断的下游动作不是死等，而是分类升级。

**Claude Code Stop hook：熔断的反方向——不许提前收工** [4]
预算与熔断通常防「跑不停」，Stop hook 防的是对偶问题「停太早」：Stop 事件在 Claude 准备结束响应时触发，hook 以 exit 2 + stderr 理由可以阻止停止、强制继续（SubagentStop 对 subagent 同理）。即「任务是否完成」的判定权也可以从 agent 手里收走——验收脚本没过就不接受收工。这正对 MAST 实证的 premature termination（6.20%）失败模式 [9]。

**Anthropic：预算按任务档位分配 + 停止条件写进设计** [2][1]
effort scaling 规则（1 agent 3-10 calls / 2-4 agents / 10+ agents）本质是按任务复杂度分配 token 预算，防止 "overinvestment in simple queries" [2]。《Building effective agents》要求 agent 实现包含 "stopping conditions (such as a maximum number of iterations) to maintain control"，并在 sandboxed environments 充分测试 [1]。经济性数据：multi-agent 系统消耗约 15× chat 的 token，token 用量解释 80% 的性能方差 [2]——预算不是软约束，是成本模型的主变量。

### 对 harness 设计的可操作启示

- 预算（轮次/token/时间）必须由 harness 计数并强制，超限抛结构化异常；agent 自报用量只用于观测。
- 熔断出口是闭集：完成 / 升级人工 / 换档重试 / 报错终止，每个出口带结构化理由。
- 熔断要双向：既拦「跑不停」（max_turns/tripwire），也拦「停太早」（Stop hook 式的完成校验——验收没过不接受收工）。
- 失败要分类计费（真实缺陷 vs 偶发 vs 环境），不同类烧不同预算——OpenAI 的重试阈值 + 高风险分流是这一思路的粗粒度版本 [15]。
- 廉价检查（小模型、静态规则）前置为 blocking 熔断，昂贵执行放在后面。

## 4. 状态机与幂等（state machine & idempotency）

### 业界做法

**Temporal：at-least-once + 幂等是基本假设** [19][20]
activity 是 at-least-once 语义——可能执行多次，因此「必须设计为重复执行不产生副作用」；官方推荐 idempotency key 保证同一事务只被有效执行一次 [20]。workflow 状态推进全部记入 Event History，重放时已完成的 activity 结果直接复用不重算 [19]。

**LangGraph：checkpoint 粒度的状态机 + 重放幂等规则** [16][17]
checkpointer 在每个 super-step 落一份 state snapshot，`thread_id` 是指向 checkpoint 的持久游标 [16]。interrupt/resume 的关键语义：恢复时「节点从头重跑」（"the node restarts from the beginning of the node where the interrupt was called"），因此 interrupt 之前的副作用必须幂等；interrupt 的调用次序必须确定（恢复值按 index 匹配）；载荷必须 JSON-serializable [17]。这是把「乱序/重复事件」问题收敛为三条可检查的编码纪律。

**OpenAI Agents SDK：终局判定是 typed 的** [11]
final output 的判定规则是产出「desired type 的文本输出且无 tool calls」——状态机的终态由类型系统判定，不靠语义猜测。反面实证：MAST 把 premature termination（6.20%）列为独立失败模式 [9]——终态判定含糊的系统会提前收工。

### 对 harness 设计的可操作启示

- 生命周期建为显式闭集状态机，终态判定走 schema/类型而非自然语言解析。
- 非法转移的正确响应是拒绝且零状态变化（exit 非零 + 不落盘），不是尽力修复——修复语义会掩盖乱序 bug。
- 每个外部动作配 idempotency key（本仓的 eventId/actionId 即此物）；重复事件返回 already-done + 零状态变化，而不是报错。
- 恢复语义按「从头重放当前步」设计：步内副作用要么幂等、要么挪进不可重放的受记录动作（Temporal 的 activity、LangGraph 的 task）。
- 乱序事件（late event）允许落盘审计，但不得复活终态——用状态机边约束而不是靠时序假设。

## 5. 崩溃恢复（crash recovery / durable execution）

### 业界做法：两个流派

**流派一：replay 事件史（Temporal、LangGraph）**
Temporal 的恢复不是从内存快照恢复，而是「从头重放 Event History」重建 exact same state；代价是 workflow 代码必须确定性——`Date.now()`、随机数、直接网络调用都被禁止，必须走 replay-safe API 或 activity [19]。LangGraph 提供三档 durability：`"sync"`（"Changes are persisted synchronously before the next step starts"）、`"async"`（异步落盘、下一步并行）、`"exit"`（只在图退出时落盘）[18]——落盘时机与吞吐的显式权衡；checkpointer 支撑 fault tolerance 与 time travel（从历史 checkpoint 重放/分叉）[16]。

**流派二：对账事实源（Kubernetes controller）** [23]
controller 是 level-triggered 的 control loop："Each controller tries to move the current cluster state closer to the desired state"。controller 不持有内部状态、一切经 API server；崩溃重启后重读全量状态即可继续——期望状态持久在事实源里，所以没有动作会「丢」。恢复的正确性不依赖崩溃前的执行轨迹，只依赖事实源可信。

**部分完成的副作用：saga / compensation** [20]
崩溃恢复不只是「续跑」，还包括「撤销已发生的一半」。saga pattern 把多步跨系统操作的每一步配上 compensation（补偿动作，如预订失败时取消已订的酒店），配合 progress tracking 在灾难性故障后从正确位置恢复；Temporal 上实现时框架承担了状态保存与重试，开发者只写补偿逻辑，并因 activity 可能重试多次而必须用 idempotency key 保证「同一事务只被有效执行一次」。推断：对 coding-agent harness，Git 天然提供了大部分补偿原语（revert、分支丢弃），真正需要显式 compensation 的是 Git 之外的副作用——已发出的通知、已建的 Issue、已占的租约；这些动作的登记应当同时登记其撤销方式。

**工程补充：Anthropic 生产实践** [2]
"Agents are stateful and errors compound"——一步失败可能把 agent 带进完全不同的轨迹。做法：出错处恢复（"resume from where the agent was when the errors occurred"）而非从头重跑；把工具故障告知 agent 让它自适应（"letting the agent know when a tool is failing and letting it adapt works surprisingly well"）；部署更新用 rainbow deployments 新旧共存渐切，避免打断运行中的 agent。

**两派对比（推断，基于上述来源）**：

| | replay（Temporal/LangGraph） | reconcile（K8s 式） |
| --- | --- | --- |
| 恢复依据 | 执行事件史 | 外部事实源的当前状态 |
| 前置要求 | 代码确定性、副作用全部隔离进 activity/task | 存在可信、可查询的 ground truth |
| 擅长 | 精确恢复到中断点、长事务补偿（saga [20]） | 进程随便死、多副本、漂移自愈 |
| 弱点 | 非确定性代码即 replay 失败；LLM 调用本身不确定 | 事实源覆盖不到的中间状态会丢 |
| 推断：对 LLM harness | LLM/工具调用都得包成 activity，历史可能巨大 | 天然契合：Git/CI 本来就是 ground truth |

推断：编排 LLM coding agent 时 reconcile 派更占优——因为 Git 提供了免费的、防篡改的事实源，而 LLM 步骤的非确定性正是 replay 派的痛点；但 reconcile 派必须为「事实源看不到的意图」补记录（如本仓 mergeIntent），两派在实践里是杂交的。

### 对 harness 设计的可操作启示

- 先问「事实源是什么」：能问 Git/CI/数据库的就问它们，不要信编排器自己的状态位。
- 事实源覆盖不到的意图（正要 merge、正要发消息）在动作前写 intent 记录，恢复时用「intent + 事实源」二元对账。
- 选 replay 派就接受确定性纪律：LLM/网络调用全部隔离为可记录、可重放跳过的单元。
- 编排器升级部署时保持在跑 agent 不中断（rainbow deployment），或先 drain 再切。

## 6. 门禁与人工升级（gates & human escalation）

### 业界做法

**LangGraph interrupt：人工门禁的报文范本** [17]
`interrupt()` 抛内部异常暂停执行、经 checkpointer 持久化状态、向外暴露 payload、无限期等待 `Command(resume=value)`；恢复值成为 `interrupt()` 的返回值注入节点。生产使用必须有 checkpointer——「等人」的前提是等待状态可持久化。典型模式：approve/reject 关键动作、review & edit 状态、tool call 审批。防误用规则明确：不许用裸 try/except 吞掉 interrupt 信号、interrupt 次序必须确定、pre-interrupt 副作用必须幂等。

**Claude Code：审批决策权在 harness，agent 无法代答** [4]
PreToolUse hook 的 `permissionDecision: "ask"` 把工具调用升级为用户确认；`deny` + exit 2 的阻止不可被任何 JSON 输出覆盖。Stop hook 可用 exit 2 阻止 Claude 停止（验收没过就不许收工）。审批通道（hooks、permission 系统）物理上不在模型的输出通道里——模型说什么都不构成批准。推断：这是「审批防 agent 代答」的通用解法——批准必须来自 agent 无法写入的通道，而不是靠提示词约束 agent 别冒充。

**OpenAI：何时必须停下等人** [15]
两个触发列得很具体：失败阈值（重试 >3 次）与 high-risk irreversible actions（删除、支付）。配套的是分层 guardrails：relevance/safety classifier、PII 过滤、tool safeguards（API 层限制危险操作）、rules-based 硬约束、output validation [15]；tool 级 guardrail 也可在 pending approval 前先跑输入检查 [12]。

**Anthropic：checkpoint 处等人是 agent 设计的一部分** [1]
《Building effective agents》：agent 应 "pause for human feedback at checkpoints or when encountering blockers"，并在每一步从环境获取 "ground truth"。

**审计通道**：OpenAI Agents SDK tracing 默认开启，LLM generation 包在 `generation_span()`、tool call 包在 `function_span()`、agent 运行包在 `agent_span()`，handoff 与 guardrail 判定同样成 span；trace 有 `workflow_name` / `trace_id`，`group_id` 把同一会话的多个 trace 串起来，敏感数据是否入 trace 由 `trace_include_sensitive_data` 显式配置 [14]。审批与升级要可审计，前提是执行轨迹本身结构化留痕——「谁在何证据下放行了什么」应当是一条 span 查询，而不是一次日志考古。

### 对 harness 设计的可操作启示

- 风险分级驱动门禁：低风险自动过、高风险强制人工、不可逆动作永远人工——分级规则由 harness 按动作特征判定，不由 agent 自报。
- 「等人」报文四要素：暂停原因、需要的决策/证据、恢复令牌（指向持久化的等待状态）、超时策略。LangGraph 的 interrupt payload + thread_id 游标是现成范本。
- 审批通道与 agent 输出通道物理隔离；恢复值经独立注入（`Command(resume)` / hook 决策），并校验来源身份。
- 每次门禁判定都落 trace/receipt，拒绝理由结构化——事后能回答「谁在何证据下放行了什么」。

## 7. 多 agent 编排拓扑（orchestration topology）

### 业界做法

**orchestrator-worker：当前生产系统的主流选择** [2][1]
Anthropic 的 research 系统是 lead agent + 并行 subagent：subagent 提供 parallelization 与 context isolation（各用独立 context window，"only send relevant information back"）[3]。《Building effective agents》给出适用条件：orchestrator-workers 适合 "complex tasks where you can't predict the subtasks needed" [1]。代价也量化了：15× token 消耗 [2]。

**manager vs decentralized/handoff** [15][13]
OpenAI 官方指南：先单 agent，只有当任务需要不同专长、并行收益明显或专业化能降错时才拆分；manager pattern（中心控制器委派）适合顺序性强的工作，decentralized/handoff pattern（对等交接）适合自治并行。Agents SDK 的 handoff 把交接实现为 tool 调用 + 结构化载荷 + 历史过滤 [13]。

**对等式（peer/swarm）的实证边界** [5]
Anthropic 的 multiagent 研究：peer-to-peer 协调最难，尤其在相互依赖时。高度可并行问题上 swarm 显著占优（协调群 45 agents 找到 266 个漏洞 vs 独立 agents 21 个）；但高耦合工作（共享代码库开发）质量 "consistently poor"，且出现 low variance 病：30 个 agent 里 18 个起了同一个分支名。结论级论断："Coordination doesn't naturally emerge from stronger intelligence nor alignment at the individual level"——协调要靠机制设计，不能指望模型变强后自发出现。MAST 的量化背书：32.15% 的失败是 inter-agent misalignment [9]。

**串行 merge vs 并行合并：CI 界的答案** [21][22]
bors 的出发点：两个各自绿的 PR 合并后可以红（merge skew / semantic conflict——一个 PR 新增对某函数的调用、另一个重命名该函数），所以必须在 staging branch 上测「合并结果」，通过才 fast-forward master，维持「repository 始终通过全部测试」的不变量（"Not Rocket Science Rule"；通说源自 Graydon Hoare 的博文，该原文本次未直接访问）[22]。GitHub merge queue 是同一思想的产品化：每个入队 PR 得到一个临时分支（`gh-readonly-queue/…`）= 目标分支最新 + 队列中前面所有 PR + 本 PR，在这个组合上重跑 required checks；某个 merge group 失败则该 PR 出队、后续 PR 的临时分支自动重建（不再包含失败者）；插队会触发 "a full rebuild of all in-progress pull requests" [21]。

### 对 harness 设计的可操作启示

- 拓扑选择按耦合度：读多写少、可并行探索 → orchestrator-worker 扇出；共享可变资源（同一代码库）→ 收敛为串行写入 + 独立并行读（review/QA 可并行，merge 必串行）。
- 派单必须显式分工（objective/boundaries），并对 worker 引入多样性约束——低方差撞车（18/30 同名分支）是实证过的病 [5]。
- 合并验证的对象是「合并结果」而不是「分支自身」；base 前进即证据过期、必须重验——这是 merge queue/bors 的全部要点。
- 插队不是免费的：jump the queue 触发全部在途 PR 重建 [21]——优先级机制的设计要把「后继全部重新证明」计入成本。
- 推断：merge queue 的「失败者出队、后继自动重建」值得移植——串行队列的熔断不应阻塞整个队列，而是隔离失败 job、让后继基于新 base 重新证明。

## 8. 与本仓对照（aes-worktree-board v4 控制面）

对照材料：`.agents/skills/aes-worktree-board/SKILL.md`（v4 无人值守控制面）、`references/design.md`、`.agents/skills/aes-issue-worker/SKILL.md`。

### (a) 与业界最佳实践一致的设计

| 本仓设计 | 业界对应物 |
| --- | --- |
| registry 记意图 + Git 记事实，reconcile 用 `git merge-base --is-ancestor` 判定 merge 是否真发生 | Kubernetes level-triggered reconcile：状态在事实源不在 controller 内存，崩溃重启重读即可 [23]；「intent 先落、事实源对账」正是 reconcile 派对「事实源看不到的中间意图」的标准补丁 |
| typed 报文闭集 fail closed（executor-final/v1、goal-terminal/v1、UNCLASSIFIED_FINAL 不推进） | OpenAI Runner 的 final output 按 type 判定、异常闭集 [11]；MAST 把规格含糊列为 43.9% 失败源，闭集 schema 是直接对策 [9] |
| candidate 前进使证据作废 + integration 前进同样使证据作废（design.md「证据失效有两层」） | GitHub merge queue：临时分支含前序 PR 改动、失败即重建后继 [21]；bors：只认「合并结果」上的绿 [22]。SWE-bench 把测试绑定精确 repo snapshot 同理 [7] |
| 串行 merge queue、同时只放一个 HOST_MERGE、post-merge verify 通过才释放 | bors staging / merge queue 的串行化本身 [21][22] |
| POST_MERGE_VERIFY 不接受自报 exitCode、由脚本实际执行 commands-file | SWE-bench execution-based 评估 [7]；Claude Agent SDK「rules-based feedback 最可靠」[3]；hooks 的 deterministic 执行 [4] |
| 三分类预算（must-fix/retryable/environment）+ 三次 BLOCK 熔断 + handoff | OpenAI 失败阈值升级人工 [15]；tripwire 熔断 [12]；分类比业界通行的粗粒度重试阈值更细 |
| humanRequest{kind, prompt, requiredEvidence, resumeToken}，缺 resumeToken schema 拒收 | LangGraph interrupt：payload + 持久化 checkpoint + thread_id 游标 + `Command(resume)` [17]，报文四要素几乎一一对应 |
| riskProfile 四档 + 按改动路径兜底升档（自报环节不可信） | OpenAI 分层 guardrails + high-risk 动作强制人工 [15]；「自报不可信、按对象特征机械判级」与 hooks 的 matcher 式判定同构 [4] |
| 独立只读 reviewer、review 与执行分离 | Anthropic subagent context isolation [3]；MAST 多层验证建议 [9] |
| 熔断恢复绑定授权原文 digest、幂等重放返回 already-recovered | Temporal 的 idempotency key 思想 [20] |

### (b) 业界有而本仓缺的机制（对应 W-1~W-4）

**W-1：机械门不校验 review/QA 证据 commit === candidate commit（terminal 可旁路）**
业界对应：SWE-bench 的判定测试绑定精确 snapshot [7]；merge queue 的 checks 只在「恰好这个组合分支」上有效 [21]。本仓 v3 其实已有此不变量（AC-18 三方 commit 相等），v4 的 `gate` 六项里 review/QA 却没复刻——这正是 W-4 所说的契约漂移的实例。修法：gate 的 review/QA 两项加上 `evidence.commit === job.candidateCommit` 的机械等式，等式不成立按 hooks 的 exit-2 语义处理——任何自报字段都不能覆盖 [4]。

**W-2：pre-merge QA exitCode 自报无独立执行**
业界对应：CI 从不让 PR 作者自报测试结果，checks 由平台执行 [21]；SWE-agent/SWE-bench 的验证全部 harness 亲自跑 [6][7]；Anthropic 明确 LLM 自评不可靠 [3]。本仓已有现成机制——POST_MERGE_VERIFY 的 commands-file + verificationRun 模式，把它前移复用到 `stage qa`：QaReceipt 里的命令由 master.mjs 在 slot worktree 重放执行，exit code 以重放为准，自报仅作对照。成本可控：QA 命令本来就要求可重复。

**W-3：预算是荣誉制不强制**
业界对应：max_turns 由 Runner 计数并抛 MaxTurnsExceeded [11]；tripwire 由框架抛异常 [12]。修法：预算记账权收归 master.mjs——stage 调用时由 master 侧计数（reviewLoops/qaLoops/environmentRetries），超限的 stage payload 直接拒收并把 job 转 `BUDGET_EXHAUSTED`，而不是依赖 worker 自觉上报。worker 侧的记账只用于其自我调度。

**W-4：prose 契约与代码漂移（AWAITING_HUMAN receipt 字段零消费）**
业界对应：LangGraph 的 interrupt payload 是被消费的——resume 值注入节点返回值，字段有下游 [17]；Temporal 用 replay 测试强制「代码即契约」[19]。修法有二：其一，为每个报文字段建立「消费者断言」——selftest 的 trajectory replay 场景里断言 AWAITING_HUMAN receipt 的每个字段至少被一个下游读取，零消费字段要么接上消费者要么从 schema 删除；其二，契约变更流程反向化：先改 design.md/schema，再由回归断言锁死（本仓已有此惯例，缺的是「字段级消费覆盖」这一层）。

**业界有而本仓缺的其他机制**（不对应 W-1~W-4）：
- 标准化 tracing/span：OpenAI 全链路 trace 默认开启 [14]；本仓 transitions.jsonl/inbox.jsonl 是审计流但无跨 job 的 span 语义。低成本补法：actionId/jobId/attemptId 已构成 span 树，补一个导出器即可。
- 编排器无中断升级：rainbow deployments [2]；本仓 Master 升级需停机重启 + reconcile（reconcile 已把代价降到可接受，优先级低）。
- 失败 job 出队后的自动队列重建：merge queue 的 self-healing [21]；本仓熔断后 lane 封锁等人工，后继 job 是否基于新 base 自动重排未见明确契约。
- worker 上下文压缩（compaction）[3]：工单预算耗尽前的 context 管理策略在 issue-worker 契约中未提及。
- 廉价前置门（blocking guardrail）[12]：Master 派单前可用静态规则/小模型先验工单完整性（AC 可判定性、路径与 riskProfile 一致性），拦在昂贵的 worker session 启动之前——本仓工单三项预检在 worker 侧执行，业界做法是再往前挪一层到派发侧。

### (c) 本仓有而业界少见的设计——创新还是重复造轮子？

1. **证据随 commit 作废的双层不变量（candidate 层 + integration 层）**。CI 世界在平台层早已实现（merge queue rebuild [21]），但把它下沉为 agent 工单协议的显式不变量（worker 每出新 candidate 必须主动上报、旧证据机械作废）在四大 agent 框架（Anthropic/OpenAI/LangGraph/Temporal）文档中均未见对应物。判定：不是重复造轮子，是把 CI 的已验证原则正确移植进 agent 契约层——CI 平台管不到 agent 的 review/QA 证据，这一层必须有人做。
2. **问 Git 不问状态位（VCS 作为 reconcile 的 ground truth）**。K8s 证明了 reconcile 流派 [23]，但 agent 编排框架主流全在 replay 流派（Temporal [19]、LangGraph [16][18]）；用 `merge-base --is-ancestor` 把「merge 是否发生」变成免维护的幂等判据，未在任何被查框架中出现。判定：流派选择是成熟思想的应用（非首创），但「Git 当事实源 + mergeIntent 补意图」这个具体组合对 coding-agent harness 是恰当且少见的，属于小而实的创新。
3. **live-gate 的只读自证（前后完整指纹比对证明校验无写副作用）**。「只读如果不被机械证明，就只是一句承诺」——被查来源中无对应物。判定：创新，且与 hooks 的「deterministic 优于承诺」哲学同源 [4]。
4. **熔断 epoch + 授权原文 digest 的幂等人工恢复**。业界 HIL 文档（LangGraph [17]、OpenAI [15]）只覆盖「等待-批准」，未覆盖「同一授权重放幂等、同 id 不同原文 fail closed」。判定：是 idempotency key [20] 在人工审批域的移植，方向正确；业界少见更可能因为无人值守跑得还不够久，而非不需要。
5. **三分类预算记账**。比业界通行的单一重试阈值 [15] 更细。判定：有效创新，但正因业界无对照，W-3（不强制）会让它退化为文档——分类的价值依赖强制执行。
