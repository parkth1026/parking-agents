# aes-gate 设计·行业实践四路验证

- 关联：wayfinder #41（设计票）/ `.aes-workflow/grilling/2026-08-24-aes-gate`（workflow-interview 会话）
- 日期：2026-08-25
- 方法：4 个并行调研 subagent，各限一个论证面，要求一手来源（官方文档/论文/GitHub 实测星数与文件命中数）、可验证数字、找不到证据就明说。星数/命中数为 2026-08-25 实测。

## 合成判定：行业最佳实践还是一厢情愿？

| 设计支柱 | 判定 | 实锤 |
| --- | --- | --- |
| 统一注册（run.toml kind=gate + `.\run` wrapper + 显式 argv） | **行业实锤** | pre-commit（15.5k★、约 23 万仓库文件命中、id/args 字段同构）、cargo-make（command+args 数组最同构、内置 CI gate 流）、lefthook 单 YAML、npm scripts 事实注册表、GNU `make check` 历史正统、Gradle Wrapper 跨平台 wrapper 官方推荐姿势；「禁 shell 字符串」有 GitHub Actions 官方 script injection 文档背书（从严但非主流） |
| 审计评分体检（六维加权+总分+档位+缺口清单+JSON/HTML 分离+默认不自动修） | **行业实锤（保守稳妥侧）** | OpenSSF Scorecard 同构（官方 20 项检查、风险加权平均、100 万项目官方数字）；SonarQube Quality Gate 证明「条件集合+fail 阻断流水线」是官方设计用途；Allure/lcov/npm audit --json/Checkov/SARIF（OASIS 标准）= 数据呈现分离公认架构；npm audit/Sonar 的保守修复默认与我们一致 |
| 踩坑记门+棘轮（单条沉淀主路径） | **行业实锤的合理工具化** | 「bug found → tests created before addressed」是 XP 1999 官方规则；Google SWE Book「block a change if it is missing tests」；LLVM/GitLab 成文规范；缺陷聚类实证（Fenton & Ohlsson 2000、Ostrand 2005：前 20% 文件集中绝大多数故障、Just 2014：73% 变异耦合）；棘轮=Codecov `target:auto`/Google「delta from prior version」门禁/Sonar Clean as You Code/Betterer 工具生态。把「bug→测试」泛化为「坑→任意门禁条目」是合理外推（Google Tricorder 迁移期防倒退为同类先例） |
| agent 做门禁维护者（整套执行者假设） | **分层：机制成熟/生成有实证/闭环空白** | 机制层：Claude Code 官方 hooks（PreToolUse 拦截、Stop 强制验证）、Codex 沙箱+hooks；内容生成层：Meta TestGen-LLM（73% 被工程师合并）、Meta 变异测试（73% 接受）、Diffblue×Goldman（36%→72%）、Qodo（百万开发者）——共同前提=**生成物过确定性验证门，无一靠 agent 自评**；自主维护闭环层：**无任何公开先例**，最近的是 Greptile/CodeRabbit 的自然语言规则累积，OpenAI 官方自划界「AI 审查是 additional reviewer，硬执行在 tests/branch protections」 |
| selftest（植入违规必须检出） | **工业标准形态** | Semgrep `ruleid:`/`ok:` 规则测试、ESLint RuleTester valid/invalid 就是这个形态；理论根基=变异测试（Just 2014） |
| 风险对冲的必要性 | **证据充分** | AI 生成测试断言弱（FSE 2024 arXiv:2305.04207）、LLM judge 30% 轨迹误判成功（AgentRewardBench）、人类开发者自评也不可信（METR：实测 +19% 时间却自信省 20%）——agent 自称「门已加好」一律不可信，selftest+确定性验证+退出码显式读取是必要条件非可选项 |

**结论：不是一厢情愿。** 四个支柱中三个是行业成熟实践的直接同构或合理工具化，全部积木（注册表/评分/棘轮/验证闭环）各有头部工具或论文实锤；唯一无先例的是「agent 自主维护门禁的完整闭环」——那是先行者地带，但通往它的每一级台阶（官方钩子机制→已验证的生成管线→确定性验证门）都有人走通过。设计已内置的护栏（selftest、确认门、退出码显式读取、四不变量）恰好是行业成功案例的共同必要条件。

**第一性原理核对**：单一事实源（注册）、观测与投影分离（registry/board）、缺陷驱动回归（坑→门）、便宜检查先行、生成物必须过确定性验证——无一条违反经典工程原理；新颖性集中在「执行者是 agent」这一层，而这层的证据结构是「机制在、实证在、闭环没人走过」。

## 必须吸收的修订（落进契约，来源见各路报告）

1. **CI 服务端强制升格为硬前提**：git 官方文档坐实本地钩子一行 `--no-verify` 即可绕过（甚至有 AI agent 绕钩子的 issue 实证）；组装 G1（聚合 check）后若不接 required checks + branch protection，整套退化为纸面注册表——从「残余提示」升格为验收条件。
2. **权重与档位依据文档化**：OpenSSF Scorecard 被批评的软肋正是权重赋值不透明；六维权重 30/20/15/20/15/10 与三档阈值须在 references 写明依据。
3. **registry 留分数历史序列**：Scorecard 的价值一半来自百万项目基线；我们无生态基线，必须保留历史快照做自我对比，不报单次孤立分数。
4. **棘轮带泄压阀**：Codecov threshold、Google「低阈值+只看增量」、删码豁免——只许收紧但不能无逃生口；不把指标数值当目标（Goodhart）。
5. **先行者风险入残余节**：agent 自主维护闭环无公开先例，效果证据须自己积累（首条路径=本仓自举+变异式 selftest 记录）。

## 附：四路报告全文

### 第一路：统一门禁注册实践

（要点已并入上表；完整论据与全部一手来源链接见本节）

- 「单一 manifest 注册全部 gate」直接同构先例：pre-commit（官网原文「The pre-commit config file describes what repositories and hooks are installed」；`pre-commit run [hook-id]` 按 id 选择性执行；15.5k★；`.pre-commit-config.yaml` GitHub 文件命中约 230,400）；cargo-make（`[tasks.build] command="cargo" args=["build","--all-features"]` 官方一等公民写法，2.9k★，内置 `ci-static-code-analysis-tasks` gate 流）；lefthook（单 `lefthook.yml`，8.7k★）；npm scripts（官方生命周期+pre/post 约定的事实注册表）；just（35.5k★，`just --summary` 可程序解析，命中约 79,488）；GNU Make（`Makefile` 命中约 17.5 万亿级——体量之王，GNU Coding Standards 规定 `make check` 为必备目标）。
- 「显式 argv 数组」先例：cargo-make args 数组、pre-commit args 数组（entry 仍字符串，混合形态）、GitHub Actions 官方安全文档（`run:` 内插不可信输入=script injection，首选 action 参数传递）；npm scripts 为 shell 字符串反例（跨 shell 语义分裂催生 cross-env）。「全面禁 shell 字符串」比主流严，属有依据的从严。
- 跨平台 wrapper 先例：Gradle Wrapper（官方推荐执行方式，`gradlew`+`gradlew.bat` 双入口零预装）；Rails `bin/rails`、Django `manage.py` 同类。
- 失败模式（唯一官方级证据）：`git commit --no-verify` 官方定义即绕过 pre-commit/commit-msg hooks；GitHub required checks + 「Do not allow bypassing」是平台侧强制对策；pre-commit 官方 CI 集成（pre-commit.ci）的存在本身=官方生态承认「只在本地跑不够」。
- 总判定：单一 manifest（id/name/kind/argv）+ 统一 wrapper 是行业成熟模式的组合复刻（pre-commit+cargo-make+Gradle Wrapper 三重同构），非自造轮子；成立前提是全部 gate 由 CI 服务端强制执行。

### 第二路：审计评分工具实践

- OpenSSF Scorecard：官网原文「Each automated check returns a score out of 10 and a risk level. The risk level adds a weighting to the score, and this weighting is compiled into a single, aggregate score」；当前官方 checks.md 实列 20 项（Critical 2/High 8/Medium 6/Low 4）；采用规模=100 万项目（OpenSSF 2022 官方博客/新闻稿，Google 官方博客同数）；权重方法论无成文依据（软肋），换算 Critical=10/High=7.5/Medium=5/Low=2.5 散见文档；被批评点：启发式局限（官方自认「A low score is therefore not a definitive indication…」）、学术实证质疑（Zahan et al. ICSE 2023 SEIP）、Goodhart 化风险。
- SonarQube Quality Gate：官方定义「a set of conditions against which the code is measured」；默认 Sonar way 四条件（新问题=0/Hotspots Reviewed=100%/新代码覆盖率≥80%/重复率≤3%）作用于**新代码**；「fail the pipeline job」为官方 CI 集成设计（`sonar.qualitygate.wait=true` 非零码退出）。
- JSON+HTML 分离：Allure（结果 JSON 两阶段→静态 HTML）、lcov/genhtml（采集/汇总/渲染三段）、npm audit --json、Checkov 多格式（含 SARIF——OASIS 标准化的结果交换格式）。「页面不推导状态」比部分工具更严格。
- 默认不自动修：npm audit（fix 需显式参数且默认 SemVer 兼容，--force 才破例）、Sonar（AI CodeFix 仅建议式一键审查应用）。
- 接受条件三条：可解释（每项检查公开计分规则）、声明局限不冒充保证、可配置可演进+有基线对比。

### 第三路：缺陷回填与棘轮实践

- 「bug→先失败回归测试」谱系：XP 官方规则（1999，extremeprogramming.org 经 Wikipedia 引）「When a bug is found, tests are created before the bug is addressed」；Google SWE Book ch11 官方引文「As soon as an exploratory test discovers an issue, an automated test should be added」「it is perfectly reasonable to block a change if it is missing tests」；LLVM Testing Guide「when a bug is found in LLVM, a regression test containing just enough code to reproduce the problem should be written」；GitLab/Eigen 成文规范。诚实备注：Kent Beck《TDD: By Example》未检索到 bug 专项逐字原句（canonical 机制是 red/green）；Amazon 无明文。
- 缺陷聚类实证：Fenton & Ohlsson（IEEE TSE 2000，Pareto 分布）；Ostrand/Weyuker/Bell（IEEE TSE 2005，前 20% 文件集中绝大多数故障且可用历史变更预测——「出过坑的地方更会再出坑」直接文献支撑）；Just et al.（FSE 2014，73% 变异耦合）。
- 棘轮先例：Codecov 官方 `target: auto`（基线对比）+`threshold`（泄压阀）；Google 官方博客《Code Coverage Best Practices》「gate on delta from prior version」「Drops…should prevent the code from being checked in」；Sonar Clean as You Code（只考核 new code）；专门工具生态（Betterer/mejora/git-ratchet/eslint-formatter-ratchet 等）。反方边界：Fowler 与 Google 都反对绝对数值目标；官方推荐「低阈值+增量」。
- 双层实践：pre-commit 官方「can also be used as a tool for continuous integration」+ pre-commit.ci 官方论证「本地自愿+CI 强制」双层模型；Google SWE Book「The slower a test suite, the less frequently it will be run」。
- 总判定：「踩坑即记门+棘轮」是成熟实践的合理工具化组合；前提=增量生效、留泄压阀、不当 KPI。

### 第四路：agent 维护门禁实践

- 机制层：Claude Code 官方 31 个 hook 事件（PreToolUse「Can block it」、策略执行 `exit 2`、官方示例「verifies that tests pass before allowing Claude to stop」）；Codex 官方沙箱三档+审批策略+hooks（PreToolUse 可拦截 Bash/apply_patch/MCP，仓库级 `.codex/`，官方要求非托管钩子人工审核）；Cursor rules 官方自认提示层（无拦截）；Copilot 防火墙+agent-merge「Fix failing checks」。
- 内容生成层：Meta TestGen-LLM（ICSE-SEIP 2024：75% 可编译/57% 稳定通过/25% 提覆盖，**73% 推荐被工程师合并**，有效性恰来自「生成后过确定性检查门」）；Meta 变异测试实践（2025 官方博客，privacy 工程师 73% 接受）；Diffblue Cover×Goldman Sachs（一夜 3200+ 测试，36%→72%）；Qodo（官方称百万开发者）。
- 闭环层空白：未找到任何公开产品/论文=「agent 日常自主写检查脚本+注册 CI+刷看板」；最近=Greptile 自定义规则（greptile.json，自然语言+AI 审查）与 CodeRabbit Learnings（review 教训固化）；OpenAI 官方自划界「Codex Code Review is still an additional reviewer…hard enforcement 在 tests/branch protections/required approvals」。
- 风险证据：AI 测试断言弱（FSE 2024「No More Manual Tests?」：主要短板是断言正确性；GEM 定性发现 trivial/tautological 断言）；LLM-as-judge 偏差（MT-Bench >80% 一致但三偏差）；判官系统性宽松（AgentRewardBench：无 judge 精度超 70%，即 30% 轨迹被误判成功）；METR（16 名资深开发者实测 AI +19% 时间，事前预测 -24%）。
- selftest 先例：变异测试理论（Just 2014，73% 耦合+诚实给出 27% 局限）；Semgrep 规则测试（`ruleid:` 植入违规必须报出、`ok:` 不得误报，`semgrep --test`）；ESLint RuleTester（valid 不得报错/invalid 必须报出）。「组合应用于 agent 门禁」为新的。
- 总判定：机制层成熟、内容生成层双重验证、自主维护闭环无先例——「有机制无实践」到「早期实验」之间；selftest+确定性验证是必要条件而非可选项。
