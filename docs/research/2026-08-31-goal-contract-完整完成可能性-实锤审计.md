## 1. 结论（TLDR）

1. **"彻底满足完整完成"在理论上不可能，且这不是缺陷而是正确的目标设定。** Goal Contract 解决 verification（按声明的标准构建），永远解决不了 validation（标准本身是不是你要的）。本实例是活证据：三份契约全部通过 finalize（valid、A4/B1/C1、冒烟 4 红 0 崩、全部门禁过），次日被用户原话"完全复刻 mock 并把逻辑全跑通"整体打回 needs_reinterview——**所有机器闸门全绿，但契约本身不是用户要的完成定义。**
2. **这套体系的真正设计承诺不是"保证完整"，而是"把不完整变成显式、有界、可对账的交接面"**——残留风险对账、非 [A] 档点名、UNRUNNABLE 拦截、needs_reinterview 回退，四道防线在本实例中全部按设计工作。以这个标准衡量，它已达到业界罕见的水位。
3. **但本实例暴露的缺口全部在防线之外，且已全部实锤**：验收口径被默认档吞掉（根因是技能族内两条规则的冲突）、完成定义家族碎片化、过期契约自称 Ready、强约束无档位、跨仓交接无闸门、测量尺子未落进契约。逐条可修，修复清单见第 5 节。

## 3. 正面回答：能否彻底满足"goal 模式完整完成所有内容"

**理论层（不可能，且不该追求）**。goal 模式的完成判定是"验收条件全部 Verify 通过 + 强约束全部保持"。彻底成立需要两个前提：判据可机器判定（[A] 化），且判据集合穷尽"完成"的含义。前者受真实集成的本质限制（"用户在原生界面亲眼看到"是验收语义的一部分，无法自动化）；后者被本实例证伪——AC 从例子聚类，例子举完即收口，天然终点保证了不多问，也保证了对未例举维度（视觉整体性）不设防。

**工程层（现状是把不可能性管理得最好的形态之一）**。对比常规实践：多数团队的完成定义要么没落盘，要么落盘无结构校验，要么有校验无交接闸门。这套体系四道防线闭环；本实例的打回不是防线失效——needs_reinterview 机制存在、被正确触发、无静默交付、留痕完整。**防线生效了；缺口在防线之外。**

**实例层**。缺口清单见第 4-5 节，全部实锤。

## 4. 六类信息偏差源（审计定稿版）

### ① 口径偏差——默认档吞掉验收口径，根因是技能族规则内冲突

"结构 vs 像素"是验收的尺子。aes-goal-contract 自己规定"含数字门槛的（门槛值、用什么尺子量、尺子锁不锁）必须进提问区"（SKILL.md:71-73）、"判到多严（整体一致、关键字段一致、逐字节一致）……口径变了 Verify 跟着变，一起给"（SKILL.md:110-112）；但 aes-prototype 规定"Mock 定的是结构、信息与关键交互方向，**不是像素规范**；用户明确要求像素级还原时把该要求写进契约的强约束，否则执行 Agent 只需结构对照"（SKILL.md:96-97）。**两条规则并存：一边说尺子类必须问，一边说视觉口径默认结构级。** 用户没来得及明确要求之前，默认已经替他答了。

> 审计修正：这不是单次执行失误，是技能族的成文设计冲突。修法要落在规则层（冲突仲裁），不只落在触发器层。

偏差机理：技能内置哲学在无用户输入的维度上先验地收窄解空间。

### ② 采样偏差——例子聚类对整体性属性欠采样

行为行全覆盖证明聚类法在可枚举交互上的效力；但整页布局、视觉还原度这类 gestalt 属性不是任何一个例子行的侧面，聚类永远聚不出它们。修订后的 goal_oneline 补充的正是这一维——它来自 mock.html 实物，不来自任何变化行。

### ③ 确认偏差——整文确认≈扫描确认

落盘前"用户确认共同理解"确实执行了，用户也确认过含"结构非像素"的契约。但一页契约十几处决定一次点头，各处确认强度不均——口径类决定（藏在"不做什么"里）拿到的确认远低于其事后权重。体系无机制区分"扫过的确认"与"逐项的确认"。

### ④ 判定偏差——四个子项（审计后影响面扩大一倍）

- **非 [A] 自陈**：体系自知且已声明；本实例最高风险项恰好全在 [C]，结构上无解，只能压缩 [C] 面积。
- **执行者兼裁判**：[A] 命令指向尚不存在的测试文件（delegation.test.ts 等），实现者自己写断言自己跑。D-01 fixture 是唯一不由执行者发明的判据，但六条 AC 只配了一条 [B]。
- **首档遮蔽（影响面 ×2，双处同源）**：`extractVerifyLines` 正则只取 Verify 行行首第一个档位（session.mjs:519），cmdVerify 只跑行内第一个反引号命令（:521）。**AC-001 与 AC-004 双双中招**：前者 `[C]…；[A] test:workflow-ui`、后者 `[B]…；[A] records.test.ts`，两条内嵌 [A] 命令均未跑过冒烟、UNRUNNABLE 闸门对它们失效。且校验器 validate-goal-contract.mjs:183 的档位正则**同源**（也只认首档），"[A] 必须有反引号"检查（:196-198）只对首档为 [A] 的行生效——内嵌 [A] 是验证器与冒烟**双处一致的系统盲区**，无任何补救机制。
- **强约束无档位**：M1a 强约束里的 `vp run -r test` 与 desktop 冒烟不在任何 Verify 行内，finalize 冒烟只提取 `- Verify: [X]` 行，强约束命令永远不会被跑；/goal 审计里同样只有自陈。三红线中"Host 无 story 词汇"配了 grep 断言进 AC，同类约束可反驳性相差一个量级。

### ⑤ 环境偏差——跨仓双树与环境前提未检查

契约与冒烟跑在记录仓 aes-agent-manual（verify.txt cwd），Target 指向产品仓 aes-agent@a57b93fe（manifest.json:8）。两仓目录树同构（apps/packages/extensions 全同），`cd apps/server` 在错误仓也能找到目录并以"红"收场，闸门无从发现跑错仓。交接闸门只检查契约在 `repoRoot()`（=process.cwd() 向上找 .git，即记录仓）之下，且仅 WARNING；**manifest.target 在 finalize 中没有被任何闸门消费**（全文仅 :98 初始化 null、:474 写入两处）。同时"挡着的事：None（glab 本地配置即可）"隐含执行环境==访谈环境：契约全部反引号内容 21 处枚举，无任何环境前置检查命令。

### ⑥ 状态偏差——过期契约自称 Ready，且盘上三处状态互相矛盾

- manifest `stage_gates.3-contract.status = needs_reinterview`，但三份契约文件头仍写 `Status: Ready`。四个脚本 grep "Status" 零命中——连字符串都不存在，无任何对账检查。体系核心不变量"contract.md 单独拿走仍完整可交接"被击穿：单独拿走的那份是已作废却自称 Ready 的契约。
- **manifest 顶层 `"status": "ready"` 与 3-contract needs_reinterview 同时成立**（审计新发现）：`cmdStage` 的 needs_reinterview 分支（session.mjs:482-488）只重置 stage 与第一阶段 gate，不回撤顶层 status；只有 `cmdRebuild` 有降级逻辑（:659-663）。`cmdList` 会输出误导性 ready。
- **validation 块整体是拆分前存量**（审计新发现）：`validation.ran_at`（19:51:31Z）早于当前契约引用的 Q25-Q30 轮次（round 15，22:20Z）与契约 mtime——修订后的契约从未重跑 finalize，`ac_count=6` 恰好等于 M1a 单契约的 AC 数。
- 3-contract done 闸门的 mtime 对账只盯 contract.md 一个文件（session.mjs:341-352），m1b/m2 改动不触发"重跑 finalize"。

## 5. 改进路线图（P0-P2，按杠杆排序，工作量不参与排序）

### P0——直接堵本实例打回的根因

**P0-1 口径轴强制提问（修规则冲突，非仅修触发器）**
裁决技能族规则冲突：aes-prototype"视觉口径默认结构级" vs aes-goal-contract"尺子类必须进提问区"。落法：当对照物含 UI/视觉/报文面时，"判到多严"（结构/状态级/双轨/像素）禁止进默认区，必须带候选与百分比提问。把"按需附加"升级为"含视觉对照物即强制"。

**P0-2 契约失效对账（三件事一起修）**
a) finalize 增查：manifest 阶段状态非 ready/done 时，任何契约文件头 `Status: Ready` 且无 superseded 注记 → 直接拒。让"单独拿走仍完整可交接"包含"仍然现行"这个元事实。
b) `cmdStage` needs_reinterview 分支回撤顶层 `manifest.status` 并使 validation 块失效（或标记 stale），`list` 不得输出误导性 ready。
c) done 闸门的 mtime 对账覆盖 3-contract/ 下全部契约文件。

**P0-3 家族终态**
里程碑拆分是体系自己的设计（"聚出六条以上就拆"），但拆完必须有家族级完成定义落盘（M1a∧M1b∧M2∧整页对照∧全量回归的清单，机器可判）。当前 contractPath() 硬编码只指向单份 contract.md（session.mjs:65-67），前置关系只活在文件头文字里；dossier 的"家族"指 issue 家族（rounds/manifest 过程文件归档），不是契约家族终态。注：档案家族化已由 #146 了结，此处说的是**契约**的家族终态，另一件未闭环的事。

### P1——堵交接后的结构性漂移

**P1-4 强约束档位化**：强约束节允许标注 Verify 形态，[A] 级强约束（`vp run -r test`、grep 断言）纳入 finalize 冒烟范围。"普通 Session 零变化"从自陈变成可反驳。

**P1-5 尺子落盘时机**：视觉/性能类 AC 在 finalize 前尺子必须已写入契约（视口、容差、固定数据夹具、动态差异清单）。本实例 round 19 已取样候选值且用户已 confirm，但"契约阶段锁定"未发生——这类"已取样未锁定"状态应列为阻塞项而非可无限推迟项。Goodhart：尺子留在执行者手里时，改尺子永远比改工件容易。体系对优化型目标已有"测量脚本不可修改"规则，应推广到视觉判定。

**P1-6 跨仓交接闸门**：finalize 检查 manifest.target 与契约路径的仓库关系；不同仓时强制"读什么"用绝对路径、显式指明执行树、警告双树分叉风险。当前 repoRoot 闸门检查的是记录仓，target 字段零消费。

### P2——工具与纪律

**P2-7 混合 Verify 行全命令冒烟**：extractVerifyLines 解析行内全部 [X] 段、cmdVerify 跑全部反引号命令；validate-goal-contract.mjs 的同源正则一并修。影响面：本实例 AC-001+AC-004 两条内嵌 [A]。

**P2-8 环境前置清单**：glab auth、pnpm/vp 可用性、配对流程文档指针落成可执行检查项，堵"环境假设=访谈环境"。

**P2-9 [C] 升格纪律**：[C] 应是"无法自动化的残余"而非"默认"。AC-001 的"打开 Map 观察推荐批"可进 test:workflow-ui（apps/web/package.json:13，Vitest browser-mode + Playwright chromium 的 workflow-ui 项目已存在）；AC-006 的"原生界面亲见"保留 [C] 是对的。每条 [C] 附一句"为什么升不了 [A]"。

**P2-10 审计锚对账**：交接指令只内联契约「目标」节第一句话（session.mjs:756-764），而 manifest.goal_oneline 是另一句独立维护的话——**两者在本实例已经分叉**（M1a 目标节不含整页复刻修订，goal_oneline 含），无一致性检查。落法：finalize 生成交接指令时把审计锚与 goal_oneline 对账，分叉即报；并把"这句话将单独扛住 /goal 每 turn 完成审计"亮给用户确认。注：SKILL.md:194-195 已有落盘前对「目标」节的用户确认，但不覆盖 goal_oneline、不发生在交接时刻——补的是这一段，不是否认已有机制。

## 6. 双向 Steelman

**反方最强论证（goal 模式不可能完整完成）**：validation 不可传递——任何 spec 体系只能保证"按声明标准构建"，不能保证"标准=意图"；本实例所有闸门全绿后的整体打回是公理级证据。真实集成的验收语义（亲见、在场认可）本质需要人在环，[C] 档不是覆盖不足而是验收定义的一部分。结论：追求"彻底完整"是把 contract 当成了它不可能是的东西。

**正方最强论证（这套契约范式已是可得的最优实践）**：打回事件恰恰证明系统按设计工作——回退机制存在、被正确触发、无静默交付、全程留痕、修订被组织成"原契约验收标准的修订"而非失控的需求蔓延。四道防线 + 例子聚类天然终点 + 被否决候选保留，每一项都优于行业常规。姊妹篇第 4 节的"值得保留的部分"（事实先行、真实验收边界、人工参与不假装消除、分解经用户选择）进一步支持：剩余缺口是精度问题，不是范式问题。

**Crux**：Goal Contract 的正确目标函数是"最小化交接后才发现的意图偏差"，不是"保证完整完成"。本实例失分不在 Verify 档位体系（它对不可能性的管理是诚实的），而在**口径采样（默认档）、家族聚合（终态）、状态一致性（过期 Ready）**——三处都是"共同理解的边界画错了"，而非"边界内的判定不严"。

**三个可能推翻本结论的关键问题**（证据检验题，影响改进优先级）：

1. **/goal 的完成审计实际每 turn 重读契约全文，还是只锚 objective 一句话？** 若前者，"审计锚漂移"与 [C] 自陈的严重度需重估。本次未审计 /goal 实现本身，列为对账项。
2. **"完全复刻"是新需求还是旧意图的澄清？** 时间上它出现在契约确认之后。若判定为新需求，则"默认档吞口径"根因不成立，P0-1 方向应改为"修订触发器"（何时必须回访谈）；两种机理在现有证据下无法区分，但堵法不同。
3. **三份契约是否本就预期分三次独立 goal 会话执行？** 若是，"家族终态缺失"降级为可选，P0-3 让位于 P0-1/P0-2。
