# 影响面: 2026-08-13-cli-list-grouping

判据：改完之后，这个程序在哪些地方跑起来不一样了？每一处不一样，谁会看见、谁会受影响？

## 用户可见界面

无。`session.mjs list` 只往终端打印纯文本，没有 GUI、没有网页、没有可点击控件。分组和筛选后的
观感差异算在「可运行输出」里，不单出 `mock.html`。

## 可观察行为

有。同样的 issue 集合，跑 `list` 加不加参数、加什么参数，看到的分组/筛选结果不一样：

- 不加参数：保持现状，摊平单表，逐行不变。
- 加 `--group`：同一批 issue 按 `manifest.stage` 分桶展示，组内保持原排序（slug 字典序）。
- 加 `--stage <阶段名>`：只保留该 `manifest.stage` 的 issue，非法阶段名报错退出而非静默忽略。
- 加 `--status in_progress`：只保留顶层 `manifest.status === 'in_progress'` 的 issue（Q1 已定，
  筛的是顶层 status，不是阶段 gate 的 status）。
- 筛选命中 0 条：要不要打印任何东西——这一点用户没在访谈阶段明确要求，留给对照物阶段的
  `behavior.md` 具体举例请用户确认。

出 `behavior.md`。

## 可运行输出

有。终端里实际打印出来的文本形状变了：分组之后会多出「组标题行」这类结构，和现在的
无表头单表不一样。

出 `example-run.md`（写「怎么调、看到什么」，不重复定义 behavior.md 已经定的规则，只给
端到端跑起来的具体样子）。

## 对外接口报文

无。`list` 不发请求、不接收请求，没有 API 报文形态。

## 用户配置

有。新增命令行选项 `--group` / `--stage <值>` / `--status <值>`，这是「用户配置」意义上的
变化（CLI 参数就是这个工具的配置面）。写进 `behavior.md` 的「配置差异」节：列出新增的每个
参数、合法值、不传时的默认值。

## 历史兼容性

有，而且是这次访谈里唯一被标为强约束的一条：用户确认自己电脑上有一个不在本仓库内的
PowerShell 小脚本，靠当前 `list` 输出的固定列宽/列顺序去 parse 纯文本，喂给他自己的一个
提醒小工具（1-interview/rounds.jsonl 第 1 轮 Q2/Q3）。用户已明确要求：不加任何参数时，
`list` 的输出必须和现在逐字节一样，不能有任何改动。写进 `behavior.md` 的「不变清单」，
并且 `example-run.md` 要专门起一个「这条现在能跑，改完之后必须逐字节一样能跑」的场景，
用当前真实输出做基准。
