# 模拟访谈记录（without_skill 基线，自问自答）

本次任务明确要求**不使用**任何 `.claude/skills/` 下名字带 `aes-` 或
`workflow-interview` 的 Skill——包括它们的方法论（分诊、百分比候选等）。以下问答
只是"遇到真实歧义时，我作为普通高级工程师会怎么问、怎么记录"，不套用 asking.md
的格式。

## 调查阶段先做了什么

在开口问任何问题之前，先读了：

- `workflow-interview/SKILL.md`（编排器文档）——三阶段划分、门禁、回退小节。
- `workflow-interview/scripts/session.mjs`——尤其是 `cmdStage` 里
  `needs_reinterview` 分支的具体状态流转代码（不是只看文档描述）。
- `aes-interview/SKILL.md`、`aes-prototype/SKILL.md`、`aes-goal-contract/SKILL.md`
  ——想确认"中途改需求"落在哪个阶段的职责范围内，以及各阶段自己怎么处理"过程中
  撞出新歧义"。
- `validate-goal-contract.mjs`——确认改验收条件不会撞上结构校验的隐藏假设（比如
  AC 编号连续性、条数上限）。

调查结论（见 OUTPUT.md 的"根因"一节）：仓库里**已经有**一条为"过程中发现问题
要往回改"设计的路径——`needs_reinterview`：任何子阶段撞出新歧义时报它，
`session.mjs` 把 issue 打回 `1-interview`，其余阶段的 gate 状态原样保留。
`aes-goal-contract/SKILL.md` 第 147–149 行还另外写了一条更轻的路径："任务已经
存在时改它的契约文件，不新建……改现有标准、补现有实现、修刚发现的缺陷都回原契约
重做"——这条路径完全不touch `1-interview`/`2-prototype`。

所以"要不要问用户"这件事，答案是肯定的：原始请求"允许中途改需求"如果按字面直接
做（比如加一个新命令、新状态、甚至一个新的"改需求"子技能），大概率是在仓库已有
机制之上重复造轮子，而且极可能踩中两条现成路径中的一条却不自知。不问清楚就设计，
返工风险明显大于问一轮的成本。

## 自问自答（按题目给的人设）

> 人设：workflow-interview 的作者，提需求时确实没想清楚。

**Q1. 你说的"中途"，具体是三个阶段里的哪个阶段、哪个时间点？**

A（人设）：访谈已经问完、对照物也确认过了，进入到收尾阶段（第三阶段，锁验收）时，
突然想加一条新的验收条件。

→ 定位：场景发生在 `3-contract`（`aes-goal-contract`）阶段内部，而不是执行阶段
（契约已交接给执行 Agent 之后）、也不是访谈或对照物阶段中途。这一点很关键，因为
它直接决定了该用哪条现成机制。

**Q2. 这跟仓库里已经有的 `needs_reinterview` 回退机制，有什么不一样？**

A（人设）：（想起来仓库里确实有这套）……好像就是想要一个更轻的版本，不用把整个
流程打回第一阶段重新走一遍。

→ 这句话把范围定死了：`needs_reinterview` 的语义是"发现了会改变前面阶段结论的
新歧义"，代价是回到 `1-interview` 重新收口。但人设描述的场景（多想到一条验收
条件）并不必然推翻已经定下的目标、范围或已确认的对照物——它更像是"验收阶段自身
还没问完"，不是"前面阶段问错了"。所以正确路径大概率不是"做一个更轻的
`needs_reinterview`"，而是"在 3-contract 阶段内部就能吸收这件事，根本不需要
碰 1-interview / 2-prototype"。这一点在 `aes-goal-contract/SKILL.md` 147–149 行
已经写了对应做法（回原契约重做），只是没人把它当成"中途改需求"的正式入口来用。

**Q3. 你想要一个新命令、新状态，还是新的子技能来承接这个功能？**

A（人设）：不想要一个全新的子系统或新命令。

→ 排除方案：新建 `aes-amend` 之类的子技能、给 `session.mjs` 加一个新的顶层
子命令（如 `amend`）、给 `STATUSES` 加一个专门的新状态值都超出了这条约束的
容忍度。约束收窄到：只能在**已有**的 `session.mjs stage` 子命令、**已有**的
状态值（`pending` / `in_progress` / `done` / `skipped` / `needs_reinterview`）
和**已有**的 `aes-goal-contract` 收尾文档基础上做增量，不引入新词汇表。

**Q4. 如果新加的验收条件其实会推翻已经定下的目标/范围，或者让 `aes-prototype`
判过"无差异"的某一面现在变得有差异了，还走这条轻量路径吗？**

A（自答，人设未覆盖，按仓库现有分工原则推断）：不应该。`aes-prototype/SKILL.md`
明确说"迭代中暴露的新材料歧义要报回去问清，不在对照物里现场糊过去"，
`aes-goal-contract/SKILL.md` 也是同一句话（"起草时暴露出新的材料歧义，报
`needs_reinterview`"）。轻量路径只覆盖"纯粹新增/细化一条验收标准、不动已锁定的
上游结论"这一种情况；一旦触及已锁定的范围或对照物，仍然要走现成的
`needs_reinterview`，这不是本次要新建的东西，是已有机制该管的事，不能因为嫌
"回访谈"重就绕过判断直接吸收进契约。

**Q5. "改需求"里，"目标本身"要不要包含在这次范围内？**

A（自答，按人设"不想要新子系统"的约束反推）：不包含。人设给的场景（收尾阶段
多想到一条验收条件）本身没有触及目标——如果目标本身要变，那已经不是"补一条
验收条件"，而是彻底的"重新定义要做什么"，理应回到 `1-interview`（`needs_reinterview`
已经覆盖）。把"目标变了"也塞进这次的轻量路径，会让两条路径的判据变得模糊，
违反人设"不想要一个新的复杂子系统"的初衷。

## 分诊结论

| 待定项 | 分类 | 处理 |
| --- | --- | --- |
| "中途"指哪个阶段/时间点 | User decision | 已问清：3-contract 阶段内、契约还没 finalize 或刚 finalize 完 |
| 是否已知现有 `needs_reinterview` | Fact（可调查，但仍需向"作者"确认心理预期） | 已问清：知道，想要更轻的版本 |
| 要不要新命令/新子系统 | User decision（难逆：一旦建了新子系统，后续所有阶段文档都要跟着引用它，成本高） | 已问清：不要 |
| 新验收条件是否可能推翻已锁定范围/对照物 | Agent-owned 判据（仓库已有分工原则可以直接推断，不需要单独问） | 按仓库既有的"新材料歧义走 needs_reinterview"原则处理，本次功能只覆盖不推翻的情况 |
| "改需求"是否包含目标本身 | Agent-owned（由 Q3+Q4 的回答直接推出边界，不需要单独占用一个问题） | 不包含，理由见上 |

三条真正跨出"我能从仓库读出来"的边界、答案会改变设计方向的问题（Q1、Q2、Q3）
问了；两条（Q4、Q5）能从仓库已有的分工原则和前三条答案直接推出来，没有反复
拿去问用户，避免把访谈拖成走仪式。
