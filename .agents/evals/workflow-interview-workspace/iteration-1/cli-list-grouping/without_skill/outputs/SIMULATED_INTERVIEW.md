# 需求澄清问答记录

在读完 `.claude/skills/workflow-interview/scripts/session.mjs` 的 `cmdList`（第 429-458 行）之后，
输出是一张扁平表：`name  stage  status  goal片段`，按 name 排序。分组和筛选都还没有。有三处判断我自己拿不准，问了维护者。

---

## Q1：分组和筛选，如果只能先做一个，你要哪个？

**A（维护者）**：分组更要紧。先做分组，筛选可以往后放，甚至这次不做也行——但如果顺手能做我也不反对。

## Q2：默认调用（不带任何 flag）的输出，是不是必须和现在逐字节一致？还是只要求人眼扫一眼还能看懂就行？

**A**：不需要逐字节一致。只要求换成分组之后，人眼扫一眼还是能看懂的样子——不要因为加了花哨的分隔符或者颜色把它变得反而更难读。

## Q3：现在有没有别的东西依赖 `session.mjs list` 现在这个输出格式？

**A**：有一个。我自己写了个脚本，不在这个仓库里，每天早上跑一遍，解析 `session.mjs list` 的纯文本输出，数一下卡在每个 stage 的 issue 各有多少个。如果默认输出换成分组表格，这个脚本的解析逻辑会直接失败（它现在是按你说的那种"一行一个 issue、列对齐"的格式在切字段）。

## Q4（追问）：这个脚本大概是怎么切字段的？如果默认格式换了，你是想让 `list` 保留一个开关能拿到旧格式，还是你自己改脚本去适配新格式？

**A**：脚本大概是按空格/列对齐切的，具体记不清了，反正就是假设"一行一个 issue"。我不想因为这个把默认输出锁死成老样子——分组更重要。如果你们能顺手留一个开关拿到那种老的一行一个 issue 的格式，我就把自己脚本指过去，省得再改它的解析逻辑；如果做不到也行，我自己找时间改脚本。这个不是这次工单的重点，你们按自己的判断来就行。

---

## 小结（我自己的判断，不是逐字转述）

- 分组 > 筛选，这是硬优先级。
- 默认输出允许变样子，但不能变得让人看不懂。
- 存在一个真实的外部消费者（个人脚本）依赖当前的"一行一个 issue"格式，它没有版本化、不受这个仓库控制，所以不能把它当成"必须保持 API 兼容"的硬约束，但值得用一个低成本的方式照顾到——加一个能拿到旧样式输出的开关，写进方案里作为可选项，不作为验收硬指标。
