# FINAL REPORT（对照组 / 无辅助技能）

## 我对需求的理解

`session.mjs list` 目前把 `.aes-workflow/grilling/` 下所有 issue 摊平成一张四列表（name / stage / status / goal片段），issue 一多就没法快速定位。要做两件事：

1. **按 stage 分组显示**（`1-interview` / `2-prototype` / `3-contract` 三个阶段各自成组），这是维护者明确表态"两个只能先做一个"时会选的那个，优先级更高。
2. **加筛选**：只看某个 stage，或者只看 `in_progress` 的（对应 manifest 顶层 `status` 字段，代码里只观察到 `in_progress`/`ready` 两个取值，不是封闭枚举）。

我把这两件事都写进了方案，并额外加了一个 `--flat` 开关（保留旧的扁平格式），起因是问到"有没有别的东西依赖现在的输出格式"时，维护者说他自己有个不在仓库里的个人脚本在解析这个纯文本输出——这不是这次工单的硬指标，但成本很低（旧代码原样保留即可），所以顺手放进方案，标注为非硬性验收项。

## 我认为的验收标准（详见 OUTPUT.md 的"验收标准"节）

- 默认调用按 pipeline 顺序分组、只显示非空分组、每组有组头（阶段名+数量）、有总数提示。
- `--stage <value>` 精确匹配三个合法 stage 值，非法值报错退出并列出合法值。
- `--status <value>` 精确匹配，不命中不报错，只提示"没有符合条件"。
- 两个 filter 可以 AND 组合。
- 空目录 / 无 issue 的提示语行为不变。
- `--flat` 复现旧的扁平输出（非硬指标，但方案里给了）。
- 用法注释（文件头 8-17 行）同步更新。

## 还没搞清楚 / 留给实现或下一轮确认的点

- 分组标题的具体符号样式（`--`、`##`、颜色等）没有钉死，只要求"含阶段名+数量、人眼可读"，这是我自己的判断，没有回去追问，因为维护者已经明确说"不要求逐字节一致，能看懂就行"，我认为进一步纠结符号是过度设计。
- manifest 损坏的行怎么分组（我定的是单独归一组）不是这次的核心分歧点，我按最小意外原则做了决定，没有专门确认。
- `--status` 要不要做成大小写不敏感、要不要支持除 `in_progress` 外的模糊匹配——没有问，按精确匹配处理，因为当前代码里 status 取值本来就是固定小写 slug，没有理由做额外容错。
