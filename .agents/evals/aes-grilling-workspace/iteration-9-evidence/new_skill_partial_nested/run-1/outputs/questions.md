- 用到计数器的测试要在开头调 `resetForTests()`（`src/metrics.mjs` 导出），否则互相污染。
- **没有覆盖率工具，没有覆盖率门槛。**

**这次要出哪种对照物：行为对照表，不出界面 mock**

这个服务没有任何用户可见界面 —— 对外只有 `POST /v1/events`、`GET /metrics`（纯文本）、`GET /healthz`。所以不出 mock。但采样会改现有可观察行为（落盘量、转发出去的内容、HTTP 响应体里的 `accepted` 数字、`/metrics` 计数器的含义），所以**收口之后我会出一张行为对照表，一行一个具体场景写「现在 → 改后」，请你逐行质疑。**

**「采样」这个词在这个仓库里已经被占用了，而且和你说的不是一个意思**

`README.md` 第 24–33 行有一整节叫「### 单请求控制采样」，写着：

> 支持 `X-Sample-Rate` 请求头，取值 0 到 1，业务方可以自己决定这一批要不要抽样上报

后面还带了 curl 例子。但是：

- 我 grep 了整个仓库（`src/`、`test/`、`config/`、`scripts/`、`docs/`、`*.json`、`*.yml`），`sample` / `rate` 相关的命中**只有 README 这三行，代码里一个字都没有**。
- `src/receiver.mjs` 从请求头里只读 `x-app-id`（第 18 行），没有任何地方读 `x-sample-rate`。
- README 自己在第 35–36 行加了注：「这一段是 1.x 时代写的，2.0 重构之后头部处理逻辑整个换过一遍，文档没跟着改全，具体行为请以 `src/` 为准。」

也就是说：**仓库文档里的「采样」= 业务方自己决定这批要不要少发，而且这个能力其实不存在（文档在骗人）；你说的「采样」= 服务端保护自己的磁盘和下游。** 这两个是不同的东西，按哪个意思走我不替你定，见下面 Q3。

**其余相关事实**

- **配置不能热更新，而且配置不完全在这个仓库里。** `src/config.mjs` 第 19–20 行注释：「配置文件是部署时渲染出来的，进程只读一次，不监听变更。想改配置要重新部署，不能热更新。」`docs/runbook.md` 更进一步：「这个仓库里的 `config/*.json` 只是**样例与本地开发用**：线上实际生效的配置文件是 infra 仓库的模板渲染出来后投放到容器里的，模板不在这个仓库，改配置项要同时改那边。」→ 加一个采样率配置项，意味着要动 infra 仓库；线上调采样率 = 改 infra 模板 + 分批滚动重启。
- **运维现在靠 `events_by_app` 定位「磁盘涨得快」。** `docs/runbook.md` 常见故障表里：「磁盘涨得快 | 某个业务方量突增，看 `events_by_app` 定位」。还写了「`events_total` 与 `events_rejected_total` 是最常看的两个」。计数器是进程内的，重启归零（预期行为）。
- **转发形状是硬契约。** `src/forwarder.mjs` 第 5 行注释：「下游只认 `{events:[...]}` 这一种 body 形状，改它要跟下游同步发版。」`docs/schema.md`：「POST 给下游的 body 固定是 `{"events": [ ...事件对象... ]}`。下游只认这一种形状。」
- **落盘格式也是硬契约，而且有个回捞工具依赖它。** `src/storage.mjs` 第 6 行注释：「下游有从这些文件回捞的工具，所以文件名和一行一个 JSON 的格式不要随便改。」那个工具是 `scripts/replay.mjs`：从 `data/events.ndjson` 逐行读出来**重新塞进 forwarder 转发给下游**，用途是「下游出故障丢批之后用它补数」。→ 这里有个坑：如果磁盘和下游用**不同**的采样率，replay 补数时会把「磁盘上有、下游本来就不该有」的事件灌给下游，下游的量级统计会被污染；反过来「下游有、磁盘没有」的事件永远补不回来。这个坑决定了 Q1 怎么答。
- **事件里有做一致性采样的材料。** `docs/schema.md` + `test/fixtures/event-valid.json` 显示事件有可选的 `user_id`、`session_id`。而 `test/fixtures/event-batch.json` 恰好是个反例演示：u-1 有 `page_view` + `click`，u-2 有 `page_view` + `purchase`（`props.amount: 4200`）。**如果按单个事件独立随机丢，很可能留下 u-2 的 page_view 却丢掉他的 purchase，漏斗和转化率就废了。** 这一条决定 Q2 怎么答。
- **未知字段默认放过，但这不等于下游认。** `src/validate.mjs` + `docs/schema.md`：`validate.rejectUnknownFields` 为 false，「业务方加字段不该被中继卡住，字段治理放在下游做」。注意这说的是**中继放过业务方的字段**，不保证下游 `analytics-ingest` 会接受我们新加的字段。
- **服务端会覆写 `app` 字段**：`docs/schema.md` 写「由服务端按 `X-App-Id` 覆写，业务方传了也会被盖掉」，`src/receiver.mjs` 第 40 行 `{ ...raw, app: appId }` 确认。
- **已登记的上报方写死在代码里**：`src/auth.mjs` 有 8 个，其中两个是压测用的 —— `loadtest-runner`、`loadtest-soak`。注释写「新增业务方走发版，不走配置」。
- **现有响应契约**：`src/receiver.mjs` 整批里有坏事件时好的照收、坏的单独退回（注释解释了原因：「业务方普遍不重试，整批退回等于直接丢数据」）。有 rejected 返 **207**，全好返 **202**，body 是 `{accepted: <数字>, rejected: [...]}`。`test/receiver.test.mjs` 里有 `parsed.accepted === 2` 的现成断言。
- 关闭转发有现成开关：`forward.enabled`（`config/*.json`）。生产的 `batchSize` 是 500、`flushMs` 1000、`maxRetries` 5；`storage.rotateBytes` 生产是 256MB，超了滚一个 `.1`，`data/` 由 infra 侧定时任务搬走并清理。
- 这个仓库现在**还没有** `docs/goal-contracts/` 目录，这会是第一份契约。

### 二、我的完整推荐草案（这是靶子，不是结论，你改哪条就是哪条）

**目标一句话**
让 metrics-relay 能按配置对上报事件做服务端采样，在业务方不改一行代码的前提下，把落盘量和转发给下游的量按比例降下来。

**做什么（一句）**
在接收链路上加一层服务端采样：采样率来自配置文件、可按 `X-App-Id` 覆写，被采样掉的事件既不落盘也不转发，同时新增计数器让人看得出采样在生效，并同步 README / schema / runbook 三处文档。

**不做什么（一句）**
不做限流、背压或配额（不新增「超限拒收」这种行为），不改事件 schema 的必填字段，不改 `{"events":[...]}` 外层转发形状和 `events.ndjson` 一行一 JSON 的落盘格式，不做热更新或运行时调整接口，不碰 401 / 400 / 校验失败这三条既有路径。

**验收的大致方向**
用现有的 `npm test`（零依赖 runner + `node:assert/strict`）写断言，围绕这几个点：采样率 1.0 时行为和现在完全一样（现有 19 条测试零 diff）；0.0 时不落盘不转发但 HTTP 仍返回 202；按 app 覆写确实生效；`/metrics` 新计数器数值对得上；配置里没写采样率时等于 1.0。数字门槛（磁盘降多少）单独定 —— 见 Q5，因为**这个仓库里没有任何基准脚本，要验数字就得先建基建**。

### 三、以下 8 条我按查到的事实定了，你不反对就算定

- **默认采样率 = 1.0，配置里不写就完全等于现在的行为** — 现有部署（含 infra 那边还没改模板的情况）升级后行为零变化，不会有人半夜发现数据少了一半 — 代价：光升级这个服务不解决磁盘问题，得等 infra 那边下发了配置才真正生效。
- **采样只作用于校验通过的事件；401（未登记 app）、400（body 不是合法 JSON）、校验失败被 reject 这三条路径一个字不改** — 被拒的事件本来就不落盘不转发、不占磁盘也不占下游 — 代价：坏事件产生的 `log.warn('rejected events')` 日志量不受采样控制，日志盘该涨还涨。
- **新增计数器 `events_sampled_out_total`，并按 app 分一维（形如 `events_sampled_out_by_app{app="web-portal"}`），沿用 `/metrics` 现有纯文本行格式** — 不加这个，采样到底有没有生效、抽掉了多少，运维只能靠猜 — 代价：`/metrics` 多出几行，infra 侧的抓取方要加一次采集配置才看得到，这是本仓库之外的一次改动。
- **HTTP 响应体形状保持不变，不加 `sampled_out` 之类的新字段** — 业务方拿到这个数也没有可执行动作（他不能重发，重发只会被再抽一次），加了就是多一处要长期维护的公共契约 — 代价：业务方自查「我发的量为什么在下游少了」时，只能来问运维看服务端 `/metrics`，没法自助。
- **不为压测 app（`loadtest-runner`、`loadtest-soak`）内建任何特殊规则，它们只是 per-app 配置里两条普通条目** — 内建规则会把 app 名字写死进采样代码，重复 `src/auth.mjs` 那个「改一次就得发一次版」的毛病 — 代价：压测想拿全量数据得记得在配置里显式给这两个 app 写 1.0，忘了就跟着全局率被抽掉，压测结论可能对不上。
- **采样率配置项写进 `config/default.json` 和 `config/production.json`，不引入环境变量开关** — `scripts/lint.mjs` 有条规则专挡 `process.env.X || 默认值` 这种把默认值散在代码里的写法，走环境变量会直接撞 lint — 代价：调采样率必须改 infra 仓库的模板并重新部署，没有「临时 export 一个变量试试」这条快路。
- **采样不做热更新，也不加运行时调整用的 HTTP 接口** — 和这个服务现有的配置模型一致（`src/config.mjs`：部署时渲染、进程只读一次、不监听变更）；破例做热更新等于给这个服务开第二套配置通道 — 代价：线上量突增想紧急降采样，最快路径是改 infra 模板 + 分批滚动重启（`docs/runbook.md` 说发布是分批滚动、一批起来观察一段再放下一批），不是一条命令的事。
- **同步改三处文档：`README.md` 的接口/采样一节、`docs/schema.md` 的落盘与转发形状、`docs/runbook.md` 的观察项与「磁盘涨得快」那条故障处置** — 这三处正是运维和业务方实际会去查的地方，尤其 README 那节 1.x 遗留的 `X-Sample-Rate` 说明不能留着和新行为并存两套说法 — 代价：占一部分工时；README 那节具体怎么处理取决于你 Q3 怎么选。

### 五、下面 5 个是真两难，需要你裁决

> 你可以一次回复完，比如「Q1 选 B，Q2 选 A 但 session 缺失时改成丢弃，Q3 选 A，Q4 按推荐，Q5 选 C」。

**Q1. 磁盘和下游，是「同一次采样决定」还是「各自一个采样率」？**
已知事实：`scripts/replay.mjs` 会把落盘的 `data/events.ndjson` 逐行读出来重新转发给下游，用途是下游丢批后补数（`src/storage.mjs` 第 6 行也注明「下游有从这些文件回捞的工具」）。所以磁盘和下游的内容一旦不是同一份，补数动作就会算错量。

A. 入口只做一次采样决定，被留下的事件同时落盘 + 转发，被抽掉的两边都没有 — 45%（推荐）
- 选什么：`src/receiver.mjs` 里在 `store.write` / `forwarder.add` 之前统一筛一次，磁盘和下游拿到的**是同一份事件**。**不覆盖**「磁盘留全量当兜底、下游只要一小部分」这种诉求 —— 选了 A 就没有全量兜底了，磁盘上被抽掉的事件永久消失，事后想补也补不出来。
- 好处：`scripts/replay.mjs` 不用改一个字，补数天然正确；只有一个配置项和一个心智模型，运维不会搞混；磁盘和下游同比例下降，你说的两个痛点一次解决。
- 代价：丢掉了「磁盘是全量、可回溯」这个隐含的安全网 —— 现在如果下游发现某个分析口径要重算，理论上还能从 ndjson 回捞全量，采样之后回捞到的也只是抽样；采样率一旦定错（比如误配成 0.01），损失的是**磁盘上原始数据**，不可逆。

B. 落盘和转发各自一个采样率，分别配置 — 40%
- 选什么：两个独立配置项（比如 `storage.sampleRate` 和 `forward.sampleRate`），可以配成磁盘 1.0、下游 0.1，也可以两边都 0.5。**不覆盖**「`scripts/replay.mjs` 自动做对」——必须同时决定 replay 的行为：它从全量 ndjson 回捞时，是原样全灌给下游（下游量级统计被污染），还是也照 `forward.sampleRate` 抽一遍（那就得改 replay，并且抽到的和当初漏掉的不是同一批）。
- 好处：磁盘可以先只降一点、下游狠降，两个痛点的紧急程度不一样时能分开处置；万一采样率配错，全量还在磁盘上，可逆。
- 代价：`scripts/replay.mjs` 必须一起改并重新确认语义，这是这次改动之外多出来的一块；两个率的组合会出现「磁盘 0.5、下游 0.1」这种下游拿到的是磁盘的子集的情况，任何跨磁盘/下游对数的人都得先搞清两个率；配置项和文档都多一倍。

C. 只对转发下游采样，磁盘保持全量，磁盘那边改用别的手段（调小 `rotateBytes`、让 infra 更勤地搬走） — 15%
- 选什么：只在 `forwarder.add` 处筛，`storage` 一个字不改。**不覆盖**你说的「磁盘吃不住」—— 磁盘问题被推给 infra 侧的搬运和清理策略，本仓库不解决。
- 好处：改动面最小，落盘格式和 replay 完全不受影响，全量数据永远在；下游的压力立刻降下来。
- 代价：磁盘这半个痛点这次没解决，你还得再去推 infra 那边改保留策略，那是另一个仓库另一次沟通；而且 `storage_bytes_total` 不会有任何改善，运维看不到进展。

**Q2. 抽样的「单位」是什么 —— 单个事件，还是一个会话/一个人？**
已知事实：`docs/schema.md` 里 `user_id`、`session_id` 都是**可选**字段。`test/fixtures/event-batch.json` 里 u-1 是 `page_view`+`click`，u-2 是 `page_view`+`purchase`（`props.amount: 4200`）。按单事件独立随机丢，很容易留下 u-2 的 page_view 却丢掉他的 purchase。

A. 按 `session_id` 做一致性哈希（缺失时回退 `user_id`，两个都缺失时按事件独立随机） — 44%（推荐）
- 选什么：同一个 session 的事件要么全留、要么全丢，漏斗、留存、转化路径这类按会话串起来的分析在抽样后仍然成立（只是样本量变小）。**不覆盖**两件事：一是没有 `session_id` 也没有 `user_id` 的事件（schema 里两个都是可选），这部分只能退回单事件随机，它们的会话完整性保证不了；二是**不保证实际抽样比例精确等于配置值** —— 哈希按 key 分桶，如果某个 session 的事件数特别多，实际留下的事件数会偏离配置的百分比。
- 好处：下游做漏斗和转化的口径不会因为采样而算错，这是采样最常见的翻车点；确定性 —— 同一个 session_id 每次判定结果一样，测试可以写成不依赖随机数的固定断言，符合 `docs/testing.md` 那套零依赖断言风格。
- 代价：实际磁盘/下游降幅会围着配置值波动，不是精确的 10% 就是 10%，量小的时候波动更明显；`session_id` / `user_id` 缺失的事件行为和其它事件不一致，这个不一致要写进文档，运维查数时得知道；下游如果按「每条事件独立同概率」的假设做估算，会算偏。

B. 每个事件独立随机（掷一次骰子，低于采样率就留） — 30%
- 选什么：最直白的按比例抽样，实际比例在量大时非常接近配置值。**不覆盖**任何跨事件的关联性 —— 同一个 session、同一个 user 的事件会被拆散，漏斗分析在抽样数据上直接失效（会出现「有 purchase 没有对应 page_view」和反过来的情况）。
- 好处：实现和心智都最简单，一句判断；实际降幅精确可预测，你说「降到 10%」它就是 10%，运维对着 `storage_bytes_total` 一看就知道对不对；不依赖 `session_id` / `user_id` 存不存在，所有事件行为一致。
- 代价：会话级/用户级分析在采样后不可用，而这类分析往下游要不要重新设口径，得下游那边确认 —— 这件事我在仓库里读不出来，只有你知道下游现在拿这些数据在算什么。
- 注：如果下游只做「按事件名计数」这类聚合，这条代价其实为零，B 就是最优解。所以这题的答案取决于下游的用法。

C. 按事件名分级配置（比如 `page_view: 0.1`、`click: 0.2`、`purchase: 1.0`，未列出的走默认率） — 26%
- 选什么：把「哪些事件廉价可抽、哪些事件必须全留」的决定权交给配置。**不覆盖**会话完整性 —— 同一 session 里 page_view 被抽 90%、purchase 全留，会话就是不完整的（只是不完整的方式是你选的、可预期的）。
- 好处：`purchase` 这种低频高价值事件一条都不丢，同时把 `page_view` 这种量大廉价的事件狠狠压下去 —— 单位磁盘换到的信息量最高；量的削减集中在真正占地方的事件上。
- 代价：配置从「一两个数字」变成「一张会长期增长的事件名表」，而这张表活在 infra 仓库的模板里，每加一个事件名都要走一次那边的改动 + 滚动重启；漏配一个新事件名它就悄悄走默认率，可能是你不想要的；这张表事实上是一份数据治理策略，得有人负责维护，仓库里现在没有这个角色。

**Q3. 采样率谁说了算 —— 只服务端，还是业务方也能插手？顺带：README 里那节骗人的 `X-Sample-Rate` 怎么办？**

A. 只有服务端配置说了算，`X-Sample-Rate` 请求头不实现也不读，README 那节改写成「该头不生效，已在 2.0 移除」 — 42%（推荐）

- 代价：如果真有业务方在发这个头，他们会发现「文档说的功能被官方确认为不存在」，这是一次要主动沟通的对外说明；紧急场景下业务方不能自助降量，全部压力都落在改 infra 配置 + 滚动重启这条路上。

B. 服务端配置定「上限」，请求头可以在上限内进一步降低，但不能提高 — 38%
- 选什么：最终采样率 = `min(服务端配置率, 请求头率)`。业务方能主动少发（利他行为，允许），但不能给自己开后门多发。**不覆盖**请求头传非法值的情况需要单独定：传 `abc`、传 `1.5`、传 `-1` 是当 400 拒掉、还是忽略走服务端配置 —— 这也是一个要定的公共行为（我倾向忽略并 warn，不新增拒收行为，和默认区第 2 条一致）。
- 好处：README 那节的承诺基本被兑现（语义收窄成「只能往下调」），不用对外承认文档骗人；业务方在自己量突增时能自助降压，不必等你改 infra 配置和滚动重启，这条正好补上默认区第 7 条那个「没有快路」的代价。
- 代价：采样率从此有两个来源，`/metrics` 上看到某个 app 被抽掉一堆时，你分不清是服务端配的还是他自己传的 —— 除非再加一个维度的计数器，那又是一次 infra 抓取配置的改动；请求头的非法值处理、和 per-app 覆写谁优先，都得写进文档并测到；业务方传的值不受任何评审，他改一次你不会知道。

C. 真正实现 README 写的那个头，业务方自己控制，服务端配置只兜一个底（业务方没传时才用） — 20%
- 选什么：以请求头为准，服务端配置只是缺省值。**不覆盖**「服务端能保护自己」这件事 —— 一个业务方只要不传头或者传 1.0，服务端就拿他没办法，你说的「磁盘和下游吃不住」在最坏情况下原封不动。
- 好处：README 一个字不用改，文档和实现终于对上；业务方对自己的数据完全自主。
- 代价：这条路根本解决不了你提的问题 —— 需要被限的恰恰是那个不愿意自己限的业务方；而且它把服务端的自保能力交给了外部调用方，后面真要收回来又是一次破坏性变更。

**Q4. 要不要让下游能还原真实量级 —— 在数据里带上采样标记？**
已知事实：`src/forwarder.mjs` 第 5 行「下游只认 `{events:[...]}` 这一种 body 形状，改它要跟下游同步发版」。`docs/schema.md` 说 `rejectUnknownFields` 为 false、「字段治理放在下游做」，但那说的是**本中继放过业务方的未知字段**，不代表下游 `analytics-ingest` 会接受我们新加的字段 —— 下游认不认，我在这个仓库里查不出来。

A. 不带任何标记，下游看到的就是普通事件，量级还原靠「双方约定好采样率是多少」 — 34%
- 选什么：转发出去的事件和现在逐字节同构。**不覆盖**「下游能自己算出真实量级」—— 下游必须从别的渠道（口头、配置文档、你告诉他）知道当前采样率，而且采样率一变、按 app 不同、历史数据混着不同采样率的时候，下游只能靠时间段去猜。
- 好处：转发形状零变化，下游不用发版，也不用去确认它认不认新字段；这次改动完全收在本仓库内。
- 代价：下游所有基于「量」的报表（日活、PV 总量、按 app 的量）在采样启用后会直接变小，而数据里没有任何线索说明为什么 —— 这类事故的典型形态是几周后有人发现某个业务指标腰斩，排查半天才想起来加过采样；采样率一变，历史数据就不可比，而且无法事后修正。

B. 每个事件对象上加一个 `sample_rate` 字段（比如 `0.1`），落盘和转发都带 — 44%（推荐）
- 选什么：事件对象多一个字段，值是这条事件当时被判定用的采样率。下游乘以 `1/sample_rate` 就能还原量级，历史数据也自带上下文。落盘的 ndjson 也带，`scripts/replay.mjs` 回捞出来的事件因此仍然是自解释的。**不覆盖**「外层 body 形状变化」—— `{"events":[...]}` 这个外壳一个字不动，只是数组里的对象多一个 key。也**不覆盖**「下游一定认」—— 这需要你或我去确认 `analytics-ingest` 对未知字段的处理，确认不了就是阻塞项。
- 好处：下游能算对量级，采样率变了、按 app 不同、历史混着多种采样率都不影响，因为每条数据自己带着口径；落盘数据同样自解释，将来谁回捞都不会算错；比「靠双方口头约定」少一个长期的失配风险。
- 代价：事件对象多一个服务端注入的字段，这是对下游的一次契约变更，得跟下游确认它对未知字段的处理（严格 schema 的话下游要先发版），拿不到确认这条就是阻塞；每条事件多约 20 字节，采样到 10% 的场景下这点开销无所谓，但采样率 1.0（默认值）时是**净增磁盘占用** —— 除非约定 1.0 时不写这个字段，那又是一处要测的分支；这个字段和 `app` 一样属于「服务端覆写/注入」，业务方自己传了 `sample_rate` 要不要被盖掉，得和 `app` 一样明确写进 `docs/schema.md`。

C. 不动事件对象，改在批级别 —— 转发 body 变成 `{"events":[...], "sample_rate": 0.1}` — 22%
- 选什么：外层多一个同级字段，整批共用一个采样率。**不覆盖**「一批里混着不同采样率的事件」—— 如果按 app 或按事件名分别配率（Q2 选 C 或 per-app 覆写生效），一个批次里的事件可能来自不同 app、用的不是同一个率，批级别的单个数字就是错的。也**不覆盖**落盘数据 —— ndjson 是一行一个事件，没有批的概念，磁盘上的数据仍然不自解释。
- 好处：每条事件不增加字节；语义上「这批是按这个率抽的」比较自然。
- 代价：**直接违反 `src/forwarder.mjs` 和 `docs/schema.md` 明写的硬约束**（「下游只认 `{events:[...]}` 这一种 body 形状」），下游必须同步发版，属于跨团队协调；和 per-app / per-event 采样率是冲突的，除非转发时按率分批，那是额外一块复杂度；落盘数据仍然不自解释，replay 回捞出来的东西还是算不出量级。

### 二、以下 5 条我按查到的事实定了，你不反对就算定

- **一致性哈希用 `node:crypto` 的 `createHash('sha1')` 取摘要前 4 字节转无符号整数再除以 2^32，得到 [0,1) 的确定值，小于采样率则保留** — 仓库零依赖（`README.md` 第 5 行），`node:crypto` 是内建模块；取模方式固定下来才能保证同一个 `user_id` 在任何进程、任何重启之后判定一致 — 代价：这个算法一旦上线就等于锁死了「哪批用户被留下」，将来想换算法或换取位方式，等于把样本集整个换一批，下游的同比数据会出现一次断档。
- **哈希输入固定为 `user_id` 或 `session_id` 的字符串原文，不拼 app id、不拼日期、不加盐** — 拼了 app id，同一个用户在不同 app 的行为链会被拆开（跨端漏斗就断了）；拼日期会让样本集每天换一批，同比直接不可比 — 代价：样本集是永久固定的那一批用户，长期抽样会系统性偏向这批人；真要轮换样本必须改算法，而改算法就是上面那条代价。
- **采样率与白名单、丢弃名单都写进 `config/*.json` 里同一个 `sampling` 段（形如 `{"sampling": {"rate": 1.0, "byApp": {}, "keepEvents": [], "dropApps": []}}`），不散在 `storage` / `forward` 各自的段里** — Q1 你选了「入口一次决定」，采样发生在落盘和转发之前，它不属于任何一边；集中一段，infra 那边加模板改一处 — 代价：infra 模板要一次性加一整段而不是一个字段，那边的改动稍大；`sampling` 段整段缺失时全部走代码默认值，这个「整段缺失」的分支得单独测。
- **被采样掉和被丢弃的事件都不写日志** — 采样掉的量本身就是海量（这正是这次的目的），每条一行日志等于把磁盘压力从 ndjson 挪到日志盘 — 代价：单独一条事件「为什么没落盘」事后无法追溯，只能看聚合计数器；排查「我这条数据怎么没了」只能回答概率，不能回答个案。
- **采样掉和丢弃分成两个独立计数器：`events_sampled_out_total`（+ 按 app 一维）和 `events_discarded_total`（+ 按 app 一维），不混成一个** — 这两件事的语义完全不同：采样掉是「按设计抽掉的真实业务数据」，丢弃是「本来就不该来的压测数据」，混成一个数的话，运维看到它涨了不知道该不该管 — 代价：`/metrics` 一次多出四类行，infra 侧抓取方要加一次采集配置才看得到（本仓库之外的一次改动）；`snapshot()` / `resetForTests()` 要同步维护，漏一个会污染其它测试。
