## 第 1 轮（批量，4 个互不依赖歧义）

### 已查清事实（不占提问轮次，先同步给你）

- `server.mjs` 中 `/summary` 的慢来自三段**串行**聚合，各自模拟一次慢查询（`await sleep(180); await sleep(160); await sleep(150)`），合计约 490ms；三段之间没有数据依赖。
- 响应体是固定 JSON `{ items: 12, total: 3200 }`；其他路径返回 `ok`。
- README：内部面板后端，`node server.mjs` 监听 :3000，前端首屏渲染依赖 `/summary`，仓库暂无测试或基准工具。

### 完整推荐候选（靶子，改哪条就是哪条）

- Goal：`/summary` 接口在本地可复现的测量下，延迟从约 490ms 降到 p95 ≤ 200ms，响应内容与现在语义一致。
- In：`/summary` 路径的聚合方式优化（如三段并行化），以及一个可重复运行的延迟测量手段。
- Out：不改其他路由、不引入外部依赖（数据库/缓存服务）、不做前端改动。
- AC 方向：基准测量下 p95 延迟低于阈值；响应 JSON 与优化前一致；测量方法可被任何人重复执行。

### 问题（每题含证据摘要 / 选项 / 推荐 / 代价）

**Q1. 多快算"不慢了"——性能阈值定在哪？**
证据：当前约 490ms。三段并行化后理论下限约 180ms（最长一段）；要更低就得动"查询"本身或引入缓存。
- A. p95 ≤ 200ms（并行化即可达成，改动小、无新组件）【推荐】
- B. p95 ≤ 300ms（更宽松，几乎任何优化都能过，但"优化"力度存疑）
- C. p95 ≤ 100ms（必须引入缓存或改造数据源，改动大、可能引入数据新鲜度问题）
- D. 不定数值阈值，只要求"显著快于现状"（AC 不可判定，校验器会拒，不建议）
代价：阈值越低，改动越大、越可能牺牲数据新鲜度。

**Q2. 怎么测——仓库没有任何基准工具，测量手段要不要纳入交付范围？**
证据：README 明确"仓库暂无测试或基准工具"，AC 要可判定就必须有可重复的测量方法。
- A. 在仓库内加一个小型基准脚本（如 Node 脚本连发 N 次请求统计 p50/p95），随本次交付【推荐】
- B. 只用手工 curl 计时，不留脚本（不可重复，换个人测结果不可比）
- C. 引入第三方压测工具（autocannon 等）作为依赖（多一个依赖，内部小服务偏重）
代价：A 增加少量仓库文件；B 让 AC 事实上不可判定；C 引入外部依赖。

**Q3. 兼容性——响应内容和数据新鲜度必须保持什么？允许缓存吗？**
证据：前端首屏渲染依赖 `/summary` 的 JSON（`items`、`total` 字段）；若允许缓存则命中时可能返回旧数据。
- A. 响应 JSON 结构与字段语义保持不变，且每次请求返回新鲜聚合结果（不允许跨请求缓存）【推荐】
- B. 结构不变，但允许短 TTL 缓存（可低于并行化下限，代价是数据可能滞后）
- C. 可以顺带调整响应结构（需要前端配合改动，超出后端范围）
代价：A 把优化空间限定在并行化/查询本身；B 引入数据滞后；C 波及前端。

**Q4. 范围边界——只动 /summary，还是顺带整理整个 server？**
证据：仓库只有一个 `server.mjs`，除 `/summary` 外仅有兜底 `ok` 路径。
- A. 只动 `/summary` 的聚合逻辑，其他路径与启动方式一字不动【推荐】
- B. 顺带重构整个 server（路由拆分等）（本次诉求只是接口慢，扩大范围回报低）
代价：B 扩大 diff 与回归面。
