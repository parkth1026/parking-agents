## 第 1 轮：批量问清歧义（4 个互不依赖的决定）

### 推荐候选（靶子，不是结论）

- Goal 一句话：首页 `/summary` 接口在可复现基准下响应时间从约 490ms 降到门槛以下，响应内容与其余路由行为保持不变。
- In 一句话：优化 `server.mjs` 中 `/summary` 三段聚合的编排方式，并新增一份锁定的基准测量脚本。
- Out 一句话：不改响应 JSON 内容、不改其余路由行为、不缩短三段模拟查询各自的延迟数值（那是改尺子不是改工件）。
- AC 大致方向：基准脚本下 `/summary` 延迟低于门槛；响应体逐字节不变；基准脚本落盘且声明为不可修改；测量口径（次数/分位数/并发）写死在脚本里。

### 已查清的事实（不占提问轮次）

- `/summary` 现为三段串行模拟慢查询（180+160+150 ≈ 490ms），并行化的理论下限是最长一段 ≈ 180ms 加少量开销。
- 仓库无测试、无基准工具（README 明示）。因此「怎么算过」没有默认档可用，必须由你裁决。
- 本目标含数字门槛且属优化型：按流程，门槛值、量尺、量尺是否锁定都必须问你。

### Q1. 性能门槛定多少？

- 证据：当前约 490ms；纯并行化可稳定做到约 180-200ms；要低于 180ms 就必须动三段查询本身的语义（缓存或改数值）。
- 选项：
  - A) p95 < 250ms —— 并行化即可稳定达成，改动最小、风险最低。
  - B) p95 < 200ms —— 并行化加少量余量，本机波动下偶发超线可能需要微调，风险仍低。
  - C) p95 < 100ms —— 必须引入缓存或改变三段查询语义，改动大、语义变化需另行对齐。
  - D) 其他数值（请给出）。
- 推荐：A。代价：门槛宽松，若你实际期望「首屏明显变快」的更强指标，A 可能不够激进。

### Q2. 用什么尺子量、尺子锁不锁？

- 证据：仓库无任何基准工具，`[A]` 自动化档没有现成命令；优化型目标若不锁测量脚本，执行 Agent 可能改测量而不是改工件。
- 选项：
  - A) 新增 Node 原生基准脚本 `scripts/bench-summary.mjs`（无新依赖，输出 p50/p95 与是否达标的退出码），写入契约并声明为不可修改。
  - B) 手动 curl 计时步骤（`[C]` 档）——零代码，但可复现性差、无法防作弊。
  - C) 引入第三方压测工具（如 autocannon）——口径更专业，但引入新依赖，与「仓库暂无基准工具」的现状差距大。
- 推荐：A，且锁定（契约声明执行 Agent 不得修改该脚本）。代价：需要先写好这份脚本并随契约交付为 fixture 级产物。

### Q3. 测量口径：采样次数与并发规模？

- 证据：当前实现无共享状态，Node 单进程处理并发请求时三段 sleep 互不阻塞；但「首页接口」上线场景通常有并发访问。
- 选项：
  - A) 串行 30 次采样取 p95（预热 3 次不计入）——最简单稳定，覆盖单请求延迟。
  - B) 并发 10、总 100 次取 p95——同时覆盖并发下的扩展性，更接近首页真实负载，脚本稍复杂。
  - C) 两者都测、都设门槛——最全面，但两个门槛两把尺，维护成本翻倍。
- 推荐：A。代价：不覆盖并发场景；若你关心高并发下的表现，A 测不出退化。

### Q4. 优化手段边界：允许走多远？

- 证据：三段 sleep 模拟的是真实慢查询；直接把 180 改成 10 等于删需求而不是优化。
- 选项：
  - A) 只允许改编排（并行化三段聚合），三段各自的延迟数值不可缩短，不引入缓存——语义最保守，结果可预期（≈180ms）。
  - B) 额外允许缓存（首次仍慢、后续命中缓存变快）——能突破 180ms 下限，但改变数据新鲜度语义，需要另行定义缓存失效规则。
  - C) 不设限，执行 Agent 自行选择手段（含改数值）——最快达标，但「优化」可能退化为作弊。
- 推荐：A。代价：延迟下限被最长一段（180ms）锁死，若门槛选了 C（<100ms）则 A 不可行。
