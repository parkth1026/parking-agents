## 第 1 轮：推荐候选草案 + 8 个独立歧义

> 独立歧义 8 个 > 4，按 SKILL 用编号文本一次全列（不拆轮次）。

### 先给靶子：推荐候选（不是结论，改哪条算哪条）

- **Goal（一句话）**：notes-cli 增加 `search` 子命令，用户给一个关键词就能直接定位到笔记，不用再靠 `list` 翻几百条。
- **In（一句话）**：新增 `search` 子命令，按关键词筛选笔记并用现有列表格式输出。
- **Out（一句话）**：不动 `add` / `list` / `archive` / `delete` 的现有行为，不做全文索引、模糊匹配、排序选项和搜索历史。
- **AC 大致方向**：① 关键词能命中并按 list 格式输出；② 匹配范围与大小写规则明确；③ 归档笔记的处理明确；④ 无命中时的输出与退出码明确；⑤ 现有四个命令行为逐条不变。

### 问题清单

**Q1. 搜索范围：关键词在哪些字段里找？**
证据：笔记有 `title` / `body` / `tags` / `created_at` 四个可读字段；`list` 已经把 tags 整列显示出来了。
- A. 只搜标题
- B. 搜标题 + 正文 ← **推荐**（tags 已在 list 里一眼可扫，纳入搜索会让「为什么这条也算命中」变难解释）
- C. 搜标题 + 正文 + 标签
- D. 搜全部字段（含日期字符串）
代价：B 的代价是想按标签找时得用 `list` 肉眼扫；C 的代价是结果里会出现标题正文都不含关键词的笔记。

**Q2. 匹配方式：怎么算「命中」？**
证据：仓库没有任何现成匹配逻辑，四种都实现得起，差别在用户心智。
- A. 普通子串匹配，不区分大小写 ← **推荐**（记笔记时大小写不稳定，`Deploy` / `deploy` 应当同命中）
- B. 普通子串匹配，区分大小写
- C. 正则匹配
- D. 模糊匹配（容错拼写）
代价：C 的代价是关键词里的 `.` `*` `(` 会变成元字符，普通关键词也可能报错或误命中；D 的代价是命中集不可预测、无法写确定性验收。

**Q3. 已归档笔记搜不搜？**
证据：`list` 已经有 `--all` 语义 —— 默认隐藏归档，`--all` 显示全部。
- A. 默认不搜，加 `--all` 时连归档一起搜 ← **推荐**（与 `list --all` 同义，不增加新心智）
- B. 总是搜（归档也算）
- C. 永远不搜归档
- D. 另起一个 `--archived` 开关只搜归档
代价：A 复用了已有旗标含义，代价是想「只搜归档」得自己在结果里挑。

**Q4. 结果长什么样？**
证据：`list` 的表头与列宽由一处 f-string 渲染，复用它成本最低。
- A. 与 `list` 完全相同的表格 ← **推荐**（改动面最小，输出可预测）
- B. 表格 + 命中处正文片段摘要
- C. 表格 + 关键词高亮（ANSI 颜色）
- D. 只输出命中的 id
代价：A 的代价是看不到命中在正文哪一段，得再开笔记确认；B/C 会引入新的渲染逻辑和终端兼容问题（重定向到文件时 ANSI 码会写进去）。

**Q5. 一条都没搜到时，输出什么、退出码是多少？**
证据：`list` 在库为空时只打印表头、退出码 0；`archive` / `delete` 找不到 id 时 stderr 报错、退出码 1。两种惯例都在，得选一种。
- A. stdout 打印一行 `no notes matched "kubernetes"`，不打印表头，退出码 0 ← **推荐**（「没找到」是正常结果不是错误；退出码 1 留给「操作对象不存在」这类真失败）
- B. 只打印表头、没有数据行，退出码 0（与 `list` 空库一致）
- C. 什么都不打印，退出码 0
- D. stderr 提示 + 退出码 1（与 `archive`/`delete` 一致）
代价：A 的代价是脚本里想用退出码判断有没有命中的话得改判 stdout；D 的代价是 `search` 在 `set -e` 的脚本里会中断流程。

**Q6. 明确排除哪些？**
- A. 模糊匹配、排序选项、搜索历史都不做 ← **推荐**
- B. 要加排序选项（按时间/按 id）
- C. 要加模糊匹配
- D. 要记搜索历史

**Q7. 起草 AC 之前，先出一份对照物吗？**
证据：`search` 是新增子命令，没有现有行为可对照，但它的输出格式与 `list` 强耦合，且「哪条该命中、哪条不该」用文字描述很容易各理解各的。
- A. 出一份 CLI 行为对照表（Markdown）：一份固定示例数据 + 每个场景的具体命令与逐字期望输出，逐行确认 ← **推荐**（确认过的例子行可以直接转成验收用的黄金用例，不用二次发明数据）
- B. 跳过对照物，直接起草 AC（更快，但 AC 只能引用一份没人看过的想象输出）
- C. 出界面 mock HTML（CLI 没有图形界面，价值低）

**Q8. 「怎么算过」：仓库没有任何测试基建，`[A]` 自动化命令这一档默认不可用，怎么验收？**
证据：无 tests / 无 pytest / 无 CI / 无覆盖率工具 / 无依赖声明。
- A. `[B]` 黄金用例：落盘一份固定的示例 `notes.json` + 一份逐字期望输出，跑命令逐字节比对 ← **推荐**（不引入任何依赖，判据是确定的字节，执行 Agent 无法自说自话）
- B. `[C]` 可复现手动步骤：写清命令与预期观察结果，人工执行
- C. `[A]` 引入 pytest + 建测试套件（这个工具目前零依赖，会改变项目性质）
- D. `[D]` 只检查 README / help 文本有没有写 search
代价：A 的代价是要多维护两个 fixture 文件；C 的代价是给一个 109 行的单文件脚本引入测试框架和依赖管理。

### 用户回答（第 1 轮）

- **Q1 → B**：标题和正文都要搜；标签不用搜，标签少，`list` 扫一眼就够了。

- **Q6 → A**：对，不要模糊匹配、不要排序选项、不要搜索历史。
- **Q7 → A**：出对照表。
- **Q8 → A**：接受推荐，用黄金用例，别给这个小脚本装测试框架。
