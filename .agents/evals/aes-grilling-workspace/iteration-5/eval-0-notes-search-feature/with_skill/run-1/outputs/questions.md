## 轮次 1 · 材料歧义批量提问（7 题，一次发全）

### Q1. 搜索以什么形态出现？（决定是否触碰现有 `list` 的行为与兼容性）

已知证据：现有命令都是 argparse 子命令；`list` 已有 `--all`。这一项也决定了本次需不需要「行为对照表」——若改 `list` 就有今昔差异。

- A（推荐）独立子命令 `python notes.py search <关键词>`。代价：多一个子命令名要记；好处是 `list` 一个字符都不用动。
- B 给 `list` 加参数 `list --search <关键词>`。代价：`list` 的公共行为发生变化，需要行为对照表并承担兼容风险。
- C 两者都做（`search` 子命令 + `list --search` 别名）。代价：两套入口，两处都要测。

**用户答：A**。理由：现有 4 个命令的行为一个都不能变。

### Q2. 搜哪些字段？

已知证据：笔记有 `title` / `body` / `tags` 三个文本字段。

- A 只搜标题。代价：记在正文里的命令、链接搜不到。
- B（推荐）标题 + 正文。代价：正文长时命中会略宽。
- C 标题 + 正文 + 标签。代价：标签是枚举式短词，容易出现「搜 work 把所有 work 标签笔记全倒出来」的噪音。
- D 标题 + 正文 + 标签 + ID。代价：ID 已有 `list` 可看，几乎无收益。

**用户答：B**。标签不用搜——标签就那么几个，`list` 扫一眼就行。

### Q3. 匹配方式？

- A（推荐）普通子串匹配，不区分大小写。代价：无法表达「以…开头」这类精确诉求。
- B 普通子串匹配，区分大小写。代价：`Docker` 和 `docker` 要输两次。
- C 正则表达式。代价：能力最强，但语法要记，且元字符会意外生效。
- D 通配符 glob（`*` `?`）。代价：介于两者之间，仍需记规则。

**用户答：A**，并明确：不要正则，觉得复杂、记不住。

### Q4. 已归档的笔记搜不搜？

已知证据：`list` 默认过滤归档，`--all` 纳入全部。

- A（推荐）默认只搜未归档，`search <关键词> --all` 时连归档一起搜（与 `list` 语义一致）。
- B 默认搜全部。代价：归档等于没归档。
- C 默认不搜，另加 `--archived-only`。代价：多一个开关，与 `list` 语义分叉。

**用户答：A**。

### Q5. 结果怎么显示？

- A（推荐）复用 `list` 的表格，列与列宽完全一致。代价：看不到关键词出现在正文哪一段。
- B `list` 表格 + 一列匹配片段摘要。代价：需要定义截断规则，行会变宽。
- C 表格 + 终端高亮关键词。代价：引入 ANSI 转义，重定向到文件时会留下乱码。
- D 只输出命中的 ID。代价：还得再 `list` 一次。

**用户答：A**。和 `list` 一样的表格即可，不需要高亮或摘要。

### Q6. 一条都没搜到时，显示什么、退出码是几？

已知证据：`archive` / `delete` 未找到时是 stderr + 退出码 1；`list` 在空库时只打印表头、退出码 0。

- A（推荐）stdout 只打印表头（形状与 `list` 一致，便于管道处理），stderr 打印一行 `no notes matched: <关键词>`，退出码 **0**。代价：脚本里想用退出码判断「有没有搜到」要改看 stdout 行数。
- B 只打印表头，什么提示都没有，退出码 0。代价：人分不清「没搜到」和「命令没跑对」。
- C 打印提示，退出码 **1**（grep 风格）。代价：与 `list` 的空结果语义不一致；放进 `&&` 链里会中断。
- D 什么都不打印，退出码 0。代价：最安静，也最容易让人以为程序没反应。

**用户答：A**（接受推荐）。用户补充：这一点本来就是他在意的，很高兴被问到——空结果的显示和退出码必须写死在验收里。

### Q7. 明确不做什么？（把 Out 钉死，防止执行 Agent 顺手扩张）

- A（推荐）排除：模糊/近似匹配、排序选项、搜索历史、多关键词布尔组合（AND/OR）、关键词高亮。
- B 保留多关键词 AND。代价：要定义分词与转义规则。
- C 保留按创建时间排序选项。代价：多一个开关与一组测试。

**用户答：A**。原话覆盖：不要模糊匹配、不要排序选项、不要搜索历史。

## 轮次 3 · 验收标准逐条带候选，批量提问（5 题，一次发全）

### Q8. AC-01（匹配规则）判到多严？

- A（推荐）五个侧面全断言：标题命中、正文命中、大小写两种写法结果相同、仅标签存在不命中、正则元字符按字面。代价：用例最多，但每条都对应一个真实误交付。
- B 只断言标题与正文能命中，不测大小写。代价：执行 Agent 用 `in` 直接写就过了，大小写不敏感这条会漏掉。
- C 在 A 基础上再加多关键词组合。代价：与 Q7 的 Out 冲突。

**用户答：A**。

### Q9. AC-02（归档范围）判到多严？

- A（推荐）两条都断言：默认只返回 id 1；`--all` 返回 id 1 与 id 4。代价：无。
- B 只断言默认排除归档。代价：`--all` 可能根本没接上，也能过。

**用户答：A**。

### Q10. AC-03（空结果）判到多严？

- A（推荐）逐字符断言三件事：stdout 只有表头、stderr 文案为 `no notes matched: <关键词>`、退出码 0。代价：以后想改文案要同步改测试。
- B 只断言退出码 0。代价：显示形态完全没被锁住。
- C 断言「有某种提示」但不锁具体措辞。代价：介于两者之间，仍可能变成空白输出。

**用户答：A**。这正是他最在意的一条，要锁死。

### Q11. AC-04（输出格式一致）判到多严？以及黄金用例的数据怎么办？

- A（推荐）`[B]` 黄金用例：落盘输入 `notes_sample.json` + 期望 stdout `expected_search_docker.txt`，逐字节比对。代价：改格式时要同步更新期望文件——这正是想要的阻力。
- B 只断言表头字符串一致。代价：数据行的列宽跑偏也能过。
- C 删掉这条，靠 AC-01 的用例顺带覆盖。代价：格式没有独立负责人。

同批一次问全 `[B]` 档的四件事：

- 数据从哪来？→ 候选：①（推荐）用 mock 里那 4 条合成数据，不涉隐私、覆盖归档与大小写两个边界；②用户导出真实 `notes.json` 脱敏后提供。
- 期望输出以什么为准？→ 候选：①（推荐）以确认版 mock 的状态 1 为准，人工写定；②以首次实现的实际输出为准（有把 bug 固化成期望的风险）。
- fixture 放哪？→ 候选：①（推荐）`fixtures/notes-cli/tests/fixtures/`；②与 `notes.py` 同级。

**用户答：A**；数据用合成的那 4 条（真实笔记不想外泄，且格式验证不需要真实数据）；期望输出以 mock 为准；fixture 放 `tests/fixtures/`。

### Q12. 整体「怎么算过」用哪种验证方式？（升级项：仓库零测试、零 CI，`[A]` 默认档不可直接采用）

已知证据：仓库无 tests/、无 CI 配置、无 lint 配置；环境已装 pytest 9.0.2；`DB_PATH` 硬编码，测试需自行隔离（monkeypatch 模块属性即可）。

- A（推荐）在 `fixtures/notes-cli/tests/` 新增 pytest 用例，`python -m pytest fixtures/notes-cli/tests -q` 退出码 0 作为 `[A]` 档。代价：给这个小工具引入一个开发期依赖，但环境里已经有了。
- B 用标准库 unittest，`python -m unittest discover`。代价：零依赖，但断言写起来啰嗦。
- C 不写测试，AC 全部降为 `[C]` 手动复现步骤。代价：每次改动都要人肉重跑 6 个状态，回归靠自觉。
- D 用户提供真实 `notes.json` 做端到端黄金用例。代价：涉隐私，且真实数据对格式验证没有额外代表性。

**用户答：A**。附带确认：pytest 只作开发期测试依赖，运行时仍然只用标准库。
