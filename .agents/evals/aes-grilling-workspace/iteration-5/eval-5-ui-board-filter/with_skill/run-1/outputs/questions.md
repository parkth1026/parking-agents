## 轮次 1：批量问清歧义（先给候选靶子，再一次问 4 题）

### 先给出的推荐候选（供用户挑毛病，不是结论）

- Goal（一句话）：看板顶部可以选一个负责人，三列只显示他的卡片；筛选状态跟着 URL 走，刷新和分享链接都能还原。
- In：单选负责人筛选控件 + 筛选渲染 + URL 同步/还原 + 清空筛选。
- Out：多选负责人、按状态或标签筛选、卡片详情改动、服务端 `/api/tasks` 改动。
- AC 方向：控件与过滤结果、下拉选项来源、URL 还原（刷新 + 分享）、清除筛选、无匹配时的呈现。

用户对候选的回应：

> 方向对。补充三条边界：不需要多选负责人，不需要按状态或标签筛选，不改卡片详情。动机是卡片一多每个人只想看自己负责的，现在只能肉眼扫。刷新后筛选要还在，链接发给同事对方看到的也要是同样的筛选结果。

（→ Out 三条按用户原话收进 Scope；Intent 与 Outcome 得到确认。）

### 问题（4 个互不依赖的歧义，用 AskUserQuestion 一次发全）

**Q1. 筛选状态存在哪里？**
已知证据：纯静态前端，无路由库；用户要求「刷新还在 + 链接可分享」。
- A（推荐）：写进 URL 查询参数（如 `?assignee=ayan`）。刷新与分享都满足；代价是筛选值会暴露在链接里、需要处理进入页面时的解析。
- B：`localStorage`。刷新能还原，但**链接分享不成立**——同事打开看到的是他自己的上次筛选。
- C：URL + localStorage 双写。两者都有，但两个真相源会冲突（带参链接与本地记录不一致时以谁为准），复杂度不划算。

> **用户答：A。**「刷新要还在，发链接给同事对方看到一样的」这两条正是我要的。

**Q2. 过滤在前端做还是后端做？**
已知证据：`/api/tasks` 目前无查询参数，返回全量 4 条；数据量小。
- A（推荐）：纯前端过滤，`/api/tasks` 一字不改。契约不变、无兼容风险；数据量大后才需要重新考虑。
- B：后端加 `?assignee=` 过滤。改变了公共接口行为，本次没有性能理由。
- C：两边都做。最贵，且要维护两套等价语义。

> **用户答：A（未覆盖 → 按推荐）。**

**Q3. 下拉里的负责人名单从哪来、怎么显示？**
已知证据：仓库里没有人员名单，也没有 assignee → 显示名的映射，卡片上直接显示 `ayan` 这样的短名。
- A（推荐）：从当前 `/api/tasks` 数据里提取 assignee 去重生成，加一个默认项「全部负责人」；显示原始短名，与卡片上一致。数据变了下拉自动跟着变。
- B：在前端写死名单。数据里新增负责人时下拉会漏人。
- C：新增 `/api/assignees` 接口。要动服务端，与 Q2 的选择相悖。

> **用户答：A（未覆盖 → 按推荐）。**

**Q4. 链接里的负责人在数据里不存在时（例如同事改了参数、或那人任务被删光）怎么办？**
已知证据：现有数据每个负责人都至少有一张卡，「筛选后一张卡都没有」只会由这种情况触发。
- A（推荐）：保留该筛选值，看板呈现为空。链接语义不被静默改写；「空」的具体呈现留到 mock 阶段一起对齐。
- B：回退成「全部负责人」。用户会以为筛选没生效，且分享出去的链接被悄悄换了意思。
- C：弹错误提示。对一次筛选来说过重。

> **用户答：A（未覆盖 → 按推荐）。**

## 轮次 4：验收标准逐条带候选，一次发全（第 4 步 4b）

先做 4a 的例子收集：例子直接取自确认版 mock 的关键状态与交互，不重新问一遍。
S1 默认全量 / S2 选中 ayan 后的三列 / 下拉选项来源 / 地址栏参数写入 / 刷新与新窗口还原 / 清除筛选 / S3 空态。

聚类为 5 条（一个簇一条）。AC-01 与 AC-02 拆开的理由：一个判「过滤结果」，一个判「选项名单怎么来」，例子彼此不像。
不再单独立一条「整体与 mock 一致」的结构对照 AC —— 逐点 AC 已覆盖，再立一条是同一件事判两遍。

分流说明（同时告知用户，避免它们混进 AC 编号）：`npm test` 退出码 0 属于所有任务共享的质量门 → Completion 的 Quality 一行；「`/api/tasks` 报文不变」「无筛选时看板与现状一致」「不引入依赖」属于必须保持的现有行为 → Constraints。

Verify 档位说明：`docs/testing.md` 明确页面改动靠本地人工浏览器验证、且无截图对比/视觉回归工具，因此五条一律 `[C]`（可复现步骤 → 可观察结果），并引用确认版 mock 路径。用户对验收方式的表态是「跟着仓库测试约定走，你推荐什么就是什么」，与默认档一致，不构成升级条件（无数字门槛、无真实数据依赖、基建判据无歧义）。

以下五条一次全列（超过 4 条，按 SKILL 改用编号文本，并告知可以一次回复完，例如「1 选 B，删 5，其余按推荐」）：

**1. AC-01 判定口径：选中负责人后三列怎么算对？**
- A（推荐）：三列只保留该负责人的卡片，列结构与列标题保持不变（某列为空也仍在）。代价：需要显式验证「空列不塌」。
- B：只判卡片数量对，不管列结构。可能出现某列被整个隐藏也算过。
- C：连卡片排序也一并锁死。现状渲染顺序本就跟随接口顺序，锁死会额外约束实现。

**2. AC-02 判定口径：下拉选项名单？**
- A（推荐）：「全部负责人」+ 数据中出现过的 assignee 去重；并验证数据新增负责人时下拉自动跟随。代价：验证要临时改一次 `src/server.mjs` 再还原。
- B：只验证当前四个选项存在，不验证「跟随数据」。写死名单也能蒙混过关。
- C：额外要求选项按字母序。现在没人提这个需求。

**3. AC-03 判定口径：URL 还原判到多严？**
- A（推荐）：地址栏出现 `?assignee=` 参数；F5 刷新与新开无痕窗口粘贴同一 URL 两种途径都还原（下拉回显 + 卡片结果）。代价：要跑两次验证动作。
- B：只验刷新。分享链接这条就没被真验过（正是本次动机之一）。
- C：额外要求浏览器前进/后退按钮也能逐步回退筛选历史。范围变大，用户没提。

**4. AC-04 判定口径：清除筛选？**
- A（推荐）：点击后卡片回到全部、URL 参数被移除、按钮随之消失（三项一起判）。
- B：只判卡片回到全部，不管 URL。会留下一个「显示全部但链接仍带筛选」的不一致状态。
- C：删掉这条，并进 AC-01。两个不同交互挤一条，验证时容易被整体点头放过。

**5. AC-05 判定口径：无匹配空态？**
- A（推荐）：显示「没有匹配的任务」，且筛选值保留不被改写（与轮次 1 Q4 的选择一致）。
- B：只判文案出现，不管筛选值是否被改写。与 Q4 的决定脱钩。
- C：删掉这条。空态是用户在 mock 阶段明确提的第 3 条意见，删掉等于把它交给运气。

> **用户答：全部按推荐（A / A / A / A / A）。**「验收方式跟着仓库测试约定走，你推荐什么就是什么。」

AC 定稿，五条，Verify 全部 `[C]`。
