## 轮次 1：批量问清歧义（7 个独立歧义，超过 4 个，故用编号文本一次全列）

### 先给出的推荐候选（靶子，不是结论）

- Goal（一句话）：看板顶栏可以选一位负责人，只显示该负责人的卡片，筛选状态跟着 URL 走，刷新与分享链接都能还原。
- In（一句话）：负责人单选筛选控件 + 筛选后的卡片渲染 + 筛选状态写入并还原 URL 查询参数。
- Out（一句话）：多选负责人、按状态/标签筛选、卡片详情改动、后端筛选接口与登录态偏好存储。
- AC 大致方向：控件存在且选项正确 / 选中后只剩该负责人卡片 / 清空回到全部 / 刷新与分享链接还原 / 无匹配时有明确空态 / 筛选逻辑有 `npm test` 断言 / 界面与确认版 mock 结构一致。

### 提问与回答

**Q1. 筛选状态怎么持久化、怎么分享？**
证据：页面当前不读任何 URL 参数，也没有 localStorage。
- A. 写进 URL 查询参数（如 `?assignee=ayan`）——刷新保持，链接可分享（**推荐**）
- B. 存 localStorage——刷新保持，但链接分享不出去
- C. 两者都做——同一份状态两个来源，冲突时要额外定优先级规则
- D. 不持久化，刷新即回到全部
代价：A 需要在页面加载时解析 URL 并在切换时更新地址栏；B 做不到「发链接给同事」。
**用户答：A。**（用户原话意思：刷新后筛选要还在；把链接发给同事，对方打开看到的也是同样的筛选结果。）

**Q2. 单选还是多选负责人？**
- A. 单选，另有「全部」（**推荐**，与 Q1 的 URL 单值最省事）
- B. 多选（复选框，URL 里多值）
代价：B 会牵出「多选时空态、清除、URL 编码」一整套额外规则。
**用户答：A，明确不需要多选。**

**Q3. 筛选在前端做，还是给 `/api/tasks` 加参数在后端做？**
证据：`/api/tasks` 目前一次性返回全部 4 条，没有任何查询参数。
- A. 纯前端过滤，接口不动（**推荐**，数据量小、接口契约零风险）
- B. 后端加 `?assignee=` 参数
- C. 两边都支持
代价：B/C 改动公共接口契约，且前端仍要自己维护 URL 状态，收益为零。
**用户答：A（选推荐项）。**

**Q4. 筛选后三列怎么呈现？空列要不要收起？**
- A. 三列结构始终保留，空列只是没有卡片（**推荐**，位置稳定，不会因为筛选让人找不到列）
- B. 隐藏没有卡片的列
- C. 隐藏空列并把剩余列拉宽
**用户答：A（选推荐项）。**

**Q5. 下拉里的负责人名单从哪来？**
证据：负责人是任务数据里的字符串（`ayan`/`bo`/`chen`），仓库没有成员名单或用户表。
- A. 从当前任务数据里动态提取去重（**推荐**，数据变了不用改代码）
- B. 在前端写死名单
- C. 新增一个成员接口
代价：B 会随数据漂移；C 属于新建后端能力，明显超出本次范围。
**用户答：A（选推荐项）。**

**Q6. URL 里的负责人当前没有任何任务（例如手改成 `?assignee=dora`）时怎么办？**
- A. 照常筛选，结果为空并显示空态文案（**推荐**，行为一致、可预期）
- B. 静默回退到「全部」
- C. 回退到「全部」并弹提示
代价：B 会让分享链接静默变成另一种结果，反而更难解释。
**用户答：A（选推荐项）。**

**Q7. 卡片和下拉里显示负责人的什么？**
证据：数据里只有 `ayan` 这类小写标识，没有中文名或头像。
- A. 直接显示 `assignee` 原值，显示名映射列入 Out（**推荐**）
- B. 本次加一份标识到中文名的映射
**用户答：A（选推荐项）。**

用户另外主动补充的边界：不改卡片详情；不需要按状态或标签筛选；验收方式跟仓库测试约定走，「你推荐什么就是什么」。
