**1. 上报链路长什么样（`src/receiver.mjs`）**

一次 POST `/v1/events` 的处理顺序是：

1. 读 `X-App-Id` 头，`src/auth.mjs` 里没登记的 app 直接 401；
2. 解析 body，单个事件或事件数组都接（`Array.isArray(parsed) ? parsed : [parsed]`）；
3. 逐个过 `validateEvent`，好的进 `accepted`（并被服务端覆写 `app` 字段），坏的进 `rejected`；
4. `accepted` 非空时**同一个数组**同时喂给两个消费者：`store.write(accepted)` 落盘、`forwarder.add(accepted)` 攒批转发；
5. 响应：有 rejected 就 207，否则 202，body 是 `{"accepted": <数字>, "rejected": [...]}`。

关键点：磁盘和下游吃的是**同一份 accepted 数组**，代码里现在没有任何地方把这两条路分开。你说的「磁盘和下游都吃不住」在代码里是两个消费者，但只有一个数据源。

**2. 磁盘那一头（`src/storage.mjs`、`docs/schema.md`、`docs/runbook.md`）**

- 落盘是 `data/events.ndjson`，一行一个事件 JSON，超过 `storage.rotateBytes` 就 rename 成 `.1`；
- default 配置 `rotateBytes` 是 67108864（64MB），production 是 268435456（256MB）；
- `docs/schema.md` 和 `storage.mjs` 的注释都写了「有从这些文件回捞的工具，文件名和一行一个 JSON 的格式不要随便改」，那个工具是 `scripts/replay.mjs`；
- `scripts/replay.mjs` 从 ndjson 读回事件，逐条 `forwarder.add()` 再 flush，用途是「下游出故障丢批之后用它补数」；
- `docs/runbook.md`：`data/` 下的 ndjson 由 infra 侧定时任务搬走并清理，本服务只管写。

**3. 下游那一头（`src/forwarder.mjs`、`docs/schema.md`）**

- 攒批，批满 `forward.batchSize` 或到 `forward.flushMs` 就发；
- default 是 batchSize 200 / flushMs 2000 / maxRetries 3，production 是 500 / 1000 / 5；
- POST body 形状固定 `{"events": [...]}`，`forwarder.mjs` 注释和 `docs/schema.md` 都写明「下游只认这一种形状，改它要跟下游同步发版」；
- 重试到上限后**丢批**并 `forward_failures_total += 1`。

**4. 已登记的上报方（`src/auth.mjs`，8 个）**

`android-app`、`billing-worker`、`crm-sync`、`ios-app`、`loadtest-runner`、`loadtest-soak`、`web-admin`、`web-portal`。注释：新增业务方走发版，不走配置。

这里我要指出一件我看到但不敢替你判断的事：这 8 个里面，`crm-sync` 和 `billing-worker` 看名字像业务链路（同步、计费），`loadtest-runner` 和 `loadtest-soak` 看名字像压测流量。一刀切的全局采样会把这四类一视同仁地削。名字只是名字，实际是什么得你说。

**5. 配置怎么下发（`src/config.mjs`、`docs/runbook.md`）**

这条对「采样比例怎么调」影响很大：

- `config.mjs` 注释原文：「配置文件是部署时渲染出来的，进程只读一次，不监听变更。想改配置要重新部署，不能热更新。」代码里 `cached` 一旦有值就直接返回；
- `docs/runbook.md` 原文：这个仓库里的 `config/*.json` **只是样例与本地开发用**，线上实际生效的配置是 infra 仓库的模板渲染后投放到容器里的，**模板不在这个仓库，改配置项要同时改那边**；

也就是说：如果采样比例只走 `config/*.json`，那么线上调一次比例 = 改 infra 仓库模板 + 一次滚动发布，而且滚动期间会有一段时间新旧比例并存。
