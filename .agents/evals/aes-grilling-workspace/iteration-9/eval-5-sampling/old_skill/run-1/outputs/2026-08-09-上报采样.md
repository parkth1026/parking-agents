# Goal Contract: 给上报链路加服务端采样与压测流量丢弃，同时保住运营日报的口径连续

- Status: Ready
- Target: metrics-relay（`src/receiver.mjs`、`src/config.mjs`、`src/metrics.mjs`、`config/*.json`）
- Updated: 2026-08-09

## 原始请求

> 上报量涨太快了，磁盘和下游都吃不住。给上报加个采样吧。先别写代码，帮我理清需求、写份 goal contract。

访谈过程中用户补充的：上报量三个月涨了六倍；`loadtest-runner` 与 `loadtest-soak` 是压测流量、占总量四成左右，这部分应该整个丢掉而不是采样；运营的每日事件量日报是从 `/metrics` 抓 `events_total` 出数的，抓取配置在 infra 仓库；下游有转化漏斗分析，按单条事件独立随机丢会打断同一用户的行为链；`purchase` 一条都不能丢；采样率默认值必须是 1.0；README 里 `X-Sample-Rate` 那节要整节删除。

## 目标

给 `/v1/events` 的上报链路加入服务端采样与压测流量丢弃，在运营日报口径连续、关键事件零丢失、缺配置时默认不采样这三个前提下，把落盘与下游转发的事件量降到可承受范围。

## Why

- 上报量三个月涨六倍，`data/events.ndjson` 的磁盘增速和下游 `analytics-ingest` 的吞吐都已经吃不住；`src/forwarder.mjs` 重试到 `maxRetries` 上限就丢批，下游压力大时数据是真丢。
- 涨量里约四成来自 `loadtest-runner` / `loadtest-soak` 两个压测上报方，这部分数据进落盘和进下游本身就是错的，一直没治。
- 现有链路里 `store.write(accepted)` 和 `forwarder.add(accepted)` 吃的是同一个数组，没有任何削量手段；唯一一处叫「采样」的东西是 README 里 1.x 遗留的 `X-Sample-Rate` 文档，代码里早已不存在。
- 做到之后：磁盘与下游同时降量、压测流量不再污染数据、关键业务事件仍然全量、运营日报数字不断档。

## 范围

**做什么**

1. 在 `src/receiver.mjs` 里校验通过之后、`store.write` 与 `forwarder.add` 之前插入采样判定；被采样掉的事件既不落盘也不转发（一次判定，两条路同削）。
2. 按 app 配采样率；未出现在配置里的 app 一律按默认值 1.0 全留。
3. 采样选键三级降级：有 `user_id` 按 `user_id` 一致性哈希；无 `user_id` 有 `session_id` 按 `session_id` 哈希；两者都无退化为独立随机，且随机源可注入。
4. 丢弃名单：名单里的 app（本次为两个 loadtest 上报方）事件整段丢弃，校验照跑，状态码与响应体与今天完全一致。
5. 事件名白名单：白名单里的事件名 100% 保留、不参与采样；丢弃名单优先于白名单。
6. `/metrics` 口径调整：`events_total` 改为数「校验通过进来的条数」（丢弃名单命中的不计入），新增被采样掉、被主动丢弃、走随机退化路径三个计数器；`events_by_app` 保持实收落盘条数。
7. 采样配置的启动时校验：非法值直接拒绝启动。

**不做什么**

- 不复活 `X-Sample-Rate` 请求头，采样率不受任何请求头影响；传了不报错也不生效。
- 不做运行时热改采样率，不加管理接口，不加 SIGHUP 重载配置。
- 不做限流、不做背压。
- 不改 401 鉴权逻辑，不改 `src/auth.mjs` 的登记名单。
- 不改转发给下游的 body 形状、不改 ndjson 落盘格式与文件名、不改 `storage.rotateBytes` 滚动策略、不改转发的重试与退避逻辑。
- 不做按 `props` 内容或其它事件内容的条件采样。
- 不给 `scripts/replay.mjs` 加任何采样或丢弃行为。
- 不引入任何第三方依赖。
- **不删 README 里「单请求控制采样」那一节**：它是本次访谈里唯一能独立交付的一条，用户决定另开一份契约、由他自己完成，本契约不承载它。
- **不做量级效果的门槛验证**（磁盘增速降到多少、下游 QPS 降到多少）：仓库没有任何基准或压测脚本，建一套约需 2 至 3 个工作日；用户明确不要，上线后由他自己看 `storage_bytes_total` 增速和下游曲线判断。

## 强约束

**必须保持的现有可观察行为**

1. 未登记 app 仍返回 401 与 `{"error":"unknown app id"}`；采样判定发生在鉴权之后。
2. body 不是合法 JSON 仍返回 400 与 `{"error":"body is not valid json"}`。
3. 202 与 207 的判定条件不变，只看 `rejected` 是否非空；采样掉与丢弃都不影响状态码，不允许因为采样出现 207。
4. `/v1/events` 响应体形状不变，仍为 `{"accepted":N,"rejected":[{"index":I,"errors":[...]}]}`，不新增字段；`accepted` 仍是「校验通过的条数」而不是「最终留下的条数」。
5. `rejected` 只装校验失败的事件；被采样掉的与被丢弃的一律不进 `rejected`，`events_rejected_total` 口径不变。
6. 服务端仍以 `X-App-Id` 覆写事件的 `app` 字段。
7. 转发给下游的 body 固定为 `{"events":[...]}`，事件对象里不新增任何采样相关字段。下游发版不与本服务同步，这一条不许破。
8. 落盘仍是 `data/events.ndjson`、一行一个 JSON、`.1` 滚动命名。`scripts/replay.mjs` 和 infra 的搬运任务都依赖它。
9. `storage_bytes_total`、`forward_batches_total`、`forward_failures_total` 口径不变；`batchSize`、`flushMs`、`maxRetries`、`50 * attempt` 退避全不动。
10. 计数器仍是进程内的、重启归零；`/metrics` 仍是纯文本，infra 侧抓取配置不需要改动。
11. 配置仍然只读一次、不监听变更。
12. `scripts/replay.mjs` 行为不变：它读到的 ndjson 已经是采样后的结果，原样重放，不做第二次采样也不做丢弃判定。这条同时意味着采样逻辑不许放进 `src/forwarder.mjs`，否则 replay 会被二次采样。

**本次访谈定死的实现约束**

13. 必须走「按 app 配采样率 + 独立丢弃名单」，不引入用采样率 0 表达完全丢弃的做法：补偿逻辑里不允许出现除以采样率。
14. 必须走「`user_id` → `session_id` → 独立随机」三级选键的一致性哈希，不引入逐条独立随机作为主路径。
15. 哈希函数必须是纯函数且不含进程级随机性（不许用 `Math.random` 参与选键、不许依赖对象迭代顺序）；同一个键在同一采样率下的去留必须跨进程、跨重启稳定。哈希算法本身归执行 Agent 选，只能用 Node 内建模块。
16. 采样率的默认值必须是 1.0（默认不采样）。理由是滚动发布期间新老配置文件共存，老模板里没有这个配置节，那一刻代码里的默认值就是实际生效值；默认值若小于 1.0，灰度开始那一刻未拿到新模板的机器会立刻开始丢数据。这条不许为任何理由放宽。
17. 采样配置含非法值时必须拒绝启动（抛错、非零退出），不许退回默认值继续跑、不许钳位、不许隐式类型转换。`0` 与 `1` 都是合法采样率，不许判为非法。
18. 丢弃名单优先于事件名白名单：命中丢弃名单的 app，其白名单事件也一并丢弃。
19. `events_total` 必须由「留下条数 + 被采样掉条数」直接相加得出，不许用 1/采样率 折算；被丢弃名单丢掉的条数不计入 `events_total`。
20. `events_by_app` 必须保持实收落盘条数，不做任何补偿；被丢弃名单命中的 app 不允许在 `/metrics` 输出里出现对应的 `events_by_app` 行（是不出现，不是值为 0）。
21. 零依赖：采样与哈希只用 Node 内建模块。
22. 「行为对照表 v2」（本文件「访谈记录」一节内）是确认版对照物，声明为不可修改。执行 Agent 改的是产品，不是对照表。

## 验收条件

- AC-001: 采样按「`user_id` → `session_id` → 独立随机」三级选键；同一个键的全部事件同去同留；同一个键在同一采样率下的去留在重复调用与重建实例后完全一致。
  - Verify: [A] `node test/run-tests.mjs sample` → 退出码 0；用例须覆盖同一 `user_id` 多条全留与全丢两个分支、无 `user_id` 有 `session_id` 时按 `session_id` 判、两者皆无时按注入的固定随机序列判、以及同一键重复判定结果相同。
- AC-002: 事件名白名单里的事件在任意采样率与任意哈希结果下都被保留；命中丢弃名单的 app 其白名单事件仍被丢弃。
  - Verify: [A] `node test/run-tests.mjs sample` → 退出码 0；用例须构造一个哈希未命中的 `user_id` 发送 `page_view` 加 `purchase`，断言只有 `purchase` 进入落盘与转发，并另有一例断言丢弃名单命中时 `purchase` 也不落盘不转发。
- AC-003: 丢弃名单命中的 app，其校验通过的事件既不落盘也不转发，但校验照跑、状态码与响应体与今天完全一致，且 `/metrics` 里不出现该 app 的 `events_by_app` 行。
  - Verify: [A] `node test/run-tests.mjs receiver` → 退出码 0；用例须覆盖纯合法批（断言落盘与转发均为 0 条、状态码 202、响应体 `{"accepted":4,"rejected":[]}`、`events_by_app` 不含该 app 键）与含一条缺 `ts` 的混合批（断言状态码 207、`rejected` 含该条、`events_rejected_total` 为 1、好的两条被丢）。
- AC-004: `/metrics` 的口径变化不影响运营日报的连续性——`events_total` 在采样上线前后对同一批真实进入的流量给出同一个数（丢弃名单命中的压测流量除外，它不计入），同时能从 `/metrics` 分别读出实收、被采样掉、被主动丢弃、走随机退化路径这四个量。
  - Verify: [A] `node test/run-tests.mjs metrics` → 退出码 0；用例须复现对照表第 13 行场景（某 app 进 100 条留 20 条、压测 app 进 40 条）并断言 `render()` 的整段输出文本逐字等于期望值，其中包含 `events_total 100`、实收 20、采样掉 80、丢弃 40、随机退化路径计数，且整段文本中不含任何压测 app 的 `events_by_app` 行。
- AC-005: 配置里没有采样节、或某个 app 未配采样率时，该 app 的落盘内容、转发内容、响应与计数与采样上线前一致，一条事件都不丢。
  - Verify: [A] `npm test` → 退出码 0；须新增一例传入完全不含采样节的配置并断言全部事件落盘转发且内容与不带采样时深相等，另一例传入含 app 映射但不含 `crm-sync` 的配置并断言 `crm-sync` 全留；同时现有 19 个用例不得因本次改动而需要修改。
- AC-006: 采样配置含非法值时进程启动失败并以非零码退出，stderr 指明是哪个 app 的哪个值不合法；`0` 与 `1` 作为采样率不被判为非法。
  - Verify: [A] `node test/run-tests.mjs config` → 退出码 0；用例须逐类断言 `1.5`、`-0.1`、字符串 `"0.2"`、`null`、以及丢弃名单不是字符串数组这几种情况各自抛错且错误信息包含出问题的 app 名，并另有用例断言 `0`、`0.2`、`1` 三个值不抛错。

## 挡着的事

- None. 六条验收条件全部落在仓库现成的 `npm test` 上，不需要用户提供真实数据、不需要 infra 仓库配合、不需要新建任何验证基建。用户自行安排的预发压测与预发 `/metrics` 曲线对比按他的明确要求不写进契约，因此不构成阻塞。

## 设计取舍

### D-1 采样点放在落盘与转发的分叉之前

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| 只削转发，磁盘全量 | `store.write` 拿全量，`forwarder.add` 拿采样后的 | 用户原话的「磁盘吃不住」完全没解决；且 `scripts/replay.mjs` 会变成危险工具，要么被二次采样、要么把全量灌给下游 | 只解决一半问题，还引入 replay 的新失败模式 |
| 只削落盘，下游全量 | ndjson 写采样后的，下游收全量 | 「下游吃不住」没解决；replay 只能捞到采样后的数据，基本失去意义 | 同样只解决一半 |
| 两段各自配比例 | 落盘与转发两个独立采样率 | 配置项翻倍；两边留下的不是同一批事件，「盘里有下游没有」变成常态，每次排查都要先确认是采样还是丢批 | 运维心智成本高于收益，且用户此刻并无「两边要不同比例」的真实需求 |
| 分叉之前同削（选定） | 一次判定，采样掉的既不落盘也不转发 | `scripts/replay.mjs` 的补数能力降级——下游丢批时只能补回采样后留下的那部分；采样率配错时损失不可逆，无本地兜底 | 无 |

选定分叉前同削。取舍在于：磁盘与下游是两个消费者但只有一个数据源，在源头削一次能同时解决两个问题并保证盘与下游内容永远一致，代价是牺牲 replay 对被采样数据的补数能力。而 replay 的设计用途是「下游故障丢批后补数」，补的是下游收不到的部分，采样掉的数据本来就不打算给下游，所以这个牺牲与它的用途并不冲突。配错的不可逆风险改由 D-5 的启动时校验承担。

落进契约的形态：`范围` 写「校验通过之后、落盘与转发之前插入采样判定」；`强约束` 第 12 条写「采样逻辑不许放进 `src/forwarder.mjs`，否则 replay 会被二次采样」。

### D-2 按 app 配采样率，压测流量走独立丢弃名单

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| 全局一个采样率 | 一个标量对所有 app 生效 | `crm-sync`、`billing-worker` 这类量小但业务关键的上报方被无意义削掉，收益接近零风险实打实；真正吵的 app 要降到 0.05 才够，意味着所有人都被降到 0.05 | 与 runbook 自己的运维经验相反：量的问题是按 app 分布不均的问题 |
| 用采样率 0 表达完全丢弃 | 压测 app 配 0 | 与计数补偿打架（1 除以 0）；「采 0%」与「不要」在配置上无法区分，真实业务方被误配成 0 时没有任何信号 | 把一个丢弃语义藏进采样语义里，特例分支等于把丢弃逻辑埋在采样内部 |
| 从登记名单删掉压测 app 走 401 | 改 `src/auth.mjs` | 压测从此压不动这个服务，连解析路径都进不去；runbook 里「大量 401」这条故障判据失效 | 用户明确否决：「我不动 401 鉴权那块，压测得能压得动」 |
| 解析 body 之前就丢 | 命中名单立刻返回 202 | 压测测到的是一条空路径，压测数据不再说明服务真实处理能力；校验也跳过，压测数据本身格式坏了发现不了 | 省下的 CPU 换掉了压测的意义 |
| 按 app 配采样率加独立丢弃名单（选定） | 两个独立配置概念，丢弃名单优先 | 多一个配置项与一个新概念，运维要理解两者的先后关系；响应仍返回 202 意味着代码里存在「告诉对方收下了但其实扔了」的路径，需要注释解释 | 无 |

选定按 app 配加独立丢弃名单。取舍在于：采样与丢弃是两件不同的事（一个是按比例抽，一个是完全不要），把它们表达成两个概念的代价是多一个配置项，把它们挤进一个概念的代价是除零特例加语义歧义加配置误写无法识别。前者的代价是一次性的理解成本，后者是长期的正确性风险。

落进契约的形态：`强约束` 第 13 条写「必须走按 app 配采样率加独立丢弃名单，不引入用采样率 0 表达完全丢弃的做法」，第 18 条写丢弃名单优先于白名单。

### D-3 一致性哈希三级选键，另设事件名白名单

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| 逐条独立随机 | `Math.random()` 小于采样率就留 | 漏斗与会话分析在下游直接失真且失真是静默的；测试只能写统计断言，会偶发失败让 CI 不可信 | 用户的下游有转化漏斗分析，这条直接不可接受 |
| 按 `session_id` 哈希 | 以会话为键 | 跨会话分析（留存、回访）失真；`session_id` 缺失面可能比 `user_id` 更大 | 用户要的是用户级完整性，会话级不够 |
| 按 `user_id` 哈希、缺则全留 | 无 `user_id` 的事件一律保留 | 若噪音大头恰好不带 `user_id`（压测流量很可能不带），采样对它完全无效，磁盘继续涨，而这个风险上线后才发现 | 留下一个上线才暴露的失效路径 |
| 按事件名配独立采样率替代白名单 | 两级采样率相乘或取最大 | 合成规则是纯复杂度来源；一条事件的有效采样率变成两个数的函数，补偿系数跟着变，测试组合数翻倍 | 用户此刻没有「某类事件采 50%」的真实需求 |
| 三级选键加布尔白名单（选定） | `user_id` → `session_id` → 独立随机；白名单事件 100% 保留 | 系统里有两套采样语义（哈希与随机），文档与测试都要覆盖两条；白名单事件全量而前置事件采样，下游算转化率会虚高，需要有人告知下游 | 无 |

选定三级选键加白名单。取舍在于：一致性哈希保住的是「留下来的用户行为链完整」，白名单保住的是「关键事件一条不丢」，这两个目标在数据口径上是冲突的（白名单会让转化率虚高）。用户在明知冲突的前提下选择两个都要，并承担与下游沟通的责任（他的原话是「转化率虚高这件事我知道，下游那边我去说」）。这个冲突是有意接受的，不是遗漏。

落进契约的形态：`强约束` 第 14、15 条写选键策略与哈希稳定性要求，第 18 条写丢弃名单优先于白名单。

### D-4 `events_total` 改为数进来的条数，`events_by_app` 保持实收

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| `events_total` 保持实收，另加估算指标 | 指标名各司其职 | 运营日报抓的是 `events_total`，数字仍会一夜掉九成，除非同步改 infra 仓库的抓取配置——另一个仓库、另一次发布、非原子 | 用户明确否决，跨部门事故风险 |
| 乘 1 除以采样率折算 | 每留一条按采样率折算加进 `events_total` | 一致性哈希下实际留量不精确等于采样率，小流量 app 的估算值会明显失真；丢弃名单场景要处理除零 | 有更准且更简单的办法 |
| 滑动窗口动态校准系数 | 进程内维护窗口统计 | `events_total` 变成不确定值，测试写不出精确断言；为一个日报数字引入运行时状态机 | 复杂度与收益严重不匹配 |
| `events_by_app` 也做补偿 | 两个量指标口径统一为估算 | `events_by_app` 不再反映真实磁盘压力，而磁盘吃不住正是本次出发点；runbook 里「看 `events_by_app` 定位磁盘涨」这条用惯了的排查动作要换掉 | 用户否决：「这条我天天在用，不能给我换掉」 |
| 直接数进来的条数，`events_by_app` 保持实收（选定） | `events_total` 等于留下加采样掉，不做除法 | `events_total` 与 `events_by_app` 之和不相等，是必然会被问到的怪现象，runbook 必须写清两者口径不同；`countAccepted` 签名要改 | 无 |

选定直接相加。取舍在于：日报要的是「进来多少」的连续曲线，排查磁盘要的是「盘上写了多少」的真值，这是两个不同的量，硬塞进同一个指标必然牺牲一个。分开成两个口径的代价是它们加起来对不上，收益是两个用途都拿到精确值、没有估算误差、没有除零、且 infra 侧抓取配置一行不用改。

落进契约的形态：`强约束` 第 19、20 条写 `events_total` 的算法与 `events_by_app` 的实收口径，以及被丢弃 app 不出现在输出里。

### D-5 配置走 `config/*.json`，非法值拒绝启动，缺失退默认 1.0

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| 环境变量覆盖 | 读环境变量优先于配置文件 | 直接撞 `scripts/lint.mjs` 的规则，改规则等于推翻仓库一条写明了理由的约定；配置来源变两处 | 为省一步改模板推翻既有约定，不划算 |
| 运行时管理接口改比例 | 新增写操作 HTTP 接口 | 引入本仓库完全不存在的写接口：鉴权（`auth.mjs` 无管理员概念）、审计、多机一致性全是新问题；重启后回落配置值，「现在生效的是哪个」要查日志 | 为一个配置项引入一整套新攻击面 |
| config 加 SIGHUP 重载 | 收到信号清缓存重读 | `loadConfig()` 从不变量变成可变量，`config.test.mjs` 断言的同一性失效；`forwarder`、`storage` 在启动时各拿一次 cfg 就一直用，重载全部配置是更大的工程 | 只为采样率开一个信号可行但收益有限，且 infra 侧要多一个人工步骤 |
| 非法值退默认 1.0 继续跑 | 校验失败当未配置 | 错误可能长期无人发现，表现是「采样没生效、磁盘继续涨」，而这恰是当前症状，会被误判为方案无效 | 静默失败与当前症状同形，无法区分 |
| 非法值钳到合法区间 | 负数当 0、大于 1 当 1、字符串尝试转数字 | 负数当 0 意味着该 app 数据全丢，把明显的配置错误变成静默的全量数据丢失 | 钳位里最危险的一种正好最容易发生 |
| 不做任何校验 | 保持 `deepMerge` 现状 | 采样率配错是不可逆删数据，与 `batchSize` 配错不在一个量级 | 拿「其它配置项也没校验」类比，忽略了这是唯一会永久删数据的配置项 |
| config 加启动时校验、缺失退 1.0（选定） | 与现有配置节同构下发；缺失用 1.0；非法抛错拒启动 | 配错采样率到发现再到改回是一整个发布周期；滚动期间新旧比例并存，那段数据是两个比例的混合，事后分析要额外解释；一个配置错误会让服务起不来 | 无 |

选定 config 加启动时校验，缺失退 1.0。取舍在于两种失败要用相反的策略处理：**缺失是宽容的**（老模板没有这个配置节是滚动发布的正常状态，必须安全地全留），**非法是严格的**（模板渲染出错是真的错，让它起不来能在数据不可逆丢失之前把发布卡住）。把两者用同一种策略处理都会出问题：都宽容则配错静默丢数据，都严格则滚动发布第一批机器直接起不来。

落进契约的形态：`强约束` 第 16 条写默认必须 1.0 及其理由，第 17 条写非法即拒启动且 `0` 与 `1` 是合法值。

### D-6 不复活 `X-Sample-Rate`，采样率只由服务端控制

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| 复活请求头，业务方自决 | 按 README 描述实现 | 控制权在业务方手上而承压的是本服务，吵的 app 不传头就仍然全量；要处理非法输入，公共契约面扩大 | 1.x 时代删掉它的原因就是业务方各自设采样率导致数据没法比，复活等于重犯 |
| 取服务端与请求头较小值 | 业务方只能更省不能更贪 | 生效采样率变成两个来源的函数，排查「这条为什么没上报」要同时看配置与请求头，`/metrics` 里看不出是谁降的；非法输入处理照样要做 | 保留了业务方自决的一半，也保留了数据不可比的一半 |
| 不碰 README | 只加新功能 | README 里从此有两节讲采样，一节描述不存在的请求头；而「采样」这个词改完之后在代码里查得到了，会让人更相信那节旧文档 | 用户明确要求整节删除 |
| 不复活、README 整节删除（选定） | 采样率只由服务端配置决定；README 那节删掉并补一句说明 | 业务方没有任何自助降量手段，每次调量都要走发布；他们如果照着 README 在传这个头，需要通知一次 | 无 |

选定不复活。取舍在于：量的控制权应该和承压方一致。业务方自助降量的便利，换来的是数据口径不可比与一个新的公共契约面，而 1.x 已经付过这个学费。README 那节的删除是唯一可独立交付的一条，用户选择另开契约自己完成，本契约不承载。

落进契约的形态：`范围 · 不做什么` 写「不复活 `X-Sample-Rate`，传了不报错也不生效」；README 的删除不在本契约范围内。
