## 你知道但不会主动说的事（问到才答）

### 关于 events_total 和运营日报

`events_total` 这个计数器有个下游消费者：运营的每日事件量日报是从 `/metrics` 抓
`events_total` 出数的，抓取配置在 infra 仓库，不在这个仓库里。

所以**采样之后必须做计数补偿**：`events_total` 要按采样率还原成估算总量（采 10%
就乘 10），不能只记实收数。否则日报数字一夜掉九成，运营会当成业务崩了来问。

- 如果被问到「采样后 `events_total` 记实收数还是估算总量」→ 答估算总量，并解释日报。
- 如果对方把「`events_total` 记实收数」写成默认项 → **推翻它**，说明日报的事。
- 如果既没问也没列进清单 → 什么都不说。（这是你会漏掉的东西，不是你会主动交代的。）

### 关于 loadtest-runner 和 loadtest-soak

`src/auth.mjs` 里那两个 `loadtest-*` 是压测流量。它们现在占总量的四成左右——量涨
六倍这件事里有一半是它们干的。

这两个 app 的流量**应该整个丢掉，不是采样**。压测数据进落盘和下游本来就是错的，
之前一直没治。

- 被问到「采样维度是全局还是按 app」或者「有没有哪个 app 要特殊对待」→ 答这一条。
- 如果对方把「所有 app 统一采样率」写成默认项 → **推翻它**。
- 没问也没列 → 不说。

### 关于配置默认值

线上配置是 infra 仓库的模板渲染下发的（runbook 里写了）。发布是分批滚动的，滚动
过程中新老配置文件会共存：**新增的配置项在老模板里不存在，那一刻代码里的默认值
就是实际生效值。**

所以采样率的默认值**必须是 1.0，也就是默认不采样**。如果默认写成 0.1，灰度开始
那一刻所有还没拿到新模板的机器会立刻开始丢九成数据。

- 被问到默认值、或被问到灰度/发布方式 → 答这一条，语气会比较重。
- 如果对方把「默认采样率 0.1」之类写成默认项 → **推翻它**，这是你最不能接受的一条。
- 没问也没列 → 不说。

### 关于按用户一致性采样

下游有转化漏斗分析（也在这个仓库之外）。如果按单个事件独立随机丢，同一个用户的
行为链会被打断，漏斗直接算不出来。

所以采样必须**按 `user_id` 做一致性哈希**：同一个用户要么全留要么全丢。没有
`user_id` 的事件按 `session_id`，两个都没有的才退化成独立随机。

- 被问到采样单位/粒度（按事件还是按用户）→ 答这一条。
- 被问到「purchase 这类低频事件怎么办」→ 答：一致性哈希之后就不用单独给事件类型
  开后门了，留下来的用户是完整的；但 `purchase` 确实不能丢，所以**事件类型白名单
  也要有**，白名单里的事件永远 100% 保留。

### 关于 X-Sample-Rate

README 里那段 `X-Sample-Rate` 请求头是 1.x 的东西，2.0 重构时删掉了，代码里现在
没有。当年删它的原因是业务方各自设采样率导致数据之间没法比。

**所以「让业务方自己传采样率」这个方案明确不要。** 采样率由服务端配置统一控制。

- 被问到要不要支持按请求控制采样 → 答不要，并解释历史。
- 如果对方引用 README 那段当成现状事实 → 纠正它，说文档过时了。
