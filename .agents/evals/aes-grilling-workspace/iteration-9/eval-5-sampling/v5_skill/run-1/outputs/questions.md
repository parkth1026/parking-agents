**F-1 上报链路是一个入口两个出口。**
`POST /v1/events` 进来之后：`auth.isRegistered(X-App-Id)` 鉴权 → `validateEvent` 逐条校验 → 好的进 `accepted` 数组 → 同一个 `accepted` 数组同时喂给 `store.write(accepted)`（落盘）和 `forwarder.add(accepted)`（转发），然后 `countAccepted(appId, accepted.length)` 记数。出处 `src/receiver.mjs:47-51`。也就是说落盘、转发、计数三者现在是绑死的，任何采样都会同时动到这三个地方。

**F-2 「采样」这个词在这个仓库里已经有一个旧含义，而且它和代码不一致。**
`README.md:24-37` 有一整节叫「单请求控制采样」，写的是支持 `X-Sample-Rate` 请求头、取值 0 到 1、业务方可以自己决定这一批要不要抽样上报。但 `src/receiver.mjs` 里完全没有读 `req.headers['x-sample-rate']`，我全仓库搜了 `sample`，除了 README 这一节之外没有任何代码、配置或测试提到它。README 自己在那节末尾加了注：「这一段是 1.x 时代写的，2.0 重构之后头部处理逻辑整个换过一遍，文档没跟着改全，具体行为请以 `src/` 为准」。

所以「加个采样」有两种读法：一种是把 README 里这个已经消失的按请求采样做回来，另一种是做一个全新的服务端采样。仓库语言是证据不是权威，这条我不替你定，见下面 Q2。

**F-3 8 个注册 app 混在同一个入口里，量的性质明显不同。**
`src/auth.mjs:2-11` 硬编码了 8 个已登记 app：`web-portal`、`web-admin`、`ios-app`、`android-app`、`crm-sync`、`billing-worker`、`loadtest-runner`、`loadtest-soak`。它们走同一个 `/v1/events`、同一套校验、写同一个 `data/events.ndjson`、转发给同一个下游。从名字看至少有三类：页面/客户端埋点（web-*、ios-app、android-app）、业务系统同步（crm-sync、billing-worker）、压测（loadtest-runner、loadtest-soak）。同一个采样率作用在这三类上，后果差别很大。注释还写着「新增业务方走发版，不走配置」。

**F-4 采样会改掉两个运维天天看的指标的含义。**
`src/metrics.mjs:11-14` 的 `countAccepted` 直接按 `accepted.length` 累加 `events_total` 和 `events_by_app{app=...}`。而 `docs/runbook.md:12-16` 明确写着「`events_total` 与 `events_rejected_total` 是最常看的两个」，并且「磁盘涨得快」这个故障的排查手段就是「看 `events_by_app` 定位」。采样一旦真的丢事件，这两个指标从「上报了多少」变成「留下了多少」，容量排查的尺子就换了。

**F-5 落盘格式和转发形状都有外部消费者，不能自由改。**
`src/storage.mjs:5-6` 注释：「事件按 ndjson 追加，一行一个事件……下游有从这些文件回捞的工具，所以文件名和一行一个 JSON 的格式不要随便改」，那个工具是 `scripts/replay.mjs`，它读 ndjson 重新转发给下游补数。`src/forwarder.mjs:4-5` 注释：「下游只认 `{events:[...]}` 这一种 body 形状，改它要跟下游同步发版」。`docs/schema.md:18-26` 重复了这两条。这意味着如果落盘也被采样，`replay.mjs` 的补数能力也跟着只能补采样后的量。

**F-6 采样率改不了热更新，而且配置项不止改这个仓库。**

**F-7 `user_id` 和 `session_id` 都是选填的。**

**Q1. 采样砍的是哪一段：落盘、转发，还是两段一起？**

已知证据：F-1，落盘和转发现在吃的是同一个 `accepted` 数组；F-5，`data/events.ndjson` 有 `scripts/replay.mjs` 从里面回捞给下游补数。你说的是「磁盘和下游都吃不住」，这是两个压力源，可以分别处理。

- **[A] 入口采一次，落盘和转发都只拿采中的那部分。** 代价：磁盘和下游同时降；但 ndjson 从此不是全量，下游挂了之后 `replay.mjs` 只能补回采样后的量，被采掉的事件永久消失、任何口径都追不回来。
- **[B] 只砍转发，落盘保持全量。** 代价：下游降了，磁盘一点没降——而你说的第一个痛点就是磁盘；好处是 ndjson 仍是全量，replay 补数能力和事后追查完整保留。
- **[C] 只砍落盘，转发保持全量。** 代价：磁盘降了下游没降；而且 `replay.mjs` 从残缺的 ndjson 补数会和下游已有的全量数据对不上。
- **[D] 落盘和转发各自一个独立采样率。** 代价：两个旋钮更灵活（比如落盘 100% 留证、转发 10% 减压），但配置项翻倍、心智负担翻倍，而且两条链路的数据量从此永久不一致，任何对账都要先解释这件事。

推荐 **[A]**，理由是你两个痛点都提了，[B][C] 各只解一个。但我把 [A] 的真实代价再说一遍：**它是不可逆的数据丢失**，选它之前请确认没有任何审计、对账或补数流程依赖 ndjson 是全量的。

**Q3. 采样率的配置粒度：一个全局值，还是能按 app 分别配？**

已知证据：F-3，8 个 app 走同一个入口，性质分三类；F-4，runbook 定位磁盘暴涨的手段就是看 `events_by_app`，说明「哪个 app 量大」本来就是运维日常关心的维度。

- **[A] 一个全局采样率，所有 app 一视同仁。** 代价：配置最简单，一个数；但量小的 app 被无谓采掉，量大的 app 降得不够，而且没法处理任何单个 app 的特殊情况。
- **[B] 一个全局默认值 + 可选的按 app 覆盖。** 代价：能精确按 F-4 定位到的那个 app 下手；配置结构从一个数字变成一个 map，`config/default.json` 和 infra 仓库模板都要跟着改（F-6）。
- **[C] 只按 app 配，没配到的 app 一律 1.0 不采样。** 代价：最保守，漏配的后果是「没省到」而不是「丢了数据」；但每接一个新 app 都要记得配一次。
- **[D] 按事件名（`event` 字段）配，不按 app。** 代价：粒度最贴近业务（`page_view` 采、`purchase` 不采）；但事件名是业务方自定义的、没有登记表，配置会长期漂移，而且 F-4 的 `events_by_app` 排查路径对不上。

推荐 **[B]**。理由：F-4 说明运维已经在按 app 看量了，旋钮和排查维度对齐最省事；[D] 粒度更细但缺一张事件名登记表，会变成长期维护负担。

**Q4. 有没有哪类流量是「绝对不许采样丢掉」，或者反过来「应该整个不收」的？**

**Q5. 采样的单位是什么：单个事件独立抽，还是同一个用户要么全留要么全丢？**

已知证据：F-7，`user_id` 和 `session_id` 都是选填字段；F-1，一个请求 body 可以是单个事件也可以是事件数组，服务端逐条处理。

- **[A] 每个事件独立随机决定。** 代价：实现最简单，总量控制最精确；但同一个用户的行为序列会被打散——留下 `add_to_cart` 丢掉 `purchase` 这种，任何漏斗或路径分析都会算出错的转化率。
- **[B] 按 `user_id` 一致性哈希：同一个 `user_id` 要么全部留下要么全部丢掉。** 代价：漏斗和路径分析在采样后仍然成立（只是样本变小）；但必须回答「没有 `user_id` 的事件怎么办」（F-7 说它是选填），而且总量控制不如 [A] 精确——用户之间量差大的话实际留存比例会偏离设定值。
- **[C] 按 `session_id` 一致性哈希。** 代价：同上，但会话比用户短，跨会话的分析仍然会被打散。
- **[D] 按整个请求批决定：一批要么全收要么全丢。** 代价：实现最省，判定一次而不是 N 次；但批的边界由业务方的攒批逻辑决定，跟任何分析维度都不对应，等于随机性由客户端说了算。

推荐 **[B]**。理由：埋点数据的主要用途是行为分析，[A] 省事但会安静地把转化率算错，这类错误不会报错、只会给出一个看起来合理的错数字。选 [B] 的话我要接着问你没有 `user_id` 的事件怎么处理。

**Q6. 采样之后，`/metrics` 里的 `events_total` 和 `events_by_app` 记什么数？**

已知证据：F-4，这两个计数器现在按 `accepted.length` 累加；runbook 明确说 `events_total` 是最常看的指标之一，而且「磁盘涨得快」的排查靠 `events_by_app`。

- **[A] 记实际留下的数（采样后）。** 代价：改动最小，一行都不用动；但你原本用来判断「上报量涨太快」的那个指标从此看不到真实上报量了——采样一开，曲线立刻掉下去，之后真实量再涨你也看不见。

## 先说清一件事：随机行为怎么写成能判定的测试

你这次要的东西核心是随机的，而「随机」和「可判定的验收」天生冲突。这件事有三条路，代价差别很大，**我给概率和途径，后果得你判**：

- **[途径 1] 把随机源变成可注入的依赖。** 仓库里已经有这个模式的先例：`src/forwarder.mjs:6` 的 `createForwarder(cfg, deps = {})` 就是靠 `deps.post` 注入假的 post 来测的，`test/forwarder.test.mjs` 全靠它。同样给采样判定留一个 `deps.rng`，测试里传一个确定性函数，`npm test` 一分钟出结果，**退出码 0/1 直接可判**。代价：生产代码里多一个只为测试存在的注入口——但这在本仓库不是新增模式，是跟随现有模式。
- **[途径 2] 固定盐 + 真实哈希 + 黄金用例。** 盐写成常量之后，`user_id` 到「留/丢」的映射就是确定的。先算出一批已知判定的 id（比如 `u-keep-1`…`u-keep-5`、`u-drop-1`…`u-drop-5`），连输入事件和期望的落盘结果一起落到 `test/fixtures/`。代价：**盐一改这批 fixture 全废**，所以盐必须声明为不可修改；另外这批 id 是我算出来的，不是真实用户 id。
- **[途径 3] 大样本比例断言。** 发一万条不同 `user_id` 的事件，断言留存比例落在 0.1 ± 0.02。代价：`npm test` 会变慢（估计几秒到十几秒，本仓库现在全套 19 个测试是瞬间跑完的），而且这是**概率性断言，会偶发变红**——CI 偶发红比没有这条测试更糟，因为它会训练人无视红灯。
- **[途径 4] 你给一组真实数据做黄金用例。** 这条始终在场：从生产 ndjson 里取一段真实事件（含真实 `user_id` 分布），跑一遍采样，把结果存成期望输出。代价：需要你确认这批数据能不能脱敏、放不放进仓库；好处是它能回答「真实 `user_id` 分布下留存率是不是真的接近 0.1」——途径 2 用我编的 id 回答不了这个问题。
- **[途径 5] 真实压测看磁盘曲线。** 这个仓库**没有任何基准或压测脚本**（`docs/testing.md:26` 自己写明了），也没有端到端测试基建。要走这条得先建，我估最小可用的基准脚本 1 到 2 个工作日，真实流量回放环境不在这个仓库、我判断不了工期。

我推荐 **途径 1 + 途径 2 组合**：判定逻辑用注入的确定性 rng 测（快、稳），一致性哈希用固定盐的黄金用例测（真实走哈希路径）。**不推荐途径 3**，偶发红的代价太高。**途径 4 我想问你要不要**，它是唯一能验证「留存率在真实数据上真的是 0.1」的办法。

  - **`[A]` 断言 `storage_bytes_total` 同步下降**：同一组输入下，率 1.0 与率 0.1 两次运行的 `storage_bytes_total` 之比落在 8 到 12 倍之间。代价：字节数受事件大小影响，比条数松；好处是它直接量的是**磁盘**，而你的痛点原话就是磁盘。

**Q19（最后一个判断题）：这份契约要不要拆成两份？**

- **[B] 拆成两份：一份「上报采样」，一份「压测流量丢弃」。** 代价：每份都在六条以内、各自能独立交付、压测丢弃那件事（它是量涨六倍里的一半）不会被采样的复杂度盖住；但 B4 的优先级要在两份契约里各写一遍，而且必须定一个先后顺序，否则先做的那份不知道另一半存在。
- **[C] 拆成两份，并且明确先做压测丢弃。** 代价：同 [B]，但先摘掉四成的量、见效最快、而且压测丢弃比采样简单得多，可以先上线观察磁盘曲线再决定采样率定多少——这反过来还帮你回答了「率该定 0.1 还是 0.2」这个我们一直没碰的问题。

但 **[C] 有一个我给不了的好处**：先上线丢弃、看真实磁盘曲线、再定采样率。如果你现在其实还没定采样率该是多少，[C] 比 [A] 值。请你定。
