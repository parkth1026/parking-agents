## 4. 第 3 步判定出不出对照物及理由

**判定：不出界面 mock，出行为对照表。**

- **不出 mock 的理由**：`src/index.mjs:16-33` 显示这个服务只暴露三个 HTTP 端点（`POST /v1/events`、`GET /metrics`、`GET /healthz`），仓库里没有任何 HTML、CSS、前端框架或静态资源目录。本次改动不新增也不改动任何用户可见界面。按 skill 的分类，「新增或改动用户可见界面出界面 mock」不成立。
- **出行为对照表的理由**：本次改变现有可观察行为，且改的是多处。同一个请求今天的行为是 100% 落盘 + 100% 转发 + `events_total` 加 1 + 返回 `{"accepted":N,"rejected":[]}`；改后落盘条数、转发条数、`/metrics` 数值口径都会变（响应体经 Q7 决定保持不变，但这本身也是需要用户确认的「不变项」）。按 skill 的分类，「改变现有可观察行为或兼容性（输入输出、接口报文、状态流转的今昔差异）出行为对照表」成立。
- **对照表的位置**：按 skill 与 `goal-contract-shape.md` 的规定，行为对照表不单独成文件，整张写进契约的「访谈记录」一节。因此 `outputs/` 里**没有 mock.html，也没有独立的对照表文件**——这是规范要求的结果，不是漏产出。
- **对照表规模与迭代**：11 个变化行 + 5 个边界行 + 14 条不变清单。用户逐行确认，变化行零修改，边界行 B4（丢弃名单优先于白名单）的优先级经用户明确确认，并对第 7 行（`user_id` 与 `session_id` 都缺失的分支）表示「我原来没想到，写出来是对的」。确认版在契约的「读什么」里声明为不可修改。
- **对照表如何进入验收**：按 skill 第 4 步的规定，对照表的变化行直接作为 4a 的例子参与聚类，没有另立一条「整体对照」的 AC。16 个例子聚成 6 簇，一簇一条 AC；第 7 条 AC 是用户在验收阶段补的，不来自聚类。
