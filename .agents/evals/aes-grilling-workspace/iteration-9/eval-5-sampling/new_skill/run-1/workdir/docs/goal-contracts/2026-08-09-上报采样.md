# Goal Contract: 上报采样：按用户一致性采样并对 events_total 做计数补偿

- Status: Ready
- Target: `metrics-relay`（`src/receiver.mjs`、`src/config.mjs`、`src/metrics.mjs`、`config/*.json`、`README.md`）
- Updated: 2026-08-09

## 原始请求

> 上报量涨太快了，磁盘和下游都吃不住。给上报加个采样吧。先别写代码，帮我理清需求、写份 goal contract。

访谈中用户补充：

> 补个背景：上报量三个月涨了六倍，磁盘和下游 ingest 都吃不住了。

> `src/auth.mjs` 里那两个 `loadtest-*` 是压测流量，它们现在占总量的四成左右——量涨六倍这件事里有一半就是它们干的。这两个 app 的流量应该整个丢掉，不是采样。压测数据进落盘和下游本来就是错的，之前一直没治，这次一起治了。

> `events_total` 有个下游消费者你不知道：运营的每日事件量日报就是从 `/metrics` 抓 `events_total` 出数的，抓取配置在 infra 仓库，不在这个仓库里。所以采样之后必须做计数补偿。

> 采样率默认值必须是 1.0，也就是默认不采样。线上配置是 infra 仓库的模板渲染下发的，发布是分批滚动的，滚动过程中新老配置文件会共存——新增的配置项在老模板里根本不存在，那一刻代码里的默认值就是实际生效值。

> `loadtest-runner` 打过来的事件里如果带白名单事件（压测里有下单场景，压测脚本会打 `purchase`），也必须一起丢掉。白名单不能救压测流量。

## 目标

`/v1/events` 收到的事件在落盘与转发之前按可配置比例、按用户一致性地采样，磁盘写入量和下游转发量随之下降，同时 `events_total` 通过计数补偿仍然代表估算总量，运营日报不受影响。

## Why

- 上报量三个月涨了六倍，磁盘和下游 `analytics-ingest` 都吃不住；其中约四成是 `loadtest-*` 压测流量，这部分本来就不该落盘和转发。
- 下游有转化漏斗分析（在本仓库之外），逐事件独立随机采样会打断同一用户的行为链，漏斗直接算不出来，所以采样必须按用户一致。
- 运营的每日事件量日报从 `/metrics` 抓 `events_total`，抓取配置在 infra 仓库。不做计数补偿，日报数字会一夜掉九成。

## 范围

做：

- 在 `/v1/events` 校验通过之后、落盘与转发之前插入采样判定，判定顺序为 `drop` 名单 → 事件白名单 → 归组键哈希。
- 归组键三层：`user_id` → `session_id` → 事件规范化 JSON。
- 配置新增 `sample` 节：`default` 比例、`byApp` 按 app 的比例表、`drop` 丢弃名单、`whitelistEvents` 事件白名单。
- `events_total` 与 `events_by_app` 做计数补偿输出估算总量；新增 `events_stored_total`（实收落盘条数，不补偿）与 `events_sampled_out_total`（被采样掉与被丢弃的条数）。
- 清理 `README.md` 中「单请求控制采样」这一节的过时描述。

不做：

- 不做限流、不做背压、不做按磁盘水位自适应调速。
- 不实现 `X-Sample-Rate` 请求头，不接受任何由业务方声明的采样率（2.0 重构时删除该头的原因是各家自设采样率导致数据之间无法比较）。
- 不改 `src/auth.mjs` 的鉴权逻辑，`loadtest-*` 仍然留在登记表里、仍然拿 202。
- 不改重试与退避逻辑，不改丢批行为。
- 不改 `scripts/replay.mjs`，回放路径不采样。
- 不做「白名单事件把它所属用户提升为永久保留」的进程内提升集合。
- 不把事件聚合成计数（不做预降采）。
- 不引入任何第三方依赖。

## 强约束

- 采样率默认值必须是 `1.0`：缺 `sample` 节、缺 `default` 字段、缺整个配置项都等于不采样。滚动发布期间老模板里没有新配置项，那一刻代码里的默认值就是实际生效值。`npm test` 现有 19 条测试零 diff 即为证据。
- 判定顺序固定为 `drop` 名单 → `whitelistEvents` 白名单 → 归组键哈希，不得调换。`drop` 优先于白名单，白名单优先于哈希。
- 采样判定必须是纯函数：不调 `Math.random`、不依赖时间、不依赖进程状态、不依赖已处理条数。同一条事件加同一份配置永远得到同一判定。
- 转发给下游的 body 形状保持 `{"events": [ ... ]}`，不加任何采样元信息。下游发版不与本服务同步。
- 落盘保持 ndjson、一行一个 JSON、服务端补全 `app` 之后的形状；文件名保持 `events.ndjson` 与 `events.ndjson.1`，滚动规则不变。`scripts/replay.mjs` 与 infra 的搬运任务都依赖它。
- `/v1/events` 的状态码语义不变（全好 202、有坏 207、未登记 401、body 非 JSON 400），响应体字段仍然只有 `accepted` 与 `rejected` 两个，采样不体现在响应里。
- `events_rejected_total`、`forward_batches_total`、`forward_failures_total`、`storage_bytes_total` 四个计数器的口径一个字不变。
- `/metrics` 保持纯文本、保持全整数输出，文本形状不变（infra 侧抓取与运营日报都在本仓库之外，改不到也测不到）。
- 零依赖：只用 Node 内建模块。
- AC-007 的输入 fixture 与期望字节数声明为不可修改。执行 Agent 只能改实现，不能改 fixture 或期望值。
- 「访谈记录」节里的确认版行为对照表声明为不可修改，它是设计输入不是交付物。

## 读什么

- `src/receiver.mjs`：采样判定的插入点在校验循环之后、`store.write` 与 `forwarder.add` 之前。
- `src/config.mjs`：配置只在启动时读一次、不监听变更；`sample` 节按现有分节风格加。
- `src/metrics.mjs`：`countAccepted` / `render()` / `snapshot()` / `resetForTests()` 是补偿与新计数器要改的四处。
- `docs/runbook.md`：线上配置由 infra 仓库模板渲染下发，`config/*.json` 只是样例；发布是分批滚动的。
- `docs/testing.md`：本仓库的测试约定与当前未覆盖的部分。
- `docs/schema.md`：事件字段、落盘形状、转发形状。
- 本文件「访谈记录」节的确认版行为对照表（17 行 + 不变清单），执行前完整读一遍。

## 验收条件

- AC-001: 归组键三层判定成立：同一 `user_id` 的多条事件判定必然相同；`user_id` 缺失或为空串时降到 `session_id`；两者都缺或都为空串时按事件规范化 JSON 判定；同一输入加同一配置永远得到同一判定。
  - Verify: [A] `npm test` 新增用例断言对照表第 2、3、4、6、7、8 行的输入与判定结果 → 退出码 0
  - 这条错了会怎样：下游转化漏斗算不出来（同一用户的行为链被打断），这是用户的硬要求。
- AC-002: 判定优先级的三个交叉点行为正确：`drop` 名单里的 app 连白名单事件一起丢；非 `drop` 的 app 下白名单事件 100% 保留（即使其归组键被判丢）；`drop` 的 app 对 `events_total` 与 `events_by_app` 的贡献为 0。
  - Verify: [A] `npm test` 新增三条用例，分别对应 `loadtest-* × purchase`、`web-portal × purchase × 判丢的 user_id`、`loadtest-* × page_view`（对照表第 17、5、9 行）→ 退出码 0
  - 这条错了会怎样：压测的假下单会全量进下游漏斗，比不做采样更脏。
- AC-003: 落盘与转发看到完全同一批事件：被采样掉或被丢弃的事件既不进 `data/events.ndjson`，也不进转发 buffer（`forwarder.pending()` 不因它增长）。
  - Verify: [A] `npm test` 新增用例，沿用 `test/receiver.test.mjs` 的 `written` / `forwarded` 双数组 harness，断言两个数组逐元素相等（对照表第 3、4、12 行）→ 退出码 0
  - 这条错了会怎样：磁盘和下游只降了一边，用户说的「都吃不住」只解决一半。
- AC-004: `/metrics` 的三个口径同时成立：`events_total` 与 `events_by_app` 输出补偿后的估算总量（逐事件累加 `1/生效比例`，白名单事件与 `default=1` 的系数为 1，`drop` 的 app 贡献 0，输出四舍五入为整数）；`events_stored_total` 记实际落盘条数且不补偿；`events_sampled_out_total` 记被采样掉与被丢弃的条数。
  - Verify: [A] `npm test` 新增用例，构造已知归组键与已知配置的批次，断言三个计数器等于手算值、且 `render()` 输出的每个数值都是整数 → 退出码 0
  - 这条错了会怎样：补偿算错的那种情况最要紧——数字看起来正常，只是长期偏 20%，那种没人会发现，等到有人拿日报的数去做预算或者跟财务对账才会炸，而且回头查不出是哪天开始偏的。（掉九成那种反而是快的：日报每天早上发，运营当天就会来问。）
- AC-005: 配置校验成立：`sample.byApp` 与 `sample.default` 的值只接受大于 0 且不超过 1 的数；出现 0、负数、大于 1 或非数字时进程启动即失败并打出是哪个 app 的哪个值有问题；同一个 app 同时出现在 `drop` 与 `byApp` 里时 `drop` 优先且不报错。
  - Verify: [A] `npm test` 新增用例断言非法值抛错且错误信息含 app id（对照表第 16 行）→ 退出码 0
  - 这条错了会怎样：`0` 被当成合法采样率静默丢光某个业务方的全部数据，而它长得像个正常配置，没人会怀疑。
- AC-006: 仓库里不再有任何地方声称支持 `X-Sample-Rate`：`README.md` 的「单请求控制采样」一节被删除，或改写为「1.x 遗留，2.0 已移除，不会实现」。
  - Verify: [D] `README.md` 不含 `X-Sample-Rate` 字样，或含该字样的段落同时含「已移除」
  - 这条错了会怎样：下一个人照着 README 把这个头实现出来，当年为了「各家数据可比」删掉它的决定被无声推翻。
- AC-007: 同一批固定输入在 `sample.default` 为 1 与为 0.1 两次跑之下，`storage_bytes_total` 的比值等于一个确定的常数（由 D-01 的 fixture 与哈希判定决定，不是恰好 0.1），证明磁盘写入量真的按采样比例降下来了。
  - Verify: [A] `npm test` 新增用例，两次跑 D-01 的 `test/fixtures/sample-volume-input.json` 并断言 `storage_bytes_total` 精确相等于写死的期望值 → 退出码 0
  - 这条错了会怎样：花了一次发布，磁盘该涨还是涨，而所有测试都是绿的——最初那个问题没解决，但没有任何东西会告诉你。

| 随机的东西怎么写成能判定的测试？ | A 第三层也用哈希（哈希事件规范化 JSON），采样判定全程无随机 55% / B 保留真随机但把随机源做成可注入依赖（照 `deps.post` 的模式）30% / C 统计断言：灌一万条断言留存率落在容差区间 15% | A，因为整条路径变成纯函数，测试不用注入任何东西 | A。「这正是我想问的那个方案。全程无随机、给一条事件就能重放出判定结果，这个对我排查有用——业务方来问『我这条为什么没了』，我能直接答出来。B 那个注入随机源的答不了。」 |

## 设计取舍

### D-1 采样的判定单位

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A 逐事件独立随机 | 每个事件掷一次骰子 | 实现最短，大数上留存率最准 | 打断同一用户的行为链，下游转化漏斗算出来的转化率是错的且错得看不出来；测试要注入随机源，仓库里没有这个模式 |
| B（选定）三层归组键一致性哈希 | `user_id` → `session_id` → 事件规范化 JSON，同一归组键要么全留要么全丢 | 留存率在小样本上不精确等于配置值；多两条字段缺失的降级分支 | 无 |
| C 只按 `session_id` 哈希 | 会话整体留或丢 | 跨会话的用户级分析（留存、回访）仍然断，而 `session_id` 缺失面可能比 `user_id` 更大 | 用户要保的是漏斗，漏斗是用户级的 |
| 什么都不做 | 保持现状 | 磁盘和下游继续吃不住 | 正是这次要解决的问题 |

选定 B。理由：这次要压的是量，但不能压掉数据的可分析性。逐事件随机在「压量」这个指标上表现最好，代价却落在一个看不见的地方——下游漏斗的转化率会变成一个错的数字，而且没有任何东西会报错。三层归组键多出来的两条降级分支是明码标价的复杂度，换来的是「留下来的用户是完整的」这个能被断言的性质。
落进契约的形态：`强约束` 写「判定顺序固定为 `drop` → 白名单 → 归组键哈希，不得调换」，`验收条件` AC-001 断言三层降级与同键一致性。

### D-2 采样后 `events_total` 的口径

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A 只记实收数，另加 `events_sampled_out_total` | 老计数器口径不动 | 运营日报一夜掉九成，运营会当成业务崩了 | 用户直接推翻：日报从 `/metrics` 抓 `events_total`，抓取配置在 infra 仓库 |
| B 另加 `events_received_total` 记原始入站量 | 两个计数器相减得采样掉的量 | 日报侧要有人去改成读新指标，而那不在本仓库 | 改的是消费方，成本推给了别人 |
| C（选定）计数补偿：逐事件累加 `1/生效比例`，名字不变 | `events_total` 与 `events_by_app` 输出估算总量，输出四舍五入为整数；另加 `events_stored_total` 记实收 | `events_total` 不再是「真实发生过的事件数」而是估算值，跟精确口径对账会差一点 | 无 |
| D 全局按一个「有效采样率」乘 | 实收数乘一个常数 | 各 app 比例不同时系统性算错，白名单事件也被凭空放大 | 已经定了按 app 配比例，这个乘法从第一天起就是错的 |

选定 C。理由：`events_total` 有一个本仓库看不见的消费者，它的名字已经是一份对外契约。补偿让名字与语义保持一致，代价是这个数字从精确值变成估算值；而「实际落盘了多少」这个精确值另开一个 `events_stored_total` 承接——这一条恰好也是「磁盘降没降」的唯一答案，所以它不是补偿的附属品，是这次目标的直接观测点。
落进契约的形态：`验收条件` AC-004 断言三个计数器口径同时成立；`强约束` 写「`/metrics` 保持全整数输出，文本形状不变」。

### D-3 「整个丢」与「采样率」用不用同一个配置表达

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A（选定）`drop` 名单与 `byApp` 比例表两个独立配置 | `drop` 在最前判，比例表只接受大于 0 且不超过 1 | 两个配置项，同时命中要定优先级（已定为 `drop` 优先） | 无 |
| B 一张比例表，`0` 表示整个丢 | `byApp` 允许 `0` | 「治掉压测流量」在配置里长得跟「采狠一点」一模一样，下一个人很可能把 `0` 改成 `0.1`；补偿要带除零特例 | 意图在配置里读不出来 |
| C 从 `src/auth.mjs` 登记表删掉两个 `loadtest-*` | 压测流量吃 401 | 压测压的变成鉴权分支，压测结论作废；`events_rejected_total` 常态高位撞上 runbook 的故障判据 | 破坏压测本身的目的 |

选定 A。理由：`0` 这个值同时承载了两种意图——「这个 app 我只要一点」和「这个 app 我根本不要」，而后者是个需要被读出来的决定。分成两个配置项的代价只是多渲染一项模板，换来的是意图在配置文件里自解释，以及补偿算法里没有除零分支。
落进契约的形态：`验收条件` AC-005 断言 `0` 被当作配置错误、`drop` 与 `byApp` 同时命中时 `drop` 优先。

### D-4 第三层要不要保留真随机

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A（选定）第三层也用哈希，全程无随机 | 无 `user_id` 无 `session_id` 时哈希事件规范化 JSON | 完全重复的事件得到同一判定，重复上报场景下留存率偏离配置值；「稳定序列化」要自己实现并自带测试 | 无 |
| B 真随机 + 可注入随机源 | 照 `deps.post` 的模式接受 `deps.random` | 线上排查「我这条为什么被丢了」答不出来，同一条事件两次判定可能不同 | 用户明确说这个答不了业务方的追问 |
| C 统计断言 | 灌一万条断言留存率落在容差区间 | 概率性会红；CI 从一秒变慢；仓库无此先例 | 容差定不出来，红了也分不清原因 |

选定 A。理由：把随机去掉不是为了好测，是为了可解释——业务方问「我这条为什么没了」时，纯函数能被重放，随机不能。这条选择顺带让 AC-007 不需要任何容差：判定确定，`storage_bytes_total` 的比值就是一个可以手算写死的常数，「δ 定小了偶发失败、定大了什么都验不出来」这个两难被整个绕开了。
落进契约的形态：`强约束` 写「采样判定必须是纯函数，不调 `Math.random`、不依赖时间、不依赖进程状态」；AC-007 的 fixture 与期望值锁死。

### D-5 白名单事件与被判丢用户的交叉点

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A（选定）白名单优先，孤立 `purchase` 照样留 | 白名单是哈希之前的一道判定 | 下游漏斗出现无源转化，转化率被高估，高估幅度取决于采样率 | 无 |
| B 用户级哈希优先 | 被判丢的用户连 `purchase` 一起丢 | 采 10% 就丢掉九成下单记录，对账链路直接不能用 | 钱相关的事件不能丢 |
| C 白名单事件把它所属用户整体提升为「留」 | 进程内维护一个提升集合 | 与「判定不依赖进程状态」冲突，重启清零、机器之间不一致，集合还会无界增长 | 用一个内存问题换一个磁盘问题 |

选定 A。理由：两个目的在这个交叉点上真的互斥——保住每一条下单，和保住每条下单都有完整来源，无法同时满足而不引入状态。选 A 是明确地把「钱不能丢」排在「漏斗好算」前面，并且这个代价由用户自己去跟下游打招呼，而不是被静默地留在实现里。
