## 第 1 轮 — 推荐草案（靶子，不是结论）

- **目标：** 让 metrics-relay 在服务端按可配置的比例丢掉一部分上报事件，把磁盘写入量和
  下游转发量按同一个比例压下来。
- **做什么：** 在 `/v1/events` 校验通过之后、落盘与转发之前插入一个采样判定；比例可配置；
  被采样掉的量在 `/metrics` 上看得见。
- **不做什么：** 不做聚合或预降采（不把多条事件合并成计数）、不改下游转发 body 形状、
  不改 `/v1/events` 现有状态码语义、不动 `scripts/replay.mjs` 的回放路径、不做按磁盘
  水位自动调速。
- **验收大致方向：** 给定一批输入，配某个比例后落盘条数与转发条数按该比例下降、且两者
  一致；采样掉的量在 `/metrics` 上有数；比例为 1 或缺省时行为与现在完全一致（现有 19 条
  测试零 diff）。

你改哪条就是哪条。

- D2 采样发生在校验之后，401 未登记 app 和校验失败的事件不参与采样 — `events_rejected_total`

### Q1. 你说的「采样」，服务端要不要自己做决定？

已知事实：`README.md` 第 24-35 行的「单请求控制采样」一节承诺了 `X-Sample-Rate` 请求头，
但 `src/receiver.mjs` 第 19 行只读 `x-app-id`，全仓库 grep `sample` 只命中 README 那两行——
这个头从来没实现过，README 自己也注明 2.0 重构后文档没跟全。同一个词在这个仓库里指两件事，
按哪个意思走是你的决定，仓库文档在这里是证据不是权威。

**A. 服务端按配置的比例丢，业务方无感也管不着 — 55%（推荐）**
- 选什么：服务端在校验通过后按配置比例丢事件，不读 `X-Sample-Rate`；README 那一节改写成
  「未实现」或直接删掉。不覆盖：业务方为自己的关键事件申请豁免——他们没有任何手段影响结果。
- 好处：量压不压得下来完全由我们控制，不用等任何业务方配合改代码；改动面只有这个仓库加
  infra 的配置模板。
- 代价：业务方看不到也管不了，「我的转化数少了一半」的排查责任全在我们身上；`purchase`
  这类关键事件会跟 `page_view` 一起被丢（除非 Q3 选 C）。

**B. 把 README 里那个 `X-Sample-Rate` 真正实现，比例由业务方声明 — 15%**
- 选什么：实现文档已经承诺的头部，服务端只尊重业务方声明的值，自己没有兜底权。不覆盖：
  业务方不改代码的情况——那个 app 的量一点都压不下来。
- 好处：文档和实现终于一致，不用背一个假承诺；业务方自己最清楚哪些事件重要。
- 代价：吃不住的是我们的磁盘和下游，但按钮在别人手上，得逐个业务方去推；最不配合的那个
  往往就是量最大的那个。

**C. 服务端配置兜底 + 业务方可用 `X-Sample-Rate` 声明更低的比例，取更严的那个 — 30%**
- 选什么：两层都做，实际留存率取两者的较小值；服务端的比例是上限，业务方只能更省不能更放。
  不覆盖：业务方申请比服务端更高的比例（提了不生效，也不报错）。
- 好处：我们能立刻压量，同时兑现 README 已经写出去的承诺；量大又自觉的业务方可以自己再降。
- 代价：两层叠加后的实际留存率不直观，出问题要同时查配置和请求头；测试要覆盖两层组合，
  用例数大约翻倍。

### Q2. 采样要保住的是「总量的形状」，还是「单个用户完整的行为链」？

已知事实：`docs/schema.md` 里 `user_id`、`session_id` 都是可选字段；
`test/fixtures/event-batch.json` 的四条事件正好是同一批里两个用户各自的
`page_view → click → purchase` 链条。逐事件独立随机会把这个链条打断——`page_view` 留下、
`purchase` 被丢，下游算出来的转化率就是假的。这两个答案通向不同的实现，不是同一件事的
两种说法。

**A. 按 `user_id` 一致性哈希，同一个用户要么全留要么全丢 — 50%（推荐）**
- 选什么：对 `user_id` 取哈希，落在阈值内的用户全量保留，跨进程跨天一致。缺 `user_id` 的
  事件要单独定规则（全留 / 全丢 / 逐条随机，你选了 A 我再追问这一条）。不覆盖：`user_id`
  缺失比例高的 app——对它们这套等于没生效。
- 好处：留下来的用户行为链是完整的，漏斗和留存乘个倍数还能用；判定是纯函数，测试能写成
  确定性断言，正好对上 `docs/testing.md` 要求的「断言可观察行为」。
- 代价：实际留存率在小样本上不会精确等于配置值（哈希分布不均）；多一条「字段缺失走哪」的
  分支和一组对应用例。

**B. 逐事件独立随机 — 35%**
- 选什么：每个事件单独掷一次骰子，不看任何字段。不覆盖：任何按用户聚合的分析，采样后都
  算不准。
- 好处：实现最短，大数上留存率最准，完全不用管字段缺不缺。
- 代价：漏斗断裂，下游的转化率会变成一个错的数字，而且错得看不出来；测试要注入随机源才
  能断言，`test/` 目前没有任何这类注入模式，得先立一个。

**C. 按 `session_id` 哈希 — 15%**
- 选什么：同一个会话整体保留或丢弃。不覆盖：跨会话的用户级分析（留存、回访）仍然断。
- 好处：会话内链条完整，粒度比按用户细，留存率比 A 更贴近配置值。
- 代价：`session_id` 同样是可选字段，缺失面可能比 `user_id` 更大；跨会话分析该断还是断。

### Q3. 采样率是一个全局数字，还是按业务方分别配？

已知事实：`docs/runbook.md` 故障表里「磁盘涨得快 → 某个业务方量突增，看 `events_by_app`
定位」，说明这个仓库的运维经验里量涨是单点的；`src/auth.mjs` 的登记表里已经有
`loadtest-runner`、`loadtest-soak` 两个压测 app id。但仓库里没有任何真实流量数据，这次
到底是一个 app 在涨还是全体在涨，我读不出来——这条跨在仓库边界之外，只有你知道。

**A. 按 app 配一张表，未配的 app 走一个 default — 60%（推荐）**
- 选什么：`config` 加 `sample.byApp`（app id → 比例）和 `sample.default`；未列出的走
  default，初始为 `1` 即不采样。不覆盖：按事件名分别配（比如保住 `purchase` 只压
  `page_view`），那是 C。
- 好处：跟 runbook 已有的定位路径完全对得上——看 `events_by_app` 找到那个 app，只压它，
  别人不受影响；两个压测 app 可以单独压到很低甚至 0。
- 代价：配置从一个数字变成一张会持续变长的表，每改一次都要动 infra 仓库模板并走一次分批
  滚动发布（F4）；表里写了已下线的 app id 也不会有人发现。

**B. 一个全局比例，所有 app 一视同仁 — 20%**
- 选什么：`sample.rate` 一个数字，作用于所有 app。不覆盖：只压吃量最大的那一个。
- 好处：配置最简单，一个数字，几乎配不错；不需要维护任何名单。
- 代价：为了压住量最大的那个，本来一点问题都没有的小业务方的数据也一起被砍掉同样比例，
  而它们的数据往往是最需要完整的（`crm-sync`、`billing-worker` 看名字像是对账类）。

**C. 按事件名配，或 app + 事件名两级 — 20%**
- 选什么：按 `event` 字段配比例，可与 app 组合。不覆盖：按 `props` 内容配。
- 好处：能精确保住 `purchase`、`billing` 这类关键事件，只压 `page_view` 这类高频低价值的，
  同样的降量幅度下损失的信息最少。
- 代价：事件名由业务方自己定、随时会加新的，配置表会持续腐烂；「没配到的新事件名走哪个
  默认值」又是一个决定，配漏了就是静默全留或静默全丢。

### Q4. 采样掉的量在 `/metrics` 和 HTTP 响应里怎么体现？

已知事实：`src/metrics.mjs` 的 `events_total`、`events_by_app` 现在统计的是「实际收下并
落盘」的事件数；`docs/runbook.md` 说 `events_total` 与 `events_rejected_total` 是最常看
的两个，并且「抓取方在 infra 侧配置，本仓库不感知」。也就是说这两个数字的口径一变，别人
看板上的曲线就变，而看板不在这个仓库里——有没有告警挂在上面，我读不出来。这条改错了要
再动一次线上指标才能改回来，属于难逆。

**A. 老计数器口径不动，新增 `events_sampled_out_total`（按 app 拆）— 65%（推荐）**
- 选什么：`events_total` 继续只数留下来的；被采样掉的进新计数器。不覆盖：暴露采样前的
  原始入站量——想要的话那是第二个新计数器（即 B）。
- 好处：新老指标各管一段，采样掉了多少是可观察的；infra 侧的抓取配置一个字都不用改。
- 代价：`events_total` 上线当天直接下台阶，按这条曲线做告警或做容量推算的人会以为业务
  出事了；得提前通知，而我不知道该通知谁。

**B. 在 A 之上再加 `events_received_total` 记原始入站量 — 25%**
- 选什么：同时暴露采样前的真实入站量，采样掉的量也可以由两个数相减得到。不覆盖：按 app
  拆分原始入站量（除非这个也按 app 拆，那就是两张 map）。
- 好处：「上报量涨太快」这件事本身在采样之后仍然看得见——不然你就失去了观察真实压力的
  唯一途径，而这正是你这次做采样的起因。

### Q5. 「整个丢」和「采样率配成 0」是同一件事吗？

**A. 两个独立的配置：一份 `sample.drop` 丢弃名单 + 一份 `sample.byApp` 比例表 — 70%（推荐）**
- 选什么：名单里的 app 在校验通过后直接丢弃，不落盘不转发，也不参与任何补偿；比例表只接受
  `(0, 1]`，`0` 被视为配置错误。不覆盖：按事件名丢弃（丢弃只有 app 这一个维度）。
- 好处：「这个 app 的数据我们根本不要」和「这个 app 的数据我们要但只要一部分」在配置上就

- 代价：两个配置项，一个 app 同时出现在两处时要定优先级（我会定丢弃优先，并写进契约）；

**B. 只有一张比例表，`0` 就表示整个丢 — 25%**
- 选什么：`sample.byApp` 允许 `0`，`0` 时跳过落盘转发，补偿在 `0` 上特例为「不计入」。

#### AC-007 同一批输入在 `default=1` 与 `default=0.1` 之下，`storage_bytes_total` 的比值符合预期

这条要判定什么：这次改动真的把磁盘写入量压下来了，而不是只让逻辑测试变绿了。

这条错了会怎样：你花了一次发布，磁盘该涨还是涨，而所有测试都是绿的——最初那个问题没解决，
但没有任何东西会告诉你。

**A. 不要容差：固定 fixture + 确定性哈希 ⇒ 比值是一个可以手算写死的精确常数 — 65%（推荐）**
- 选什么：落盘一份固定的 N 条事件 fixture（`test/fixtures/sample-volume-input.json`），
  因为 Q8 A 定了采样判定全程无随机，这 N 条在 `default=0.1` 下留哪几条是**完全确定的**，
  `storage_bytes_total` 是一个确定的字节数。断言写成精确相等，不写区间。
  - 门槛值：精确值，由 fixture 决定，第一次实现时把实际值填进用例（可以，因为判定是纯函数）。
  - 尺子：`npm test` 里的这条用例本身。
  - 锁不锁：**fixture 与这条用例声明为不可修改**（写进契约「强约束」），执行 Agent 只能改
    实现不能改 fixture 或期望值——不然它会去改期望值让测试变绿。
  - 不覆盖：真实流量的留存率。这条验的是「机制生效」，不是「线上真的降到 10%」。
- 好处：不需要定任何容差，也就不会有「δ 定小了偶发失败、定大了什么都验不出来」的问题；
  这是 Q8 选 A（全程无随机）换来的直接好处。
- 代价：比值不会精确等于 0.1（N 条里留下来的条数由哈希分布决定，比如 1000 条留 97 条），
  所以这条 AC 的措辞得写成「等于那个确定值」而不是「等于 0.1」；有人看到 0.097 会以为不对，
  用例里要写一句注释解释。
