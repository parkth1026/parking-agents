## 事实通报（不占提问轮次）

调查后向用户通报的仓库事实：

- 验证基建存在：`npm test` → `node test/run-tests.mjs`，退出码 0 为过（docs/testing.md）；测试约定要求消费链路改动补失败路径断言，无集成环境，用本地 jsonl 数据验证。
- src/consumer.mjs：handle 抛错时事件仅 `console.error` 后被丢弃，无重试、无留痕（代码内注释已承认此问题）。
- src/handler.mjs：非法金额（amount 缺失或 <= 0）抛错；注释说明下游写台账偶发网络抖动也会抛错——两类错误走同一异常通道，仓库没有错误分类机制。
- 台账格式：成功事件逐条追加 data/ledger.jsonl，每行 `{ id, ok: true }`。
- 样例数据：data/events.jsonl 现有 2 条订单事件。

## 第 1 轮（批量提问，先展示完整推荐候选）

展示的候选草案：

- Goal（一句话）：order-consumer 处理订单事件失败时不再丢事件——失败自动重试，最终失败进入可回放的死信留痕。
- In：src/consumer.mjs 消费链路的失败处理（重试 + 死信落盘）及配套失败路径测试。
- Out：不改队列/事件来源，不加监控、告警或界面。
- AC 方向：成功路径兼容、重试行为、死信内容与可回放性、「不丢事件」恒等式；验证走 `npm test`。

提出的问题（4 个独立歧义，一次发全；每题含证据、互斥选项、推荐与代价）：

- Q1 失败后的处理策略（证据：consumer.mjs 注释「没有重试也没有留痕」；handler 有偶发网络抖动抛错）
  - A. 有限次数重试 + 递增间隔（推荐；代价：永久性错误会多耗几次无效尝试）
  - B. 不重试，失败直接留痕（代价：本可自愈的网络抖动失败也落死信）
  - C. 无限重试直到成功（代价：一条坏事件卡住整个批次）
  - 用户答（PERSONA）：A。失败自动重试 3 次、间隔递增。
- Q2 最终失败事件的去向（证据：现状是打日志后丢弃；上月丢两单靠人工补数据）
  - A. 死信文件落盘 data/ 下 jsonl，保留原始事件（推荐；代价：需要人工回放流程）
  - B. 只打结构化日志（代价：仍无法可靠补数据）
  - C. 失败事件写回 events.jsonl 尾部循环消费（代价：坏事件可能造成死循环）
  - 用户答（PERSONA）：A。3 次都失败进死信文件 data/dead-letter.jsonl，保留原始事件和失败原因，格式要能直接人工回放。
- Q3 永久性校验错误（如 invalid amount）是否也走重试（证据：handler.mjs 校验错误与网络抖动同一异常通道，仓库无错误分类）
  - A. 不区分，统一重试后进死信（推荐；代价：坏数据事件多耗 3 次空重试，但实现最简单、不引入分类约定）
  - B. 校验类错误跳过重试直接进死信（代价：需要引入并维护错误分类约定）
  - 用户答：PERSONA 未覆盖 → 按人设「选推荐项」→ A。
- Q4 范围边界：是否需要监控/告警/管理入口（证据：仓库是纯脚本，无服务框架）
  - A. 纯后端改动，不加界面/面板/告警（推荐；代价：死信堆积需人工巡查）
  - B. 顺带加简单告警（代价：引入通知通道，超出当前仓库形态）
  - 用户答（PERSONA）：A。不需要管理界面、监控面板、告警通知，纯后端改动；也不换队列、不引入中间件。
  - 用户补充（PERSONA 主动给出的约束）：现有 ledger.jsonl 台账格式不能变，成功路径行为保持不变。

第 1 轮后维度自评：Intent 已定；Outcome 部分（「重试 3 次」计数语义、死信记录形态待定）；Boundary 已定；Constraints 已定；Context 已定。

## 第 2 轮（由第 1 轮回答解锁的追加问题）

追加理由：Q1 的「重试 3 次」解锁计数语义歧义；Q2 的「死信 + 可直接回放」解锁记录形态歧义；两者叠加解锁「失败事件是否在台账留痕」。三者都会改变可观察行为。

- Q5 「重试 3 次」的计数语义
  - A. 首次失败后最多再重试 3 次，共 4 次尝试（推荐；与「重试」字面一致）
  - B. 含首次共 3 次尝试（代价：实际重试只有 2 次，弱于用户表述）
  - 用户答：PERSONA 未覆盖 → 选推荐项 → A。
- Q6 死信记录形态（须满足「保留原始事件和失败原因」且「能直接人工回放」）
  - A. 每行一个 JSON 记录：原始事件逐字段完整保留在独立字段中，另带失败原因（推荐；回放 = 提取原始事件字段写回 events.jsonl，一步可完成，原因与事件不会错位）
  - B. 死信行就是原始事件原文，失败原因另存旁路文件（代价：原因与事件分离，易错位丢失）
  - 用户答：PERSONA 未覆盖 → 选推荐项 → A。
- Q7 最终失败事件是否同时写入 ledger.jsonl
  - A. 不写台账，失败只进死信文件；台账仍只含成功记录（推荐；与「台账格式不能变」最稳妥兼容）
  - B. 台账写入 ok: false 记录（代价：改变台账消费方对内容的假设）
  - 用户答：PERSONA 未覆盖 → 选推荐项 → A。

第 2 轮后维度自评：Intent / Outcome / Boundary / Constraints / Context 全部已定。收口审计通过：剩余可问问题只影响措辞不影响执行。停止提问。
