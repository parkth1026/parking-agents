# Goal Contract: 给 export_logs.py 加日期范围与输出路径参数，并报出被跳过的行数

- Status: Ready
- Target: `export_logs.py`（仓库根目录唯一脚本）
- Updated: 2026-08-09

## 原始请求

> fixtures/log-export 这个日志导出脚本太难用了,帮我改进一下。先把需求理清楚再给我一份 goal contract,别直接动手改。

访谈中用户补充的原话：

> 最痛就是这个：每次都导出全部，又慢文件又大。我要的是按日期范围过滤，`--from` / `--to`。第二痛是输出路径写死成 `export.csv` 太别扭。

> 不传 `--output` 的时候必须保持现在的默认路径和文件名，别的脚本依赖它。

> CSV 列名和列顺序不能动，下游是按列位置解析的。编码也保持 UTF-8 不变。

> 跳过行还是跳过，但结束的时候把跳过了多少行打到 stderr 给我看。我要的是一眼看见数字，不是一句「有脏行」。

> 压缩、自动上传、按级别过滤这次都不要，以后再说。

## 目标

让 `export_logs.py` 能按日期范围导出、能指定输出路径、并在结束时报出被跳过的行数，同时零参数调用的行为与今天完全一致。

## Why

- 现在每次都全量导出，日志越攒越多，导一次又慢、产出文件又大，而数据分析同事通常只要某几天的数据。
- 输出路径写死为脚本所在目录的 `export.csv`，同时导多批、或者分别导给不同人只能靠事后改名挪文件。
- 有多少行因为格式不匹配被静默丢掉，使用者完全不知道，拿到的 CSV 无法自证完整性。

## 范围

做什么：

1. 给脚本加三个可选命令行参数：`--from`、`--to`（日期，格式 `YYYY-MM-DD`，闭区间且两端都含当天全天）、`--output`（输出文件路径）。
2. 导出结束时把「无法解析而被跳过的行数」报到 stderr，带出具体数字；跳过 0 行时 stderr 不输出任何内容。
3. 新建一套最小 pytest 验证基建：测试文件、fixture 日志样本与 `-k` 选择约定。仓库目前一个自动化验证入口都没有，这套基建属于本次交付的一部分（访谈中估算约 0.5 人日，用户已确认值得）。

不做什么：

- 不做压缩输出（gzip / zip）。
- 不做自动上传或投递（邮件、对象存储、推送给下游同事）。
- 不做按日志级别或关键字过滤（用户明确「以后再说」）。
- 不做 JSON / Parquet 等其它输出格式。
- 不改 CSV 的列名、列顺序、列数与编码。
- 不改零参数调用的默认行为，也不把默认输出路径挪到别处。
- 不做性能优化，也不设任何性能数字门槛（本次靠「只导一段」缓解体积与耗时）。
- 不改输入来源，仍然只读脚本所在目录下的 `logs/*.log`。
- 不为 `--help` 单独立验收条件（`argparse` 自带；用户裁决删除）。

## 强约束

- CSV 表头文字与列顺序固定为 `timestamp,level,message`：不改名、不换序、不增删列。下游按列位置解析，破坏即断链。
- 输出文件编码固定 UTF-8 且**显式声明**，不依赖平台默认编码（Windows 下默认非 UTF-8）；写文件继续使用 `newline=""`，不产生多余空行。
- 不传 `--output` 时，输出路径必须仍然是「脚本所在目录 + `export.csv`」，文件名不许变。别的脚本依赖它。
- stdout 那行 `exported N rows -> 路径` 的文字格式保持原样；本次新增的信息只走 stderr，不许写进 stdout。
- 退出码语义保持：正常完成为 0，包含「范围内 0 行匹配」和「存在被跳过的行」两种情况。
- 输入来源保持为脚本所在目录下的 `logs/*.log`，按文件名排序遍历。
- 行解析正则与支持的级别集合（`DEBUG|INFO|WARN|ERROR`）不变。
- 无法解析的行继续跳过：不写进 CSV，不导致失败。
- 目标输出文件已存在时继续直接覆盖，不备份、不追加、不要求额外确认。
- 参数不合法时必须在写文件之前失败：不创建、不覆盖、不清空任何输出文件。
- 必须走「在本仓库新建最小 pytest 用例」这条验证路径，不引入 tox / nox / CI 平台配置等额外基建。
- 本契约「访谈记录」里的行为对照表是确认版对照物，**不可修改**。实现时改的是脚本，不是对照表。

- `logs/app.log`：现有日志样本，跨 2026-07-30 / 07-31 / 08-01 三天且含一行不可解析内容，可作为测试 fixture 的来源。

- D-02: `tests/fixtures/logs/app.log`：测试用日志样本。至少跨 2026-07-30、2026-07-31、2026-08-01 三天，且含一行不可解析内容；可直接取自仓库现有 `logs/app.log`。

## 验收条件

- AC-001: 传 `--from` / `--to` 时只导出落在该日期区间内的日志行，区间两端都含当天全天；只传一端时另一端不限；两端都不传时导出全部；区间内没有数据时产出只有表头的 CSV 且退出码为 0。
  - Verify: [A] `python -m pytest tests/test_export_logs.py -k range` → 退出码 0（用例锁死：`--from 2026-07-31` 得 3 行、`--to 2026-07-31` 得 4 行、`--from`=`--to`=`2026-07-31` 得 2 行、`--from 2026-08-02` 得 0 行只剩表头）
- AC-002: 参数不合法时（日期不是 `YYYY-MM-DD` 格式、`--from` 晚于 `--to`、`--output` 的父目录不存在）以非零退出码失败，且没有创建、覆盖或清空任何输出文件。
  - Verify: [A] `python -m pytest tests/test_export_logs.py -k invalid` → 退出码 0（用例断言非零退出，并断言已存在的目标文件内容未被改动）
- AC-003: 传 `--output` 时 CSV 写到该路径且脚本所在目录不产生 `export.csv`；不传时仍写到脚本所在目录的 `export.csv`；两种情况下 stdout 那行 `exported` 打印的路径都指向真实写入的文件。
  - Verify: [A] `python -m pytest tests/test_export_logs.py -k output` → 退出码 0
- AC-004: 存在无法解析的行时，结束时向 stderr 输出一行**含具体跳过行数这个数字**的统计；跳过 0 行时 stderr 不输出任何内容；两种情况下 stdout 那行 `exported` 的格式与退出码 0 都不变。
  - Verify: [A] `python -m pytest tests/test_export_logs.py -k skipped` → 退出码 0（用例分别断言：有脏行时 stderr 匹配含数字的统计行且 stdout 那行未变；无脏行时 stderr 为空）

| AC-002 非法参数在写文件前失败 | 今天最坑行为的延续：参数打错却静默导全量；更糟的是报错前已经把上次的 `export.csv` 覆盖清空，旧文件也没了 | `[A]` 断言非零退出**且**目标文件未被改动 / `[C]` 手工跑三条错命令，但「文件没被动过」人眼最容易漏看 | `[A]`，关键断言是「副作用没有发生」 | 按推荐 `[A]` |
| AC-003 `--output` 与默认路径 | **最贵的一条**：别的脚本依赖默认路径，错了是定时任务静默断链，第二天才有人发现 | `[A]` 断言两种路径落点 / `[C]` 手工跑两次看文件落哪，但这条最不能靠「记得跑」 / `[B]` 判定对象是路径不是内容，真实数据换不到额外信息 | `[A]`，后果最重 | 按推荐 `[A]` |
| AC-004 跳过行统计 | 最轻，错了只是少一条提示；但若顺手打到 stdout 就会污染 `exported` 那行，升级为影响抓 stdout 的调用方 | `[A]` 基建已被前三条摊掉，边际成本近零 / `[C]` 手工要分开重定向两个流才看得出 stdout 有没有被污染 | `[A]`，搭车最便宜 | `[A]`，**但措辞要改**（见下） |
| AC-005（候选）`--help` 打印用法且不写文件 | 几乎没有后果，`argparse` 自带 | —— | **建议删**：不是本次独有的可观察结果，是换用 `argparse` 的附带品；反面意见是「防止以后有人改坏 `--help`」，但会占一条编号 | **删掉**。「对照表第 11 行留着当行为口径就行」 |
| 要不要走 `[B]` 黄金用例 | 只有用户知道真实日志里有没有别的脏行形态 | 现有 `logs/app.log` 已含跨三天数据 + 一行脏数据，足够覆盖全部边界；若真实日志有多行栈 / 非 UTF-8 / 超长行则必须走 `[B]` | 不需要 `[B]`，但这条始终在场 | 不用 `[B]`。「真实日志没有别的脏行形态，就是偶尔有几行格式不对的，编码一直是 UTF-8」 |

用户对 AC-004 的措辞改写（原话）：「不要只写『报到 stderr』。要写明 stderr 那行必须带出具体跳过了多少行这个数字，而且跳过 0 行的时候一个字都不要输出。我要的是一眼看见数字，不是一句『有脏行』。」已按此改写 AC-004 并落进上面的验收条件。

AC 条数由聚类得出：12 行对照表聚成 4 个簇（范围过滤 / 参数校验与无副作用 / 输出路径 / stderr 统计），第 5 个候选簇（`--help`）被用户裁决删除。不变清单 9 条一条都没进 AC，全部进「强约束」——AC 说「要变成什么」，不变量说「不许变什么」，方向相反。

## 设计取舍

### D-1 「被跳过的行」这个信息走哪条通道

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A 塞进 CSV | 加一列「是否脏行」，或在末尾加一条汇总行 | 破坏既有三列结构 | 用户确认下游按列位置解析，加列或加行直接把下游解析炸掉 |
| B（选定）打到 stderr | 结束时向 stderr 输出一行含具体行数的统计，0 行不出声 | 只能知道丢了多少，不知道丢了什么；stderr 为空有两种含义（无脏行 / 根本没跑到） | 无 |
| C 旁路文件记录脏行 | 把原始脏行原样写到另一个文件 | 多一个文件要管、要清理、要约定放哪、要说明谁来删 | 用户要的是「知道丢了多少」，不需要回查具体内容；为不需要的能力引入一个新产物不划算 |
| D 遇到脏行直接失败 | 非零退出码 | 一行脏数据卡死整次导出 | 与「继续跳过」的既有行为直接冲突，运维定时任务里更危险 |
| 什么都不做 | 保持静默跳过 | 导出结果无法自证完整性 | 用户明确要这个信号，是三个痛点之一 |

选定 B。理由：这个信息的用途是「让人对导出结果有信心」，不是「排查脏行内容」，所以只要一个数字就够；而 CSV 那条通道被「列结构锁死」这个更硬的约束封掉了，stderr 是唯一既不破坏既有契约、又能被人和脚本同时看见的通道。落进契约的形态：`强约束` 写「新增信息只走 stderr，不许写进 stdout」，加 AC-004。

### D-2 验证路径：新建 pytest 基建，还是手工复现

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A（选定）新建最小 pytest | 建 `tests/`、一份 fixture 日志、一个测试文件与 `-k` 约定 | 一次性约 0.5 人日；本仓库此前一个自动化验证入口都没有，这笔建设不是免费的 | 无 |
| B 真实日志黄金用例 | 用户提供真实片段，落盘输入 fixture + 期望 CSV 逐字节比对 | 用户要提供数据并确认脱敏 | 用户确认真实日志没有额外脏行形态、编码一直是 UTF-8，`[B]` 的额外成本换不到额外信息 |
| C 手工按步骤复现 | 按 12 行对照表逐条跑命令看结果 | 零建设，但每次改动都要人跑一遍；「文件没被动过」「stdout 没被污染」人眼最容易漏 | AC-003 错了会让依赖默认路径的下游静默断链，这条不能靠「记得跑一遍」 |
| 什么都不做 | 只靠 review diff | 判不了退出码，判不了 stderr | 本次有 5 行差异只体现在退出码和 stderr 上，review 看不出来 |

选定 A。理由：四条 AC 里有三条的判定对象是「退出码」和「有没有发生副作用」，这两样恰好是人工验证最容易漏看、机器最容易锁死的；基建一旦建起来，第四条几乎零边际成本搭车，而用户也确认「这脚本以后还得改」，建设成本会被后续改动摊薄。落进契约的形态：`强约束` 写「必须走本仓库新建最小 pytest 这条路径，不引入 tox / nox / CI 平台配置」，并把基建写进 `范围` 的「做什么」和「要落盘的东西」。

### D-3 默认行为要不要顺手改成「更合理」的样子

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A 默认改成最近 7 天 | 零参数时只导最近 7 天 | 悄悄改变现存调用方拿到的数据，且改变没有任何提示 | 用户确认有别的脚本依赖默认路径与全量语义 |
| B（选定）零参数完全等价 | 三个参数全为可选，缺省行为逐字节等于今天 | 默认输出路径以后永远不能挪到更合理的位置（比如 `out/`） | 无 |

选定 B。理由：这个脚本的默认调用是别人的生产入口，把「更合理」这件事强加给现存调用方，收益归自己、风险归他们。落进契约的形态：`强约束` 写默认输出路径与文件名不许变，加 AC-003。
