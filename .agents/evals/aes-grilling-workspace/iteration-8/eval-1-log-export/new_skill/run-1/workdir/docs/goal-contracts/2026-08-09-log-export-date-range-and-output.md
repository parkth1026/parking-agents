## 目标

运维可以只导出指定日期区间的日志并指定输出文件，同时看得见有多少行因无法解析被跳过；不带参数调用时的产物与改动前逐字节一致。

## Why

- 现在每次都导出全部日志，又慢文件又大；日志按天堆积，但脚本无条件读 `logs/*.log` 的全部行。
- 输出路径写死在脚本所在目录下的 `export.csv`，导给分析同事之前要手工搬运或改名。
- 无法解析的行被静默丢弃，日志格式一变就少数据，而少数据这件事目前没人会发现。
- 做到之后：常规导出只取需要的日期段，产物可以直接落到目标位置，丢行有数字可查，而所有老调用方式一个都不断。

## 范围

做：给 `export_logs.py` 增加三个命令行参数 `--from`、`--to`（都收 `YYYY-MM-DD`，区间两端都含）与 `--output`，并在导出结束时把被跳过的行数打到 stderr。

不做：按日志级别过滤、压缩输出（gzip 等）、自动上传到任何目标位置、CSV 之外的输出格式（JSON / Parquet）、增量续导、改动 CSV 列结构、改动默认输出落点、递归扫描 `logs/` 的子目录、把被跳过的原始行落成旁路文件。

## 强约束

- 必须走标准库 `argparse`，不引入任何第三方依赖；脚本保持单文件、拷到装了 Python 的机器上不做安装即可运行。不引入 click、typer，也不手写 `sys.argv` 解析。
- CSV 表头逐字节保持 `timestamp,level,message`，列顺序不动，不新增列——下游是按列位置解析的。
- 输出编码保持 UTF-8 无 BOM；行尾保持现有产物形态（`csv.writer` 配 `newline=""`，Windows 下为 CRLF）。
- 不传 `--output` 时，输出路径与文件名保持为脚本所在目录下的 `export.csv`，不改成当前工作目录。
- 覆盖语义不变：目标文件已存在即整体覆盖，不追加、不备份、不加时间戳。
- 日志来源不变：脚本所在目录下的 `logs/*.log`，按文件名排序，不递归子目录。
- 可解析行的判定规则不变：只认 `DEBUG|INFO|WARN|ERROR` 与 `YYYY-MM-DD HH:MM:SS`；无法解析的行跳过、不中断、不进 CSV。
- 导出成功时 stdout 仍只有 `exported N rows -> 路径` 这一行，格式不变；本次新增的诊断输出一律走 stderr。
- 过滤结果为零行时仍写出只含表头的 CSV，并以退出码 0 结束。
- 参数校验在打开输出文件之前完成；校验失败时不创建、不截断、不覆盖任何输出文件。
- 落盘后的 fixture（D-01 到 D-05）与本契约「访谈记录」里的行为对照表一律声明为不可修改：执行时改产品，不改对照物和期望值。

| AC-005 不带参数产物与改动前逐字节一致，这条错了会怎样：行尾从 CRLF 变 LF 或多出 BOM，编辑器看不出来但 Excel 和下游解析器有反应 | A `[B]` 改动前存产物基线，改动后逐字节 diff 66% / B `[A]` 只断言表头与总行数 24% / C `[D]` 检查源码里 csv.writer / newline / encoding 未改 10% | A，因为它一次兜住列名、列顺序、编码、行尾、覆盖语义五件事，正是用户说绝对不能动的那些 | A。用户原话：「基线一定要在动手改之前生成,这条你自己也写了。」 |
| AC-006 零行仍产出只含表头的 CSV 并退 0，这条错了会怎样：下游可能拿到「文件不存在」，读文件那步直接炸 | A `[A]` 用 `--from 2026-08-02` 跑一次断言退 0 且只有表头 64% / B `[C]` 用户自己试一次 21% / C 不单独立这条，零行由 AC-001 第四组黄金用例覆盖 15% | A，因为它把「空结果不是错误」独立钉住 | C —— 删掉。用户原话：「零行的情况让 AC-001 的第四组用例带着验就够了,别单独占一条。零行必须退 0 这件事你写进强约束,别写成 AC。」 |

裁决结果：AC 从 6 条收敛为 5 条。AC-006 删除，其判定内容并入 AC-001 的第四组黄金用例（`expected-empty.csv`），「零行仍写只含表头的 CSV 并退出 0」按用户要求改记进 `强约束`。AC-003 采用用户改写后的措辞。这个 15% 的选项被选中，正是这份记录要留下的东西：当时我判它只有 15%，理由是「独立钉住更稳」，用户按「同一件事不判两遍」翻掉了，下次改这份契约的人应该先重新验证零行这条还有没有人挡着。

## 设计取舍

### D-1 参数解析走标准库还是第三方 CLI 框架

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A click 或 typer | 引入第三方 CLI 框架定义三个参数 | 脚本从「零依赖单文件」变成「先装依赖」，要新增 requirements.txt 与安装说明，运维机器上多一个会坏的环节 | 本次只有三个参数，框架的收益（子命令、彩色帮助、自动补全）基本用不上，换不回部署复杂度 |
| B（选定）标准库 argparse | 用 argparse 定义 `--from` / `--to` / `--output`，`--help` 白送 | 帮助文本朴素；参数多起来后写法略啰嗦 | 无 |
| C 手写 `sys.argv` 解析 | 自己循环解析参数 | `--help`、参数缺值、未知参数报错都要自己写一遍 | 这些恰好是最容易出边界 bug 的部分，而 argparse 免费给了 |
| 什么都不做 | 继续没有任何参数 | 每次全量导出、路径写死原样保留 | 正是这次要解决的问题 |

选定 B。理由：这个脚本现在只 import 标准库、没有 requirements.txt、没有虚拟环境，实际部署方式就是「拷一个文件过去跑」。引入框架的代价不是几行代码，是把一个无环境依赖的运维工具变成有环境依赖的工具，而它换来的能力这次一条也用不上。
落进契约的形态：`强约束` 写「必须走标准库 argparse，不引入任何第三方依赖」。

### D-2 输出路径可配之后，默认落点要不要顺手修正

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A 默认落点改成当前工作目录 | 加 `--output`，同时把默认从脚本目录改成 cwd | 破坏性变更：写死老路径的下游会静默读到一份不再更新的旧文件 | 失败形态是「文件还在、只是不更新」，是最难发现的一类；本次没有任何收益能抵掉它 |
| B（选定）默认落点一字不变 | 加 `--output`，不传时仍写脚本所在目录下的 `export.csv` | 把一个反直觉的默认（产物落在脚本旁边而非 cwd）永久固化，以后想改要另开一次带迁移期的变更 | 无 |
| C 改成默认写 stdout | 数据走 stdout，落盘交给 shell 重定向 | 现有 stdout 上的 `exported N rows -> 路径` 得挪走，所有现有调用方式全部作废 | 与「老调用方式一个都不能断」直接冲突 |
| 什么都不做 | 路径继续写死 | 每次导给别人都要手工搬运 | 正是这次要解决的痛点之一 |

选定 B。理由：用户明确说别的脚本靠默认路径捞文件。默认落点属于公共契约，改它的收益是「以后不用解释这个反直觉行为」，代价是「现在可能静默打断下游」，这两者不在同一个量级。反直觉的默认可以留给一次专门的、带迁移期的变更去处理，不该搭在一次纯增量改进里。
落进契约的形态：`强约束` 写「不传 `--output` 时输出路径与文件名保持为脚本所在目录下的 `export.csv`，不改成当前工作目录」。

### D-3 过滤维度只取时间，不取日志级别

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A 时间与级别都做 | 同时加 `--from`/`--to` 与 `--level` | 验收面翻倍（时间边界、级别大小写、两者叠加各要验）；级别过滤一上线，「多级别」「WARN 以上」马上跟着来 | 用户明确说级别过滤以后再说；这次交付会因此变慢 |
| B（选定）只做时间 | 只加日期区间过滤 | 只想看 ERROR 的人还得自己在 CSV 里再筛一遍 | 无 |
| C 只做级别 | 只加 `--level` | 历史越长文件越大这件事没解决，同一个痛点会回来 | 没有对准「又慢文件又大」的根因 |

选定 B。理由：日志按时间堆积，切时间就是切体积，一次砍掉的量最大，而且过滤发生在解析后、写盘前，只多一个判断，回归面最小。
落进契约的形态：`范围` 的「不做」里写明不做按日志级别过滤。
