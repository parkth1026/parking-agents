# 过程判断记录

## 第 1 步：查了哪些事实

工作仓库只有三个文件（`PERSONA.md` 属评测装置，不算产品代码），所以没有派 subagent——skill 规定「存在两个以上互不依赖的事实问题且可以创建 subagent 时」才并行派遣，这里事实面小到宿主直接读完更快。

查到并写进上下文、告知用户、不占提问的事实：

1. `workdir/server.mjs` 第 6-11 行：`/summary` 命中后连着 `await sleep(180)` / `(160)` / `(150)`，串行相加固定约 490ms，随后 `res.end(JSON.stringify({ items: 12, total: 3200 }))`。注释自述「三段串行聚合，各自模拟一次慢查询」。结论：慢是写死的串行等待，不是抖动、不是数据量、不是吞吐瓶颈；三段之间无数据依赖迹象；优化理论下限是最慢那段约 180ms。这条事实直接决定了 200ms 这个门槛「恰好只有真并发才过得去」。
2. 除三段等待外没有别的耗时来源：第 9 行直接序列化返回，无中间件、无 IO。
3. **固定必查项：仓库现有验证基建 = 无。** 全仓只有 `README.md` 与 `server.mjs`：无 `package.json`、无 `node_modules`、无 test 目录、无 CI 配置（无 `.github/`）、无 lint 配置、无 fixture 约定、无任何基准或压测脚本。`README.md` 自述「仓库暂无测试或基准工具」。据此第 4 步的候选池只剩三项：新建基准脚本（代价含建设工作量）、用户本人手动跑、用户提供真实数据/场景。候选里明确写出「上压测平台」的真实代价是「先接入环境与权限，周期以天计」，而不是含糊的「代价较高」。
4. 其它路由：`/` 以外任何路径返回纯文本 `ok`；启动打印 `listening :3000`。这些进了不变清单。
5. 术语核对：用户说的「太慢」「秒开」是产品口径，仓库里没有任何对应的数字定义，因此「秒开换算成接口门槛是多少」是 `User decision`，不是可查事实——这条作为第 1 轮问题 1 提出。

事项分筐：

- `Fact`：490ms 的成因、三段无依赖、零验证基建、其它路由行为、启动方式。
- `User decision`：门槛值、尺子形态、尺子锁不锁、报文兼容口径、实现路径与排除项、范围边界、并发化后单段失败时的对外行为。
- `Agent-owned`：并发化的具体写法（`Promise.all` 还是别的）、bench 脚本的输出排版、分位数的插值细节。
- `Blocked`：无。全部所需材料都在本仓库内，不需要外部凭据或环境。

第 5 个 `User decision`（实现路径）之所以不是 `Agent-owned`：并发化、进程内缓存、外部缓存、改部署四条路都成熟，但成本结构完全不同（新鲜度语义 / 运维组件 / 部署形态），skill 规定这种情况选哪条归用户。

## 第 3 步：出不出对照物，以及理由

**判定：不出界面 mock，出行为对照表。**

- 不出 mock：仓库里没有任何页面、组件或前端代码，本次改动落在后端 HTTP 处理函数内，没有用户可见界面被新增或改动。
- 出行为对照表：这一条是本次唯一需要判断的边界情形，理由记在这里。纯性能优化容易被草率归入「不触及公共行为的内部改动」从而跳过第 3 步，但这次不是：
  - `/summary` 的响应耗时本身是对外可观察的行为，而且有明确的今昔差异（约 490ms → 约 180ms），可以写成具体数据的对照行；
  - 更关键的是「不变清单」在这次有实质内容且用户确实依赖它（报文取值、Content-Type、状态码、其它路由、启动方式、依赖、失败语义），skill 明确说不变清单与变化行同等重要——用户要确认「变的是他要的」，也要确认「不变的是他依赖的」；
  - 并发化顺带暴露出一个现状里根本不存在的行为（任一段失败时怎么办），这必须让用户看见并裁决，对照表是让它显形的地方。
- 因此按 skill「改变现有可观察行为出行为对照表」执行，且按规定不单独成文件，整张写进 Goal Contract 的「访谈记录」一节。本次没有产出 mock/html 文件，`outputs/` 里也就没有 html。
- 对照表在第 2 轮一次确认通过（画像覆盖的 N1、N6 与变化行 2/3 与表一致，其余按画像规定取推荐项），无第二版迭代。确认版对照表在契约里被声明为访谈产物并从「读什么」指路；D-01 快照声明为不可修改，与锁尺子同理。

## 提问轮次

共 4 轮，全部退化为编号文本（宿主无 `AskUserQuestion`），逐字原文见 `outputs/questions.md`。

1. 第 1 轮：先报事实（4 条，不占提问）+ 给完整推荐草案当靶子（目标一句、做什么一句、不做什么一句、验收大致方向）+ 一次发全 7 个互不依赖的材料歧义。每题都带已知证据摘要、2-4 个互斥选项、推荐项和真实代价。轮末逐维度自评并显式报告（意图/结果/边界/约束/现状 全部「已定」）。
2. 第 2 轮：行为对照表（4 变化行 + 2 边界行 + 9 项不变清单），邀请逐行质疑。一轮确认。
3. 第 3 轮：3 条验收条件各带候选，候选主轴是「这条错了会怎样 → 那就这么验」；概率与途径由我从仓库出，影响由用户出。数字门槛按 skill 要求把三件事一并进候选：门槛值、用什么尺子量、尺子锁不锁。另附「哪三件事不立 AC」的分筐说明。轮末做收口自评。
4. 第 4 轮：落盘前的最终确认（目标/范围/强约束/AC/阻塞项摘要），用户确认后才写文件。

没有跳过任何提问或确认环节。第 2 轮和第 4 轮虽然是「确认」而非「提问」，也照样把完整原文写进了 questions.md。

## 遇到的困难

1. **第 3 步的分类是真正的判断点。** 纯性能优化「报文一个字不变」很容易被读成「无既有行为可对照 → 跳过第 3 步」。我选择出行为对照表，理由如上；如果按「跳过」执行，第 4 步就得靠 4a 从零补例子，而且那 9 项不变清单没有任何环节会让用户看见——`不引入缓存中间件`、`不改部署方式` 这两条恰好是用户主动提出的，可见他对不变量确实在意。
2. **AC-003 的分筐与规范有张力。** `goal-contract-shape.md` 明确规定「必须保持不变的现有行为」进 `强约束`、不占 AC 编号，而「报文不变」形式上正是不变量。但它同时给了自查问题「把它去掉会放过哪一种具体的错误交付」，这次答得出非常具体的一种（砍掉一段聚合换速度，total 从 3200 变 2000，且因为变快了看起来像成功）。我的处理是把这个张力本身作为一个候选交给用户裁决（第 3 轮候选 3 明写了「它该占不占编号」），推荐立成 AC 并落 fixture，同时 `强约束` 保留不变量表述——AC 判一次、强约束在整个实现过程中都成立，朝向不同。这条判断已完整记进契约的「设计取舍 D-3」。
3. **优化型目标的作弊面比一般任务大。** 门槛值、尺子、期望值三样全是这次新造的，执行 Agent 同时握着工件和尺子。用户自己也点破了这一点（「改了等于作弊」）。落地时把 `scripts/bench.mjs`（D-02）和优化前快照（D-01）双双声明为不可修改，并要求快照必须实际抓取而不是照源码推断写出——这次两者恰好一样，所以这条约束此刻看起来多余，但它防的是「从源码抄期望值」这个习惯。
4. **200ms 门槛贴着理论下限。** 理论最好约 180ms，余量只有 20ms 左右，本机有负载时 p95 存在偶发不过的可能。我在候选 1 里把这个代价原样写出来了，用户仍选 200ms（画像明确指定）。缓解手段是样本数 50 与 p95（而非 max）口径，已写进 AC-002 的口径检查。
5. **门槛的「本机测量」是弱约束。** 用户说「本机测量即可」，意味着换机器结论可能不同。这不构成 `Blocked`（不缺任何东西），但它是这份契约的已知局限：AC-001 的判定绑定在执行者的机器上。契约里把测量口径（50 次、p50/p95、不排除首发）写死到可复现的程度，是我能做的最大压缩。
6. 工具层面无坑：validator 一次通过，`AC_COUNT: 3`，无 WARNING、无 ERROR，退出码 0。写作时避开了 validator 的两个已知敏感点——用「低于 200ms」而不是紧贴字母的 `<...>` 形式以免被判成模板占位符，正文不出现 TODO/TBD/FIXME 一类标记。
