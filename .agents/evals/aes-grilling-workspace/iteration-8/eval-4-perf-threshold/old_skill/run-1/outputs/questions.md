```text
先把仓库里查到的事实摆出来，这些不占提问：

【事实 1】/summary 现在慢是写死的，不是抖动。
server.mjs 第 6-11 行：命中 /summary 后连着 await sleep(180)、await sleep(160)、
await sleep(150) 三次，串行等，固定 490ms 左右，然后返回
{"items":12,"total":3200}。注释写的是「三段串行聚合，各自模拟一次慢查询」。
也就是说三段之间没有数据依赖的迹象，490ms 是三段相加得来的，不是某一段特别慢。

【事实 2】这个仓库现在没有任何验证基建。
整个仓库只有 README.md 和 server.mjs 两个文件：没有 package.json，没有
node_modules，没有 test/ 或 __tests__ 目录，没有 CI 配置（无 .github/workflows），
没有 lint 配置，没有 fixture 约定，也没有任何基准/压测脚本。README 自己写着
「仓库暂无测试或基准工具」。
这一条直接决定了后面「怎么验」的候选池：这个项目此刻只有两条路——你本人手动跑一遍
看结果，或者先把基建建起来（这份工作量要算进这次的成本，不能当成免费的）。

【事实 3】这次不涉及界面。
改的是后端 HTTP 接口，没有任何页面或组件在这个仓库里，所以我不做界面 mock。
但「优化前后接口对外表现有什么变、有什么不许变」是可观察行为的今昔差异，
我会出一张行为对照表让你逐行质疑（第 2 轮）。

下面是我的推荐草案，它是给你挑毛病的靶子，不是结论。你改哪条就是哪条：

- 目标：把首页依赖的 /summary 接口响应耗时压到「秒开」能接受的范围内，
  且返回内容不变。
- 做什么：只改 /summary 这一个接口内部的聚合方式（三段串行改成并发），
  并新建一个能重复测量它耗时的基准脚本。
- 不做什么：不动前端、不动其它路由、不引入外部缓存组件、不改部署方式、
  不改 /summary 的返回字段和取值。
- 验收大致方向：用一个定稿后不许再改的基准脚本量出 p95 耗时低于某个门槛，
  同时证明返回报文和优化前一模一样。

以下 7 个问题互不依赖，你可以一次全回答，比如「1 选 B，2 选 A 但样本改成 100 次，
5 排除 C 和 D，其余按推荐」。

────────────────────────────────────────
问题 1：「秒开」换算成 /summary 的耗时门槛，定在哪个数？

已知证据：现在固定约 490ms（三段 180+160+150 串行）。三段真并发后，理论下限是
最慢那段 180ms 左右，再加上 HTTP 与序列化开销。你说的「秒开」是首页整体体感，
但我这次只能对 /summary 这一个接口下判定，前端渲染部分不在这个仓库里。

- [A] p95 低于 200ms。含义：三段必须真并发（否则达不到），几乎贴着理论下限
  180ms，留给自己的余量只有 20ms 左右。代价：本机跑基准时如果机器有负载，
  可能偶发不过，会有一定的翻车率。
- [B] p95 低于 300ms。含义：同样要求并发，但留了 120ms 余量，判定稳定。
  代价：门槛比你能拿到的最好结果宽松，等于允许实现留一段没优化干净也算过。
- [C] p95 低于 500ms。含义：几乎等于现状（490ms），这个门槛拦不住任何东西。
  代价：这条 AC 形同不存在。
- [D] 不定绝对值，定相对值：比优化前快 60% 以上。代价：需要先测一份优化前的
  基线并落盘，否则「比之前」没有参照物；基线一旦机器换了就不可比。

推荐 [A] p95 低于 200ms。理由：三段并发是这次唯一实质的优化手段，200ms 恰好是
「只有真并发才过得去」的那条线，能让这条 AC 真的起到拦截作用。翻车率的问题用
问题 2 的样本量和统计口径来压。

问题 2：用什么尺子量这个门槛？仓库现在什么都没有，所以尺子必须现造，
造哪一把是你的决定。

已知证据：无 package.json、无依赖、无基准工具（事实 2）。所以任何选项的代价里
都包含「先把它建起来」。

- [A] 新建 scripts/bench.mjs（零依赖，Node 原生 http/fetch）：对 /summary 连续
  发 50 次请求，输出 p50/p95。代价：要写这个脚本，大约几十行，半小时内的事；
  它只测单机单连接的串行时延，测不出并发下的表现。
- [B] 用 curl -w '%{time_total}' 手动跑几次，肉眼看数。代价：零建设成本，
  但没有 p95、不可重复、不同人跑出不同结论，验收阶段没法当判定依据；
  也没法防止「我这次运气好」。
- [C] 引入 autocannon 或 k6 做真压测（并发 + QPS + 分位数）。代价：要引入
  package.json 和外部依赖（autocannon）或安装 k6 二进制；能测并发行为，
  但这次的慢是固定 sleep 不是吞吐瓶颈，压测量出来的主要还是那 490ms，
  多出来的建设和依赖买不到对应的信息量。
- [D] 上团队的压测平台跑。代价：需要接入、需要环境和权限，不在本仓库内，
  周期以天计；对一个 sleep 造成的固定时延，收益极低。

推荐 [A]。理由：这次要判定的是「三段有没有真并发」，串行单连接的 p95 就足以
判定；零依赖能让基准脚本跟仓库现状（无 package.json）不冲突，也不给这次任务
附带一堆依赖决策。

- [B] 只要求结构不变，取值允许变（因为三段聚合本来就是模拟的）。代价：

  在按 text 解析会受影响；它是另一件事，会把这次的范围撑大。

推荐 [A]。理由：这次是纯性能优化，报文是你依赖的东西，任何变化都是回归而不是

- [D] 不改代码，改部署（多实例 + 前置 CDN/网关缓存）。代价：不解决单次请求
```
