# Goal Contract: 把 /summary 的三段串行聚合改成并发，p95 耗时压到 200ms 以下且报文不变

- Status: Ready
- Target: webapi 仓库（server.mjs 的 `/summary` 路由，新增 scripts/bench.mjs）
- Updated: 2026-08-09

## 原始请求

> 首页 /summary 接口太慢了，想优化一下。先写份契约。

访谈中的补充（用户原话）：

> 首页要等 /summary，产品要求「秒开」，现在明显超过半秒。
>
> 门槛：p95 低于 200ms，本机测量即可，不上压测平台。
>
> 仓库没有基准工具。新建 scripts/bench.mjs：对 /summary 连续请求 50 次，输出 p50/p95。
>
> bench 脚本一旦定稿，优化过程中不许改它，改了等于作弊。
>
> 响应内容不能变：items/total 的值必须和现在一致。
>
> 不做的：不引入缓存中间件（Redis 之类），不改部署方式。

## 目标

首页依赖的 `/summary` 接口从现在约 490ms 降到连续 50 次请求的 p95 低于 200ms，且响应报文与现在完全一致。

## Why

- 首屏渲染阻塞在 `/summary` 上，现在固定约 490ms，产品要求的「秒开」达不到，前端同事被首页白屏拖住。
- 这个耗时不是抖动也不是数据量问题，是三段互不依赖的聚合被串行执行、等待时间相加造成的。
- 做到之后首屏等待降到单段聚合的量级，并且仓库第一次拥有一个可重复的耗时基准，后续任何人把它改慢都能被同一把尺子量出来。

## 范围

做什么：

1. 改 `server.mjs` 里 `/summary` 的三段聚合，让三段并发执行，总等待从三段之和降到单段最大值。
2. 新建 `scripts/bench.mjs`：零依赖，对 `/summary` 连续发 50 次请求，打印 p50 与 p95，p95 不低于 200ms 时以非 0 退出码结束。
3. 落盘一份优化前 `/summary` 响应体的快照 fixture，用于优化后的逐字节回归比对。该快照必须从当前 `server.mjs` 实际请求一次抓取，不允许照源码推断写出。

不做什么：

- 不动前端与首屏渲染代码（不在本仓库）。
- 不动 `/` 等其它路由。
- 不引入 Redis 之类的外部缓存中间件。
- 不改部署方式：不加实例、不加网关或 CDN 缓存。
- 不以缓存（含进程内内存缓存）作为本次达标手段；达标必须来自并发化本身。
- 不改 `/summary` 的报文字段、取值、状态码与 Content-Type。
- 不做聚合失败时的降级返回（部分数据、默认值填充都不做）。
- 不引入 lint、CI 或单元测试基建，本次只建基准脚本这一件基建。

## 强约束

- `/summary` 响应体的 `items`、`total` 取值与 JSON 结构与现状一致（`items` 为 12，`total` 为 3200）。
- `/summary` 不显式改动 Content-Type，状态码仍为 200。
- 其它任何路径继续返回纯文本 `ok`；启动方式仍是 `node server.mjs`，监听 3000 端口并打印 `listening :3000`。
- 必须走并发化这条路，不引入外部缓存中间件，不改部署方式。
- 仓库保持零运行时依赖，`scripts/bench.mjs` 只用 Node 原生能力实现。
- 聚合任一段失败时整个 `/summary` 失败，不降级、不返回部分数据。
- `scripts/bench.mjs` 与 D-01 的响应快照定稿后不可修改。达标要靠改 `server.mjs`，不靠改测量或改期望值；确实需要调整门槛或统计口径时回到本契约重定，不在实现过程中就地改动。

聚类结果 3 条 AC，是数出来的：4 个变化行加 2 个边界行聚成 AC-001 与 AC-002 两条（一条判「数字达标」，一条判「尺子口径」），不变清单里唯一需要判定动作的 N1 成为 AC-003；其余不变项进「强约束」。

第 3 轮后收口自评：还想问的（bench 输出要不要带单位、fixture 用什么扩展名）不同答案只改变 Verify 的措辞，不改变执行 Agent 到底要跑什么、跑到什么程度，故收口。

### 第 4 轮：落盘前确认

向用户展示目标、范围、强约束、3 条验收条件与「挡着的事：无」的摘要，用户确认表达了当前共同理解，无修改意见，随后落盘。

## 设计取舍

### D-1 优化手段：并发化，还是缓存，还是改部署

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A 进程内缓存 | `/summary` 前面加内存 Map 加 TTL | 第二次之后接近 0ms；但引入数据新鲜度问题（TTL 定多长、要不要主动失效），首次请求仍是 490ms | 首页白屏这个具体痛点里，最疼的就是首次请求；缓存只解决一半，还额外背上新鲜度语义 |
| B（选定）三段并发 | 三段无数据依赖的聚合并发执行，总等待从三段之和降到单段最大值 | 改动面几行，可逆，零新增依赖，不动部署；优化上限就是最慢那段约 180ms，再要更快得动数据源本身 | 无 |
| C 外部缓存中间件（Redis 之类） | 引入 Redis 缓存 `/summary` 结果 | 新增一个必须运维的组件，本地开发、部署、故障面全部跟着变 | 一个单进程内部面板背不起这个运维成本，用户也明确排除 |
| D 改部署 | 多实例加前置网关或 CDN 缓存 | 不解决单次请求时延，只提高吞吐；要改部署方式 | 这次的痛点是单次时延，方案答的不是这个问题；用户也明确排除 |
| 什么都不做 | 保持 490ms | 首页继续白屏，产品的秒开要求达不成 | 就是这次要解决的问题 |

选定 B。慢的成因查清了就是串行等待，不是吞吐不够也不是数据源本身慢，所以对着成因改是最短的一刀，别的方案都是绕开成因去补偿后果。落进契约的形态：`强约束` 写「必须走并发化，不引入外部缓存中间件，不改部署方式」，写成约束而不是实现步骤，约束不会过时。

### D-2 尺子怎么造，以及为什么要锁

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A 手动 curl 目测 | `curl -w` 跑几次看数 | 零建设成本；不可重复、没有分位数、不同人跑出不同结论 | 数字门槛需要一把所有人都能复现的尺子，目测给不出判定 |
| B（选定）零依赖 bench 脚本 | 新建 `scripts/bench.mjs`，连续 50 次请求，输出 p50/p95，p95 不达标非 0 退出 | 要写几十行；只测本机单连接串行时延，测不出并发下的真实表现 | 无 |
| C 引入 autocannon 或 k6 | 加依赖或装二进制做真压测 | 引入 package.json 与外部依赖，或安装外部二进制；能测并发但这次的慢是固定等待不是吞吐瓶颈 | 多出来的建设与依赖买不到对应的信息量 |
| D 上压测平台 | 接入团队压测平台 | 要环境与权限，周期以天计，不在本仓库内 | 对一次由固定等待造成的时延，投入产出完全不成比例；用户明确排除 |

选定 B，并把它连同 D-01 快照一起声明为不可修改。这是优化型目标的特有风险：门槛写在契约里，而量门槛的尺子和期望值都是这次新造的，执行 Agent 手上同时握着工件和尺子时，改尺子永远比改工件省力。锁住尺子之后，`AC-001` 唯一的达标路径就只剩改 `server.mjs`。落进契约的形态：`强约束` 写「`scripts/bench.mjs` 与 D-01 定稿后不可修改，要改门槛或口径回到本契约重定」。

### D-3 报文不变：写成强约束，还是立成一条带黄金用例的 AC

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A 只写强约束 | 「items/total 取值与结构不变」进 `强约束`，不占编号 | 符合「不变量进强约束」的常规分筐；但没有对应的判定动作，回归靠执行 Agent 自觉 | 这次恰好存在一条极省力的作弊路径（砍掉一段聚合换速度），只靠自觉挡不住 |
| B（选定）立成 AC-003 加黄金用例 | 优化前响应快照落盘为 D-01，优化后逐字节比对 | 多一个 fixture 文件，占一个 AC 编号 | 无 |
| C 内联断言命令 | 一句 curl 加 grep，期望值写在命令里 | 与 B 判定力相当，但期望值没有落盘 | 下次改动时看不出「当初的正确答案是什么」，fixture 比命令里的字符串活得久 |

选定 B。判据用的是契约规范里的自查问题：把这条去掉会放过哪一种具体的错误交付？答案很具体——「为了快把某段聚合砍掉，total 从 3200 变成 2000，而且因为变快了看起来像成功」。这个具体形态答得出来，说明它值一个编号。同时 `强约束` 里保留取值与结构不变的表述：AC 负责判一次，强约束负责在整个实现过程中都成立，两者朝向不同，不算判两遍。
