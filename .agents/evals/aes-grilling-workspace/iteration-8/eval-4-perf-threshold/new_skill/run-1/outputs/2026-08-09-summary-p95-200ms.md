# Goal Contract: 把 /summary 的本机 p95 压到 200ms 以内，响应体一字节不变

- Status: Ready
- Target: `server.mjs`（webapi 内部面板后端）
- Updated: 2026-08-09

## 原始请求

> 首页 /summary 接口太慢了，想优化一下。先写份契约。

访谈中的补充原话：

> 首页要等 /summary，产品要求「秒开」，现在明显超过半秒。
> 门槛 p95 低于 200ms，本机测量即可，不上压测平台。
> 仓库没有基准工具。新建 scripts/bench.mjs：对 /summary 连续请求 50 次，输出 p50/p95。
> bench 脚本一旦定稿，优化过程中不许改它，改了等于作弊。
> 响应内容不能变：items/total 的值必须和现在一致。
> 不引入缓存中间件（Redis 之类），不改部署方式。

## 目标

`/summary` 在本机基准脚本下的 p95 从现状约 538ms 降到 200ms 以内，同时响应体与现在逐字节一致。

## Why

- 首页首屏渲染要等 `/summary`，现状本机实测 min 506ms / p50 509ms / p95 538ms，明显超过半秒，产品要求的「秒开」达不到。
- `/summary` 的三段聚合互不依赖却串行等待，这半秒里有约 310ms 是纯粹的等待重叠损失，属于白给的延迟。
- 仓库此刻没有任何基准工具，「快了多少」说不清；这次一并把尺子建起来，之后的性能回归才有基线可比。

## 范围

做：

- 让 `/summary` 的三段聚合并发执行，消掉串行等待。
- 新建 `scripts/bench.mjs` 作为本次唯一的测量尺子（连续 50 次顺序请求，输出 p50/p95）。
- 落盘现状响应体 fixture，供逐字节比对。

不做：

- 不引入 Redis 一类缓存中间件，也不加进程内内存缓存或 TTL。
- 不砍掉任何一段聚合查询，不降低其精度，不让单段查询「假装」变快。
- 不改响应体、不改响应头（包括不补 Content-Type）、不改状态码。
- 不动 `/summary` 以外的任何路径。
- 不改部署方式、监听端口和启动命令，不新增运行时依赖。
- 不做前端改动，不改接口形态（不分片、不流式）。
- 不做并发吞吐档的验收，不上压测平台。

## 强约束

- 必须靠三段聚合并发执行达标，不引入任何缓存（中间件、进程内对象、TTL 均不许），不减少查询段数、不降精度。
- `/summary` 的响应体逐字节保持 `{"items":12,"total":3200}`（键序、无空格、无末尾换行），状态码保持 200。
- `/summary` 的响应头保持现状：现在没有 Content-Type，改后也不许新增、删除或修改任何响应头。
- 其它任何路径（`/`、`/other`、任意未命中路径）仍返回纯文本 `ok` 与状态码 200，不引入 404。
- 监听端口保持 3000，启动方式保持 `node server.mjs`，不新增依赖。
- 数据新鲜度不变：每次请求都实时算三段，不复用上一次结果。
- `scripts/bench.mjs` 首版按 D-01 写完即为定稿，此后不可修改：不许放宽采样次数、门槛值、判定分位或比对口径。优化过程中要改的是 `server.mjs`，不是尺子。
- 门槛判定分位固定为 p95。50 次采样里最慢的一次偶发超过 200ms 不算失败（并行后实测 max 约 203ms），后续任何人不得改用 max 判定。
- 确认版行为对照表（见「访谈记录」）不可修改，它是设计输入不是可调整的产物。

## 读什么

- `server.mjs`：`/summary` 的现状实现，三段串行等待在同一个 handler 里。
- `README.md`：本仓库的启动方式，以及「仓库暂无测试或基准工具」这一现状声明。
- 本文件「访谈记录」里的确认版行为对照表：变化行给出 3 个判定例子，不变清单给出 8 条必须保持的行为，AC 就是从它们聚出来的。

## 要落盘的东西

- D-01: `scripts/bench.mjs`：对 `http://127.0.0.1:3000/summary` 连续发 50 次顺序请求（一次返回后再发下一次），统计并打印 p50 与 p95；p95 低于 200ms 且响应体比对通过时退出码 0，否则非零退出。只测顺序时延，不测并发。写完即定稿，之后不可修改。
- D-02: `tests/fixtures/summary-response.json`：现状响应体的逐字节副本，内容为 `{"items":12,"total":3200}`，供 AC-002 比对。期望值取自本机实测，不含真实业务数据。

## 验收条件

- AC-001: `/summary` 在本机基准脚本的 50 次顺序采样下，p95 低于 200ms，且脚本同时打印出 p50。
  - Verify: [A] `node scripts/bench.mjs` → p95 低于 200ms 时退出码 0，并在 stdout 打印 p50 与 p95 两个数字
- AC-002: 优化后 `/summary` 的响应体与优化前逐字节相同，状态码仍是 200。
  - Verify: [B] `node scripts/bench.mjs` 取到的 `/summary` 响应体 → 与 `tests/fixtures/summary-response.json` 逐字节相同，不同则非零退出
- AC-003: 提速来自三段聚合的重叠执行，而不是缓存、砍查询或降精度。
  - Verify: [D] `server.mjs` 的 `/summary` 分支里仍有 180、160、150 三次等待调用，且全文不含模块级缓存变量或 TTL 常量

## 设计取舍

### D-1 用什么手段换速度

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A 三段并发（选定） | 三段互不依赖的等待改为同时进行，取最慢的一段为总耗时 | 地板固定在 180ms，离 200ms 门槛只剩约 12ms 余量 | 无 |
| B 进程内内存缓存带 TTL | handler 里存一份上次结果，TTL 内直接返回 | 首次请求仍约 490ms，而首屏白屏最常发生在首次访问；TTL 内返回旧数字；handler 带上了进程内状态 | 违反「不引入缓存」，且没解决首次访问慢这个真正的痛点 |
| C 砍掉或降精度一段查询 | 少算一段，或用近似值代替 | 能突破 180ms 地板，但 items 或 total 的口径变了 | 违反「响应内容不能变」，把「慢」换成了「错」 |
| 什么都不做 | 保持三段串行 | 首页继续白屏半秒，产品要的「秒开」达不到 | 正是这次要解决的问题 |

选定 A。理由：三段之间本来就没有数据依赖，串行是纯粹的浪费，并行把 490ms 的等待压成
180ms，是唯一既不动数据语义又不动报文的路径，而且改动局限在一个 handler 里，完全可逆。
它的代价是把余量压得很薄——地板 180ms 之上只有约 12ms 空间，这个薄余量是明知代价后
接受的，换来的是「数据永远实时、报文永远不变」。B 的诱惑在于余量宽裕，但它把成本转移
到了首次访问和数据新鲜度上，而首次访问恰恰是首屏白屏发生的时刻。
落进契约的形态：`强约束` 写「必须靠三段并发达标，不引入任何缓存、不减少查询段数、不降精度」。

### D-2 门槛的判定分位与尺子的归属

| 方案 | 怎么做 | 代价 | 为什么没选 |
| --- | --- | --- | --- |
| A p95 判定，尺子定稿后锁死（选定） | 50 次顺序采样取 p95 与 200ms 比；`scripts/bench.mjs` 首版即定稿，之后只许改产品 | max 会偶发超过 200ms，盯单次最慢的人会误以为没达标；换更慢的机器结论会变 | 无 |
| B 门槛放宽到 250ms | 同样采样，门槛抬高 | 250ms 不是产品要的数，而且门槛只会松不会紧，将来没人回来收紧 | 用余量换掉了目标本身 |
| C 要求 max 也低于 200ms | 50 次一次都不许超 | 实测 max 203ms，等于宣布并行这条路不达标 | 会用尺子口径把已被否掉的缓存和砍查询逼回来 |
| 尺子不锁 | bench 脚本随实现一起演进 | 执行 Agent 达不到门槛时，改测量比改产品容易得多 | 优化型目标里不锁尺子等于没有验收 |

选定 A。理由：这次的余量只有约 12ms，判定分位和尺子的可变性因此从细节变成了决定性的
东西——分位选 max 会让唯一可接受的实现方案直接判负，尺子不锁则会让门槛在实现过程中
自己长高。两件事都不是实现细节，所以都写成约束而不是建议。
落进契约的形态：`强约束` 写「判定分位固定为 p95，max 偶发超标不算失败」与
「`scripts/bench.mjs` 首版定稿后不可修改，不许放宽采样次数、门槛值、判定分位或比对口径」。
