# 过程判断记录

## 第 1 步查了哪些事实

固定项（skill 要求无论请求内容都查清的「验证基建」）：

- 目录穷举（含隐藏文件）：仓库只有 `README.md`、`server.mjs`、`PERSONA.md` 三个文件。
- 没有 `package.json`、没有测试文件、没有 `.github/` 或任何 CI 配置、没有 lint 配置、没有
  覆盖率工具、没有 fixture 目录约定、没有仓库级规则文件（CLAUDE.md / AGENTS.md）。
- README 自己写着「仓库暂无测试或基准工具」，与目录事实一致。
- 结论：候选池里没有任何现成基建。可选途径只剩「新建基建」和「用户本人真实测一遍」，
  两者的代价都写进了第 4 步候选（AC-001 的 A 明确写「得先写这个脚本，约二十行，算在
  这次工作量里」，C 明确写「没有可复现数字」）。
- 环境事实：node v24.12.0，`fetch` 与 `node:test` 可用，无需新增依赖就能写基准脚本。

请求牵涉的代码事实：

- `server.mjs` 第 8 行 `await sleep(180); await sleep(160); await sleep(150);`，注释「三段
  串行聚合，各自模拟一次慢查询」。**三段之间没有任何数据传递**，即不存在串行的必要性。
- 现状实测（本机，连续 12 次 `GET /summary`）：min 506.4 / p50 509.2 / p95 538.5 ms。
  验证了用户「明显超过半秒」的说法，并给出了具体基线数字。
- 现状响应：状态码 200，响应体 `{"items":12,"total":3200}`，**Content-Type 为空**（源码里
  只调 `res.end(...)`，从未设过响应头）。其它路径返回纯文本 `ok` + 200，没有 404 分支。
- **可行性探针**（在 scratchpad 里另建一份改成 `Promise.all` 的服务，端口 3101，不碰
  workdir 的产品文件）：连续 50 次，p50 186.1 / p95 188.2 / **max 203.4** ms。

探针这一步是这次调查里最值钱的部分。它把一个本来只能靠猜的关键量算清了：三段并行的
物理地板是 `max(180,160,150)` 等于 180ms，加本机 HTTP 往返约 6 到 8ms，所以**用户想要的
200ms 门槛只剩约 12ms 余量，而单次最慢已经摸到 203ms**。没有这个数字，就问不出第 2 轮那个
「判定分位选 p95 还是 max」的问题，而那恰恰是这次唯一能让整条实现路径直接判负的决定。

Fact / User decision / Agent-owned 分类的实际落点：

- `Fact`：三段无依赖、现状时延、响应形态无 Content-Type、无任何验证基建、并行后的可达时延。
  这些查清后直接告知用户，不占提问。
- `User decision`：目标落在接口还是首屏；允许动到什么程度（并行 / 缓存 / 砍查询）；
  「响应内容不变」的边界含不含响应头；并发档是否在范围内；判定分位与门槛值；尺子锁不锁。
- `Agent-owned`：用 `Promise.all` 还是 `Promise.allSettled`、基准脚本内部怎么算分位数、
  代码怎么组织——局部、可逆、不改外部契约，没拿去问。
- 特别注意一处升级：「用什么手段提速」本来看着像实现细节（Agent-owned），但并行 / 进程内
  缓存 / 砍查询三条路都成熟而成本结构完全不同（数据新鲜度、首次访问、报文口径），按 skill
  规则升级成 `User decision`，成了第 1 轮的 Q2。
- `Blocked`：无。`[B]` 档 fixture 的期望值可由本机实测直接取得，不含真实业务数据，不需要
  用户提供数据、不需要脱敏，所以没有阻塞项。

## 第 3 步判定出不出对照物及理由

判定结果：**不出界面 mock，出行为对照表。**

- 界面 mock 不出：判据是「新增或改动用户可见界面」。本仓库穷举下来只有一个 HTTP 服务，
  一行前端代码都没有，本次改动不触及任何用户可见界面。README 提到「前端首屏渲染依赖它」，
  但那个前端不在这个仓库里，且第 1 轮 Q1 已把目标锁在接口服务端时延、把前端渲染明确划到
  范围外。所以没有可 mock 的对象。
- 行为对照表出：判据是「改变现有可观察行为或兼容性」。这一条我判成「出」，理由有两层。
  一是本次确实改变了 `/summary` 的可观察时序行为（约 506ms 变成约 184ms），时延是外部
  可观察量，不是内部实现细节。二是更实质的：用户在这次需求里最在意的不是「变了什么」而是
  「什么必须不变」（「响应内容不能变：items/total 的值必须和现在一致」）。行为对照表的
  **不变清单**正是为这件事存在的——它让用户确认「变的是他要的」之外，还确认「不变的是他
  依赖的」。跳过它，那 8 条不变量就只能由我单方面写进强约束，用户从未逐条看过。
- 我考虑过判成「跳过」：本次报文逐字节不变，看着像「不触及公共行为的内部改动」，而变化行
  又只有时延一项，容易写成一张与 AC-001 门槛重复的退化表。最后没这么判，原因是这张表的
  重量全在不变清单那半边（8 条，其中「响应头保持现状」「冷热路径同速」「三段一段不少」
  三条是用户自己想不到、只有查过代码的人才知道边界在哪的），而不在变化行。事实证明这半边
  的产出直接变成了强约束里最关键的几条。
- 落盘形态按 skill 规则：行为对照表不单独成文件，整张写进 Goal Contract 的「访谈记录」节
  （第 3 轮）。因此 `outputs/` 里没有 mock.html，也不该有。任务目录 `docs/goal-contracts/`
  下只有契约本身一个文件。

## 遇到的困难

1. **门槛可行性差点成为隐性地雷。** 用户给的 200ms 是个漂亮的整数，但三段并行的地板是
   180ms，余量约 12ms。如果不做 scratchpad 探针，我会照抄 200ms 写进 AC，执行 Agent 跑一次
   bench 发现 max 203ms，然后要么去改尺子、要么去加缓存——两条都是这次明确禁止的。这个坑
   是靠「先在临时目录跑一遍并行版」躲过去的，代价是多花一次探针。
2. **判定分位从细节升级成了决定性约束。** 平常「p95 还是 max」确实只是措辞；在 12ms 余量下
   它决定唯一可接受的实现方案是通过还是判负。所以它没被当成 Agent-owned，而是单独成了
   第 2 轮的问题，并且答案同时写进了 `强约束` 和 D-2 取舍表——包括「后续任何人不得改用 max
   判定」这句，防的是下一个人以为收紧门槛是好事。
3. **尺子由被测者自己造，这是个结构性漏洞。** 用户要的 `scripts/bench.mjs` 现在不存在，
   得由执行 Agent 新建，而它同时是判定它自己是否达标的唯一依据。处理办法是把 D-01 的采样
   口径写死（50 次、顺序、p50 与 p95、退出码规则、只测顺序不测并发），让「定稿」有明确
   所指，再在 `强约束` 里写「首版写完即定稿，不许放宽采样次数、门槛值、判定分位或比对
   口径」。这只能抬高作弊成本，不能根除——如果这份契约要更硬，下一步应该由访谈阶段直接
   把 bench 脚本写出来交付，而不是委托给被测方。这一点我没有越界去做，因为 skill 明确写着
   本技能不实现任务里的目标。
4. **AC-003 的验证形态没有好选择。** 「不是靠缓存或砍查询提速」本质上是个否定命题，零基建
   仓库里没有任何途径能真正证明它。`[D]` 静态检查（58%）和 `[A]` 时延指纹（37%）各能抓一半，
   两个都绕得过。百分比给到 58/37/5 而不是 74/21/5，就是在如实告诉用户「这题我也没有
   好答案」，没有为了显得有主见把分布拉开。
5. **差点漏掉的兼容性细节：`/summary` 现在没有 Content-Type。** 这是实测响应头才发现的，
   源码里看不出来（因为它是「没做的事」）。如果不问 Q3，执行 Agent 重写 handler 时顺手补一个
   `Content-Type: application/json` 完全合情合理，而这是一次没人验收的行为变更。
6. **一处刻意的「不立 AC」。** 「其它路径仍返回 ok」是典型的不变量，按契约规范该进
   `强约束` 而不是占 AC 编号。我把它做成了 AC-004 候选并把「不立」设为推荐项（71%），
   这样用户看得见这件事被考虑过、且知道为什么它最后不在验收条件里，而不是被我悄悄省掉。
   最终 AC 3 条，由 12 个例子（4 变化行 + 8 条不变清单）聚类得出，不是预设条数。
