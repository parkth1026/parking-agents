## 第 1 步调查到的事实（不占提问轮次）

- `src/audit.mjs`：`audit(configPath)` 读取并 `JSON.parse` 配置文件，返回
  `{ rule, level, message }[]`；CLI 分支把结果逐行打印为 `[level] rule: message`，
  末尾打印 `clean` 或 `N finding(s)`，存在 `level === 'error'` 的项时 `exit(1)`，否则 `exit(0)`。
  配置文件不存在或不是合法 JSON 时，`readFileSync`/`JSON.parse` 会抛出未捕获异常，
  Node 打印堆栈并以默认非零码退出——当前没有任何针对这条路径的处理。

  必须先有失败测试，CLI 输出行为变更需同步文本对比断言。→ 决定 Verify 默认档可用 `[A] npm test`。
- `package.json`：`scripts.test` = `node test/run-tests.mjs`，无 CLI 解析框架、无 `--help`。
- `README.md`：只描述了当前文本用法，没有 JSON / `--help` 相关内容。

### Q1. `--json` 与默认文本输出是否互斥？

- 已知证据：现状只有一种输出模式（纯文本）；用户要求「默认文本输出必须保持兼容」，
  但没规定加了 `--json` 之后是否还要同时打印文本。
- 候选：
  - A（推荐）：互斥。提供 `--json` 时 stdout 只输出一个 JSON 文档，不再打印人类可读文本行。
    代价：CI 消费简单干净，但如果有人想同时要两者就拿不到，需要跑两次命令。
  - B：并存。文本仍打印到 stdout，JSON 额外输出到别处（例如另一个 stream 或需要新 flag 指定路径）。
    代价：实现和验证都更复杂，且用户没提出这个需求。
- 代入模拟用户（后端 TL）回答：其他未覆盖问题选推荐项 → **选 A**。

### Q2. `--json` 模式下，配置文件缺失或内容不是合法 JSON 时如何处理？

- 已知证据：现状（不论是否有 `--json`）这条路径会抛出未捕获异常，打印 Node 堆栈，
  以 Node 默认非零码退出——这类输出对机器解析不友好，正是用户提到的「文案变化搞挂」问题的同类风险。
- 候选：
  - A（推荐）：仅在 `--json` 模式下捕获该错误，输出结构化 JSON 错误对象并使用一个新的、
    与「存在 error 级 finding」（退出码 1）区分开的确定退出码（推荐 `2` 表示无效输入）；
    不带 `--json` 时这条路径行为保持现状不变（不属于本次修复范围）。
    代价：新增一个错误处理分支和一个新退出码语义，需要写进 Constraints 防止和现有退出码 1 混淆。
  - B：保持现状，`--json` 模式下遇到这类错误也一样抛出未捕获异常/堆栈。
    代价：CI 解析 JSON 时如果命中这条路径依然会解析失败，没有真正解决用户的痛点。
- 代入模拟用户（后端 TL）回答：其他未覆盖问题选推荐项 → **选 A**，退出码定为 `2`。
