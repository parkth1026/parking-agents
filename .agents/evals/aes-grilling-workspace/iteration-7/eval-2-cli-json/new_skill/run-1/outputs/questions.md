沿用 SKILL.md 第 2 步（批量问清歧义）与第 4b 步（逐条验收条件带候选提问）的做法。

## 起手候选（提问前先给的靶子）

- 目标一句话：为 minicli 的审计命令新增 `--json` 输出选项，供 CI 脚本读取结构化审计结果，
  默认文本输出与退出码完全兼容。
- 做：新增 `--json` 标志，覆盖"无 finding"“有 finding”“无效输入（缺文件/JSON 解析失败）”
  三种情况的结构化输出；README 补充说明。
- 不做：schema 版本化、配置文件、修改现有审计规则（`has-name`/`no-debug`）、修改默认文本
  输出与退出码规则。
- 验收大致方向：跟仓库既有测试约定走（`npm test`，node 内建 assert），新增行为先补失败
  测试，一条黄金用例（fixture）覆盖 JSON 字段内容。

## 第 1 轮：批量提问（材料歧义，第 2 步）

### Q1. 无效输入（配置文件不存在 / JSON 解析失败）在 `--json` 模式下要不要也变成结构化 JSON？

已知事实：当前 `src/audit.mjs` 对无效路径没有任何 try/catch，直接抛出未捕获异常，
stack trace 打到 stderr，Node 以默认方式退出（观察到退出码 1），stdout 为空。

- A（推荐）：`--json` 模式下捕获这类错误，向 stdout 输出一个结构化 JSON 错误文档
  （不再是 stack trace），仍走现有二值退出码语义（发现问题/出错都算「非 0」）。
  代价：需要新增一段错误处理逻辑，且必须只在 `--json` 分支生效，不能动默认文本路径。
- B：`--json` 模式下也维持现状——照样抛未捕获异常、stack trace 进 stderr、stdout 空。
  代价：CI 拿到的 stdout 在这种情况下不是合法 JSON，管道后面的 `JSON.parse` 会炸，
  没有真正解决"文案一变就断"的那类问题里最脆的一环。
- C：只处理"文件不存在"，不处理"JSON 内容非法"，两者区别对待。
  代价：两种无效输入表现不一致，规则本身不好解释，且实现更复杂。

**用户选了：A（未在画像里覆盖，按"其他任何未覆盖的问题选推荐项"代入）。**
补充理由代入画像："CI 要机器读结果"这条动机本身就要求无效输入也可解析，选 B 等于
没解决问题的另一半。

### Q2. `--json` 模式下，无效输入要不要给一个独立于"审计发现 error 级 finding"的退出码？

已知事实：现状下"发现 error 级 finding"退出码 1，"抛异常崩溃"也表现为退出码 1
（Node 默认行为），两者今天本来就是同一个数字，只是路径不同。

- A（推荐）：`--json` 模式下沿用现状的二值语义，不新增退出码——发现 error 级 finding
  或无效输入都是非 0（仍是 1）。代价：CI 那边如果想细分"配置本身有问题"和"配置内容
  审计不通过"，得读 JSON 里的字段而不是退出码，但这本来就是 JSON 输出要解决的事。
- B：无效输入单独给一个新的退出码（例如 2），跟"审计不通过"的 1 区分开。
  代价：这是给"退出码"引入了一条新规则，而画像明确说"退出码也不能变"；虽然这句话
  字面在说"默认文本模式"，但新增一条退出码语义本身就是一种不小的行为面扩张，
  且当前仓库没有任何地方定义过"退出码 2"的含义，等于凭空发明一个约定。

**用户选了：A（未覆盖，选推荐项）。**

### Q3. 不带配置文件路径直接跑 `--json`（即 `minicli --json`，没有第二个位置参数）应该输出什么？

已知事实：现状下不带任何参数运行 `node src/audit.mjs`，因为 `process.argv[2]` 判断
为假，CLI 什么都不做，静默退出码 0。

- A（推荐）：视为"无效输入"的一种（缺配置路径），走 Q1 定下的同一条结构化错误路径，
  给出 JSON 错误文档而不是静默成功。理由：静默退出码 0 却没有任何 stdout 内容，
  对着 `--json` 管道下游意味着"空输入喂给 JSON.parse"，一样会炸，且"什么都没做"
  被判定为"成功"本身就有点反直觉。
- B：完全保持现状——不带参数、带不带 `--json` 都一样，静默退出码 0，`--json` 分支
  也不例外。理由：改动更小，完全不碰这条路径。
  代价：这类调用今天是无操作，画像里没人明确要求改，属于"顺带扩大了范围"的那种改动。

**用户选了：A（未覆盖，选推荐项，与 Q1 保持同一套错误处理路径，逻辑更一致）。**

## 收口自评（第 2 步停止判据）

- 意图：已定——CI 要机读审计结果，不想再被文案变化打断解析。
- 结果：已定——`--json` 时 stdout 是且只是一份合法 JSON；不加 `--json` 时行为与现状
  逐位一致。
- 边界：已定——不做 schema 版本化、配置文件、审计规则变更、格式化选项（如
  `--json-pretty`，画像未要求，默认不做）。
- 约束：已定——默认文本输出与退出码完全兼容；不引入新依赖（现状 `package.json` 零
  依赖）；不新增独立退出码语义。
- 现状：已查清——现有 `src/audit.mjs`、`docs/testing.md`、`test/run-tests.mjs`、
  `package.json` 均已读取；当前 CLI 对无效输入的真实行为已用实测验证（见 process-notes）。

两条停止条件都成立，进入第 3 步判定。

## 第 4 步：验收条件逐条候选（4a/4b）

例子来源：直接复用第 3 步行为对照表里的变化行 + 不变清单里的关键项，聚类如下

### fixture 由谁提供（4b 收口问题）

`--json` 的 fixture 数据不涉及真实/敏感数据，属于"仓库现有测试同款的合成配置"，

不是另行发明的顺序。
