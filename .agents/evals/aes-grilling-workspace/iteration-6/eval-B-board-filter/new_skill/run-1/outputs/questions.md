# 提问记录（按实际发生顺序）

模拟用户画像：项目管理出身的产品负责人，不写代码。所有回答严格取自
`PERSONA.md`；画像未直接覆盖处按其「其他任何未覆盖的问题：选推荐项」的
指示选推荐项。

## 第 0 步：调查事实（不占提问，仅告知）

在开口问之前，直接查仓库查清以下事实，写进上下文告知用户：

- 前端是原生 HTML/CSS/JS，无框架、无路由库、无 URL 参数处理代码
  （`public/app.js`、`public/index.html`）。
- 任务数据当前写死在 `src/server.mjs` 的 `TASKS` 数组，`assignee` 字段是
  纯字符串，当前只有 `ayan`（2 条）、`bo`（1 条）、`chen`（1 条）三个取值，
  没有空 assignee 的情况；`/api/tasks` 原样返回整份数组，不接受任何查询参数。
- 测试基建：`npm test` 跑 `test/run-tests.mjs`（`node:assert`，退出码 0 为
  过）；`docs/testing.md` 写明页面改动目前只能本地 `npm start` 后人工验证，
  仓库没有截图对比或视觉回归工具，`package.json` 也没有装任何浏览器自动化
  测试依赖。
- 对照物判定：本次是在现有看板上新增一处用户可见的筛选控件 → 需要出界面
  mock；默认（不筛选）状态下现有行为不变，不存在「今昔行为差异」→ 不出行为
  对照表。

## 第 1 轮：材料歧义（批量，编号文本一次发全，4 题）

> 宿主环境未接入 `AskUserQuestion` 工具，按 SKILL.md「宿主没有该工具时退化为
> 编号文本，提问范围不变」的规定，改用编号文本一次发全，题量本身在 4 题以内。

**问题 1**：筛选维度只做负责人一项，还是要联动状态/标签？
候选：A 只按负责人 / B 负责人+状态 / C 负责人+状态+标签
推荐：A——卡片多的痛点是「只看自己的」，状态列本身已经是三列分组，联动会让
第一版范围膨胀。

> 用户（按画像）回答：A。补充原话：「不需要多选负责人，不需要按状态或标签
> 筛选」。

**问题 2**：负责人筛选支持单选还是多选？
候选：A 单选 / B 多选（可勾多个负责人）
推荐：A——看板负责人集合小，单选已能覆盖「只看自己的」这个核心场景，多选
会引入组合状态和 UI 复杂度。

> 用户回答：A。补充原话：「不需要多选负责人」。

**问题 3**：你要的「刷新保留 + 分享链接同事看到一样结果」，只有把筛选状态
放进 URL 才能同时满足（本地 localStorage 能保住刷新，但同事打开链接看不到
分享者的筛选）。如果同事打开的是不带筛选参数的裸链接，应该显示什么？
候选：A 默认显示全部任务（无筛选）/ B 服务端记住「上一次全站筛选」，裸链接
也复现（需要账号/会话体系，仓库目前完全没有登录态，代价是新增一整套服务端
持久化）
推荐：A——B 的代价和仓库现状（无账号体系）不匹配，且违背「链接对方打开看到
同样结果」这句话本身的语义。

> 用户回答：A（隐含确认，画像的「不做的」清单里已排除类似的账号级持久化）。

**问题 4**：顺带要不要改动卡片本身的展示（比如给负责人加头像、加粗）？
候选：A 不改卡片，只加筛选控件 / B 顺便优化卡片上负责人的视觉呈现
推荐：A——画像明确说了「不改卡片详情」，视觉调整也不属于本次筛选需求。

> 用户回答：A。补充原话：「不改卡片详情」。

## 第 3 步：界面对照物迭代

**v1（草稿，未落盘）**：筛选下拉框贴着标题放在左侧；没有「清除筛选」按钮；
筛选结果为 0 条时列直接空白，无文案。展示给用户。

> 用户（按画像）反馈，原话三条：
> 1. 「筛选控件放顶部工具栏右侧，不要放侧边」；
> 2. 「要有一个『清除筛选』按钮，一键回到全部任务」；
> 3. 「筛选后一张卡片都没有时，要显示空态文案『没有匹配的任务』」。

**v2（确认版，落盘为 `mock.html`）**：控件连同新增的「清除筛选」按钮一起挪到
`.topbar` 最右侧；三列渲染逻辑改为筛选结果为空时插入
`<p class="empty-state">没有匹配的任务</p>`；额外加了一段静态「空态示例」区块
方便直接看到空态长什么样。

> 用户（按画像）确认：「这三条改完后我第二次看会确认通过，不再提新意见」——
> v2 展示后确认通过，未再提新意见。同时确认：「视觉细节（颜色、字体）不要求
> 和示意一模一样，但结构和交互要按确认过的来，我不接受像素级较真」。此约定
> 写入 AC-001 的 Verify 说明，不写进「强约束」（它是验收判定口径，不是不可变
> 的现有行为）。

## 第 4 步：验收条件逐条带候选（编号文本一次发全，5 条，超过 4 题上限改用
编号文本）

**AC-001（负责人筛选控件位于工具栏右侧，含全部选项）**
候选：[C] 按 mock.html 人工核对 / [A] 新增 DOM 断言测试（需要引入 jsdom 或
Puppeteer，仓库目前没有）
代价：[C] 几分钟、主观，无回归保障；[A] 需要新增测试依赖和基建，约 0.5–1 人日
推荐：[C]——仓库无 UI 自动化基建，新增代价明显大于收益，且用户已明确不要求
像素级还原。

> 用户回答：按推荐，选 [C]。补充原话：「验收方式：跟着仓库测试约定走，你推荐
> 什么就是什么」。

**AC-002（选中负责人后只显示该负责人卡片）**
候选：[A] 扩展 `test/run-tests.mjs` 加筛选函数断言 / [C] 人工在浏览器里逐个
负责人试
代价：[A] 纯函数测试，复用现有断言基建，成本低、可回归；[C] 主观、不可回归
推荐：[A]

> 用户回答：按推荐，选 [A]。

**AC-003（URL 持久化 + 跨会话分享一致）**
候选：[C] 人工走一遍（打开带参链接→刷新→复制到隐私窗口打开） / [A] 引入
Playwright/Puppeteer 端到端自动化
代价：[C] 几分钟；[A] 需要新增浏览器自动化依赖和用例，约 1–2 人日，对一个
4 条任务的看板明显过重
推荐：[C]

> 用户回答：按推荐，选 [C]。

**AC-004（清除筛选按钮）**
候选：[C] 人工点击核对（AC-003 人工链路的延伸） / [A] 同 AC-003 需要浏览器
自动化基建
推荐：[C]

> 用户回答：按推荐，选 [C]。

**AC-005（筛选结果为空时的空态文案）**
候选：[C] 人工用一个数据里不存在的负责人触发空态 / [A] 只断言筛选函数返回
空数组（不验证文案是否真的渲染出来）
代价：[C] 几分钟，直接验证用户能看到的文案；[A] 已被 AC-002 的断言间接覆盖
「返回空数组」这一半，但验证不到 DOM 是否真的显示了文案
推荐：[C]

> 用户回答：按推荐，选 [C]。

无新增材料歧义，未回第 2 步。

## 小结

- 共走 2 个正式批量提问轮次（第 1 轮材料歧义 4 题、第 4 步验收候选 5 题），
  外加 1 轮界面 mock 迭代（v1 → 用户三条意见 → v2 确认）。
- 因为宿主环境未接入 `AskUserQuestion` 工具，两轮批量提问都退化为编号文本，
  题量仍分别控制在流程要求的范围内（4 题不超过工具上限；5 题超过 4 题上限，
  改用编号文本属于该情形下的规定动作）。
