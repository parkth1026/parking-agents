# Q&A 记录 — team-board 按负责人筛选

用户原始请求：「team-board 这个看板想加一个按负责人筛选任务的功能。帮我先把需求理清楚，
最后给我一份可以直接交给执行 agent 的 goal contract。先不要写代码。」

（本记录中的「用户」按 `PERSONA.md` 画像扮演作答：项目管理出身的产品负责人，不写代码。）

## 第 1 步：调查事实（不占提问轮次）

调查了仓库现状，作为 Fact 直接采纳，未占用提问轮次：

- 看板是一个纯 Node 静态服务：`src/server.mjs` 提供 `GET /api/tasks`（一次性返回全部任务的
  JSON 数组）和静态文件服务；`public/index.html` + `public/app.js` 在浏览器端一次性拉取
  `/api/tasks` 并渲染三列（待办/进行中/已完成）。
- 任务数据形状：`{ id, title, assignee, status }`，`assignee` 是自由字符串（当前样例：
  ayan、bo、chen），没有单独的人员管理接口或固定枚举。
- 当前界面没有任何筛选控件，也没有 URL 查询参数解析、没有 localStorage 使用、没有路由。
- 测试基建（`docs/testing.md`）：`npm test` 跑 `test/run-tests.mjs`，是基于 `node:assert` 的
  纯逻辑断言脚本，退出码 0 为过；页面类改动的约定是本地 `npm start` 后人工在浏览器验证，
  仓库里明确没有截图对比或视觉回归工具。这决定了第 4 步里 UI 交互类 AC 默认走 `[C]`
  人工步骤，纯逻辑类 AC 可以走 `[A] npm test`。
- 用户原始请求里已经把两条关键 Outcome 讲清楚了：筛选要「刷新后还在」、且「分享链接给同事
  打开看到的是同样的筛选结果」。这两条合在一起，在事实上排除了纯 `localStorage`（不满足
  分享场景）方案，指向「筛选状态要编码进可分享的 URL」这一结论——这是从用户陈述直接推出
  的 Fact，未再作为独立问题去问。

对照物判定：本次请求新增了用户可见的界面控件（筛选下拉、清除按钮、空态文案），归类为
「界面 Mock」。是否同时构成「行为对照表」取决于筛选是否改变 `/api/tasks` 的接口契约——这
一点读不出来，列入第 2 步的用户决定。

## 第 2 步：批量问清歧义（第 1 轮，也是唯一一轮）

先给出候选草案：

- Goal（草案）：团队看板上支持按负责人筛选任务卡片，筛选结果刷新后保留，并可通过分享
  链接让他人看到相同的筛选结果。
- In（草案）：顶部工具栏新增负责人筛选控件（单选）、清除筛选入口、空结果态文案；筛选状态
  编码进 URL，刷新/分享后保留。
- Out（草案）：不支持多选负责人；不新增按状态/标签筛选；不改卡片详情。
- AC 方向（草案）：选中负责人后仅显示其任务；刷新保留；分享链接一致；清除筛选恢复全部；
  空结果态文案；交付界面与确认版 mock 结构一致。

批量提出以下 3 个独立歧义（未超过 4 个，一轮问完）：

1. **筛选的实现层级**：前端对已一次性加载的任务数据做过滤（不改 `/api/tasks` 契约），还是
   后端 `/api/tasks` 新增查询参数、前端按参数请求？
   - 证据：当前任务数据量很小（4 条示例）、一次性全量返回，没有分页/懒加载。
   - 推荐：前端过滤，不改后端接口契约——更简单、可逆，且不引入新的对外接口行为需要
     对照表覆盖。
   - 真实代价：若未来任务量变大，前端过滤会一次性下载全部任务；但当前架构本就是全量下发，
     该代价与本次改动无关。
   - 用户（画像未覆盖此问题，选推荐项）：同意前端过滤，不改 `/api/tasks` 契约。

2. **负责人选项来源**：从当前已加载的任务数据里动态去重生成下拉选项，还是新增独立的人员
   清单/接口？
   - 证据：仓库没有人员管理相关代码或接口。
   - 推荐：从当前任务数据动态去重生成选项，不新增接口。
   - 真实代价：如果某负责人当前没有任何任务，下拉里就不会出现这个人——这是可接受的，
     因为筛选的目的是从「已有卡片」里找人。
   - 用户（画像未覆盖，选推荐项）：同意，从当前任务数据动态去重。

3. **无负责人（assignee 为空）任务**如何处理筛选？
   - 证据：当前 4 条样例任务都有 assignee，仓库里没有「未指派」相关代码路径。
   - 推荐：本次不特别处理「未指派」场景（不在下拉里加「未指派」选项），因为现有数据和
     现有代码都不支持无 assignee 的任务，属于当前不存在的情况，出现时按 Out 处理，不在
     本次 Scope 内。
   - 真实代价：如果未来数据出现空 assignee 的任务，它既不会出现在任何筛选结果里，也不会
     单独可筛；这是明确的 Out，不是遗漏。
   - 用户（画像未覆盖，选推荐项）：同意，不处理「未指派」，明确写进 Out。

### 收口自评（第 1 轮回答后）

- Intent：已定（画像已说明动机——卡片一多，只想看自己负责的，靠肉眼扫效率低）。
- Outcome：已定（筛选、刷新保留、分享一致，画像已明确给出可观察标准）。
- Boundary：已定（In/Out 经过第 2 步 3 个决定收敛：前端过滤、动态去重、不含未指派）。
- Constraints：已定（不多选、不加状态/标签筛选、不改卡片详情、不改 `/api/tasks` 契约）。
- Context：已查清（第 1 步事实调查覆盖了架构、数据形状、测试基建）。

两条收口判据都满足，没有维度停在「未定」；此刻若再问，答案不同也不会改变执行——审计通过，
本轮为唯一一轮，不追加。
