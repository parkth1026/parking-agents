# 访谈：笔记按分类统计 + 近 7 天新增统计

## 查到的事实

- `src/cli.mjs` 目前只有 `add`/`list` 两个命令，没有任何统计相关代码。
- `src/web/server.mjs` 只提供只读笔记列表页和 `/api/notes`（返回全部笔记 JSON），没有统计页。
- `data/notes.jsonl` 每行字段为 `category`、`text`、`created`（ISO 时间戳），`src/cli.mjs` 的
  `add` 命令不校验 `category` 是否为空，理论上可能产出空分类或缺字段的数据。
- `docs/testing.md`：测试用 `npm test`（`node test/run-tests.mjs`），退出码 0 为过；
  网页改动靠本地 `npm run web` 人工看，仓库没有截图对比或视觉回归工具。
- `test/run-tests.mjs` 目前是纯 `node:assert` 断言脚本，不依赖测试框架，风格是「加载数据 +
  断言」。
- `package.json` 的 `type: module`，无既有的图表库依赖。

## 验收对齐

- AC-001（分类历史总数 + 长条排序）：来自 mock v2 的关键状态，Verify 选 `[C]` 人工比对
  `mock.html`，理由是仓库没有截图对比/视觉回归工具（`docs/testing.md`），[A] 自动化断言
  测不出页面结构是否长得像 mock，[B] 黄金用例测不出「横向长条」这种呈现方式，
  只能测数字。用户的验收方式是「跟着仓库测试约定走，你推荐什么就是什么」，故直接按
  推荐口径定稿。
- AC-002（近 7 天新增卡片数字口径）：这条错了用户会直接看到错误数字，影响可感知但
  不涉及外部系统或真实数据，属于纯计算逻辑，适合 `[B]` 黄金用例：构造含窗口边界值的
  fixture（`input-notes.jsonl` / `expected-stats.json`），比现有 `test/run-tests.mjs`
  的断言风格更精确地锁死边界行为。已按仓库测试惯例定稿。
- AC-003（CLI 与网页数字一致）：这条错了两个入口会打架，用户会发现「网页说 3 条，
  命令行说 4 条」这种明显矛盾。仓库已有 `node test/run-tests.mjs` 断言基建，代价最低
  （复用现有测试入口），选 `[A]`，断言内容为「CLI 与网页共用的统计函数对同一份 fixture
  产出一致结果」。已按仓库测试惯例定稿。
- AC-004（空/缺失 category 归并未分类）：这条错了要么统计功能直接崩溃（用户完全看不到
  统计页/命令，影响最大），要么总数对不上（分类计数加总小于笔记总数，用户会怀疑数据
  丢了）。用构造的边界 fixture 最省事验证到，选 `[B]`，与 AC-002 同理由。已按仓库测试
  惯例定稿。
