# 锁定需求

这一步只做一件事：把「要做什么」问到不再有会改变结果的歧义。怎么算做完是下一个
阶段的事，怎么实现是执行 Agent 的事。

提问方法论在 [asking.md](../workflow-interview/references/asking.md)，先读它。
这里只写这一阶段问什么、查什么、产物怎么写。

## 开头

```bash
node <workflow-interview>/scripts/session.mjs init <date>-<任务词组> --request "<用户原话>"
```

幂等，已存在就续跑。拿到 issue 目录绝对路径，下面所有产物都落在它的 `1-interview/` 下。

## 1. 调查事实

读取目标仓库适用的规则，以及请求牵涉的代码、测试、设计、日志和必要的一手资料。
只调查会改变目标、范围、公共行为、兼容性、验收条件、硬约束或难逆成本的事实。

无论请求内容为何，固定查清一项事实：仓库现有的验证基建，包括测试命令、CI 门、
覆盖率工具、fixture 约定。查到的清单就是 `aes-goal-contract` 阶段验证途径的候选池。
「这个项目能怎么验」是查出来的，不是套通用分级套出来的。查不到基建时可选途径只剩
用户真实测试与新建基建，两者都要在候选里写明代价。

存在两个以上互不依赖的事实问题且可以创建 subagent 时，并行派遣只读调查；为每个
subagent 限定问题、目标路径和所需证据。**每个 subagent 把结果写进
`1-interview/facts/<主题>.md`，各写各的文件，互不重叠。** 它们返回事实、证据位置和
未知项后结束，不询问用户、不替用户作决定、不修改产品，**也不碰 `manifest.json`**。
当前宿主 Agent 同时调查其余事实并汇总证据；无法使用 subagent 时自行完成调查。

能由仓库或环境证据回答的事实，查清后写进上下文并告知用户，不占用提问。但事实一旦
暗示该怎么做（该跟哪个模式、该接受哪种代价、该把什么排除在外），整个决定仍然归用户。

用户用的词与仓库文档或代码里的词冲突、或者一词多义时，拿出具体出处，把「按哪个
意思走」列为用户决定。仓库语言是证据，不是权威。

将每个相关事项归为：

- `Fact`：由仓库或环境证据回答；
- `User decision`：会改变结果或边界，必须由用户裁决；
- `Agent-owned`：局部、可逆且不改变外部契约，交给执行 Agent。有几条都成熟、
  但成本结构不同的路径可走时，它不再是 `Agent-owned`，选哪条是 `User decision`；
- `Blocked`：缺少权限、凭据、外部前置条件或当前无法取得的必要用户决定。

推荐项只是建议，不能代替用户决定。

**这一步不判定影响面。** 改完之后程序在哪里跑起来不一样、要出哪几种对照物，
是 `aes-prototype` 的第一件事，在那里判比在这里判少一次跨阶段传递。

## 2. 批量问清歧义

只问不同答案会改变目标、范围、公共行为、兼容性、可观察验收、权限风险或难逆成本的
问题。不问可调查事实、成熟的低风险默认做法或 `Agent-owned` 实现选择。

几条实践路径都成熟、但成本结构不同时（性能与可读性、改动面与工期、通用与专用），
不能拿「都是最佳实践」把选择权含糊过去。这类选择定下来要写进 `强约束`，回头改要
重做已经做完的工作，按 [asking.md](../workflow-interview/references/asking.md)
的分诊至少进确认区；你自己也说不清哪条更划算时进提问区，并写明各自的真实代价。
写成约束而不是实现步骤：「必须走 X，不引入 Y」不会过时，步骤会过时，而且会挤掉
执行 Agent 本该自行发挥的部分。

每问完一轮，把这一轮追加进 `rounds.jsonl`，格式见下。

### 什么时候停

每轮回答后逐维度自评并显式报告状态（已定、部分、未定）：

- `意图`：为什么要做，解决谁的什么问题；
- `结果`：做完之后能观察到什么，用什么判；
- `边界`：做到哪里，明确不做什么；
- `约束`：什么现有行为、兼容性或限制必须保持；
- `现状`：已有代码库时，相关现状是否已查清。

两条同时成立才结束提问：

1. 没有维度停在「未定」，且不做什么和执行 Agent 可自行决定的范围都已写明；
2. 收口审计通过。还想问的问题，不同答案只会改变措辞，不会改变执行。

歧义低是开始审计收口的许可，不是继续钻的许可。判据没满足就不进下一阶段，问了
多少轮都一样。没有材料歧义时直接进下一阶段，不为流程制造提问。

## 产物

### `1-interview/facts/<主题>.md`

只有派了 subagent 时才有。一个 subagent 一份，文件名取调查主题。

```markdown
# Fact: <主题>

- 派遣问题：<限定给这个 subagent 的问题>
- 完成：<ISO 时间>

## 查到的

| 事实 | 证据出处 |
| --- | --- |
| <一句> | `<文件:行号>` |

## 未知项

- <查了但没查出来的，写清查到哪一步>

## 没查的

- <超出派遣范围的，写清为什么不归它>
```

分片是 `context.md` 的证据来源，聚合之后保留不删。

### `1-interview/context.md`

宿主写。分片存在时先聚合分片。

```markdown
# Context Snapshot: <slug>

- 创建：<ISO 时间>
- 分片来源：<facts/ 下的文件，没有就写「无，宿主直接调查」>

## 任务陈述
<用户原话，一个字不改>

## 用户提出的方案
<他自己带来的方案，没有就写「未提出」>

## 意图假设
<他真正要解决的问题。这一段常常和任务陈述不是一回事，写清差在哪>

## 已查事实
| 事实 | 出处 | 分类 |
| --- | --- | --- |

## 验证基建候选池
<下一阶段的验收途径从这里选，逐条写代价；仓库没有的基建写明「代价含先建」>

## 术语冲突
<用户的词与仓库的词对不上的地方，带出处；没有就整节省略>

## 四分类
- **Fact** / **User decision** / **Agent-owned** / **Blocked**

## 决定边界未知项
<拿不准该归哪一类的，要在提问里确认；没有就省略>

## 未知项
<跨出仓库边界、读不出来的，标明「必须问」>
```

### `1-interview/rounds.jsonl`

一行一条，追加，**只用脚本写**：

```bash
node <workflow-interview>/scripts/session.mjs round <issue-dir> '<一行 JSON>'
```

分诊结果与提问共用这一个文件，`tier` 区分。不另出一份分诊清单——那只会是这份文件的
渲染。三档的字段：

| 字段 | 谁有 | 说明 |
| --- | --- | --- |
| `stage` / `round` / `tier` | 都有 | `tier` ∈ `default` / `confirm` / `ask` |
| `item` / `why` / `cost` / `user` | `default`、`confirm` | 定了什么、为什么、代价、用户反应 |
| `q_id` / `question` / `known_facts` | `ask` | 问题本身与已知事实 |
| `options[]` | `ask` | 每项含 `key` `text`；`pct` 仅单选语义（缺省或 `single_select`）必填；可选 `recommended` `covers` `pros` `cons` |
| `response` / `choices` | `ask` | 结构化应答：`response.type` ∈ 九种（缺省 `single_select`）；`multi_select` 用 `min_selections`/`max_selections`/`exclusive_keys`（`min`/`max` 为别名，写入时正规化）；`choices` 记多选结果集 |
| `irreversible` / `allow_custom` / `required` | `ask` 可选 | 难逆（分诊表「难逆」列落盘）、允许自定义答案、必答（缺省必答） |
| `user_choice` / `user_verbatim` | `ask` | 选了哪个，原话照录 |
| `overturned_recommendation` | 都可有 | 你给低了却被用户选中时为 `true` |
| `cross_repo_boundary` | 都可有 | 这一项跨出仓库边界时为 `true` |
| `triggered_by` | 回流的问题 | 由哪份草稿或哪个阶段撞出来 |

同一轮内单选语义 `ask` 行的 `pct` 加和 100（校验留 ±2 容差——pct 是主观估计，卡整不
卡准）；多选的选项是候选集合不是概率分布，不带 `pct`（与 Web 载体的发布 schema 同一套，
见 workflow-interview-web 的 web-protocol.md）。`round` 命令会按这张表当场校验：`stage`、
`round`、`tier` 必填，`ask` 行要带 `question` 且单选语义下 `options` 的 `pct` 加和落在
100±2，`default` / `confirm` 行要带 `item`。不合 schema 的行拒收，不落盘。

`overturned_recommendation` 做成可 grep 的字段而不是靠人眼在表格里找，因为它是整份
记录里唯一能看出「当时判断偏在哪」的信号。下一个改这份契约的人靠它知道该重新验证
什么。它常常和 `cross_repo_boundary` 同时出现，这不是巧合。

## 收尾

```bash
node <workflow-interview>/scripts/session.mjs stage <issue-dir> 1-interview done \
  --assessment '{"意图":"已定","结果":"已定","边界":"已定","约束":"已定","现状":"已定"}' \
  --goal "<目标一句话>" --next "<下一步一句话>"
```

有维度停在「未定」就别报 `done`。用户说「别问了直接干」时照办，但把因此没问的东西
用 `--residual-risk` 记一句话。

`done` 不是自报的：命令会当场校验 context.md 必需节齐全、rounds.jsonl 每行合
schema、五维自评无「未定」，不过就拒收。它挡的是结构不是质量——问得好不好，
仍由自评与用户确认负责。

然后交回 `workflow-interview` 继续流转。

被单独调用（不经编排器）时同样按上面走，收尾照报，只是没有下一步流转。
