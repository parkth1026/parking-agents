# design: log-error-summary

## 意图与触发场景

为什么有这个技能：排查 Jenkins 构建/服务日志时，第一件事往往是「这份日志里到底有哪几类错误、各出现多少次」——徒手 grep 再人工数数每次都重做一遍，且口径漂移（有时数 ERROR 级别行，有时连 Error/error 一起数）。

用户会说什么话、什么上下文触发：

- 「统计一下这份构建日志里的错误分布」「这份日志有哪些错误，各出现多少次」
- 「把 xx.log 的错误归个类，出个表」
- 上下文：手里有一份或多份文本日志（Jenkins 构建日志、服务运行日志），要快速定位高频错误模式

期望产出形态：一个 markdown 频次表（错误模式 / 次数 / 代表样例三列），同型错误归并计数，按次数降序；附一行总数（共 N 条错误、M 类）。

## 设计取舍

- 归并口径用「错误签名」：把行内数字、引号串等可变量归一后取前 80 字符做签名——为什么没选逐字去重：时间戳/路径/会话 id 不同的同型错误会拆成几十行，表失去概括力。
- 错误行判定：包含 ERROR/error/Error 字样的行（大小写不敏感）——为什么没选只认日志级别前缀（`[ERROR]`）：真实日志格式杂，级别前缀不总是出现；为什么没选正则穷举常见错误消息：面太窄、维护不动。
- 计数逻辑放 `scripts/summarize-errors.mjs` 确定性脚本（低自由度）——为什么没选让 agent 肉眼数：数数这种事脚本零出错、零 token，agent 数错无法复现。
- 输出 markdown 表（高自由度部分只有表头措辞）——为什么没选 CSV/JSON：这份表的消费者是人，直接贴进报告/PR。
- 单意图、不编排：只做「日志→错误频次表」这一件事——为什么没选顺带做警告统计/全文摘要：description 会开始招揽不相干请求，触发面变脏（见结构审查信号 2）。

## 验收条件

| 编号 | 条件 | 类型 |
| --- | --- | --- |
| AC-1 | 对只含大写 ERROR 行的日志，表格计数与逐条人工核对一致 | script |
| AC-2 | 大小写混杂（ERROR/Error/error）的日志全部计入，无漏计 | script |
| AC-3 | 输出为 markdown 表格，含「错误模式/次数/代表样例」三列，按次数降序 | script |
| AC-4 | 仅可变量（数字/引号串）不同的同型错误归并为一行，次数累计 | script |
