# UE 运行日志分析工作流

脚本给事实，本文给推理顺序。适用于"卡住/崩溃/GPU 归零/掉帧/打包后异常"类反馈。

## 第一步：判活（先回答"进程死没死、卡在哪"）

```bash
node scripts/ue-log-analysis.mjs frames  <log> --json   # 帧 0 占比/最大帧/停滞段/骤降
node scripts/ue-log-analysis.mjs timeline <log>          # 里程碑 + 终止形态 + 心跳
```

四问：
1. **出过帧吗**？（全程帧 0 → 卡在启动/同步加载，去看 LoadMap 之后谁在刷屏）
2. **帧号停在哪**？（停滞段时间点 = 卡点，取空窗前最后几行就是阻塞现场）
3. **怎么终止的**？（正常退出 / 崩溃 / 戛然而止；戛然而止 + 心跳正常 = 被杀，去问运维而非查引擎）
4. **活着但慢**？（FPS 骤降段 + 空窗 = 找后台负载：流送/编译/网络）

多份日志判定"是否同因"必须分两层走，先各自跑 frames/timeline/errors 再对比：

1. **错误谱一致 → 只是同因候选，不得直接判"同因复现"**。共同错误常是共享的
   非致命缺陷（缺包/噪声/性能债），全份携带；"一致"说明同环境，不说明同死因。
2. **判活形态分岔优先，存活份是反例对照**：有出帧存活的份时，它携带同一错误
   仍出帧 ⇒ 该错误降级为非致死；致死候选 = 仅卡死份独有的阻塞模式（对比各份
   noise/gaps 的计数与空窗位置，卡死份独有的高频等待模式优先）。
3. **两档结论分开下**："共享缺陷"（全份一致，列性能债/卫生债）与"致死机制"
   （卡死份独有），修复优先级跟致死机制走——把共享缺陷排第一会误导工程投入。

形态完全不同 → 区分"三次失败"还是"一次运行的多份拷贝"（比对首行时间戳与线程号）。

## 第二步：定位卡点

```bash
node scripts/ue-log-analysis.mjs gaps <log> --min-ms 3000   # 空窗 + 前后 3 行上下文
```

- 空窗**前的最后几行**是阻塞开始时正在做的事；空窗**后的第一行**是恢复后谁在说话。
- 空窗前是 `Waited for PSO creation` → 渲染线程编译风暴。
- 空窗前是某插件的文件 IO 循环 → 同步 IO 阻塞游戏线程（帧号通常同时停滞）。

## 第三步：错误分组与噪声还原主干

```bash
node scripts/ue-log-analysis.mjs errors <log>
node scripts/ue-log-analysis.mjs noise  <log> --min-count 10
```

- errors 表按次数降序，但**排在第一的不一定是根因**：ensure/callstack 常是上游缺文件的连锁
  （见 ue-log-format.md 模式库），要从"第一类错误的首次出现时间"往前追 1-2 行找触发者。
- noise 聚类出刷屏模式后，用 `grep -vE "<噪声模式>"` 过滤再看时间线，主干会立刻清晰。

## 第四步：根因假设与报告

每条结论必须挂日志证据（时间戳/行号/帧号），区分三档：
- **实锤**：日志直接证明（帧停滞 55s + PROJ 循环刷屏）
- **强假设**：机理成立但缺直接证据（GPU 归零推断为"无新帧提交"）
- **待澄清**：日志覆盖范围外的现象（玩家连接后冻结，但日志止于连接前）

报告结构：环境（从启动参数还原：GPU/分辨率/像素流/预热）→ 时间线 → 证据链 → 根因排序
→ 修复建议（按优先级）。时间线节必须包含 `gaps` 输出的空窗表（每处空窗的起止时间戳
+ 时长 + 空窗前最后 3 行）：空窗是卡点的第一现场，评测实证执行者常算出空窗却在写报告时
丢掉——脚本已算出的证据不进报告等于没算。AES 工程的落盘约定：诊断报告放 `Plugins/Docs/bugs/`，
文件名 `YYYY-MM-DD-主题.md`（kebab-case）。

## 常见陷阱

1. **帧号是游戏线程的**：渲染/异步加载/网络线程的日志行带的是"打日志那一刻的"帧号，
   帧号停滞期间仍可能有日志增长——那是别的线程在说话，恰是"谁还活着"的证据。
2. **GPU 占用≠健康度**：低分辨率预热、LOW-POWER 模式下 GPU 0% 是设计行为。
3. **日志终止≠崩溃**：先看尾部有无 Fatal/Critical；戛然而止优先怀疑被杀/拷贝截止。
4. **`_2` 后缀日志**：可能是同秒启动的另一实例，不是同一进程的第二份输出；比对内容与
   线程号再下结论。
5. **时间戳是 UTC**：与用户口述的本地时间对不上时先换算，别怀疑分析。
