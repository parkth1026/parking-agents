# 思维导图协作

正本是一份 `*.mindmap.md`：人用 VS Code Markmap 插件预览和手改，你直接改文本。不生成 HTML，不调用 markmap-cli，预览交给插件。

写之前先读 `references/rules.md`，它规定了结构语法、节点字数、分组、状态标记、（注）和溯源的写法，以及每条规则的理由。新建文件从 `assets/template.mindmap.md` 起步。执行任务通常只需这两份：`scripts/lint.mjs` 与 `fixtures/` 是校验和测试件，跑 lint 即可、不必读源码；需要看完整范例时再翻 `fixtures/good.mindmap.md`。

## 每次都做

1. **改前读最新版**。人可能刚在插件里改过，凭记忆改会覆盖人的改动。
2. **改后跑 lint**：

   ```bash
   node <技能目录>/scripts/lint.mjs <文件.md>
   ```

   退出码 0 才算完成；1 时按逐行提示修改再跑。lint 只管数值和语法，MECE、分组是否合理、叶子有没有丢信息要你自己再看一遍。
3. **回复里列出变动**：新增、删除、移动、改名的节点，按分支归类；批量改动时附上 lint 的统计行（改前 → 改后）。

## 场景 A：从文档或 wiki 生成

1. 读材料，先定 3–5 个一级分支：它们是看这件事的不同角度，不是材料的章节顺序照抄。
2. 往下展开：分支只写关键词，原来括号里的说明下沉为「用户：…」「职责：…」这样的叶子。
3. 叶子保留材料里的判断、口径和约束，写成一句话。压成一个词就是丢信息。
4. 标出关键决策点的状态（✅已定 / 🧪探索 / ❓待定），待定和探索项用（注）写依据。
5. 顶部写来源注释；引用到的 wiki 页名列进「关联 wiki」注释，节点里不放 `[[ ]]`。
6. 给细节分支加 `<!-- markmap: fold -->`，让首屏只剩骨架（约 20 个节点以内）。
7. 文件名用 `<主题>.mindmap.md`。用户没指定位置时，放在源材料旁边，或放在用户正在工作的目录。

## 场景 B：批量重构

拆分、合并、整枝搬移、重排、批量改名、按规则统一格式。

1. 先跑一次 lint，记下改前统计。
2. 按指令改。搬移整枝时连同子树一起移动，缩进整体平移；不要顺手改写用户没提到的节点。
3. 跑 lint，在回复里给出改前 → 改后统计和变动清单。
4. 指令和规范冲突时（比如用户要求的分组会超过 7 个子节点），照用户的意思做，并说明 lint 报了什么，让用户决定是否再调整。

## 场景 C：对话中边聊边记

1. 每当讨论出结论、新问题或待定项，就增量写进导图的对应分支；找不到合适的分支就新建，不要堆在根节点下。
2. 只改受影响的节点，不重写整张图。
3. 新出现的未决问题标 `❓待定`；后来定下来的，改成 `✅已定` 并更新（注）。
4. 每次写入后跑 lint，用一两行告诉用户记到了哪里。

## 测试

改动本技能后跑回归测试：

    node run-tests.mjs

它会用 `fixtures/good.mindmap.md`（规范范例，应判 0 违规）和 `fixtures/bad.mindmap.md`（埋了 12 类违规）黑盒验证 lint，并检查模板本身合规。
