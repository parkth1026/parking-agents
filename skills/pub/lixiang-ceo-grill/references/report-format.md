# 李想方法论复盘报告模板

复盘结束后按本模板产出最终报告。裁定与推荐必须可追溯：每条结论都要能对回 `question-bank.md` 里「李想的标准」原文、用户的原话引用或外部证据——**有理有据是硬要求，无依据的结论与推荐不进报告**。

```markdown
# 李想方法论复盘报告：<产品名>（YYYY-MM-DD）

## 一、总览
- 复盘范围：全量九模块 / 子集（列出实际复盘的模块）
- 访谈轮次：N 轮；证据分布：有据 X 项 / 口头断言 Y 项 / 答不上 Z 项
- 总裁定：符合 a / 部分符合 b / 缺失 c / 冲突 d（a+b+c+d = 已复盘模块数）

## 二、九模块符合度矩阵
| 层 | 模块 | 裁定 | 证据强度 | 核心差距（一句话） |
| --- | --- | --- | --- | --- |
| 认知 | 1 行业趋势 | 符合/部分符合/缺失/冲突 | 有据/口头断言/答不上 | … |
| 认知 | 2 行业问题 | … | … | … |
| 认知 | 3 进攻方向 | … | … | … |
| 战略 | 4 用户定位 | … | … | … |
| 战略 | 5 时间节奏 | … | … | … |
| 战略 | 6 目标要求 | … | … | … |
| 业务 | 7 业务架构 | … | … | … |
| 业务 | 8 在线系统 | … | … | … |
| 业务 | 9 运营系统 | … | … | … |

裁定口径：
- 符合：合格线全项达成且有证据
- 部分符合：方向对但合格线有缺口（缺口写入「核心差距」）
- 缺失：该模块从未被明确回答过（不是答错，是没有答案）
- 冲突：现状与该模块标准方向相反，或与其他模块答案自相矛盾

## 三、逐模块明细（每个已复盘模块一小节）
### 认知层 / 行业趋势 —【部分符合】
- 李想标准：（question-bank.md 对应原文引用）
- 用户原话：（本次复盘引用到的用户表述，带来源；这是裁定的对照材料）
- 产品现状：（对照后得出的现状描述）
- 证据：（文件路径 / 数据 / 访谈来源；口头断言需标注「未验证」）
- 差距：（具体差什么，对应合格线的哪一项）
- 推翻该裁定的条件：（出现什么新证据/新事实时改判）

## 四、你是怎么思考这个产品的
引用用户原话 3-5 条（带来源：文件路径或对话轮次），呈现思维方式——如何归因、如何取舍、在哪类问题上具体、哪类问题上含糊。**只引用、不复述行为**：「你在《方向》里写过『X』」，不写「你表现出 Y 特质」。这一节是给用户自己看的镜子，不是评语。

## 五、层间依赖断裂点
（按 question-bank.md「层间依赖检查」四项逐条给结论；点名的断裂要指明牵连的模块编号）

## 六、前三差距与最小补救动作
按对产品方向的杀伤力排序。**每条推荐必须有理有据**，缺任一要素不成立：
- **差距**：具体差什么（对应哪个模块合格线的哪一项）
- **依据**：李想原文哪一句 ＋ 用户哪条原话/证据暴露了这个差距
- **影响**：不补会怎样（对方向/节奏/架构的具体后果）
- **推荐强度与最小动作**：强烈推荐 / 建议 / 可选 ＋ 一个具体到可执行的最小动作

## 七、推翻整个复盘结论的关键问题
（本报告依赖哪些前提；哪些前提若被证伪，整体结论不成立——至少 3 条）
```

落盘约定：默认报告输出在对话内；用户要求落盘时写入其指定路径。若当前项目有自己的证据/文档目录约定（见该项目 AGENTS.md），优先遵循其归档规则（如 WDP6 项目内部证据归 `agent/evidence/`）。
