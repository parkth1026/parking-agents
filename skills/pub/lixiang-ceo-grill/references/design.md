# design: lixiang-ceo-grill

## 意图与触发场景

把李想创业公开课《如何做一个专业的 CEO》的方法论（认知/战略/业务三层九模块）变成一把固定的尺子，以逐题访谈（拷问）的形式检验当前产品：每个模块先亮出李想的原文标准，再问产品现状，追问到具体、有证据为止，最终产出逐模块符合度裁定（符合/部分符合/缺失/冲突）与差距报告。

触发场景：用户说「李想拷问」「用李想的方法论盘一下产品」「方法论体检」「产品方向拷问」，或想检验产品在行业趋势/行业问题/进攻方向/用户定位/时间节奏/目标要求/业务架构/在线系统/运营系统任一维度的清晰度。

产出形态：对话内的逐题访谈 + 最终符合度报告（可选落盘）。

## 设计取舍

| 决定 | 自由度 | 为什么没选别的 |
| --- | --- | --- |
| 固定题库（9 模块 × 核心问题 + 追问 + 红旗 + 合格线 + 合理答案示例），按认知→战略→业务固定顺序走 | 低（题库锁定在 question-bank.md，不许现场发明维度） | 方法论复盘的价值在「尺子固定」，现场生成问题会漂移成普通访谈 |
| 角色＝方法论镜子：先逐字引用用户已表达过的思考对照标准，只对缺口提问（非纯拷问官） | 低（协议锁定） | 用户裁定 2026-09-23：核心是引用用户怎么思考，纯拷问姿态产出对抗不产出补全；引用式复盘（quote, don't characterize）与复述确认参考 gstack office-hours |
| 一次只问一个问题，问完即停（结束回合） | 低（协议锁定） | 一次一问是用户点名的形式；office-hours 也实证了 ONE AT A TIME + 追问才逼得出具体答案 |
| 问题写在对话正文，不用 AskUserQuestion 类结构化提问工具 | 低 | 用户裁定 2026-09-23：提问工具能显示的内容太有限——放不下原文标准、用户原话引用与对照结论；且答案是开放论证，不是选择题 |
| 每条推荐必须有理有据：差距＋依据（李想原文＋用户证据）＋影响＋推荐强度与最小动作 | 低（格式锁定） | 用户裁定 2026-09-23：推荐方向无依据等于没说 |
| 事实自己查（repo / wiki / web），判断才问用户；用户原话逐字进事实底座 | 高（文字指令） | 借鉴 grilling 的「facts are your job」；让用户复述文件里已有的东西是浪费复盘火力 |
| 每模块结束给初步裁定（附依据），用户确认后记录；最终报告按 report-format.md（含「你是怎么思考这个产品的」节） | 低（格式锁定） | 裁定必须可追溯：每条结论都要能对回李想原文的哪一句与用户哪条原话 |
| 原文全文存档在 references/lixiang-ceo-article.md，只读不改 | 低 | 题库是提炼，原文是 ground truth；两者分开，题库错了能对回去 |
| 支持子集复盘（只盘指定层/模块）、smart-skip（原话已覆盖合格线的模块直接出示对照裁定）与不耐烦降级协议 | 高 | 全量 9 模块访谈约需数十轮对话，用户常只要某一层；office-hours 的 smart-skip 与 escape hatch 是成熟做法 |

## 验收条件

| 编号 | 条件 | 类型 |
| --- | --- | --- |
| AC-1 | 原文存档完整：lixiang-ceo-article.md 含三层九模块全部 9 个模块名与各自的原文标准句 | script |
| AC-2 | 题库完整：question-bank.md 覆盖 9 个模块，每个模块含「核心问题」「追问」「红旗」三要素 | script |
| AC-3 | SKILL.md 访谈协议包含：一次一问、原文标准先行、证据分级、裁定四档（符合/部分符合/缺失/冲突）、跳层检查 | script |
| AC-4 | 报告模板存在且含 9 模块矩阵 + 层间依赖断裂点 + 前三差距 + 推翻条件四节 | script |
| AC-5 | 访谈顺序遵循认知→战略→业务（方法论依赖方向），SKILL.md 不允许跳过认知层直接拷问业务层（子集模式除外） | script |
| AC-6 | 主观访谈质量（引用是否逐字、追问是否逼出具体证据、红旗是否点名）由人工评审，不做脚本断言 | manual |
| AC-7 | 复盘协议含：引用用户思考核心动作、合理答案判据、对话正文提问（禁用结构化提问工具）、校准式认可、复述确认；报告模板含「你是怎么思考这个产品的」节与推荐依据（差距/依据/影响/推荐强度）强制 | script |
