# Goal Contract 长什么样

访谈定下来的东西落进一份自包含的 Goal Contract，骨架在下面。写完跑
`node scripts/validate-goal-contract.mjs <路径>` 判定，别靠眼睛。

`目标`、`范围`、`强约束`、`验收条件` 四节合起来算一份验收摘要，后面的实现、评审、
验收全都挂在这份摘要上。这四节里任何一个字变了，已经做完的工作就不算数了，
得重来。所以它们只放访谈真正定死的东西，标题名一个字都不能改，也不能换成英文。
别的章节随便加，改了不作废已经做完的工作。

任务已经存在时改它的这份契约，不新建文件。判据只有一条：这次要动的是现有验收
标准，还是一件新的事。改现有标准、补现有实现、修刚发现的缺陷都回原契约重做，
把改动过的内容换成新版本；只有能独立交付的新事才另开一份新契约。

骨架里的提示各占一行，写完删掉。

```markdown
# Goal Contract: <一句话说清要做什么>

- Status: Ready | Blocked
- Target: <仓库、模块或路径>
- Updated: <YYYY-MM-DD>

## 原始请求

> 用户原话，一个字不改。他后来补充的也照录。

## 目标

一句话。做完之后什么变好了，不写打算用什么技术。

## Why

<!-- 可选。缺失时不影响契约有效，但能帮执行 Agent 判断"这条错了会怎样"。 -->
- <现有的问题或限制>
- <做到之后创造了什么价值>

## 范围

做什么，不做什么。「不做什么」比「做什么」值钱：它是执行 Agent 停手的地方。

## 强约束

必须保持的现有行为、兼容性、性能、安全或政策限制。
不变量写在这里，不占 AC 编号。

## 自主边界

<!-- 可选但强烈建议。它和「强约束」方向相反：强约束说不许变什么，这一节说不用问就能
     定什么。长时程执行里最贵的两种失败——为了一件小事停下来等人，和自作主张把改动
     摊大——都长在这一节缺失的地方。两栏都要写，只写一栏等于只堵一头。 -->

不用问，直接定：
- <一句。例如：文件怎么拆、内部数据结构、日志措辞、测试用什么断言风格>

必须停下来问：
- <一句。例如：改公共接口签名、加新依赖、动数据格式或迁移脚本、删既有能力>

<!-- 规则 A（2026-09-04 owner 裁决，先例：#104/#158 merge 归档）：实现中发现契约外
     行为——同一不变量在契约未点名的实例上同样成立（如同一诚实性规则覆盖更多
     operation 路径）——不算越线，可一并实现，不再占用提问轮；但回执必须单列
     「契约外行为清单」，由 merge review 以契约为尺子逐项 diff 后裁决归档。
     「必须停下来问」保留给有独立爆破面的决策：新依赖、删既有能力、改公共
     接口签名、wire 破坏性变更（有真实用户后此类升格为 ask-first）。 -->

## 读什么

<!-- 可选。访谈实际依赖的证据来源，以及确认版对照物的路径——它们在同一个 issue
     目录的 2-prototype/ 下，用相对路径点名，例如 `../2-prototype/api-mock.md`。
     指路不是预写事实：告诉执行 Agent 先读哪份文件，不替它把结论写出来。 -->
- <文件路径、issue 链接，或执行前该读的设计文档>

## 要落盘的东西

<!-- 可选。验收条件已经点名全部产物时省略整节。有 [B] 档 Verify 时必须写：
     fixture 得落盘才能被验证。用 D-01 这样的编号，Verify 行指得到。 -->
- D-01: <文件路径>：<内容要求>

## 验收条件

- AC-001: 一个可观察、可判定的结果
  - Verify: [A] `<命令>` → <退出码或门槛值>
- AC-002: 一个可观察、可判定的结果
  - Verify: [B] <输入 fixture 路径> → 匹配 <期望输出 fixture 路径>

## 挡着的事

<!-- 可选。缺权限、缺凭据、缺外部前置条件的写在这里，并写明精确解除条件。
     没有就整节不写。 -->
- None.

## 残留风险

<!-- 可选。用户喊停、访谈提前收口、某个阶段被跳过，因此没问清的东西记在这里，一条一句，
     并写明它错了会怎样。

     它和「挡着的事」不是一回事：那节是客观前置条件缺失，别人补上就能解；这节是主观上
     决定不问了，是一次下注。两者混在一起，执行 Agent 会把「我们赌了一把」读成「有人在
     等外部条件」，于是什么都不做地等下去。

     manifest 里的 residual_risk 和被跳过的阶段会跟这一节对账，对不上 finalize 直接拒。 -->
- <没问清什么> — 错了会怎样：<一句>

## 交付后人工复核

<!-- 可选。真人才能执行或判定的验收落这里：一条一行，写明复核什么、看哪个证据
     （指向「要落盘的东西」的 D-XX）。它不进执行 Agent 的完成判定——进了 Verify，
     /goal 的完成审计永远判不了人的确认。finalize 会把这一节转成用户待办清单，
     随交接指令一起交给用户本人。 -->
- <复核什么> — 证据：<D-XX 或产物路径>

## 访谈记录

<!-- 可选但推荐产出。问了什么、否决了什么、为什么这么定，只留在聊天记录里
     等于没留：下一个人看不到，你自己过两周也看不到。

     它是 rounds.jsonl 的聚合定稿，不是逐行搬运：原始逐轮记录在那边，这里只留
     结论与被否决的候选。走过对照物阶段就把每一版给用户看了什么、提了什么意见、
     改成什么也记一行；对照物本身在 2-prototype/ 下，不往这里抄。 -->

一轮一张表。**被否决的候选要留着**，它是这份记录最值钱的部分，说明当时考虑过
什么、为什么没走那条路。只留最终答案，等于把思考过程扔了。

### 第 1 轮

| 问题 | 候选（带当时给的百分比） | 推荐 | 用户选了 |
| --- | --- | --- | --- |
| <问了什么> | A <...> 18% / B <...> 78% / C <...> 4% | B，因为 <...> | A。补充：<用户原话> |

百分比照原样记下来，包括你给低了却被用户选中的那个。它是这份记录里唯一能看出
「当时判断偏在哪」的东西，下次改这份契约的人靠它知道该重新验证什么。

没占提问、走默认区和确认区定下的条目也要记，一行一条。它们同样是决定，只是没花
用户的时间；不记下来，下一个人会以为这些是执行 Agent 随手挑的，从而不敢碰也不敢问。

| 定了什么 | 档 | 为什么这么定 | 用户 |
| --- | --- | --- | --- |
| <一句> | 默认 / 确认 | <一句> | 未反对 / 翻成 <...> |

被用户翻掉的默认项尤其要留，它标出你在哪个方向上判断偏了。
```

落盘路径固定为 issue 目录下的 `3-contract/contract.md`。确认版对照物在同一个 issue
目录的 `2-prototype/` 下，由 `aes-prototype` 负责，契约只在「读什么」里以相对路径
点名它们。

`contract.md` 必须自包含：单独拿走它仍然完整可交接。唯一允许指向 issue 目录内部的
地方就是「读什么」里点名的确认版对照物，别的过程文件（`context.md`、`rounds.jsonl`、
`impact-surface.md`）一律不引用——它们是素材，契约是聚合结果。

## 哪些东西不进验收条件

三类都会被写成「做完的标志」，只有第一类属于这次的目标。

| 是什么 | 进哪 | 为什么不进验收条件 |
| --- | --- | --- |
| 这次独有的可观察结果 | `验收条件` | 就是它 |
| 每个任务都一样的质量门（测试全绿、lint 零警告、构建通过） | 不写，交接指令模板管 | 每份契约读起来一模一样，不携带这次的任何信息 |
| 必须保持不变的现有行为 | `强约束` | AC 说「要变成什么」，不变量说「不许变什么」，方向相反 |
| 真人才能执行或判定的验收 | `交付后人工复核` | 进了 Verify，/goal 完成审计永远无法判定 → 烧 turn 到 blocked 或假自陈 |
| 执行 Agent 不用问就能定的事 | `自主边界` | AC 说「要达成什么」，它说「不必回来问什么」，不是同一个问题 |

自查一条 AC 是否分错筐：把它去掉，会放过哪一种具体的错误交付？
答不上来，它多半属于后两类，或者根本不必存在。

## 条数由聚类得出

AC 不是发明出来的，是从具体例子里聚出来的。把例子按「同一条规则的不同侧面」
聚类，一个簇一条 AC，簇里的例子成为它的 Verify 素材。条数由此得出，不预设区间。

聚完读三个信号：

- 聚出六条以上，这个目标太大了。拆成几个能独立交付的任务，不要把条数压回去。
  压回去只会让被删掉的那条无人负责。
- 某条 AC 下挂的例子彼此不像，里面藏着多条规则没拆开，拆成各自成立的两条。
- 一条 AC 一个例子都举不出来，它是愿望不是 AC。删掉，或者回去把它问成一个
  有具体形态的结果。

## Verify 怎么写

每条 AC 由两部分组成：用户裁决的结果陈述，和一行 Verify。结果陈述写成可观察、
可判定的结果，不是实现步骤。「工作正常」「测试通过」这类说法无法判定。

**每条 Verify 的通过判定必须由 worktree 里可复核的证据支撑。** 这是对四档的公共
前提：`/goal` 的完成审计每 turn 重判一遍，证据不足视为未达成、继续工作。人可以是
证据的生产者，可以是交付后的复核者，但不进同步判定路径——「员工确认验收通过」
这类条款审计永远判不了：要么烧 turn 到三连闸 blocked，要么执行 Agent 假自陈完成。
真人才能执行或判定的验收（UAT、员工试走、内部评审）落「交付后人工复核」节，不占
Verify。会话式交接且用户当场点头的场景可以留一条 `[C]` 人验，但 finalize 会点名它，
转 `/goal` 前必须移走。

Verify 必须落在四种形态之一并标明档位：

- `[A]` 自动化命令，给退出码或门槛值
- `[B]` 黄金用例：具体输入数据加期望输出，双双落盘并列进「要落盘的东西」
- `[C]` 可复现的操作步骤，给可观察结果。「人工」指非命令行自动化的手动操作，执行者
  仍是执行 Agent——它可以用浏览器与 CLI 工具模拟用户的真实操作
- `[D]` 具名文件内容检查

一行 Verify 可以挂多档：`[C] 人工步骤…；[A] \`命令\` → 退出码`。首档是主档，
内嵌档段同样作数——**每个 [A] 段都会被 finalize 冒烟执行**（含内嵌），写内嵌
[A] 就必须带反引号命令，否则校验直接拒。别把多档混写当成叠保障：非 [A] 段在
长时程执行里依旧只有执行 Agent 的自陈。

档位只说形态，不说深度。同是 `[A]`，跑一句 lint 和跑一遍端到端流程，
置信度差一个数量级。深度取决于用哪条验证途径，而途径每条都交用户裁决；
用户可见表面的深度下限见下一节。

写不进任何一档的 AC 就是还没对齐完，不落盘。

## 用户可见表面：真实使用级深度强制

任务有用户可见行为（界面、API、CLI）时，主验证表面至少一条 Verify 必须是**真实
使用级操作**：前端落盘 `playwright test` spec 以 `[A]` 命令跑；API 真实调用；CLI
真实执行。途径与判到多严照常带候选问用户。这条不是每份契约同质的质量门——操作
路径取自本任务的真实用户路径，携带任务信息，与「质量门不进 AC」不冲突。

收口形态必须是确定性脚本，不是现场交互：浏览器工具（Playwright MCP 等）只用于
起草与排障，验收认 spec 文件的运行结果。交互式会话不是可留存的运行证据；同一条
指令会在残留登录态的机器上通过、在干净机器上失败。

含真实使用级 Verify 的契约，三件套防护进「强约束」，缺一不可：

1. **尺子锁定**：E2E spec 文件声明不可修改——执行 Agent 改的是产品不是尺子。
2. **判定协议**：连续三次通过才算过；首跑红次跑绿判 flaky。flaky 不是 pass，也
   不许继续修——偶发红的 E2E 在完成审计循环里是新的不可终止源，执行 Agent 会去
   修没坏的代码。flaky 走「隔离 + 上报」：该 spec 移出判定，交付报告单列。
3. **禁改清单**：不许以 sleep、retry、skip、放宽断言、换更脆的选择器让 E2E 变绿。
   这些是消红，不是修复。

无用户可见行为的任务（纯重构、纯文档、纯数据变换）走豁免：在契约里写明一行豁免
理由。豁免不是默认——理由要能指向「这个任务的用户可见面是什么、为什么真实操作
不适用」。

## 编号

`AC-001` 三位，稳定且唯一。编号一旦被下游引用就不再改字面，
要改内容就改内容，编号跟着那条 AC 走。删掉一条不补号，
后面的也不往前挪：号是身份，不是序号。
