## 1. 合格钢人的标准

钢人（steelman）= 把一方立场修到其拥有者也会认可的**最强形态**，再拿来参与比较。合格线测试：把这条论证拿给持该立场的人看，对方的反应应当是「对，我会这么说」，而不是「你根本没理解我」。

三条红线：

- **稻草人**：夸大、断章、把对方的次要理由当主要理由打。
- **弱化版**：故意挑对方最软的论据——赢了软柿子等于没赢。
- **装饰性让步**：「对方也有道理，但是……」——让步必须落在具体论点上，不能是气氛组。

## 2. 把论证修强的五个动作

1. **补全隐含前提**：用户没说出来的成本、收益、约束，替他摆上台面。多数想法的真实理由藏在第二三层（「想统一技术栈」背后常常是「维护两套心智负担太重」）。
2. **换更强论据**：把「我觉得」升级为机制（为什么会这样）、数量级（大概多大）、先例（谁在类似条件下这么做过）。三者有其一，论证就落地。
3. **聚合分散理由**：用户东一句西一句的顾虑，合并成一条主线论证，而不是罗列五条碎理由。
4. **消化对立面**：最强辩护是能把对方最强攻击吸收进自己框架的辩护——「即使你说的是真的，我方立场仍然成立，因为……」。
5. **绑定上下文**：论证挂到用户给出的具体环境（团队规模、时间窗口、现有系统、使用频率）。通用 pro/con 清单对任何问题都适用，因此对任何问题都没有用。

双向对等：支持方与反对方的论证强度必须对等。给一方三条论据、另一方一句带过，就是在用钢人的形式做偏向性输出。

## 3. crux 的识别与表达

crux（分歧核心）= 一个可判真假的命题，它为真则一方胜、为假则另一方胜。

找法：问「双方论证到底在哪一步顶牛」。顶牛点通常不在结论层，而在某个**事实假设**层——成本量级、迁移风险、团队能力、时间窗口、使用频率分布。沿双方论证往回走，找到第一个共同依赖且取值相反的事实假设，那就是 crux。

表达格式：

> 若「<命题>」成立 → <一方> 胜；不成立 → <另一方> 胜。

好 crux 的检验：双方都会认账（「确实，这一条定了我就服」）。坏 crux：价值偏好（「如果你更看重稳定就别迁」）——那是 trade-off 罗列，不是分歧核心。

## 4. 关键变量怎么列

从 crux 反推：要判定这个命题的真假，需要知道哪些**可观测**的事实？

- 能量化最好（占比、次数、人日、量级），不能量化就给出判断依据。
- 每个变量标注它指向 crux 的哪一侧。
- 排序：最可能实际翻转结论的排最前——它通常就是第 5 节那个问题。

## 5. 一个问题的挑选标准

1. **直指 crux**：答案直接落入分歧核心，而不是周边信息。
2. **单一**：一个问题。三连问是变相的问题轰炸，把分析负担推回用户。
3. **一轮可答**：用户凭记忆或一次查询就能回答，不需要先做一轮调研。
4. **信息增益最大**：与候选问题相比，它的答案最能移动判断——想象每个可能答案会把结论推向哪边，推不动的删掉。

反例：「你还有什么顾虑？」（开放式，信息密度低）；「选 A 还是 B？顺便说说预算和时间？」（伪装多问）。

## 6. 裁决回合怎么写

- **立场先行**：第一句话就是判断，不和稀泥。「方向对，但范围要砍半」是合格立场；「各有优劣，看你取舍」不是。
- **理由挂 crux**：说明用户的回答落在 crux 的哪一侧、为什么因此倒向该方。回答没定住 crux 时直说，给最稳妥的一步（通常是缩小赌注：先试点、先收集某个变量、先做不可逆性最低的动作）。
- **下一步可执行**：2~4 步，每步有明确产出与先后；有验证点更好（两周后按什么标准复盘）。

## 7. 常见失败模式

| 失败模式 | 表现 | 修正 |
| --- | --- | --- |
| 提前泄底 | 第一回合末尾流露倾向或半成品结论 | 结论硬性推迟到第二回合 |
| 问题轰炸 | 结尾连问 2~5 个问题 | 只留信息增益最大的一个 |
| 通用清单 | 正反论证换个主题照样成立 | 每条论证点名用户上下文 |
| 假平衡 | 「双方都有道理」收尾 | 强度对等的明确比较，或承认一侧更强并说明为什么 |
| 重述=复读 | 把原话换个说法再写一遍 | 补隐含前提与约束，写成升级版 |
| crux 藏在论证里 | 论证写了但没提炼成可判真假命题 | 单独成段，用「若……成立 →」格式 |

## 8. 完整两回合示例

**用户**：我准备把个人笔记从 Notion 全部迁到本地 markdown + git，你觉得这个方向对吗？

### 第一回合（分析回合）

**重述**：你想解决的其实是三件事叠在一起——笔记数据的长期可持有性（不想被单一 SaaS 绑定或陪葬）、版本可回溯（Notion 历史有深度限制且不可 diff）、与现有开发工作流（git、编辑器、检索工具）打通。「全部迁移」隐含两个假设：你的笔记以文本为主（不含重度数据库结构），且你愿意用协作与移动端体验的下降换长期控制权。若你的笔记重度依赖 Notion 数据库视图或多人共享，这个重述就偏了——请纠正。

**支持方最强论证**（迁）：格式生命周期与工具链复利。markdown 是三十年不会死的纯文本，git 提供无限深度历史与免费灾备；迁移后笔记与代码共享同一套检索、编辑、脚本生态，「笔记即仓库」，两套心智负担并成一套。迁移成本是一次性的，锁定成本是永续复利的——越晚迁，沉淀在平台里的存量越多。

**反对方最强论证**（不全迁）：按使用频率加权，这笔账很可能是负的。Notion 的核心价值在「随手捕获」和结构化视图（表格、看板、关系引用），这些是日常高频动作；数据持有是低频的「担心」。迁到文件后，手机端秒开记一条、表格筛选复盘这些路径全部变慢——省下低频焦虑，付出高频摩擦。且数据库结构无法机械转换，「全部迁移」实际多半演变成新旧双轨，比锁定更乱。

**crux 与关键变量**：crux 是「你的日常高频操作以纯文本读写为主，还是以结构化视图 + 移动端捕获为主」。若是前者 → 迁移收益真实；若是后者 → 全迁把最高频路径变慢，不该全迁。关键变量：过去一个月移动端随手记的条数占比（指向反对方）；数据库视图（表格/看板）的真实使用频率（指向反对方）；是否已有日常 git 习惯（有 → 维护成本近零，指向支持方；无 → 平白多一套要维护的系统）。

**一个问题**：回看过去一个月，你在 Notion 里最高频的操作是什么——手机上随手记、表格/看板整理、还是检索回看旧笔记？大致的使用分布是怎样的？

### 第二回合（裁决回合）

**用户回答**：随手记很多，大概三成在手机上；表格整理也高频，项目清单和读书笔记全靠表格视图；检索回看旧笔记相对少。

**判断**：不全迁。文本性、长期沉淀的内容迁到 markdown + git；结构化清单与移动端捕获留在 Notion。方向对一半。

**理由**：你的回答落在 crux 中间偏「结构化」一侧——三成移动端捕获 + 重度表格视图意味着全迁会把两条高频路径同时变慢；而「长期可持有」的收益只对文本性沉淀成立。分轨后各取所长，且文本部分先迁、赌注最小。

**下一步**：1）只迁「读书笔记/长文沉淀」这一类，试运行两周，验证 git 工作流是否顺手；2）项目清单保留 Notion，不动；3）两周后按「捕获摩擦有没有实际变高」复盘，再决定扩大迁移还是回退。
