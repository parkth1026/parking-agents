# design: steelman-analysis

## 意图与触发场景

用户带着一个想法、方案或方向性决策来征求意见时，agent 的常规回答有两个毛病：顺着用户说（确认偏误），或者立刻给出自己的结论但论证过程用户看不见、也参与不进去。本技能把回答改造成两回合审议协议：

- **第一回合（分析回合）**：重述用户真正想解决的问题 → 给出支持/反对的最强论证（steelman）→ 找出分歧核心（crux）与能翻转结论的关键变量 → 只问一个最关键的问题，然后停下。
- **第二回合（裁决回合）**：用户回答后，给出明确立场、对应理由与可执行下一步。

触发场景：用户要求「先钢人分析再回答」「别急着回答，帮我两面想清楚」「挑战/审视我的想法」，或在技术选型、架构改动、流程调整、工具迁移等方向性决策上犹豫征求意见。执行类请求与事实问答不适用（description 已写明）。

期望产出形态：纯对话输出，无文件产物；技能零脚本、零配置。

## 设计取舍

- **第一回合禁止给出结论**——用户要的是「想清楚」而不是「被回答」。提前亮立场会把正反钢人降格为装饰性铺垫，用户也会被锚定。因此协议把判断硬性推迟到第二回合。
- **只允许问一个问题**——多问会把分析负担推回用户；一次一问逼着 agent 排出「哪个未知数最影响结论」，这本身就是分析质量的筛选器。
- **协议输出骨架固定、段内写法自由**——可检验性优先：评测断言（AC-1…AC-5）逐段锚定，标签漂移会让断言失真。自由度分级：协议结构低自由度（固定标签与段序），论证内容高自由度（完全交给 agent 判断）。
- **保留退出条款**（用户要求立即执行时跳过协议）——技能服务对话，不绑架对话。
- **为什么零脚本**——产出是纯审议文本，没有可确定化的操作；唯一可固化的是技能文档自身的结构契约，因此 run-tests.mjs 只验结构（frontmatter、五段标签、无待办占位），内容质量交给输出评测循环。
- **术语边界**——全文仅保留 steelman、crux 两个英文核心词（命名概念 + 误解会改变执行 + 中文近似词「抬杠/分歧点」强度不足），其余一律中文。

## 验收条件
| 编号 | 条件 | 类型 |
| --- | --- | --- |
| AC-1 | 第一回合按固定骨架输出（重述 / 支持方最强论证 / 反对方最强论证 / crux 与关键变量 / 恰好一个问题），且不在第一回合给出最终结论或行动计划 | manual |
| AC-2 | 正反论证各自绑定用户具体上下文，双方强度对等；无稻草人、无「各有道理」式假平衡 | manual |
| AC-3 | crux 表达成可判真假的命题（若 X 成立→一方胜，不成立→另一方胜），并给出至少一个能翻转结论的关键变量 | manual |
| AC-4 | 唯一问题直指 crux，回答它最能改变判断；不是问题清单或伪装的多问 | manual |
| AC-5 | 第二回合给出明确立场、对应 crux 的理由与可执行下一步，不再发起完整第二轮钢人 | manual |
| AC-6 | 技能文档自身结构契约（frontmatter 合法、五段标签齐全、无待办占位、方法参考在位）由 run-tests.mjs 固化 | script |
