# 设计依据

## 意图与触发场景

用户2026-11-01要求：尽量复用matt-skills，只写一个薄的管理入口；通过wayfinder类似方法锁定Story，确认需求与执行步骤，再由主Agent通过subagent完成所有执行Issue，最后整体验收并包含全部执行证据。

触发模式：名字触发（story-workflow／故事级执行编排），不自动承接普通单票工作。用户说“帮我完成这个Story／地图对应的执行工作”时可明确选择本技能。技能已由用户移入安装源；可安装不等于长期行为验收通过，不修改旧workflow-interview与既有契约。

## 设计取舍

- 上游已有规划、拆票和执行图能力，只补两次授权的辨认、主Agent持续纠偏、最终运行验收与证据汇总。
- Story、执行Issue与决策票分别承担结果、实施和歧义，避免把wayfinder变成实施任务列表。
- 主Agent拥有既定结果内的技术决策权；目标/权限/费用/验收强度仍由用户决定。已有更严格契约优先，不能凭新技能绕过。
- 不增加数据库、脚本执行器、强制报告格式或固定测试次数。验证按用户旅程和实际风险选择。
- 同一票使用新上下文，跨票通过指针和证据衔接；不把200k当作经证明的能力阈值。

## 验收依据

| 编号 | 要观察的行为 |
| --- | --- |
| AC-1 | 只有计划确认、未授权实施时停在规划；已有明确实施授权时不逐票重复询问 |
| AC-2 | 前沿按本Story、认领与依赖过滤，独立写入可并发，依赖集成后自动推进后续票 |
| AC-3 | 主Agent处理技术摩擦，严格契约下修spec仍须按原授权；失败不引发无边界循环 |
| AC-4 | 所有票完成后仍做独立最终用户旅程验收，并汇总每票来源及失败，不靠代码审查代替 |
| AC-5 | 外部资源只阻塞相关项，不能把未知/模拟记成通过或关闭Story；上下文外置可续跑 |
| AC-6 | matt文档可发现，技能只补流程差异，不默认重置/提交/清理用户现场 |

本地回归脚本只核对分发结构与评测可追溯性，不能替代上述行为判据。实际运行需观察真实派发身份、依赖释放与独立验收工件。名字触发批量筛查仅用于早期发现明显路由问题，正式触发稳定性仍按Creator每题独立探针流程判断。
