# 故事级执行编排

把一次委托推进到完整 Story：先确认目标与执行路线，再由主 Agent 持续编排新上下文子 Agent，最后安排独立整体验收，交付成果和全部执行证据的索引。

## 入口与复用

读取用户指定的 Story／地图、仓库 AGENTS.md、tracker及标签约定（通常在docs/agents/）、领域文档，找到当前权威状态。续跑先核对已集成候选、运行中任务和未决问题，避免重复派发。

先读 [matt-skills复用关系](references/matt-routing.md)，只加载当前阶段需要的上游文档。直接复用其方法与模板；宿主没有 Skill 调用工具时读取实际文件，不虚构调用。依赖技能缺失时先查本机技能目录和源码仓，确实缺失则报告名称与路径，暂停依赖它的阶段。

主 Agent 保有目标、依赖、里程碑和关键证据，负责认领、派发、集成与纠偏；产品实现交给子 Agent，最终检查交给未参与实现的验收 Agent。主 Agent 可做调查、运行检查和必要集成，不直接接管执行票的实现。任务与决策状态以项目 tracker 为准；本地证据目录只保存工件和来源，不另建任务数据库。

## 1. 确认 Story 与路线

沿用已有用户确认；有目标歧义才读取 wayfinder、grilling 和 domain-modeling，按决策前沿澄清。事实由 Agent 查，用户只决定影响目标、边界或授权的选择。依赖未知答案的后续问题留在迷雾中，足以描述的问题建立决策票。

在一个 Story 根票中记录：用户结果、范围与不变量、主成功旅程、关键风险、里程碑、执行票关系和最终验证方式。已有 spec／契约则引用，不再复制一套正文。每个里程碑交出一段可演示或可独立验证的能力，首个里程碑优先打通最窄的真实端到端路径。

读取 to-tickets，按纵向切片起草执行票与依赖。每票限定一个新上下文可完成的结果，写清交付行为、相关上下文指针、验收途径、可自主调整范围和交接证据；实现路径由执行者调查，不要求穷举文件或所有未来故障。过大的票继续拆，后段只规划到当前能看清的程度。

向用户展示 Story 结果、里程碑顺序、执行票粒度与依赖、关键验证及外部资源成本，确认需求与执行步骤；单独辨明是否同时授权开始实施。用户已明确授权的内容直接沿用。只确认计划时在Story现有状态／评论中记明“计划已确认，实施未授权”、本次票清单与确认来源，发布计划后停止，提供同一Story链接的继续指令。续跑先核对该确认与现行票据，再按后续明确实施授权进入执行；使用项目状态词，不另造状态机。

wayfinder 地图保留决策票与原有单票节奏；执行票归属 Story 并使用项目执行标签，不把 wayfinder 子票直接标成 ready-for-agent。若入口只有决策地图，链接一个 Story 执行根票。地图所需前置决策未定时，推进其他已明确且不依赖它的工作，不代答人类决定。

## 2. 主 Agent 持续执行

获得实施授权后，先认领 Story 根票作为编排所有者；已有其他所有者则协调，避免双主派发。读取 implement-spec 的依赖图、新上下文和集成方法，按复用文档中的权限适配执行。一次授权覆盖已确认范围与资源边界内后续解锁的执行票，无须每张票重新询问“是否继续”；新发现任务先核对是否仍在该边界内。进入真实外部验证前核对当前环境与本批有限授权，旧预算不自动沿用。

反复执行：

1. 查询本 Story 的执行票，选择尚未认领、ready-for-agent 且阻塞项已集成验收通过的前沿；读回真实状态，先认领再派发。外部会话已认领的任务跳过。
2. 先选能推进主成功旅程的任务。独立写入范围可并行，共享未稳定接口或同一文件的写入串行，或先拆出接口契约。
3. 用宿主专用子 Agent 工具启动新上下文实现者（如collaboration.spawn_agent的fork_turns=none），取得实际Agent身份再开始执行票；在票的现有工作记录中关联该身份、基线和证据位置。只传 Story／当前票、相关决定与来源、集成基线、写入归属、当前授权和预期证据位置。给实现者的是单票任务，不让它重新启动整个Story编排。若工具缺失、槽位不足或启动失败，等待可用槽位或记录准确阻塞，不以主 Agent 自写产品代替派发。桌面可见chat的create_thread／fork_thread是另一种用户操作，不作为缺少子Agent工具时的替身。
4. 回收结果后核对差异、候选身份和测试证据，集成并做本票关键行为检查；接受作者报告不等于接受实现。未提交工作用明确文件清单与摘要标识，不强求 Git 提交。
5. 验收通过后按 tracker 规则关闭执行票并记录结果／证据；缺项准确返工。关闭一票后立即刷新前沿，持续推进新解锁任务。
6. 每个里程碑检查新增或受影响的实际集成旅程，核对“用户现在能做什么”；未受影响证据可按来源复用，昂贵完整旅程留到最终验收。发现任务过大、证据反复失败或路线失效时，重新归因与拆分，不靠无限延长同一子任务完成。

没有 ready 票时检查认领者、依赖环、未标就绪的已准备任务和新发现问题。已批准、依赖已集成验收且资料足够的执行票，由主 Agent 按tracker规则补齐ready状态后认领派发；他人认领或仍有歧义的票保持原归属。前沿为空不等于完成。资源受阻只阻塞依赖项，继续可独立完成的工作；确实无可推进项时记录阻塞及准确恢复入口，不申报 Story 完成。

## 3. 自主纠偏

在已确认结果和授权内，自主调整内部方案、执行顺序、票的拆合与必要修复，并把理由和影响记在相关票。新发现的必要工作，若是当前票的原子修复则更新该票并复验；否则创建关联Story的执行票，写清结果、依赖和验证方式，再进入前沿。发现未想清的技术问题，先调查再决策；会改变用户可观察结果、删能力、扩大权限／费用或降低验证强度时，提出具体选项交用户决定。

把失败分为产品、测试宿主、环境与目标歧义，再选择行动。测试的运行细节可由主 Agent 安排另一新上下文 Agent 复核：确认精确差异不改变业务断言、覆盖范围和成功标准后，在授权允许时另版修复，保留旧失败。现有仓库或契约若要求用户批准该类修改，先取得变更授权，不用本技能覆盖。放宽期望、忽略真实失败或改验收含义仍交用户裁决。

把不影响当前里程碑的非阻塞优化放回有归属的后续票；不得把已承诺的本 Story 必需结果移出后就宣布完成。每次活动都应说明它如何推进当前旅程或保护必要不变量。

上下文用于当前票，长日志与历史留在外部证据中，按需读取。为验证与交接预留余量；出现反复压缩、范围持续扩张或难以说明完成边界时，保存候选、证据和未完成项，结束当前子任务后用新上下文接续。200k不作为能力保证或必须耗尽的配额。

## 4. 独立整体验收与证据交付

执行票集成后，用宿主工具启动未参与实现的新上下文验收 Agent，记录其真实身份与最终候选。交给它用户确认的 Story、最终候选／装配身份、关键旅程、风险与全部执行票的证据索引；按需用 code-review 做代码审查，并独立运行最高可用表面的真实端到端操作。审查或作者测试通过不能代替用户旅程成立。无法启动独立验收时保留待验状态，不以主 Agent 自验冒称独立验收。

每张执行票保留可定位记录：实际变更与候选、验证命令／环境、输入与期望来源、原始结果与失败、已知缺口。主 Agent 汇成一个最终证据索引，让全部执行证据可追溯；不把日志全文塞进提示，也不复制凭据等敏感原文。

验收发现问题，主 Agent 归因并派发有界修复，受影响证据随候选变化失效后重验。最终验收记录绑定最终集成候选；先前票的证据保留其原版本，不能冒称都证明最终版本。重复失败先调整任务或诊断方法，避免无边界修测循环。

关闭前核对验收期间没有使候选失效的并发修改或未决执行。只有 Story 必需结果、当前候选的集成旅程和必要证据均满足，才按 tracker 规则关闭 Story，更新关联地图进度。这里关闭的是Story执行根票，不连带关闭仍有未决问题的wayfinder地图；执行子票按票级验收关闭。模拟／本机／真实外部运行分开标明；NOT_RUN、资源缺失和未知保持原状态。交付结果入口、里程碑与Issue结果、整体验收结论、全部证据索引及剩余风险。部署、提交、推送、合并和清理遵循用户与仓库现有授权。
