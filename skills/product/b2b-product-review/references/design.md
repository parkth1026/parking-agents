# design: b2b-product-review

## 意图与触发场景

在下一笔资源投入之前，对 B 端产品方案（B2B / B2G、标品）做逆向审查（失败预演）并以成功产品证据形态做正面对照：把方案主张还原成证据，按 6 层 18 类失败机制逐层核查，对照三层成立与八课决策关口，产出最能改变决策的待检验假设、有区分力的验证设计与五选项投入建议。

- 触发语：「审查/评审这个方案」「帮我质疑一下这个立项」「失败预演」「这个方案有什么问题」「该不该继续投入」「投前挑刺」。
- 输入：一份方案文档（立项汇报、标品提案、PRD、方向定义）或用户口述的方案描述。
- 产出：结构化审查报告（markdown），固定结构与词表，可直接用于团队评审。
- 用户用法裁定（2026-09-24）：100% B2B / B2G——技能定位随之收紧为 B 端；通用产品类型知识保留不删（忠实于源报告，对 B 端子形态仍有参照价值）。
- 知识来源（两份，编号互不通用）：
  - 失败篇：`agent/research/如何把一个产品做失败_2026-09-23.html`（六层 18 机制、证据矩阵、六阶段标准、五选项出口、指标口径；机制语义不得改写）。S 编号 → `references/sources.md` 失败篇索引。
  - 成功篇：`agent/research/b2b_product_success_report.html`（三层成立、验证重量 2×2、八课关口、七案例卡、十种假象；2026-09-24）。B 编号 → `references/sources.md` 成功篇索引。

## 设计取舍

| 决定 | 自由度 | 为什么没选别的 |
| --- | --- | --- |
| 全文字指令、零 scripts | — | 审查是判断型任务，没有可确定性执行的步骤；没有重复代码可固化 |
| 18 机制与证据规则固化为 references | 低（内容固定） | 这是领域知识而非风格，每次审查重造必然漂移失真；语义忠实比精简重要 |
| 状态四值/决策五值/阶段六段固定词表 | 低 | 跨次审查、跨方案比较靠词表稳定；词表漂移报告就不可比 |
| 证据归类、机制命中判断、假设聚焦 | 高 | 依赖方案语境，硬规则会把审查变成打勾游戏 |
| 每条命中预警强制过「反面提醒」 | 低（流程铁律） | 本技能最大质量风险是变成「逢方案必风险」的打分器；源报告每条机制自带适用边界，这是解药不是装饰 |
| 不设评分权重、不出总分 | 低 | 源报告明确 18 类机制无统计权重、不能相加成失败概率；分数会制造虚假精度 |
| 输出模板固定在 report-format.md | 低 | 报告要进团队评审流程，结构漂移毁掉复用价值 |
| 正例对照独立成 positive-signals.md，不混入机制表 | 低（内容固定）+ 适用范围高 | 失败侧判「命中预警」、成功侧判「证据形态缺口」，口径不同，混排会稀释两面纪律；正例限定 To B/标品，非 B2B 方案标不适用而非硬套 |
| 两份报告来源编号分立（S / B） | 低 | 两套 S01 起编的索引直接混用会产生静默错引；分立后机器可检（run-tests 分别解析） |
| 更名 b2b-product-review、定位收紧 B 端（2026-09-24 用户裁定） | 低 | 名字随实际用法自文档化，消费类语域不再抢触发面；不拆双技能——失败面与成功面是同一次审查的两只手，共享证据盘点与阶段判定，拆开两边都要重造 |
| B2G 边界以「需专项验证」清单呈现，不给结论 | 低（表述固定） | 两份源报告均无政企采购实证；把招投标/合规前置等写成结论就是编造——只能列为改变交付路径的待验项（机制 15 口径） |
| 按需展开硬指令 + references 按需读取（2026-09-24 用户裁定 token 偏高） | 低 | iteration-2 方差实证：同为 with 臂 269k vs 632k，差别就在无实质条目是否全展开——收紧行为而非删知识，18 机制覆盖与 AC-2 不变；不做快审双模式，避免输出形态分裂稀释词表可比性 |

## 验收条件

| 编号 | 条件 | 类型 |
| --- | --- | --- |
| AC-1 | mechanisms.md 完整包含 18 机制×六层，每条含五要素（失败做法/可观察预警/怎样检验/反面提醒/有条件的结论）——run-tests.mjs 结构自检 | script |
| AC-2 | 审查报告逐条覆盖 18 机制，每条给出四值状态之一；「本阶段不适用」附理由 | manual |
| AC-3 | 报告保持证据分级：不把未验证判为失败或成功，未知事项保持未知 | manual |
| AC-4 | 报告把方案主张映射到证据类型，指出越级之处（如把赞美/意向当需求证据） | manual |
| AC-5 | 报告给出 2-3 个最能改变决策的假设，各配有区分力的验证（含通过/反证/停止条件） | manual |
| AC-6 | 报告落在五选项决策建议之一，附理由与资源边界 | manual |
| AC-7 | 命中预警的机制核对过反面提醒，无机械套用（如不把早期人工交付直接判失败） | manual |
| AC-8 | 报告按方案阶段调整否定标准，未用成熟期指标扼杀探索期方案 | manual |
| AC-9 | To B / 标品方案的审查含成立层级判定（主张层 vs 证据支持层分开陈述，只用三层词表）与八课关口对照，缺口指向对应失败机制；非 B2B 方案标「不适用」并说明 | manual |
| AC-10 | 方案引用成功案例时逐条核对案例卡「不能照搬」边界（如免费入口≠无销售成本、平台业务规模≠公司收入），不把案例收入数字当判据 | manual |
