# 来源质量细则（source-quality）

> SKILL.md 只留规则一行版；判定口径、阈值与操作步骤都在本文件。

## 1. 官方阶梯

| 层 | 来源 | 用法 |
| --- | --- | --- |
| 1 | 官方文档、上游源码、release notes / changelog、标准原文 | 可直接支撑 material claim |
| 2 | maintainer 指南、官方论坛/issue 中的维护者答复 | 可支撑，注明"维护者口径" |
| 3 | 三方博客、教程、社区讨论（Reddit/HN/Stack Overflow） | 仅补充；不得先于第 1 层使用；与官方冲突时按第 4 节处理 |

上游提案/规范类问题（如 TC39 提案阶段）以**上游仓库现状**为准，即使官方产品页更"权威"——产品页可能陈旧（实例：momentjs.com 曾长期停留 Stage 3，TC39 仓库已是 Stage 4）。

## 2. fetch-not-snippet

- material claim = 会改变调用方决策的论断（版本号、弃用状态、推荐路径、行为变化、数字结论）。
- 每条 material claim 至少一条来自**实际打开的页面**的证据；搜索结果摘要、转述、缓存不得作为唯一依据。
- 打不开的页面（付费墙/bot 拦截）要么换官方镜像（registry、GitHub raw），要么在「冲突与缺口」里如实记"未能核实"。

## 3. registry 口径（包发布日期）

- 以 **npm registry `time` 字段**（`registry.npmjs.org/<pkg>` 的 JSON）为准；其它生态用对应 registry 的等价字段。
- GitHub Release 对象的 `published_at` **不是**发包时间：release 对象可被删除重建，实例——moment 2.30.1 的 GitHub `published_at` 显示 2026-07-26，npm 实际发版 2023-12-27，相差近两年半。
- 引用发布日期时写明口径来源（`registry time` 或页面标注）。

## 4. 时效（AS_OF）

| 来源类型 | 新鲜阈值 | 超阈值动作 |
| --- | --- | --- |
| 研究类（范式/最佳实践/架构指引） | 3 年 | 置信降一档 + 标注来源年份与核对日期 |
| 快讯类（版本状态/弃用公告/安全通告） | 6 个月 | 同上，且优先找更新的一手来源 |
| 版本号/发布日期 | 以 registry 核对日为准 | 偏差即写入「冲突与缺口」 |

「版本 / 日期上下文」节必须含 **AS_OF 核对日期**（本次调研核对外部事实的日期）。

## 5. 收敛门（≥2 独立域名）

- 写进「直接建议」的关键结论：≥2 个**独立注册域名**的来源支撑；同一域名下两页算一个。
- 官方文档域 + 官方 GitHub 仓库 = 2 个域名（可收敛）。
- 达不到门槛**不是删结论**，是照写并显式标「单一来源，未收敛」，置信最高记「中」。

## 6. 置信三档

| 档 | 判据 |
| --- | --- |
| 高 | 官方来源，或 ≥2 独立域名相互印证 |
| 中 | 单一可靠来源；或官方来源但信息已过 AS_OF 阈值 |
| 低 | 未核实、过期、仅社区声量、或与其它证据冲突未决 |

降档叠加：过期 + 单一来源 → 低。

## 7. 逐字摘录

适用：API 签名、默认值、配置键名、官方宣告原句（如弃用公告措辞）。
要求：逐字引用 + 就近 URL；翻译可附在引文后，但引文本体不改动。禁止凭记忆重构签名或参数名。

## 8. 用户假设来源标记

当用户问题内嵌过时/可疑假设（"我看教程都是 X"、"我记得官方是 Y"）：

1. 先给官方/上游的当前口径（正常完成调研）；
2. 在「冲突与缺口」节点名该假设的**流行来源**（如"大量旧教程/2022 年前的文章仍推荐 X"），并标记为**过时证据**，说明它与官方口径的冲突；
3. 不静默纠正：用户看得到"自己原以为的东西为什么过时、过时源头是什么"。

## 9. 引用真实性核对（scripts/verify-refs.mjs）

- 交付前对报告文件跑：`node scripts/verify-refs.mjs <报告路径>`（报文契约见 `api-mock`/`example-run` 对照物）。
- `unreachable` → 按幻觉处理：补出处或删引用；`ambiguous`（403/429 等 bot 拦截）→ 人工复核，不自动判死。
